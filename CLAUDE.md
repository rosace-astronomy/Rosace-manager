## Project overview

**Rosace** is an async REST API (FastAPI + Python 3.12) that orchestrates spectroscopic observation sessions end-to-end. It is designed to run autonomously at night, cycling through a state machine from target selection to archiving.

- Python package: `rosace/rosace/`
- Build config: `rosace/pyproject.toml`
- Virtual environment: `rosace-manager/`

## Setup and running

```bash
# Activate the virtual environment
source rosace-manager/bin/activate

# Install in editable mode with dev dependencies (run from repo root)
pip install -e "rosace/[dev]"

# First run only: bootstrap the first admin account (see Authentication)
python -m rosace.main --create-admin <username>

# Start the server
cd rosace
uvicorn rosace.main:app --host 0.0.0.0 --port 8000
# or: python -m rosace.main

# Alternative: try it with zero setup (no hardware, no admin bootstrap,
# self-seeded catalogue, isolated under ~/.rosace-demo) — see "Trying Rosace
# without hardware" below
# python -m rosace.main --demo-mode

# Interactive API docs
# http://localhost:8000/docs

# The web GUI is served by the same process, at the same port
# http://localhost:8000/
```

## Architecture

### State machine (`main.py`)

The global singleton `state` (a `SystemState` instance) drives the orchestration loop:

```
IDLE → INIT_SESSION → [SCHEDULER → SEQUENCER → REDUCTION → SHARING → ARCHIVE] × N → CLOSE_SESSION → IDLE
```

The session runs as a FastAPI background task. `POST /control/start` starts it; `POST /control/stop` sets `state.is_running = False`. No plugin needs to know about this flag: `session_runner()`'s own loop checks `state.is_running` before every stage call, so a stop request is picked up between stages and reaches `CLOSE_SESSION` cleanly — no exception involved.

On any plugin error in the observation loop, the error is recorded in the DB, and the loop restarts from **SCHEDULER** (not from INIT_SESSION) — except `SchedulerFatalError` (see SCHEDULER plugins below), which stops the session instead, since it signals a configuration/data problem that retrying cannot fix.

**Plugins never block waiting on external conditions.** The active SCHEDULER plugin is the one plugin that could, in principle, need to wait (for a target to become observable) — but it must still answer within a few seconds: if nothing is observable right now, it sets `obs.scheduler_data["target"] = None` and returns immediately, rather than sleeping internally. `session_runner()` treats `target is None` as "nothing to do yet" (not an error — no `db_set_error`, no restart-from-SCHEDULER log): it waits `SCHEDULER_RETRY_SECONDS` (`config.py`, in small interruptible steps via `_interruptible_sleep()` so a stop request during the wait still takes effect promptly) and asks SCHEDULER again.

No SCHEDULER plugin imports `main.py` or touches `state` — a plain top-level `from ..main import state` fails at import time with a circular-import error, since `main.py` imports the plugin registry before defining `state` (see HISTORY.md for the incident that established this rule).

For a sub-plugin whose own work spans several internal steps (e.g. `star_spectra_acquisition.py` looping over several sub-exposures, see below), the same no-`state`-import rule still applies — but it still needs *some* way to notice a stop request between two of its own steps, not just between stages. `Observation.stop_check` (`models.py`) is that narrow, read-only escape hatch: a plain callable, `None` outside a real session run, set by `session_runner()` on every freshly-created `Observation` (`stop_check=lambda: not state.is_running`, right next to `hardware=session.hardware`) — same "live, not persisted" pattern as `hardware` below. A sub-plugin that wants to be interruptible checks `obs.stop_check()` between its own steps, exactly like it reads `obs.hardware[...]`, without ever touching `main.py` itself. `SessionContext.stop_check` (`plugins/camera_cooldown.py`) mirrors the same mechanism onto the one other object that ever needs it: `INIT_SESSION` acts on a `SessionContext`, not yet an `Observation`, so its own multi-step cooldown wait needs the same narrow escape hatch — set by `session_runner()` right before `INIT_SESSION` runs, same `lambda: not state.is_running`.

### Plugin system (three mechanisms)

**Stage plugins** (`plugins/__init__.py` registry) — one per `OrchestratorStage` enum value. Two interfaces (`models.py`): `SessionStagePlugin` for `INIT_SESSION`/`CLOSE_SESSION` (`run(self, ctx: SessionContext) -> SessionContext`), and `ObservationStagePlugin` for `SCHEDULER` → `ARCHIVE` (`run(self, obs: Observation) -> Observation`).

**SCHEDULER plugins** (`plugins/schedulers/` registry) — the SCHEDULER stage itself is pluggable: several interchangeable target-selection algorithms can coexist, each in its own subdirectory with its own class and its own tests, one chosen at startup via `active_scheduler` (`conf/config.yaml`, resolved to `ACTIVE_SCHEDULER` in `config.py`). This is a distinct axis from `SEQUENCER_BACKEND` below — that one is a closed, binary technical choice (simulated vs. real hardware protocol for the *same* sequencing logic); this one is an open-ended set of alternative *scheduling algorithms*, meant to grow as different observers contribute their own. `plugins/schedulers/__init__.py::_build_registry()` is the explicit name→class registry (no filesystem auto-discovery, consistent with `pipeline_loader.py`'s own registry below); `load_scheduler()` instantiates the active one, called once by `plugins/__init__.py` at import time. `SchedulerFatalError` also lives here (`plugins/schedulers/__init__.py`) rather than inside any one scheduler, since any SCHEDULER plugin may raise it.

  Every SCHEDULER plugin must honor the same `scheduler_data` contract (documented in full, in English, in `plugins/schedulers/blank/scheduler.py`'s docstring — the copyable template): populate `target` (a `Target`), `queried_name`, `program`, `priority`, and `exposure` (an `ExposureConfig`) when a target is selected, or set `target = None` when nothing is observable right now (see the "never block" rule above). This contract is **not** checked at runtime in plugin code — by design, to keep plugins simple — but every scheduler's own test suite must verify it via `conftest.py::assert_scheduler_contract()`, with explicit failure messages naming the offending key.

  Two schedulers exist today: `schedulers/scheduler_rosace_2026/` — the real one, described below — and `schedulers/blank/` — a minimal example (hardcoded Vega/Arcturus/Castor, no `targets.db` access at all) meant purely as a template to duplicate when writing a new scheduler. To add one: duplicate `schedulers/blank/`, implement `run()`, write its tests (checking the contract via `assert_scheduler_contract()`), register the class in `_build_registry()`, add its name to `config.py`'s `_VALID_SCHEDULERS`, and set `active_scheduler` accordingly.

**Sub-plugins** — loaded dynamically by `pipeline_loader.py` at runtime from a YAML program file, one reload per observation (`obs.scheduler_data["program"]`, set by the active SCHEDULER plugin — there is no global "active program" setting). A program's own `sequencer:` list is never the *whole* SEQUENCER story: the active hardware profile may declare its own `sequencer_prefix:` (a list, e.g. `[guiding_dark_acquisition, home_sync_am3]` for an AM3 mount) — steps every program run against that equipment needs, regardless of which science it's doing. `pipeline_loader.py::hardware_sequencer_prefix()` is the single source of truth for this list (`[]` if the key is absent, or if `SEQUENCER_BACKEND` isn't `"indi"`), read identically by `load_pipelines()` (to build the actual pipeline) and by `SequencerPlugin.run()` (to set `obs.program_steps["sequencer"]`) — both prepend the same list, so the two can never disagree and desynchronize the step names from the sub-plugin instances they're `zip()`-paired against. Loaded through the exact same dynamic-resolution mechanism as any program-declared step (same directory convention, same `DISPLAY_NAME`/docstring discovery, same tests) — this isn't a new plugin family or a new extension point, just a second source feeding the same SEQUENCER list. This is what keeps equipment-specific sub-plugins out of scientific program YAMLs entirely — a program never needs to know or declare anything about the mount (or any other equipment) it happens to run on (see HISTORY.md 2026-09-08). Sub-plugins share the same interface as stage plugins: `execute(self, obs: Observation) -> Observation` (`sub_plugin_base.py`). A sub-plugin *may* write its own nested sub-dict inside its parent stage's casier, keyed by its own declared name (e.g. `reduction_data["bias"] = {"corrected_files": [...]}`) — but only when it has something genuinely descriptive to add to the observation record (data about what the observation *contains*: images, positions, computed values). A sub-plugin with nothing descriptive to report (e.g. a cleanup step whose only fact is "it ran") writes **no casier at all**.

  **Casiers are not a flow-tracking mechanism.** `Observation`/the observation YAML describe the observation — target, session, images, dates — not the pipeline's own execution history; which step ran, in what order, and whether it succeeded is the log's job, not the YAML's. Concretely: a sub-plugin never checks a previous step's casier just to confirm "did it succeed" — the orchestrator's own `try/except` around every `execute()` call already guarantees that a failed step stops the whole stage before the next sub-plugin is ever reached, so re-checking that is redundant, dead code that can never actually catch anything. A sub-plugin *does* still read a previous casier when it genuinely needs that step's **data** to do its own job (e.g. `dark` reads `reduction_data["bias"]["corrected_files"]` — the actual files to process, not a signal that bias "succeeded") — and if that data isn't there, it still raises an explicit error naming what's missing, the same as any other required input. The difference is purely about *why* the check exists: validating that a real input is present, never gatekeeping on another sub-plugin's completion for its own sake. This is also why a casier should never repeat data that's already elsewhere in `obs` (e.g. the target's name — already in `scheduler_data`) purely to be "complete": a casier only ever holds what that specific sub-plugin uniquely produced. (See HISTORY.md for the incident that established this principle.)

  A sub-plugin has access to the whole `obs` object — every casier collected so far, not just its own stage's. This is an implementation choice made by whoever writes that sub-plugin, not a dependency the framework tracks or enforces. No fallback chains: the program YAML is trusted to sequence steps consistently with what each sub-plugin actually reads, not defended against at runtime. Sub-plugins have no config of their own — all configuration lives in `conf/` (see below), consistent with the rest of the app.

**Logging convention**: the orchestrator (`sequencer.py`/`reduction.py`/`sharing.py`) already announces each step before calling it (`"[SEQUENCER] → {step}"` etc.) and logs a failure itself if `execute()` raises — a sub-plugin doing one atomic action (a single hardware/IO call, nothing else worth tracing) should therefore log **once**, after that action succeeds, not once before and once after. A sub-plugin with several genuinely distinct internal phases (not just one action) is the exception — a log line per phase there is legitimate, since each one is a real checkpoint useful for diagnosing a failure partway through. Documented in each `blank_*` template's own docstring.

  **One directory per sub-plugin**, named after the sub-plugin itself (e.g. `sequencer_plugins/slew/`, `reduction_plugins/bias/`) — chosen deliberately over a purely flat layout so the catalogue of sub-plugins stays discoverable/documentable as it grows (a real concern once many programs/equipment variants each need their own sub-plugins, most unused by any single observation). Resolved **dynamically via `importlib`** by `pipeline_loader.py` — a sub-plugin declared `"<name>"` in a program YAML resolves to module `<name>/<name>.py`, class `<Name>Plugin` (snake_case `<name>` converted to PascalCase per underscore-separated word, e.g. `pointing_72ed` → `Pointing72edPlugin`), by naming convention alone. No central registry file to maintain, and only the sub-plugins actually declared by the program being loaded are imported — not the whole catalogue. Both the program name and every step name (sequencer/reduction/sharing) are validated against `^[A-Za-z0-9_]+$` (`pipeline_loader.py::_validate_name()`) before being interpolated into a filesystem path or a Python module path — defense in depth against path traversal, since `ProgramCreate.name` (below) is already validated at the API boundary but this module has no way to know a given caller did that.

  Sub-plugin directory names must additionally be all-lowercase (PEP8: modules/packages are all-lowercase) and unique across the three families (sequencer_plugins/, reduction_plugins/, sharing_plugins/) — both checked once at server startup by `pipeline_loader.py::validate_subplugin_catalogue()` (called from `plugins/__init__.py`), which raises a `RuntimeError` naming the offending director(y/ies) rather than letting either mistake surface later as a confusing `ModuleNotFoundError` mid-observation or an ambiguous program YAML/observation dossier. Lowercase matters because `build_pipeline()`/`load_sharing_plugin()` lowercase whatever name a program YAML declares before resolving it to a module path — an uppercase directory could never be found that way. Cross-family uniqueness matters for human readability, not correctness: `sequencer_data`, `reduction_data` and `sharing_data` are separate casiers, so e.g. a sequencer sub-plugin and a reduction sub-plugin sharing a name would never actually collide in code — but they would make every program YAML and every observation dossier ambiguous to a reader (is `dark` the capture step or the processing step?). This is also why the three copyable templates are named `blank_seq`/`blank_red`/`blank_share`, not a bare `blank` reused three times.

- Sequencer sub-plugins: `plugins/sequencer_plugins/<name>/` (`slew`, `focus`, `star_spectra_acquisition`, `dark_acquisition`, `bias_acquisition`, `calib_acquisition`, `flat_acquisition`, `guiding_dark_acquisition`, `home_sync_am3`, `pointing_72ed`, `spectro_light_source_to_sky`, `stop_phd2_guiding`) — read/write `obs.sequencer_data`, read `obs.scheduler_data` for target/exposure. The only sub-plugin family with a backend axis (`SEQUENCER_BACKEND`, `config.py`), resolved **inside each sub-plugin's own directory** rather than as a separate directory tree:
  - `<name>/<name>.py` — the canonical, no-suffix filename, used whenever there's no backend ambiguity: always for REDUCTION, and for SEQUENCER when `SEQUENCER_BACKEND="indi"`. `focus.py` is still a **placeholder** (`sleep(1)`, same contract as the demo version) — no autofocus algorithm exists yet.
  - `<name>/<name>_internal.py` — a **deliberate, narrow exception**, not a first-class backend: used only when `SEQUENCER_BACKEND="internal"` (simulation, level-1 demonstrator). Since `internal` exists purely as a demo, **only the sub-plugins actually needed for the demo program have an `_internal.py` file** — its absence for a given sub-plugin is normal, not a gap. Nesting `internal`/`indi` as a subdirectory inside each sub-plugin (`slew/internal/slew.py`) was explicitly rejected (see HISTORY.md). `star_spectra_acquisition_internal.py` still names its produced files via `acquisition_helpers.py::build_fits_root_name()` — same convention as the `indi` backend (see below) — even though it only `touch()`s an empty placeholder file, not a real FITS image; a plain simulation-only filename was tried first and dropped once `--demo-mode` made these files visible to an actual observer trying the app (see HISTORY.md).
  - `pipeline_loader.py::_resolve_module_and_class()` does this resolution; `SequencerPlugin.run()` itself stays agnostic of the backend.
- Reduction sub-plugins: `plugins/reduction_plugins/<name>/` (`bias`, `dark`, `flat`, `extract`) — read/write `obs.reduction_data`; `bias` (the first step) reads `obs.sequencer_data["star_spectra_images"]` as its initial input (see the shared-key note below), each step after it reads a specific earlier nested key it was written to expect (`dark` reads `reduction_data["bias"]`, `flat` reads `reduction_data["dark"]`, `extract` reads `reduction_data["flat"]`). No backend axis at all: these steps process already-acquired files, no hardware dependency — the INDI/ASCOM axis never concerns them, and their module name is never suffixed.

  **Shared, purpose-named keys, when a stage can have more than one interchangeable way to produce the same kind of output**: a *downstream* reader shouldn't need to know exactly which sub-plugin produced the data it needs. `star_spectra_acquisition.py` (both backends) appends every produced filename straight to `sequencer_data["star_spectra_images"]` — a fixed, purpose-named key. `bias.py` (and `blank_red.py`, the REDUCTION template) read only `sequencer_data["star_spectra_images"]`: REDUCTION must never need to know which specific SEQUENCER sub-plugin produced the raw science files, only that they land under this one fixed key. Any future alternative acquisition sub-plugin is expected to append to the same shared key rather than inventing its own.
- Sharing sub-plugins: `plugins/sharing_plugins/<name>/` — read `obs.reduction_data["extract"]["reduced_files"]`, write their own nested key in `obs.sharing_data`. Unlike SEQUENCER/REDUCTION, a program declares exactly **one** (`sharing: <name>`, a singular YAML key, not a list) — `SharingPlugin.run()` (`plugins/sharing.py`) resolves and calls that single sub-plugin via `pipeline_loader.py::load_sharing_plugin()`, instead of iterating a list. A program that needs to notify several destinations handles that *inside* its one sharing sub-plugin — the mechanism itself deliberately doesn't support a list, to keep it simple. `sharing_plugins/blank_share/` is the only one that exists today — a placeholder (logs each file, no real email/FTP/API yet) used by every program for now, and doubles as the copyable template (its docstring documents the contract in full, in English), same idea as `schedulers/blank/`.
- Programme definitions: `rosace/programs/*.yaml` — declare which sub-plugins run in order (`sequencer`, `reduction`) plus the single `sharing` sub-plugin. `demo.yaml` is a minimal, backend-agnostic program (same step names as any other) used as the default for a fresh install and for quick end-to-end verification; `Be_stars.yaml`, `bright_stars.yaml`, `nova_monitoring.yaml` are real-hardware/scenario programs.

To add a new sub-plugin: create `plugins/<sequencer_plugins|reduction_plugins|sharing_plugins>/<name>/<name>.py` (and `<name>_internal.py` too, only if a demo counterpart is actually needed — SEQUENCER only) with its own `test_<name>.py`, then declare its name in the relevant program YAML (a list entry for `sequencer`/`reduction`, the single `sharing` value for sharing) — no registry file to edit.

**Before writing a new one, check what already exists**: `python -m rosace.main --list-subplugins [sequencer|reduction|sharing]` (`pipeline_loader.py::list_subplugins()`) walks the same three directories `validate_subplugin_catalogue()` discovers from and prints each sub-plugin's name plus the first line of its own module docstring — meant for reuse/duplication decisions, not just naming hygiene. Reads via `ast.parse()`, never imports the module, so it never triggers a sub-plugin's own import-time side effects (device connections, backend-specific dependencies) and works regardless of `SEQUENCER_BACKEND`. Every module docstring's first line must already be a short, human-readable summary — `TestSubpluginDocstrings` (`plugins/test_pipeline_loader.py`) fails the test suite if any real sub-plugin is missing one.

**`DISPLAY_NAME`**: every sub-plugin also declares a short, human-readable `DISPLAY_NAME = "..."` module constant, right after its docstring and before its imports (e.g. `DISPLAY_NAME = "Dark"` in `dark_acquisition.py`) — a GUI label (see "Live SEQUENCER/REDUCTION step progress" below), deliberately separate from the docstring: the docstring documents the sub-plugin for a developer, `DISPLAY_NAME` names it for an observer watching the GUI, and the two audiences don't want the same length or tone. Read the same way as the docstring — `pipeline_loader.py::_module_display_name()`/`get_display_names()`, `ast.parse()`, never imported — for the same reasons. A sub-plugin missing one falls back to its own raw snake_case name rather than failing (not a runtime correctness risk, same posture as a missing docstring); `TestSubpluginDisplayNames` (`plugins/test_pipeline_loader.py`) still fails the test suite if a real sequencer/reduction sub-plugin lacks one. For the three sub-plugins with both a canonical and an `_internal.py` file (`focus`, `slew`, `star_spectra_acquisition`), both files must declare the *same* `DISPLAY_NAME` — they represent one logical step, and the GUI must show the same label regardless of `SEQUENCER_BACKEND`; also enforced by `TestSubpluginDisplayNames`.

### Session context and the observation dossier (`SessionContext`, `Observation`)

Two separate Pydantic objects (`models.py`), deliberately not merged:

- **`SessionContext`** — passed only to `INIT_SESSION`/`CLOSE_SESSION`. Minimal and stable for the whole night: `session_id`, `started_at`, `site_name`, `session_dir`. Recorded once in the `sessions` table.
- **`Observation`** — passed from `SCHEDULER` through `ARCHIVE`, unwrapped (no wrapper — the dossier *is* what flows). `main.py`'s `session_runner()` creates a fresh, empty instance for each observation (`id`, `created_at`, `session_id`, `obs_dir` — the only fields the orchestrator itself knows or sets) right before calling the active SCHEDULER plugin, which fills it in.

  The orchestrator never reads or writes business data — each stage plugin (and its sub-plugins) owns one casier, free-form (`dict[str, Any]`), that only it writes to: `scheduler_data`, `sequencer_data`, `reduction_data`, `sharing_data`, `archive_data`. `models.py` only declares that these casiers exist, never what's inside them. The one deliberate exception: `Observation.suggested_filename` (a `@property` on the model itself) reads `self.scheduler_data["queried_name"]` (falling back to `self.scheduler_data["target"].name`, the canonical Simbad name, if `queried_name` isn't set yet) purely to build a human-readable filename — a conscious, minimal, cosmetic exception, kept on the model (not in `main.py` or a stage plugin) precisely so `main.py` and the plugins never need to know it exists. Prefers `queried_name` over the canonical name for the same reason every other operator-facing log line does (see the Logging section) — the observer-typed name, not Simbad's own designation. Computed lazily on every access, not cached — reflects whatever `scheduler_data` currently holds (falls back to `"target"` before SCHEDULER has run).

  `Observation` also carries two top-level fields, not casiers (neither is owned by one stage) — `program_file` (the program YAML's filename, e.g. `"demo.yaml"`) and `program_steps` (the expected step lists, `{"sequencer": [...], "reduction": [...], "sharing": "blank_share"}`, the literal names declared in that YAML — `sequencer`/`reduction` are lists, `sharing` is the single value, matching its own singular YAML key) — both set together by `SequencerPlugin.run()` as its very first action, before executing any sub-plugin, so they're already on disk (`main.py` writes `obs` to its YAML file even on the exception path) even if the observation later crashes mid-pipeline. This is what lets a crash be diagnosed later: the nested casier data alone only proves what *succeeded*, not what was *supposed* to happen. Deliberately called `program_steps`, not `pipeline`: "pipeline" is internal plumbing vocabulary (`pipeline_loader.py`, `load_pipelines()`'s ordered lists of sub-plugin instances) — the observation file only ever talks about the *program*, the scientific concept the observer actually asked for.

  `Observation` is also serialized as-is to the observation's YAML file (`obs.yaml_file`) after **every** stage (`observation_file.py::write_observation_file()`, called from both the foreground loop and `run_post_obs()`) — the file only grows, becoming the complete, self-contained record of the observation by the time ARCHIVE finishes. Useful for crash diagnosis: whatever was last written on disk shows exactly how far the observation got.

Naming convention: the local variable holding an `Observation` is `obs`, a `SessionContext` is `session`. Plain `ctx` is reserved for the few genuinely generic spots (e.g. `run_stage()`) that accept either type.

### Two SQLite databases

- **`rosace.db`** (`database.py`) — sessions and observations. Functions: `db_init`, `db_insert_session`, `db_close_session`, `db_insert_observation`, `db_stamp_stage`, `db_set_error`, `db_set_yaml_file`, `db_get_recent_observations`, `db_count_observations_for_target`. `db_get_recent_observations` only returns observations from the current *astronomical day* (local noon to noon, via `time_helpers.py::astronomical_day_start_utc()`) — assumes the server runs in the site's own local timezone, since there is no explicit site timezone setting anywhere in `conf/`. Each observation row also records `program_name`, `queried_name`, and `priority` (from `obs.scheduler_data["program"]`/`["queried_name"]`/`["priority"]`) alongside `target_name` — `db_get_recent_observations()` (and so `GET /observations/recent`) includes `program_name` in every returned row, shown as its own column in the GUI's observations list, next to priority. `db_count_observations_for_target(program_name, target_name)` counts how many observations already exist during the current *astronomical day* (not scoped to a single `session_id` — stopping and restarting the session doesn't reset the count) for a given (program, target) pair, which is how the default scheduler (`scheduler_rosace_2026`) knows a target has already been "consumed" (see below).

`time_helpers.py` (`rosace/rosace/`) is a small shared module for exactly this "local noon to noon" concept — `astronomical_day_start_utc(now=None)` (a UTC instant, for DB comparisons) and `astronomical_day_local_date(now=None)` (a `YYYY-MM-DD` string in the site's own local date, for naming one directory/file per night) both derive from the same private `_local_noon_boundary()`, so the two can never disagree about where the boundary falls. `InitSessionPlugin` (`plugins/init_session.py`) uses `astronomical_day_local_date()` to name the session directory (`<date>_<site_name>/`, see "On-disk layout" below).
- **`targets.db`** (`targets.py`) — stars catalogue and scientific programs (N-N via `program_stars`, which also carries an optional per-pair `exposure_time`). CRUD functions follow the pattern `star_*` / `program_*`. `ProgramCreate.name` is restricted to `^[A-Za-z0-9_]+$` (a `field_validator`, logging the rejection) — this name later becomes a filesystem path and a Python module path in `pipeline_loader.py` (see above), so anything else is rejected before it ever reaches the database. Stars also have a `star_aliases` table (alternate names, e.g. catalogue cross-references) — `star_get_by_name()` tries the canonical `stars.name` first, falls back to `star_aliases` if nothing matches. Populated exclusively through `main.py`'s REST API (`/stars`, `/programs`, `/simbad/import` — all addressed by name, never by internal id, since the id is not something a user thinks in terms of); of the SCHEDULER plugins, only `scheduler_rosace_2026` reads it (see below), and does so read-only — `blank` never touches it. Two bulk-import endpoints exist for populating the catalogue quickly: `POST /stars/import-list` (uploaded text file, one star name per line, each line goes through the same Simbad-backed logic as `/simbad/import`) and `POST /programs/import-list` (uploaded YAML file, `{program: [star, ...]}`, links existing stars to existing programs — no Simbad call, both must already exist). Both accept real file uploads (`UploadFile`, `python-multipart`), not a server-side path, so the GUI or caller can be on a different machine than the server. Both return a per-line report (`status`: `created`/`existing`/`error` or `linked`/`program_not_found`/`star_not_found`) rather than failing the whole batch on the first bad line.

Default path is `~/.rosace/databases/` (`config.py`). Both databases are created automatically on startup.

### Authentication (`auth.py`)

Session-cookie auth. `users`/`auth_sessions` tables live in `rosace.db` (same file `database.py` uses, own module) — named `auth_sessions`, not `sessions`, specifically to not collide with `database.py`'s own unrelated `sessions` table (one row per observation night). Passwords hashed with `bcrypt`; a session is an opaque `secrets.token_urlsafe(32)` token in an `HttpOnly`/`SameSite=Lax` cookie (`rosace_session`), checked against `auth_sessions` on every request — not a signed JWT, deliberately: no secret-key rotation to manage, and revoking a session is just deleting a row.

Every existing REST route sits behind `main.py`'s `protected` `APIRouter` (`dependencies=[Depends(get_current_user)]`) — default-closed: a new route must be added to `protected` (or `admin_router`) consciously, the opposite of a middleware allowlist someone could forget to update for a route added later. `admin_router` (`prefix="/auth/users"`) additionally requires `is_admin` (`Depends(require_admin)`), for account management (`POST`/`GET`/`DELETE /auth/users...`). `/ws` is on neither router — a `Depends()`-raised `HTTPException` doesn't close a WebSocket handshake cleanly — it's checked by hand in `ws_logs()`, before `accept()`, reading the same cookie directly. `POST /auth/login`/`POST /auth/logout` are the only public API routes, declared directly on `app`.

First admin: `python -m rosace.main --create-admin <username>` (password prompted via `getpass`, never passed as an argument, to keep it out of shell history/`ps`). Refuses once any account already exists (`ensure_first_admin()`) — creating further accounts after that goes through `POST /auth/users` (admin-only), not shell access to the machine. If the only admin account is ever lost, direct `sqlite3`/DB-browser access to `rosace.db`'s `users` table is the deliberate recovery path (no separate "forgot password" flow) — just keep `password_hash` a real bcrypt hash if editing it by hand, a plaintext value there fails login silently.

`SESSION_TTL_HOURS`/`SESSION_COOKIE_SECURE` — see config table below. Session length defaults long (14 days) since the app runs unattended overnight; `secure` defaults `false` since the app typically serves plain HTTP on the local network — `true` would silently stop the browser sending the cookie back over HTTP, including on `localhost`.

### The default scheduler: `scheduler_rosace_2026` (`plugins/schedulers/scheduler_rosace_2026/scheduler.py`)

Reads `OBSERVATION_LIST_PATH` (`config.py`) fresh on every call — a plain-text, read-only CSV plan (`Priority, Program, Star, commentaire`) that this plugin never modifies. Each line is resolved against `targets.db` (program exists, star exists — by canonical name or alias, see above — and is linked to that program via `program_stars`); invalid lines are logged and skipped, never fatal. Valid lines are sorted by priority ascending (1 first; file order breaks ties) and walked **individually, one line at a time** — deliberately not collapsed into one group per (program, canonical star) with a single priority, since the same target can appear on multiple lines at *different* priorities (e.g. priority 2 and priority 4), and another target at an intermediate priority (3) must then be offered between the two occurrences, not after both. For each line, its rank among occurrences of the same (program, canonical star) seen so far in this pass — two lines naming the same star under different aliases count as the same target — is compared against `db_count_observations_for_target()` (this astronomical day — not scoped to a single session, see above): once that rank has already been fulfilled, the line is skipped. This is how a target gets "consumed" without ever rewriting the plan file, and without a session restart mid-night re-offering already-consumed targets. A line whose target's current altitude (`astro_math.py::altitude_deg()`, site position from `SITE_LATITUDE_DEG`/`SITE_LONGITUDE_DEG`) is below `MIN_TARGET_ALTITUDE_DEG` is also skipped the same way — logged, not consumed, next line tried. No day/night (sun-below-horizon) check yet, that stays a separate future chantier.

**Local horizon mask (optional, `HORIZON_FILE`)**: when `horizon_file` is declared in `config.yaml` (a Core, site-level key next to `site_latitude_deg`, exposed as `HORIZON_FILE`; absent = no mask, behavior identical to a config without it — the packaged and demo configs declare none), a line whose target is above `MIN_TARGET_ALTITUDE_DEG` but below the terrain obstruction at its current azimuth (`astro_math.py::azimuth_deg()`, North through East) is skipped the same way — logged (`below local horizon (alt < horizon at az ...)`), not consumed, next line tried. The two checks combine: the flat floor is tested first, then the mask (strict `<`, a target exactly at the horizon altitude is accepted); the mask never replaces the floor. The file is a KStars "Artificial Horizon" text export (`~/.rosace/horizon/`), read fresh on every SCHEDULER call like the plan file, parsed by `plugins/schedulers/scheduler_rosace_2026/horizon.py` (private to this scheduler — file parsing and its own `SchedulerFatalError` contract, unlike `astro_math.py`'s pure sky maths): `#` comments and blank lines ignored, the first non-numeric line is the profile name, then one `azimuth altitude` pair per line (degrees; azimuth in [0, 360] with 360 == 0, altitude in [0, 90]). Points must be listed in increasing azimuth, wrapping through 360/0 at most once and stopping before the first point again (a profile may start mid-circle, like the real St-Pancrasse export which starts at 220 — but a point out of place is almost surely a typo, which sorting alone would have silently turned into a plausible, wrong mask); identical duplicate points collapse, two different altitudes at one azimuth, fewer than 2 distinct points, or any unparseable line is an error. Altitude between points is linearly interpolated, circular across 360/0. Validate a file without starting a session with `python -m rosace.main --check-config` (see below).

**Meridian filter (optional, `min_meridian_distance_deg`)**: when `subplugin_params.scheduler_rosace_2026.min_meridian_distance_deg` is > 0 (default 0 = off, so the demo mode, the simulator and the packaged config are unaffected; `config72ED.yaml` sets 3), a line whose target's **hour angle** is within that many degrees of the meridian on either side (`|HA| < threshold`, strict — exactly at the threshold is accepted) is skipped the same way as the other filters: logged (`too close to the meridian (HA +1.2° within ±3.0°)`), not consumed, next line tried. Checked last, after the flat floor and the local horizon. Why it exists: `pointing_72ed._slew_with_backlash_approach()` first slews to `ra + backlash_offset_deg`, i.e. an approach point at hour angle `HA - backlash_offset_deg` (the RA offset is in coordinate degrees), then to the exact position; a target with `0 < HA < backlash_offset_deg` therefore has its approach point before the meridian and its exact point after it, and the AM3 flips pier side (up to three flips on V923 Aql, 2026-09-14, HA +0.2 to +1.5°). Add the 0.25°/min drift over the few minutes the four slews take and the dangerous window is roughly `(-1°, +backlash_offset_deg)` plus the mount's hysteresis, so the threshold should be at least `backlash_offset_deg + 1°` (2 + 1 = 3 on the 72ED). It is a separate parameter, deliberately not derived from `backlash_offset_deg`: that one is a per-device value of the hardware YAML, which a scheduler never reads (interchangeable, hardware-agnostic schedulers). Measured in degrees of **hour angle**, not of arc on the sky (`astro_math.py::hour_angle_deg()`, `LST - RA`, positive after the meridian): hour angle advances 15°/hour at every declination, which is what the RA axis sees, so the excluded window is the same 24 minutes per sidereal day for every target — an arc distance (`~|HA| × cos(dec)`) would make a near-polar target look permanently "on the meridian" and never selectable. Not covered: a target crossing the meridian during an already-running observation (the flip is decided at the slews in the first minutes; tracking through the meridian does not flip). Related, separate and not fixed: the same approach slew sends `dec + backlash_offset_deg`, which exceeds 90° for a target above declination 88° (see `TODO.md`).

`astro_math.py` (`rosace/rosace/`) is a small, dependency-free spherical-astronomy helper (Meeus' low-precision GMST formula + the standard altitude/azimuth formulas, plain `math`/`datetime`; `azimuth_deg()` is North through East, the exact inverse of `equatorial_from_horizontal_deg()`), used instead of AstroPy's `AltAz` transform (see HISTORY.md for why the AstroPy/IERS path was dropped) — accurate to a few arcminutes, orders of magnitude better than `MIN_TARGET_ALTITUDE_DEG` needs, with zero external data dependency and zero maintenance burden. If every line is either invalid, already fully consumed, or currently too low, `scheduler_data["target"] = None` (see the `target=None` contract above). On success, populates `scheduler_data["target"]` (canonical `Target`), `["queried_name"]` (the name as written in the file — may be an alias), `["program"]`, `["priority"]`, and `["exposure"]` (`ExposureConfig`, `exposure_time` taken from `program_stars` if set there, otherwise `None` — computing it from magnitude is a future chantier, not yet implemented, so `ExposureConfig.exposure_time` is `Optional`).

A missing/malformed plan file or horizon file (when `horizon_file` is declared — a declared file is mandatory, no silent fallback to "no mask"), or invalid data in `targets.db` (e.g. `program_stars.exposure_time` corrupted to `''` instead of `NULL` by an external tool) raises `SchedulerFatalError` — a dedicated exception, distinct from an ordinary exception. `session_runner()` treats it like an `INIT_SESSION` failure (`state.is_running = False`, session stops) instead of the usual "log and restart from SCHEDULER" retry loop, since retrying can't fix a configuration/data problem — this is the difference between `SchedulerFatalError` (stop) and any other exception from a stage (retry).

### Observation YAML persistence (`observation_file.py`)

Plays the same role for the observation's YAML file that `database.py` plays for SQLite: a dedicated persistence module, kept separate from both the orchestrator (`main.py`) and the pure data model (`models.py`). `create_observation_file(obs, target_dir)` fixes `obs.yaml_file` (using `obs.suggested_filename`) without writing anything; `write_observation_file(obs)` serializes the current full state (`obs.model_dump(mode="json")`) to that path — a no-op until `create_observation_file` has run. `main.py` only ever calls these two functions, the same way it calls `db_insert_session` — it never touches YAML or filesystem details directly.

### INDI hardware drivers (`hardware_indi/`) and connectivity check (`plugins/hardware_connectivity.py`)

`hardware_indi/` (`wrapper/` + `devices/`) holds the real, blocking (non-asyncio) Python classes that talk to an INDI server — one class per device type (`devices/camera.py::IndiCamera`, `devices/mount.py::IndiMount`, `devices/focuser.py::IndiFocuser`, etc.), all built on `wrapper/indi_device.py::IndiDevice` and `wrapper/indi_client.py::IndiClient`. Adapted from the PANOPTES/POCS observatory control software (see HISTORY.md) — the POCS-specific config loader and MongoDB-backed database layer have been stripped out (`wrapper/base.py` is now just a logger), since Rosace has its own config/databases. Devices sharing the same INDI server (`indi_host`/`indi_port`) share a single `IndiClient` instance under the hood (`SingletonIndiClientHolder`), whose setup is not thread-safe.

Each device's class is declared in the active hardware YAML (`HARDWARE_CONFIG_PATH`, e.g. `conf/hardware_indi_simu.yaml`) via `module`/`module_dir`/`class_name` fields and loaded **dynamically** (`importlib`) rather than imported directly — this is what lets the set of devices vary freely per hardware profile (a camera here, an ASI camera there, an extra `pointing_camera` in one profile but not another) without any Python code change. Each device entry also declares a `role` field (`mount`/`camera`/`focuser`/`filter_wheel`/`spectroscope`) — an explicit string, not inferred from the class — used to pick which `hardware_indi/adapters/` class wraps it (see below); a device whose role has no registered adapter yet is still connected but simply isn't included in the session's hardware mapping.

`plugins/hardware_connectivity.py::connect_session_hardware()` is called from `INIT_SESSION` (`init_session.py`), **only when `SEQUENCER_BACKEND == "indi"`**: it reads the hardware YAML into a plain dict, dynamically loads and connects every declared `INDI_drivers` device — **for the whole session, connections are left open** — plus checks PHD2 reachability (a plain TCP connect, deliberately separate from the real `phd2/phd2_client.py::Phd2Client` used later by `pointing_72ed` below — this `INIT_SESSION` check only needs to confirm the server is listening, not perform an actual RPC handshake), each bounded by `HARDWARE_CONNECT_TIMEOUT_SECONDS` (single attempt, no retry). Because of the shared-`IndiClient` thread-safety concern above, devices are connected **one at a time** (not concurrently); PHD2, an independent plain `asyncio` TCP connection, runs concurrently with the device connects. Each blocking device connect runs in a worker thread (`asyncio.to_thread`) so it never blocks the FastAPI event loop. Any failure (timeout or exception, on any device or PHD2) raises a single aggregated `RuntimeError`, which `INIT_SESSION` lets propagate — `session_runner()` already treats an `INIT_SESSION` exception as a critical, session-cancelling failure, so no extra error handling is needed there. Known simplification: if one device fails partway through, devices already connected before it are left connected rather than explicitly rolled back — acceptable since the session is about to stop anyway, revisit if it becomes a real problem.

`connect_session_hardware()` also splits each device's YAML entry, implicitly, into two halves — chosen deliberately over adding a new hardware YAML field for every business parameter, since the whole point is that SEQUENCER sub-plugins should be able to read a value a hardware profile declares (a camera's `cooling_capability`, a focuser's `focus_range`, a spectrograph's future calibration settings...) without this module, or any orchestrator code, ever having to know that field exists. A closed, universal list (`_PLUMBING_KEYS` — `role`/`module`/`module_dir`/`class_name`/`indi_client`/`indi_name`) covers exactly what's needed to load and connect *any* device, checked for every device regardless of role (missing one raises a clear error naming it, collected the same way as a connection failure); everything else in that device's entry — whatever it is — becomes that device's **params**, extracted verbatim by `_extract_device_params()` with no field named there. Devices declared purely as placeholders (e.g. `spectroscope`'s `SpectroscopePlaceholder`, see below) still declare `indi_client`/`indi_name` even though they never use them, deliberately, so this validation never needs a per-role exception. Returned as a small `ConnectedHardware(adapters, hardware_config)`, not a bare dict — `adapters` is what becomes `Observation.hardware` (unchanged), `hardware_config` is the new parallel structure, same device-name keys, holding each device's params (see below).

### Generic device interfaces (`hardware/`) and INDI adapters (`hardware_indi/adapters/`)

`hardware/` holds backend-agnostic device contracts — one `typing.Protocol` per device role (`hardware/mount.py::Mount`, `camera.py::Camera`, `focuser.py::Focuser`, `filter_wheel.py::FilterWheel`, `spectroscope.py::Spectroscope`), plus `hardware/errors.py`'s generic exception hierarchy (`DeviceError` → `DeviceConnectionError`/`DeviceTimeoutError`/`DeviceCommandError`). SEQUENCER sub-plugins are meant to depend only on these, never on a specific backend's classes — this is what keeps the door open to a future `hardware_ascom/` (Ascom/Alpaca) without touching sub-plugin code. Each interface declares only what Rosace actually needs today, not full API coverage — e.g. `Focuser` has no `autofocus()`, since the underlying INDI focuser doesn't expose one either (autofocus is a measure-move-remeasure algorithm that belongs in the focus SEQUENCER sub-plugin, not the device layer); `Camera` covers any camera role (science, guiding — see `hardware_indi_simu.yaml`'s `science_camera`/`guiding_camera` entries) via one shared contract, not a per-role interface. Method names deliberately follow ASCOM's own published device interfaces (naming only, not philosophy — INDI's more open design is still the model followed elsewhere). `Spectroscope` is a light-source selector only (`set_light_source`/`get_light_source`, `LightSource` enum: `SKY`/`DARK`/`FLAT`/`CALIB`) — deliberately narrow, since real spectrograph control varies enormously by model; richer per-model capabilities are expected to live on that model's own device class, not on this shared contract.

`hardware_indi/adapters/` (`mount.py::MountAdapter`, `camera.py::CameraAdapter`, `focuser.py::FocuserAdapter`, `filter_wheel.py::FilterWheelAdapter`, `spectroscope.py::SpectroscopeAdapter`) are the concrete INDI implementations: each owns a device instance's whole lifecycle — `connect()`, business calls, `disconnect()` — running every blocking INDI call via `asyncio.to_thread`, so the generic interfaces stay uniformly async regardless of backend. `CameraAdapter.expose()` runs the whole blocking acquisition sequence (`prepare_shoot` → `setExpTimeSec` → `shoot_async` → `synchronize_with_image_reception` → `get_received_image`) as one unit in a single worker thread, since these must happen in strict order on the same device. Adapters translate whatever `IndiDevice`/`pyindi-client` raises into `hardware/errors.py`'s generic hierarchy. `SpectroscopeAdapter` is the odd one out here: every other adapter wraps exactly one INDI device shape (INDI standardizes mount/camera/focuser/filter-wheel control), but spectrograph control isn't standardized at all — so `SpectroscopeAdapter` itself stays generic (deliberately not type-hinted to one specific device class) and the model-specific translation lives entirely in `hardware_indi/devices/` instead, one class per spectrograph model, all sharing the same small method surface. `devices/spectroscope_placeholder.py::SpectroscopePlaceholder` — a pure in-memory stand-in (no real INDI protocol at all, `connect()`/`disconnect()` are no-ops), needed because no INDI simulator exists for a spectroscope, unlike the mount/camera/focuser simulators — is still what `hardware_indi_simu.yaml` declares with `role: spectroscope`. The 72ED profiles (`hardware_indi_72ED-LAN.yaml`/`-WIFI.yaml`) instead declare `devices/spectro_Alpy600.py::IndiSpectroAlpy600` — the real Alpy600 light-source control, driven not through any dedicated spectroscope protocol (none exists) but through the Stellarmate SM Pro powerbox's own switch vector `POWER_CHANNELS`, elements `POWER_CHANNEL_3`/`POWER_CHANNEL_4`: both channels off is `SKY`, both on is `DARK`, channel 3 alone on is `CALIB`, channel 4 alone on is `FLAT` — all four confirmed against the real instrument. `hardware_indi/devices/usis_spectroscope.py::IndiUsisSpectro` also exists (real USIS protocol, used by devices like UVEX) but is unrelated to the 72ED's Alpy module and currently unused by any hardware profile — left in place, not wired up yet.

`IndiMount.slew_to_coord_and_track()`/`slew_to_coord_and_stop()` (`hardware_indi/devices/mount.py`) don't trust INDI's own synchronous property wait on `EQUATORIAL_EOD_COORD` alone to mean the mount has actually arrived. Found 2026-09-11 (see HISTORY.md): issuing a slew immediately after another command on that same property (e.g. a SYNC, which completes near-instantly) can make the wait return before the mount has moved at all — the local property object hadn't yet observed the driver's own `BUSY` transition for the new command. Both methods call `_verify_slew_reached()` right after `set_coord()` (skipped if the mount is parked, since `set_coord()` itself no-ops then): re-reads `get_current_coordinates()` and compares it to the commanded coordinate, returning only once the two are within `SLEW_POSITION_TOLERANCE_ARCMIN` (10′ — well above real completed-slew readback noise, ~1-2″, and well below the smallest deliberate close slew this codebase issues today, the 2° backlash-approach offset below), polling every 0.5s up to `SLEW_VERIFY_TIMEOUT_SECONDS` (180s) before raising. A device-layer guard, transparent to every caller (`MountAdapter.slew_to()`, `pointing_72ed`, `home_sync_am3`'s own homing attempts below) — none of them need to know it exists.

**Wired into SEQUENCER**, minimally — `slew.py` (backend indi) calls `obs.hardware["mount"].slew_to(...)` for real; `focus.py` is deliberately left as a placeholder (no autofocus algorithm exists yet, see `hardware/focuser.py`'s docstring). `star_spectra_acquisition.py` (backend indi) — the science acquisition sub-plugin — switches `obs.hardware["spectroscope"]` to `LightSource.SKY` first (leaves it in SKY afterward, no further action needed), then calls `obs.hardware["science_camera"].expose(...)` for each sub-exposure. Neither it nor `slew.py`/`focus.py` check for a previous step's casier before running — the orchestrator's own `try/except` already guarantees a failed pointing step never lets a later one run (see the Plugin system section above); this is also what lets `pointing_72ed` (below) replace `slew` in a program without this sub-plugin needing to know or care which one pointed the telescope. Exposure time/count is computed by `acquisition_helpers.py::compute_exposure_time_and_count()`, which accepts *either* an explicit `scheduler_data["exposure"].exposure_time` (already known from `program_stars.exposure_time` in `targets.db` — meant to be set there only when the magnitude-based duration wouldn't do, e.g. it would saturate that particular star) *or*, when that's unset, a target magnitude (`exposure_time_mag0 * 10**(magnitude / 2.5)`). Either way, that duration (raw) is a per-sub-exposure target, not a total integration budget to divide: if `raw <= max_exposure_time`, every sub-exposure is `raw` seconds long, repeated at least `min_exposure_count` times (a bright star with a short duration still gets a proper stack, e.g. cosmic-ray rejection, instead of a single frame); if `raw > max_exposure_time`, sub-exposures are capped at `max_exposure_time` and repeated `max(min_exposure_count, ceil(raw / max_exposure_time))` times (e.g. a raw 780s at a 300s max becomes 3×300s, not one 780s exposure) — `min_exposure_count` only ever raises the count, never lowers a higher `ceil()` result. The multi-sub-exposure loop itself stays in the sub-plugin, not the helper. Each sub-exposure is captured via `acquisition_helpers.py::capture_science_image()` (a plain `expose()`-then-`writeto()` primitive, the shared foundation the DARK/BIAS capture sub-plugins also use), writing one file per sub-exposure named via `acquisition_helpers.py::build_fits_root_name("STAR", target_name=scheduler_data["queried_name"], ...)` (a shared root name across the whole series, `-1`/`-2`/... appended per file — see `build_fits_root_name()`'s own docstring for the full naming convention, also used by `capture_guide_image()` for guide images — kept as its own separate function rather than reusing `capture_science_image()`, since it still needs to stamp FITS header cards on the image between `expose()` and `writeto()`), checking `obs.stop_check()` between two sub-exposures (not during one already started on the camera — no real hardware abort here) so a stop request doesn't have to wait for every remaining sub-exposure to finish. No casier of its own — every produced filename is appended straight to the shared `sequencer_data["star_spectra_images"]` key that REDUCTION actually reads (see the "Shared, purpose-named keys" note above). Still doesn't honor an explicitly-set `exposure.num_exposures` — deferred, along with a real stacking strategy; likewise, no FITS header keywords are stamped on science images yet beyond what the camera driver itself writes. `Observation.hardware`/`SessionContext.hardware` (`models.py`) carry the connected adapters, keyed by device name — `Field(exclude=True)`, never persisted to the YAML dossier or the DB, since these hold live connections, not observation data. `InitSessionPlugin` populates `SessionContext.hardware`; `session_runner()` (`main.py`) copies it onto every freshly-created `Observation` (sub-plugins never see `SessionContext`); `CloseSessionPlugin` disconnects each adapter (one failure doesn't block the others). `Observation.hardware_config`/`SessionContext.hardware_config` carry each device's own params (see `connect_session_hardware()` above), same device-name keys, same lifecycle — but plain, picklable data, not live connections. Also `Field(exclude=True)` — same policy as `hardware`, but by choice rather than technical necessity: a sub-plugin that wants a specific value recorded in the observation YAML copies it explicitly into its own `sequencer_data` casier, the same way any other sub-plugin output works.

**Critical detail**: `session_runner()` clears `obs.hardware` to `{}` *before* calling `obs.model_copy(deep=True, ...)` and restores it after, wrapped in its own `try/except`. `model_copy(deep=True, update={...})` does **not** skip deep-copying fields named in `update` — it deep-copies everything first and only overwrites afterward, so deep-copying live INDI adapters raises (`TypeError: cannot pickle '_thread.lock' object` — see HISTORY.md). Post-obs stages (REDUCTION/SHARING/ARCHIVE) never touch hardware anyway, hence clearing it is safe.

`pointing_72ed.py` (`plugins/sequencer_plugins/pointing_72ed/`) is a separate SEQUENCER sub-plugin, not one of the `slew`/`focus`/`star_spectra_acquisition` triad — a program declares it *in place of* `slew` for `SEQUENCER_BACKEND="indi"`. It points the telescope in two phases, each refining the previous one's precision, since only the astrometric measurement is precise enough to put the star exactly in the spectrograph slit:

- **Phase 1 (mount-precision correction)**: slews to the target (a two-step slew every time, see below), captures a guide image, plate-solves it while recording the mount's pointing error to the `pointing_errors` DB table (`plate_solve_helper.py::solve_wcs(record_error=True, observation_id=obs.id)`), reads the actual sky position at the spectrograph slit (`solve_result(fits_path, slit_x, slit_y)`), computes the offset between that and the aimed-at target (`SkyCoord.spherical_offsets_to()`), and derives a corrected target position (`spherical_offsets_by()`, same offset applied in reverse) — then slews there.
- **Phase 2 (PHD2-guiding-precision refinement)**: captures a second guide image at the corrected position, starts PHD2 guiding (`obs.hardware["phd2"].start_guiding()` — auto-selects its own guide star, generally *not* the science target itself, and only returns once settled), reads which pixel PHD2 locked onto (`get_lock_position()`), plate-solves the second image (this time without recording a pointing error — the mount is already corrected, this isn't a mount-accuracy measurement anymore — and with a much tighter search radius than Phase 1's, `phase2_search_radius_deg` below, since a precise position hint is already available and a tight cone directly cuts this synchronous solve's real wall-clock cost — found 2026-08-30 to be the actual source of a multi-second gap observed live between PHD2 settling and its lock position actually being corrected, see HISTORY.md), computes where the corrected target actually falls in this image's pixel space (`plate_solve_helper.py::world_to_pixel()`, the inverse of `solve_result()`) versus the slit position, and nudges PHD2's lock position by that same residual pixel offset (`set_lock_position(lock_x - dx, lock_y - dy, exact=True)`) — PHD2 then drives the mount until its own guide star reaches that new lock position, dragging the whole field (target included) onto the slit with sub-pixel guiding precision, impossible to reach via the mount's own slew precision alone. A second `start_guiding()` call waits for this new settle.

Every slew in both phases goes through `_slew_with_backlash_approach()` (module-private, not on the generic `Mount` Protocol): a preliminary slew offset by `backlash_offset_deg` (hardware YAML, under `mount:` — a mechanical trait of that specific mount unit) in both RA and DEC, then the exact slew — always approaching from the same mechanical side makes backlash reproducible instead of varying with slew direction. The guiding camera's own exposure time for these direct (non-PHD2) captures, along with `sampling_arcsec`/`slit_x`/`slit_y`, comes from `SUBPLUGIN_PARAMS["guiding"]` (`conf/config.yaml`'s `subplugin_params.guiding`) rather than the active hardware YAML: these four describe the optical alignment/plate-scale of the whole telescope+spectro+guiding-camera assembly, not a property of the guiding camera device in isolation — they stay the same across hardware profiles that differ only in how they reach the same physical instrument (e.g. `hardware_indi_72ED-LAN.yaml` vs `-WIFI.yaml`), unlike `backlash_offset_deg` above, which really is per-device (see HISTORY.md 2026-09-06). `stop_phd2_guiding.py` (below) and `guiding_dark_acquisition.py` (`exposure_seconds` only) read the same `SUBPLUGIN_PARAMS["guiding"]` block. A `phd2.stop_capture()` at the very start of the sub-plugin defensively stops any guiding left running from the previous observation (nothing else stops it explicitly) — otherwise its own corrections would fight the Phase 1 slews.

`stop_phd2_guiding.py` (`plugins/sequencer_plugins/stop_phd2_guiding/`, backend `indi` only) is meant to always be the last SEQUENCER step in a program — nothing else stops PHD2 once guiding has started, so without this it keeps running past the whole observation and into the next one, fighting that next observation's own mount slews. Beyond the stop itself, it also captures and plate-solves one post-science guide image, purely to log where the target actually ended up relative to the slit at the end of the observation (`sequencer_data["stop_phd2_guiding"] = {"guide_image": ..., "residual_arcsec": ...}`) — deliberately never with `record_error=True`: the `pointing_errors` table only ever records the mount's own *initial* pointing error, measured right after its first slew of the night, meant for long-term polar-alignment drift detection; a plate-solve-corrected post-science position would only pollute that signal, not extend it. Because of that capture, it's no longer a bare, no-risk "stop guiding" drop-in for any program — it needs `subplugin_params.guiding` configured and `guiding_dark_acquisition` to have already run earlier in the same session (`capture_guide_image()`'s own default dark-subtraction raises otherwise); already true of every program that starts PHD2 guiding at all, since that's the same requirement its own guide-image captures already have. A temporary diagnostic variant, `stop_phd2_guiding_diag.py`, existed alongside it from 2026-08-30 (5-shot statistics, for the Phase 2 residual investigation) until the investigation was closed and the directory deleted 2026-09-15 (see HISTORY.md).

`home_sync_am3.py` (`plugins/sequencer_plugins/home_sync_am3/`, backend `indi` only) re-homes the AM3 mount once per session, before the first real pointing — not before every observation, since re-homing is comparatively slow and the mount is expected to hold its position for the rest of a session that stays connected throughout. Declared via `hardware_indi_72ED-WIFI.yaml`/`-LAN.yaml`'s own `sequencer_prefix: [guiding_dark_acquisition, home_sync_am3]` (see the Plugin system section above and `guiding_dark_acquisition` above — its median dark must exist before this step's own guide captures), not inside `Be_stars.yaml` itself — re-homing is an equipment concern (specific to this one mount), not a scientific-program one, so a program YAML never mentions it. `hardware_indi_simu.yaml` deliberately declares no `sequencer_prefix` at all: the INDI Telescope Simulator isn't an AM3, and syncing it risks activating its own `ALIGNMENT_SUBSYSTEM_ACTIVE` model (see HISTORY.md, 2026-08-26) — this step now simply never runs when testing against the simulator, instead of needing a special case anywhere in the code.

It parks then unparks the mount (`mount.park()`, `mount.unpark()`) for a mechanical zero-position reference, then (unless `SYNC_HOME_VIA_PLATE_SOLVE`, a one-line kill switch, is flipped to `False` and the server restarted) attempts a **measured** sync rather than a computed one — closing the gap between the mount's mechanical zero and the real sky without ever trusting a value that hasn't itself been verified against the sky (see HISTORY.md, 2026-08-26/2026-09-11: a sync to a theoretically-computed position, RA=local-sidereal-time/DEC=+90, was found on the real AM3 to leave a consistent ~25′ residual — no better than `unpark()` alone, since both derive from the same time+site math — versus 1-3′ for a measured one). Up to `MAX_HOMING_ATTEMPTS` (7) homing attempts, each: picks a fresh random point at a fixed altitude (`HOMING_ALTITUDE_DEG`, 65°) and a random azimuth in `[HOMING_AZIMUTH_MIN_DEG, HOMING_AZIMUTH_MAX_DEG]` (5°-175° — the whole eastern half of the sky, never within 5° of either meridian crossing, keeping every attempt on the same side of the pier and avoiding a mid-homing flip); converts it to RA/Dec via `astro_math.py::equatorial_from_horizontal_deg()` (the same no-IERS pure-trigonometry family as the scheduler's own altitude check — not AstroPy's `AltAz`, for the same reason); slews there, captures a guide image, and plate-solves it. The first attempt that solves is synced to (`mount.sync_to_coordinates()`, the measured position) and the loop stops; a failed attempt (slew or plate-solve) is logged at WARNING and retried at a new random point — `obs.stop_check()` is checked between attempts — and running out of attempts falls back to park/unpark only, exactly as if the kill switch were off: this step must never turn into a session-blocking failure over a homing sync it couldn't get. Every slew here already goes through `IndiMount`'s own post-slew position verification (see below) — found necessary by the same field test that motivated this retry loop in the first place (see HISTORY.md, 2026-09-11/2026-09-12): a slew issued immediately after a sync can silently return before the mount has actually moved.

Casier (unlike the computed-sync version this replaced, which had none — a measured sync genuinely produces data worth recording): `sequencer_data["home_sync_am3"] = {"method": "measured_sync"|"park_unpark_only", "attempts": <int>, "guide_image": <filename>|None, "synced_ra": <float>|None, "synced_dec": <float>|None}` — only ever set on the one observation where homing actually ran (every later observation in the same session returns early, before reaching it). Tracked via a module-level "last session_id already homed" value: cheap, in-process only (lost on a server restart, same as `main.py`'s own `state` singleton — but *not* lost across a plain stop/restart of the session within the same server process, since sub-plugin modules are imported once via `importlib.import_module()` and then reused from `sys.modules`, never re-executed). Reset implicitly whenever `session_id` changes, rather than through any explicit call from `INIT_SESSION`, so `INIT_SESSION` never needs to know this sub-plugin — or the AM3 — exists.

`INIT_SESSION` also unparks the mount generically, right after connecting hardware (`plugins/init_session.py`, `sequencer_backend=indi` only) — symmetric to `CLOSE_SESSION`'s own generic `park()` (below), and deliberately not gated behind `sequencer_prefix`/`home_sync_am3`: a mount left parked by a previous session's close (or never unparked at all) can't be slewed at all until this runs (`IndiMount.set_coord()` silently no-ops, not raises, on a parked mount) — a baseline precondition every hardware profile needs regardless of which mount it declares, not an AM3-specific concern. Found 2026-09-08: before this existed, moving `home_sync_am3` out of `Be_stars.yaml` (above) meant the simulator profile — which declares no `sequencer_prefix` — never unparked its mount either, since `home_sync_am3`'s own `unpark()` call had implicitly been serving both roles at once. On the real AM3, this generic unpark is immediately followed by `home_sync_am3`'s own `park()`/`unpark()`/sync sequence — redundant but harmless, since `unpark()` alone is a fast state change, not physical motion; the real, slow re-homing motion still happens exactly once, inside `home_sync_am3`.

Not yet done: no `hardware_ascom/` (no Windows environment to validate against yet); no real autofocus algorithm (`focus.py` stays a placeholder); no real Alpy/Stellarmate device class beyond the Alpy600 (`SpectroscopePlaceholder` stands in on the simulator profile). DARK/BIAS/CALIB/FLAT acquisition are all done (see below) — but `reduction_plugins/flat` itself doesn't yet consume `flat_acquisition`'s output, still a future chantier.

### Science camera temperature and the dark-frame library (`dark_acquisition`, `bias_acquisition`, `calib_acquisition`, `flat_acquisition`, `plugins/camera_cooldown.py`)

Every DARK frame must come from the *same* science camera used for the observation, at the *same* sensor temperature as the science images — but a full DARK series is slow to shoot, so a reusable, temperature-bucketed library (`DARK_LIBRARY_DIR`) avoids reshooting one every observation when a compatible series already exists.

**Camera temperature control** (`hardware/camera.py::Camera`): `set_temperature`/`get_temperature`/`get_frame_size`/`set_cooling_on`/`set_cooling_off` (`get_frame_size` returning `(NAXIS1, NAXIS2)` of the camera's **currently configured** `CCD_FRAME`/ROI — read live via `IndiCamera.get_roi()`, not INDI's `CCD_INFO`/`CCD_MAX_X`/`CCD_MAX_Y`, which only reports the sensor's maximum capability and is otherwise unused by Rosace. Deliberately not "the full sensor resolution": a sub-framed (windowed) acquisition is a legitimate, deliberate configuration, and the four acquisition sub-plugins below only ever need "whatever size a new exposure will actually come out as right now," not "the sensor's max." Found the hard way, 2026-09 — see HISTORY.md: a stuck `CCD_FRAME` sub-window left over from an external tool made every real exposure smaller than `CCD_INFO`'s reported max, permanently breaking the dark/bias/calib/flat reuse check below until the mismatch was diagnosed and `get_sensor_size()` was replaced with this live-ROI query), with matching `CameraAdapter` methods (same `asyncio.to_thread` + `DeviceCommandError` pattern as `expose()`). The cooler on/off switch (INDI's `CCD_COOLER`) is a separate property from the temperature setpoint (`CCD_TEMPERATURE`) on many cameras — the setpoint alone has no physical effect until the cooler is actually switched on (see HISTORY.md). **Ambient temperature** comes from the focuser's own probe — `hardware/focuser.py::Focuser.get_temperature()`, backed by `IndiFocuser.get_temperature()` reading INDI's `FOCUS_TEMPERATURE`/`TEMPERATURE` property. This is an explicit, user-confirmed hypothesis, **not yet validated against the real 72ED focuser** — if that focuser turns out not to expose a temperature probe, an alternative ambient-temperature source will be needed.

**Two distinct responsibilities in `plugins/camera_cooldown.py`**, both `sequencer_backend=indi` only:

- `activate_cooling_for_every_camera()` / `deactivate_cooling_for_every_camera()` — generic, apply to **every** connected camera-role device whose hardware YAML entry declares `cooling: true`, not just the science camera (a guiding or pointing camera can independently have its own cooler). No explicit role check needed: only camera-role devices ever declare a `cooling` field at all, so iterating `hardware_config.items()` and checking `.get("cooling")` naturally filters to the right devices. Called once each, symmetrically: `activate_...` from `InitSessionPlugin` right after `connect_session_hardware()` (failures propagate — same posture as connectivity itself); `deactivate_...` from `CloseSessionPlugin`, **before** the device-disconnect loop (the cooler-off command needs a still-live connection) — each device's failure is caught and logged, not raised, same "one failure doesn't block the others" posture as the disconnect loop right after it.
- `cool_science_camera_to_target()` — specific to the science camera only, and assumes its cooler is already on (`activate_cooling_for_every_camera()` ran first): only when the active hardware profile's `science_camera` entry additionally declares `cooling: true` (checked a second time, specifically for this camera, since only it needs a precise target — a guiding camera's cooler is just switched on, never given a computed setpoint): reads ambient temperature from the focuser, computes the session's fixed target sensor temperature (`dark_library_helpers.py::compute_camera_target_temperature()` — 80% of the camera's `cooling_capability` device param as a margin below ambient, rounded **up** to the next multiple of 5 so darks bucket cleanly — e.g. ambient 15°C, capability -30°C → delta 24°C → raw -9°C → target -5°C), also clamped to never come within `MIN_COOLING_MARGIN_DEG_C` (5°C, a fixed module constant) of ambient — a weak enough `cooling_capability` could otherwise let the naive rounded-up target land at or above ambient itself, which a cooling-only camera can never reach (see HISTORY.md); when the naive target doesn't leave that margin, the next colder multiple of 5 is used instead. Commands `set_temperature()`, then polls `get_temperature()` (every 5s, logging the current reading each time so a long cooldown is visible in progress rather than silent until it either reaches target or times out) until within the camera's own `temperature_tolerance_deg_c` device param, or `CAMERA_COOLDOWN_TIMEOUT_SECONDS` elapses (fatal — `INIT_SESSION` lets the exception propagate exactly like an unreachable INDI device, session does not start; no automatic best-effort fallback), or `ctx.stop_check()` (see above) becomes true (a manual stop simply interrupts the wait, not treated as a failure). The result — `(ambient_temp_c, target_temp_c)` — is stored on `SessionContext.ambient_temperature_deg_c`/`camera_target_temperature_deg_c`, then copied by `session_runner()` onto every freshly-created `Observation` (same mechanical copy as `hardware`/`hardware_config`, but these two fields are **not** `exclude=True`: unlike live connections, they're plain descriptive facts worth persisting in the observation YAML — same top-level placement as `program_file`/`program_steps`, session-wide data that isn't any one stage's casier).

**`dark_acquisition`** (`plugins/sequencer_plugins/dark_acquisition/`, backend `indi` only, no `_internal.py`) resolves a usable DARK series for the observation, trying three origins in order, cheapest first, and records which one it used:

`dark_library_helpers.py::ensure_dark_library_structure()` pre-creates `DARK_LIBRARY_DIR` and one subdirectory per temperature bucket, from `DARK_LIBRARY_MIN_TEMP_C` to `DARK_LIBRARY_MAX_TEMP_C` (step `DARK_LIBRARY_TEMP_STEP_C` — module-level constants, `-20`/`0`/`5` by default) — a fixed range in code, deliberately not a `conf/config.yaml` key: a few extra empty directories cost nothing, so a wide-enough fixed range removes the need for a config knob entirely. Called once from `main.py`'s `lifespan()` (server startup, alongside `db_init()`/`targets_db_init()`/`auth_db_init()` — not per-session, since the library outlives any one session), using `temperature_bucket_dirname()` — the same function `dark_acquisition` itself calls to look a bucket up, so the two can never name a bucket differently. `mkdir(..., exist_ok=True)` makes every call idempotent and side-effect-free on a directory that already has darks in it (from a previous session or a manual library transfer) — safe to run on every server startup, not just the first.

1. **`current_session`** — a usable series already sits in this session's own directory (e.g. shot for an earlier observation tonight).
2. **`library`** — a usable series exists in `DARK_LIBRARY_DIR / <temperature bucket>` (`dark_library_helpers.py::temperature_bucket_dirname()` — e.g. `TempMinus5degrees`, `Temp0degrees`, `TempPlus5degrees`; never a leading `-` in a path segment), copied into the session directory before use (every session image must live there, per the on-disk layout above) — **never the other way around**: nothing in this codebase ever writes into the library itself, only a manual transfer by the observer does.
3. **`camera`** — neither of the above: switches the spectroscope to `LightSource.DARK` and shoots a fresh `DARK_COUNT`-frame series with the science camera, exposure `MAX_EXPOSURE_TIME_SECONDS`, same `capture_science_image()`/`build_fits_root_name()`/`obs.stop_check()`-between-sub-exposures pattern as `star_spectra_acquisition.py`.

"Usable" (`dark_library_helpers.py::find_usable_frame_series()`, one implementation shared by every lookup below — DARK's three origins and BIAS's two — so the matching rule can never silently diverge between them) means: at least `count_required` files of the given `image_type` (`"DARK"`/`"BIAS"`) whose filename encodes a temperature (the same `_{temp}deg_` token `build_fits_root_name()` already writes) within `TEMPERATURE_TOLERANCE_DEG_C` (2°C, a fixed module constant) of the target — not an exact match: a session restart can recompute a slightly different target temperature, and without this tolerance an otherwise perfectly usable same-night series would be rejected and reshot for no real reason. The temperature is parsed back out of the filename (regex, not a substring check) precisely to compare it numerically against the tolerance — there is no temperature card in the FITS header to fall back on. The first file's FITS header (read alone, never the pixel data) must also report `NAXIS1`/`NAXIS2` matching the camera's own `get_frame_size()` (its currently configured `CCD_FRAME`, not the sensor's max — see above) and an `EXPTIME` at least the required exposure time minus `EXPOSURE_TIME_TOLERANCE_SECONDS` (1s, same reasoning — a real camera driver doesn't guarantee the exact requested duration to the millisecond). A longer exposure is still accepted outright. Deliberately reads `EXPTIME` from the FITS header rather than parsing it back out of the filename — `build_fits_root_name()`'s own docstring already marks that field human-readable only, not meant to be machine-parsed. The origin found is recorded both in the log and in the sub-plugin's own casier — `sequencer_data["dark_acquisition"] = {"origin": ..., "dark_files": [...]}` — since both are genuinely produced by this step. The log itself never lists every filename — one line states the series shape (`Origin={origin}, series of {count}x{exposure}s at {temp}deg`), a second gives `dark_library_helpers.py::summarize_series_root_name()`'s one-name stand-in for the whole series (the first file's name with its trailing per-file index replaced by `-xxx`, e.g. `DARK_-15deg_5x300s_..._-xxx.fits`) — same two-line shape for `bias_acquisition` below.

Never re-sets or re-checks the camera's temperature itself — trusts the once-per-session cooldown above and reads `obs.camera_target_temperature_deg_c` directly, which is also why the reference frame size comes from the camera's own live `get_frame_size()` rather than an already-acquired science image: this step's position in a program's `sequencer` list relative to `star_spectra_acquisition` doesn't matter. Wired into `Be_stars.yaml` (the real-hardware program), positioned *before* `spectro_light_source_to_sky` — since the `camera` origin leaves the spectroscope on `DARK`, it must run before the step that resets it to `SKY`, not after. Deliberately **not** added to `demo.yaml`, which is backend-agnostic (`internal`/`indi`) by design; `dark_acquisition` has no `_internal.py` counterpart.

**`bias_acquisition`** (`plugins/sequencer_plugins/bias_acquisition/`, same naming reasoning as `dark_acquisition` — avoids colliding with `reduction_plugins/bias`) follows the identical shape with only two origins, no library — a BIAS series is fast enough that in practice it only ever needs remaking once, for the session's first observation: `current_session` (reused from the session directory) or `camera` (freshly shot, `BIAS_COUNT` frames at `BIAS_EXPOSURE_TIME_SECONDS`). The `camera` origin also switches the spectroscope to `LightSource.DARK` — there is no dedicated `BIAS` value on `hardware/spectroscope.py`'s `LightSource` enum, since a bias needs the exact same "no light reaches the sensor" state as a dark, just a zero-length exposure. Casier: `sequencer_data["bias_acquisition"] = {"origin": ..., "bias_files": [...]}`. Wired into `Be_stars.yaml` right after `dark_acquisition`, same before-the-`SKY`-reset positioning and same `demo.yaml` exclusion.

**`calib_acquisition`** (`plugins/sequencer_plugins/calib_acquisition/`, same naming reasoning as `dark_acquisition`/`bias_acquisition`) also follows the same two-origin shape (`current_session`/`camera`, no library at all — simpler than DARK, which does have one) but with a fundamentally different staleness criterion: **age**, not temperature. A CALIB image is a science-camera exposure of a calibration lamp — its flux dominates any dark-current concern, so this sub-plugin never reads or requires `obs.camera_target_temperature_deg_c`, unlike DARK/BIAS. `current_session` is only accepted if a usable series already sits in the session directory *and* its capture timestamp (parsed from the filename, same convention as DARK/BIAS's temperature token) is younger than `max_age_hours` (`subplugin_params.calib_acquisition`, `conf/config.yaml`) — e.g. `max_age_hours: 1` forces a reshoot roughly every hour, `max_age_hours: 24` reuses one series for the whole night. When the session directory holds more than one batch (an earlier one gone stale, reshot since), only the single most recent batch is ever considered — an older stale batch must never be picked over a fresher one sitting right next to it (`_find_usable_calib_series()`'s own docstring). `camera` (otherwise) switches the spectroscope to `LightSource.CALIB` and shoots a fresh `CALIB_COUNT`-frame series at `CALIB_EXPOSURE_TIME_SECONDS`. Casier: `sequencer_data["calib_acquisition"] = {"origin": ..., "calib_files": [...]}`. Wired into `Be_stars.yaml` right after `bias_acquisition`, same before-the-`SKY`-reset positioning and same `demo.yaml` exclusion.

**`flat_acquisition`** (`plugins/sequencer_plugins/flat_acquisition/`, same naming reasoning as the other three) is the simplest of the four: same `current_session`/`camera` two-origin shape, no library, but **no staleness check at all** — neither temperature (DARK/BIAS) nor age (CALIB). Flat-field correction is about optical vignetting/sensor uniformity, not sensor temperature or lamp drift, so once a usable `FLAT_COUNT`-frame series exists anywhere in the session directory it's reused for the rest of that session, indefinitely — shot at most once per session. `_find_usable_flat_series()` (module-local, not added to `dark_library_helpers.py` since nothing else shares it) still checks sensor size and `EXPTIME` (same `EXPOSURE_TIME_TOLERANCE_SECONDS` tolerance the DARK/BIAS/CALIB checks use), just no temperature or age filter. Like `calib_acquisition`, never reads or requires `obs.camera_target_temperature_deg_c`. `camera` (otherwise) switches the spectroscope to `LightSource.FLAT` and shoots a fresh series at `FLAT_EXPOSURE_TIME_SECONDS`. Casier: `sequencer_data["flat_acquisition"] = {"origin": ..., "flat_files": [...]}`. Wired into `Be_stars.yaml` right after `calib_acquisition`, same before-the-`SKY`-reset positioning and same `demo.yaml` exclusion.

### Guiding-camera dark subtraction (`guiding_dark_acquisition`, `capture_guide_image()`)

Found 2026-09-05: the guiding camera carries several fixed hot/defective
pixels, present at near-identical values in every exposure regardless of
where the telescope is pointed (confirmed by comparing the same pixel
coordinates across completely unrelated fields the same night). These land
among the brightest "sources" `solve-field`'s extractor ranks and tries to
match first, and were found to be the actual cause of most of one night's
plate-solve timeouts in `pointing_72ed`/the now-deleted `stop_phd2_guiding_diag` — see
HISTORY.md for the investigation. Same family reasoning as the science
camera's DARK/BIAS/CALIB/FLAT acquisition above, applied to the guiding
camera instead.

**`guiding_dark_acquisition`** (`plugins/sequencer_plugins/guiding_dark_acquisition/`,
backend `indi` only, no `_internal.py`) resolves a usable guiding-camera
dark **median** for the session, same `current_session`/`camera`
two-origin shape as `flat_acquisition` — no staleness check at all: the
guiding camera is uncooled (`hardware_indi_72ED-WIFI.yaml`'s
`guiding_camera.cooling: FALSE`), so there's no temperature to bucket, and
the fixed defects this exists to remove don't drift meaningfully within
one session. `current_session` reuses an existing
`GUIDINGDARK_*_median.fits` file already sitting in the session directory;
`camera` otherwise switches the spectroscope to `LightSource.DARK`, shoots
a fresh `GUIDING_DARK_COUNT`-frame series (`subplugin_params.guiding_dark_acquisition.count`,
default 7) with the guiding camera at
`subplugin_params.guiding.exposure_seconds` (the same duration every real
guide image uses — deliberately not a separate config value, so the dark's
exposure time can never drift out of sync with the images it corrects),
and median-combines them (plain per-pixel `numpy.median`,
computed in `float64` then cast back to the sensor's own dtype) into one
file. A third origin, **`synthetic`** (added 2026-09-08): when the active
hardware profile's spectroscope entry declares `obstructs_light: false`
(`hardware_indi_simu.yaml`'s `SpectroscopePlaceholder` — its own
`set_light_source()` never physically blocks light, so a "DARK" shot there
would just be another star exposure, not a real dark), writes a single
all-zero frame matching the guiding camera's current frame size instead of
shooting anything — subtracting an all-zero array is a true no-op, so
every downstream guide image comes out exactly as if no correction had
ever been requested, without `capture_guide_image()` or any of its callers
needing to know this equipment can't produce a real dark at all. Read the
same way as any other device param (`obs.hardware_config["spectroscope"]`)
— absent (defaults `true`) on every real spectroscope profile, so this
never changes behavior on real hardware. Casier:
`sequencer_data["guiding_dark_acquisition"] = {"origin":
"current_session"|"camera"|"synthetic", "dark_files": [...raw frames,
empty on reuse or synthetic...], "median_dark_file": "<combined or
synthetic filename>"}`. Declared via the active hardware profile's own
`sequencer_prefix: [guiding_dark_acquisition, home_sync_am3]` (72ED
profiles), ahead of `home_sync_am3` rather than inside `Be_stars.yaml`
itself (moved there 2026-09-12, see HISTORY.md) — `home_sync_am3`'s own
measured-sync homing (see below) captures and plate-solves guide images
too, so a usable dark median must already exist before it runs, same
requirement as any other guide-image capture. Deliberately **not** added
to `demo.yaml` (backend-agnostic, no real guiding camera to shoot darks
with).

Deliberately its own sub-plugin rather than folded into
`capture_guide_image()` itself (considered and rejected, see HISTORY.md):
keeps the acquisition visible as its own step in the GUI's live progress
and the orchestrator's own per-step logging, keeps it independently
testable, and keeps `acquisition_helpers.py` a plain-functions module with
no casier of its own, consistent with every other sub-plugin in this
codebase.

**`capture_guide_image()`** (`acquisition_helpers.py`) is where the actual
correction happens, consumed by every guide-image caller
(`pointing_72ed.py`, `stop_phd2_guiding.py`) with no changes needed on
their side. It always writes the untouched raw exposure first — named
`build_fits_root_name("GUIDING", ...)` with `RAW_` inserted right after
`GUIDING_` (e.g. `GUIDING_RAW_Vega_10s_....fits` alongside
`GUIDING_Vega_10s_....fits`) — never touched again afterward. A new
`subtract_dark: bool = True` parameter then controls what else happens:
`True` (the default, matching every real caller's actual need) reads
`sequencer_data["guiding_dark_acquisition"]["median_dark_file"]`, subtracts
it from the raw data (clipped to `>= 0`, cast back to the sensor's dtype),
and writes that as the plain `GUIDING_...` file — the one every downstream
plate-solve call already worked from before this raw/corrected split
existed, so `solve_wcs()` and its callers needed zero changes. Raises
`RuntimeError` if `guiding_dark_acquisition` hasn't run yet — no silent
fallback that skips the correction. `subtract_dark=False` skips the dark
lookup and the second file entirely (a byte-identical "corrected" copy
next to the raw one would be pure waste) and returns the raw path instead.
`image_to_gui` (unchanged behavior) writes whichever file the call
actually returns to the GUI's live "Guidage" panel.

### Coordinate frame convention: J2000/ICRS everywhere

Every coordinate that crosses a module boundary in Rosace — `Target.ra`/`dec` (`targets.py`, sourced from Simbad's `basic.ra`/`dec`, themselves ICRS), `hardware/mount.py::Mount.slew_to(ra, dec)`'s arguments, `scheduler_data["target"]` — is **J2000/ICRS, always**, in degrees. This is a deliberate, app-wide decision: mixing J2000 and JNow would misdirect the mount by an amount that matters at Rosace's targeting precision (well under a pixel of tolerance), so consistency across the whole chain is load-bearing, not cosmetic.

JNow (equatorial coordinates "of date", precessed/nutated for today) exists **only** inside `hardware_indi/devices/mount.py::IndiMount` — the one place that must speak it, since INDI's own standard mount property (`EQUATORIAL_EOD_COORD` — "EOD" = epoch of date) is JNow by protocol definition, not a configurable choice. `IndiMount.set_coord()` converts an incoming ICRS/J2000 `SkyCoord` to `FK5(equinox=Time.now())` right before sending it to INDI; `get_current_coordinates()` does the reverse conversion on the way back out. Every layer above `IndiMount` — `MountAdapter`, the `Mount` Protocol, every SEQUENCER sub-plugin — only ever sees J2000, and must never re-derive or assume JNow itself.

`solve-field` (astrometry.net, see the plate-solve chantier) solves against index files built from a J2000/ICRS catalogue and writes a J2000 WCS (`RADESYS`/`EQUINOX` in the resulting FITS header) — consistent with the rest of the chain, no conversion needed when comparing a plate-solved position to a catalogue target position.

`acquisition_helpers.py::capture_guide_image()` (see also "Guiding-camera dark subtraction" above, for the raw/dark-corrected file split this function writes) unconditionally switches `obs.hardware["spectroscope"]` to `LightSource.SKY` before every exposure — not a parameter a caller passes, since there is no guide image for which any other light source would ever be correct, and nothing upstream (a previous sub-plugin, an interrupted session) can be trusted to have already left the spectroscope there. Added 2026-09-04 after a real incident: a disconnect mid-`dark_acquisition` left the spectroscope on `DARK`, and a guide image captured afterward (by a different sub-plugin, in a later session) came out solid black. This is also why the function takes the whole `obs: Observation` rather than a bare `camera` — it needs both `obs.hardware["guiding_camera"]` and `obs.hardware["spectroscope"]`, and `obs.obs_dir` besides, so passing `obs` itself is simpler than threading three separate arguments through every caller. It stamps `RA`/`DEC`/`EQUINOX`/`OBJECT` into every guide image it writes, whenever the caller passes `ra_deg`/`dec_deg`/`target_name` (`pointing_72ed` always does). This exists because the camera driver may already have written its *own* `RA`/`DEC`/`OBJCTRA`/`OBJCTDEC`/`EQUINOX` via mount-snooping (e.g. INDI's CCD Simulator does, labelled J2000) — but that value isn't trusted app-wide: a different camera driver, especially on real hardware, could just as easily copy the mount's raw `EQUATORIAL_EOD_COORD` (JNow) verbatim without converting it. So Rosace always overwrites these keys with its own value — the RA/DEC it actually commanded or computed (`pointing_72ed`'s aimed-at or corrected target position, see above), never the driver's. Every stamped card's comment ends "stamped by Rosace" so a human reading the header later can tell which value the app itself vouches for — comments deliberately never contain a literal `/` character (KStars' FITS header viewer truncates a comment at the first `/`, even one that's just part of the comment text and not a real FITS delimiter — the FITS standard itself only treats the *first* `/` after the value as the comment separator, but KStars doesn't respect that).

### Pixel coordinate convention: 0-indexed, origin bottom-left

Every pixel coordinate that crosses a module boundary in Rosace — `slit_x`/`slit_y` (`subplugin_params.guiding`), `solve_result()`/`world_to_pixel()` arguments and results (`plate_solve_helper.py`), the residual-vs-slit computations in `pointing_72ed`/`stop_phd2_guiding`, and the GUI's pixel readout — is **0-indexed, with the origin at the centre of the bottom-left pixel, X to the right and Y upwards** (FITS row order: row 0 is the bottom row). This is what astropy's `WCS.pixel_to_world()`/`world_to_pixel()` already speak, and what every array index in the code already is (`data[y * width + x]`); the GUI's `FitsViewer` draws FITS row 0 at the bottom for the same reason.

Viewers outside Rosace (KStars, DS9) count from **1**: subtract 1 from each axis before copying a value read there into the config, or add 1 to compare a Rosace value against them. Not respecting this is exactly what put `slit_x`/`slit_y` off by one pixel until 2026-09-04 (measured in KStars, compared against zero-indexed plate-solve output — see HISTORY.md). PHD2's own convention for its lock position is not documented and not assumed: `pointing_72ed` only ever uses it as a difference (`lock_x - dx`), where a constant origin offset cancels.

### Configuration (`rosace/rosace/conf/`)

All application configuration lives in `conf/` — one predictable place to look, split into separate files by concern rather than crammed into a single monolith:

| `config.yaml` | Core application settings (data paths, site name, active hardware profile, active scheduler) — the packaged copy is demo defaults; a real deployment's own copy lives under `<base_data_dir>/conf/config.yaml` instead |
| `logging.cfg` | Logging setup (`fileConfig` ini format — see below) |
| `hardware_<variant>.yaml` | Hardware/instrument definitions, one file per variant (e.g. `hardware_indi_simu.yaml` for the INDI simulators, `hardware_indi_72ED-LAN.yaml`/`-WIFI.yaml` for the real telescope). ### Which config.yaml is active (multi-instrument support)

The packaged `conf/config.yaml` ships with **real-world defaults**
(`sequencer_backend: indi` — it expects a real INDI server) — but a real
deployment's own settings (site name, active hardware, observation list...)
shouldn't have to live inside the git-tracked code tree, and someone running
more than one instrument (e.g. a main telescope plus a demo scope) needs
more than one active config. `config.py::_resolve_config_path()` picks the
active file in priority order, evaluated once at import time:

1. **`ROSACE_CONFIG` env var**, if set — an explicit path (any location, `~` expanded), highest priority. `python -m rosace.main <path>` sets this from a positional CLI argument before any other import runs (see `main.py`'s top-of-file CLI handling, required to run before `from .config import ...` triggers `config.py`'s own loading); a `uvicorn rosace.main:app` launch needs the env var set directly instead (`ROSACE_CONFIG=<path> uvicorn ...`). Meant for one-off overrides — a second instrument, a test config, `--demo-mode` (below) — not the everyday case.
2. **`<base_data_dir>/conf/config.yaml`**, if it exists — where `base_data_dir` comes from `conf/base_data_dir.yaml` (a single-field file, `base_data_dir: ~/.rosace` by default). This is a real installation's own config, found automatically on every launch with no argument needed — the day-to-day case once you've configured your own instrument. `conf/base_data_dir.yaml` itself always lives in the package's own `conf/`: it has to be found before `base_data_dir` is even known, so it can't live under `base_data_dir` itself.
3. **The packaged `conf/config.yaml`** — used only if neither of the above applies (fresh install, nothing configured yet).

`python -m rosace.main --check-config [path]` validates a config without starting the server: with no argument, it validates whatever step 1–3 above would resolve to; with a path, it validates that file specifically (via the same `ROSACE_CONFIG` mechanism). Prints `[OK]`/`[FAIL]` and exits 0/1 — never reaches `uvicorn.run()` either way, so it's safe to run against a candidate config without risking a real session starting. When the config declares `horizon_file`, it also parses and validates that file (`horizon.py::load_horizon()`) and prints its point count (`[OK] horizon file valid: <path> (N points)`, or `[FAIL] horizon file invalid: ...` and exit 1) — so a freshly copied KStars export can be checked before a session ever reaches the SCHEDULER.

`python -m rosace.main --help` (or `-h`) prints this same CLI's usage — the positional `config_path` argument, `--demo-mode`, `--check-config`, `--create-admin`, and `--list-subplugins` — and exits, without starting the server either.

`python -m rosace.main --create-admin <username>` bootstraps the first admin account (see Authentication above) and exits — also never starts the server.

### Trying Rosace without hardware (`--demo-mode`)

Onboarding runs in four stages, each a superset of the trust required by the
last: **Docker demo** (zero install — `docker/`, its own self-contained
catalogue, see `docker/README.md`) → **`--demo-mode`** (installed locally,
still zero real/simulated hardware) → **INDI simulators**
(`sequencer_backend: indi` + `active_hardware: hardware_indi_simu`, needs a
real INDI server and PHD2 running, but no telescope) → **real hardware**
(same `indi` backend, `active_hardware` pointed at the real profile, e.g.
`hardware_indi_72ED-LAN`). Only the last two share one evolving config/
catalogue — the demo tier is deliberately isolated (see below), so it can
never interfere with a real installation being built up in parallel.

`python -m rosace.main --demo-mode` is pure sugar: it points `ROSACE_CONFIG`
at the packaged `conf/config_demo.yaml` and falls through to the normal
server startup (same mechanism as the positional `config_path` argument,
just resolved from a known, installation-independent location —
`Path(__file__).parent / "conf" / "config_demo.yaml"` — so it works
regardless of where `pip` put the package). `config_demo.yaml` is a full
sibling of `config.yaml` (every Core key present, same as any config) whose
values differ specifically to need nothing: `sequencer_backend: internal`
(no INDI/PHD2 to connect to), `active_scheduler: scheduler_rosace_2026` (the
real scheduler, not `blank` — see below for why), and
`base_data_dir: ~/.rosace-demo`, a sibling of the real `~/.rosace` so demo
and real data can never mix.

What actually triggers the demo behavior is not the CLI flag — it's
`config_demo.yaml`'s own `is_demo: true` key (optional everywhere else,
defaults to `false`; exposed as `config.py::IS_DEMO_MODE`), the same
"config drives behavior" principle used everywhere else in this app. Anyone
who points `ROSACE_CONFIG` at `config_demo.yaml` by hand — e.g. for a
`uvicorn` launch — gets the identical behavior, no special-casing on the
flag. When `IS_DEMO_MODE` is true, `main.py`'s `lifespan()` calls
`demo_seed.py::seed_demo_data()`: idempotent (no-ops once `targets.db`
already has a program — same guard as the Docker demo's own seed script), it
inserts 2 stars (Vega/Arcturus — the same coordinates `plugins/schedulers/
blank/scheduler.py` already hardcodes, kept consistent rather than inventing
new example data) under **one program named `"demo"`**, writes a matching
`targets/ObservationList.txt`, and bootstraps a fixed `rosace`/`rosace` admin
account (same convention and same "evaluation only, never a real install"
rationale as the Docker demo's own credential).

The program name `"demo"` is not arbitrary: `scheduler_rosace_2026` sets
`scheduler_data["program"]` from whatever `targets.db` says, and that value
is resolved directly to `programs/<name>.yaml` (see the Plugin system
section above) — `programs/demo.yaml` is the only program YAML that's
backend-agnostic (its sequencer steps all have an `_internal.py`
counterpart). This is also why `--demo-mode` uses `scheduler_rosace_2026`
rather than the `blank` scheduler template: `blank` hardcodes
`_PROGRAM = "Be_stars"` as a placeholder label, which would resolve to the
real, `indi`-only `programs/Be_stars.yaml` and fail under
`sequencer_backend: internal` — harmless today since nothing pairs `blank`
with `internal`, but worth knowing if `blank` is ever reused for something
demo-shaped.

### Key configuration (`config.py` loads `conf/config.yaml`)

`config.py` is a thin loader: it resolves which `config.yaml` is active (see above), reads it at import time, and exposes the same constants the rest of the codebase already imports (`from .config import BASE_DATA_DIR, ...`).

`conf/config.yaml` is split into two sections, and the two follow different rules — a deliberate architectural decision (see HISTORY.md): sub-plugins are meant to vary freely per installation/observer (a parameter one program's plugin needs may be meaningless to another), so requiring every installation to declare every plugin's parameters (as a flat, unconditionally-indexed `config.yaml` would) doesn't scale as the sub-plugin catalogue grows.

- **Core** — read directly by `main.py`/`auth.py`/`database.py`, or a selector key needed to pick which plugin family is active (`active_hardware`, `active_scheduler`, `sequencer_backend`) — a plugin can't declare its own selector. Every installation must set these. `config.py` reads each with `_cfg["key"]` (fails fast, at server startup, if missing) and exposes it as its own named constant, one per key — the table below. `is_demo`/`IS_DEMO_MODE` is the one deliberate exception: read with `.get("is_demo", False)`, since it's meaningful only to `conf/config_demo.yaml` — every other config simply omits it.
- **Plugin** — everything specific to one or a few sub-plugins (DARK/BIAS frame counts, `scheduler_rosace_2026`'s observation list path...). Lives under one free-form `subplugin_params:` block in `config.yaml`, with no schema enforced. `config.py` exposes exactly one constant for the whole block, `SUBPLUGIN_PARAMS: dict = _cfg.get("subplugin_params", {})` — it is never edited again just because a new plugin parameter was introduced. Each consuming sub-plugin reads its own slice with its own default (e.g. `SUBPLUGIN_PARAMS.get("dark_acquisition", {}).get("count", 5)`), so an installation that doesn't use a given sub-plugin needs no entry for it at all. A parameter read by several interchangeable sub-plugins (e.g. `max_exposure_time_seconds`, read by both `star_spectra_acquisition` and `dark_acquisition`) sits at the *root* of `subplugin_params` rather than nested under one plugin's name — the same "shared, purpose-named key" principle already used for casiers (see the Plugin system section above), applied to config. A group of several such shared values describing one coherent concept (e.g. `guiding`'s `exposure_seconds`/`sampling_arcsec`/`slit_x`/`slit_y`, read by `pointing_72ed`/`stop_phd2_guiding`/`guiding_dark_acquisition`) is still nested — under a domain name, not any one sub-plugin's name — purely for readability, without changing which "tier" (root/shared vs. plugin-specific) it belongs to. `DARK_LIBRARY_DIR` is the one exception kept in Core despite being consumed only by `dark_acquisition`: it's a directory, same shape/lifecycle as `BASE_DATA_DIR`/`LOG_DIR` above it, not a tunable behavior.

Hour angle, not arc on the sky: see "The default scheduler" above |
| `count` | `dark_acquisition` | `5` | Number of DARK frames per series, fixed for the whole session — see `dark_acquisition` below |
| `count` / `exposure_time_seconds` | `bias_acquisition` | `5` / `0.0` | Number of BIAS frames per series; BIAS exposure time — 0 by definition (no integration), overridable for a camera that refuses a literal 0s exposure — see `bias_acquisition` below |
| `count` | `guiding_dark_acquisition` | `7` | Number of guiding-camera dark frames median-combined per session — no separate exposure-time key, deliberately: it always reuses `guiding.exposure_seconds` (see below), the same duration every real guide image uses — see `guiding_dark_acquisition` above |
| `exposure_seconds` / `sampling_arcsec` / `slit_x` / `slit_y` | `guiding` | *(none — always set)* | Optical alignment/plate-scale of the whole telescope+spectro+guiding-camera assembly (guide-image exposure time, plate scale, spectrograph slit position in the guiding camera's field, zero-indexed) — shared at the root since read by several sub-plugins (`pointing_72ed`, `stop_phd2_guiding`, `guiding_dark_acquisition`), not tied to one of them. Lives in `subplugin_params`, not Core, since only sub-plugins read it — but installation-specific and instrument-critical enough that there's no sensible built-in default; every installation using `pointing_72ed` must set it. Deliberately *not* in the hardware YAML: unlike a device's own connection data or physical capabilities, these facts stay the same across hardware profiles that differ only in how they reach the same physical instrument (e.g. `hardware_indi_72ED-LAN.yaml` vs `-WIFI.yaml`) — see HISTORY.md 2026-09-06. |
| `phase2_search_radius_deg` | `pointing_72ed` | `1.0` | `solve-field` search-cone radius (degrees) for Phase 2's plate solve only — Phase 1 keeps `solve_wcs()`'s own wider default (5°), since Phase 2 already has a precise position hint (the just-slewed-to `corrected_coord`) and a tighter cone directly cuts this synchronous solve's real wall-clock cost — see `pointing_72ed` below |

**When adding a new config key**: if it's read by `main.py`/`auth.py`/`database.py`, or is a plugin-family selector, it's Core — add it to `test_rosace_core.py`'s `_write_tmp_config` test helper too, or tests that don't pass it will fail outright (`config.py` indexes it directly, no fallback). Otherwise it's Plugin — add it under `subplugin_params:` (nested under the plugin's name, or at the root only if genuinely shared by several interchangeable sub-plugins), read it with `.get(key, default)` inside the consuming sub-plugin's own module, and `test_rosace_core.py` needs no change at all.

### Logging (`log_config.py`, `conf/logging.cfg`)

Centralized logging, configured once via `configure_logging()`, called at the very top of `main.py` (right after importing `.config`, before any other internal import) — so that log messages emitted at plugin-instantiation time (which happens at import time) are also captured.

- Config format: classic `fileConfig` ini file (`conf/logging.cfg`), not `dictConfig`.
- Logger hierarchy: everything under the `spectro` logger (`spectro.main`, `spectro.plugin.*`, `spectro.subplugin.*`) propagates to a single `spectro` handler set — no per-module setup needed.
- Two handlers configured via `logging.cfg`: console (`StreamHandler`, INFO+) and rotating file (`RotatingFileHandler`, DEBUG+, 1 MB × 9 backups) at `~/.rosace/log/rosace.log`.
- `root` logger stays at WARNING to silence FastAPI/uvicorn/httpx noise.
- `configure_logging()` sets `logging.Formatter.converter = time.gmtime` right after loading `logging.cfg`, so `%(asctime)s` prints UTC, not the server's local time — `fileConfig`'s ini format has no `converter` key of its own, so this can't be expressed inside `logging.cfg` itself. Consistent with the rest of the app: DB timestamps, FITS filenames, and the astronomical-day boundary (see `time_helpers.py` below) are all UTC too, which matters when cross-referencing a log line against a FITS header or a DB row. Since `converter` is a class attribute (not per-instance), this switch is permanent for the whole process once `configure_logging()` has run once — never reset back to local time.
- A third handler, `WebSocketLogHandler` (`log_broadcast.py`), is attached to the `spectro` logger **programmatically** (not via `logging.cfg` — it needs a live asyncio loop and the set of connected GUI clients), in `main.py`'s `lifespan` startup. It buffers INFO+ records and flushes them in periodic batches (every `FLUSH_INTERVAL`, capped at `MAX_BUFFERED` with a dropped-count warning) over the `/ws` route to the GUI's Journal panel — see GUI section below.

`hardware_indi/` (`wrapper/` and `devices/`) uses `spectro.indi.*` logger names (e.g. `spectro.indi.mount`, and per-device-class names like `spectro.indi.IndiCamera` from `wrapper/base.py::Base.__init__`, the one actually in effect for every `IndiDevice` subclass — a subclass's own `self.logger = logger or logging.getLogger(...)` line, if it has one, is set before `IndiDevice.__init__()` runs and gets immediately overwritten by `Base`'s own assignment) — same `spectro` hierarchy as every other logger in the app, so these records reach the rotating file and the GUI Journal, not just the console (fixed 2026-08-30; see HISTORY.md — previously used a bare `logging.getLogger(__name__)`/class-name, which propagated to `root`, WARNING-level console only).

**Session log extraction** (`session_log_extractor.py`): the global rotating log above is the only place session activity is logged — but the on-disk layout principle (below) is that a session's own directory should hold everything about that session, already true for each observation's YAML dossier. `extract_session_log(ctx: SessionContext) -> Path`, called from `CloseSessionPlugin.run()` near the end (wrapped in try/except — one failure here must never block the session from closing, same posture as the park/disconnect steps beside it), copies just this session's own lines into `<session_dir>/<started_at>_<session_id>_session.log` (same `YYYYMMDDTHHMMSS` timestamp convention as an observation dossier's own filename, `session_id` suffix so several sessions started within the same astronomical night — a restart, or several short runs in a row — never collide on one file). Filters by **timestamp window** (`ctx.started_at` → the moment of extraction), not by tagging every log call site with a `session_id` — simpler, and correct since only one session ever runs at a time (`state.is_running` is a singleton). Reads across `rosace.log` plus however many rotated backups (`rosace.log.1`..`.9`) the session's own window spans, oldest backup first; a line with no parseable leading timestamp is treated as a continuation of whichever record precedes it. The written file opens with a header (night-of-date via `time_helpers.py`, site, session ID, started/extracted UTC timestamps, source log path) and closes with an `# End of file` footer (same rule-line style as the header, so a reader can tell at a glance the file wasn't cut short) — and if the session's own early history has already been rotated out of the source log by the time extraction runs, the header carries an explicit `# WARNING:` line instead of silently starting mid-session.

### GUI (`rosace/rosace/gui/`)

The control interface is a single-page application built **exclusively with [X4 (x4js)](https://github.com/rlibre/x4)**. No other UI framework or DOM manipulation library is permitted.

- Entry point: `src/main.ts` — one `RosaceApp` class, all layout via X4 components
- All containers must be `VBox` / `HBox`; all text via `Label`; all interactive elements via `Button` or `Component`
- Build: `npm run build` inside `gui/`, via `x4build` (esbuild-based CLI dedicated to x4js), outputs to `gui/bin/`
- Serve: FastAPI mounts `gui/bin/` as static files directly (`main.py`, end of file) — same process, same port as the API, no separate GUI server
- x4js is a regular npm dependency (`package.json`, `devDependencies.x4js`), installed under `node_modules/x4js`. TypeScript decorators are compiled correctly by `x4build` even from `node_modules`, so no local vendoring is needed.
- After editing `package.json` (e.g. bumping x4js), always run a full `npm install` and confirm `node_modules/` matches `package-lock.json` before rebuilding — a partial/interrupted install here has caused the built app to silently fail to render (blank page, no build error).
- `bin/main.js` has no version hash in its filename — after `npm run build`, a hard browser refresh (cache bypass) may be needed to actually load the new bundle; a stale cached bundle fails silently (no console error, feature just isn't there).
- Live log streaming: `RosaceApp` opens the `/ws` WebSocket via X4's built-in `Application.setupSocketMessaging()` (no custom WebSocket code — see `connectWebSocket()` in `main.ts`), subprotocol `"messaging"`. Backend batches are delivered as global events `{msg: "log.create", params: {lines: [{level, text}, ...]}}`; `MainView` picks them up via `this.onGlobalEvent(...)` and appends them to the existing Journal panel (`logMany()`). Sticky auto-scroll: `logMany()` checks whether the panel's own `<textarea>` was already scrolled to (or within a few px of) the bottom *before* appending, and only calls `scrollToBottom()` (an existing `SimpleTextArea` primitive) if it was — scrolled up to read earlier lines, the view stays put instead of being yanked back down on every new batch. `setupSocketMessaging()` has no built-in reconnect, so `main.ts` owns retry-with-visible-`Notification` on disconnect — never silent.
- Live image preview: two fixed panels, "Spectre" and "Guidage" (`MainView`'s `spectre_viewer`/`guidage_viewer`, both a generic `FitsViewer` widget — x4js `Canvas`, zoom/pan). Backend side (`image_broadcast.py`'s `ws_image_broadcaster`, `main.py`'s `GET /images/{panel}`): each panel is one fixed-name preview file (`GUI_PREVIEW_DIR/{panel}.fits`, e.g. `guidage.fits`/`spectre.fits`), overwritten on every new capture — the WebSocket message only ever needs to say *which panel* changed (`{msg: "image.new", params: {panel}}`), never a filename, since the GUI already knows the fixed URL for each panel and just re-fetches it. `acquisition_helpers.py`'s `capture_guide_image()`/`capture_science_image()` both take an `image_to_gui: bool` (default `False`, so an existing caller keeps behaving exactly as before) — when `True`, writes the extra preview copy and calls `ws_image_broadcaster.broadcast(panel)`. "Spectre" is shared by every science-frame producer (`star_spectra_acquisition.py`, `dark_acquisition`, `bias_acquisition`) — it shows whichever kind of frame was captured most recently (target/dark/bias), not a per-type history; "Guidage" is fed by `pointing_72ed`'s guide-image captures. `MainView.loadPanelImage()` maps a panel name to its viewer by a plain string match — a third panel would need a new `if` branch there, plus a new `FitsViewer` instance and layout slot, not just a new backend panel name. Each `FitsViewer`'s toolbar also ends with a pixel readout (`X: 613  Y: 614  I: 1234`, a bold monospace `Label` flush right): X/Y follow the "Pixel coordinate convention" above (0-indexed, Y upwards — directly usable as `slit_x`/`slit_y`), `I` is the physical pixel value (BZERO/BSCALE applied). It updates on cursor move (including during a drag or a zone selection) and after a wheel zoom, and is cleared when the cursor leaves the canvas or a new image is loaded. The canvas cursor is a plain arrow (easier to aim at one pixel), turning into a closed hand only while the left button is held (panning); zone mode (crosshair) and Ctrl+drag (`ns-resize`) keep their own cursors.
- Live SEQUENCER/REDUCTION step progress: each observation row's primary stage-chip line can grow up to two extra, temporary lines underneath — one showing SEQUENCER's own sub-plugin steps, one showing REDUCTION's — each a row of `Tag` chips (pending/running/done, reusing `.stage`'s color semantics via a lighter `.substep` variant in `main.scss`) built from `entry.steps`/`entry.step` and labelled via `subplugin_display_names` (`GET /subplugins/display-names`, fetched once at startup — see `DISPLAY_NAME` above — not polled, since it's static for the server's lifetime). Backed by `step_progress.py`: an in-memory-only `dict[obs_id][stage] -> {step, steps}`, deliberately never persisted to `rosace.db` (a sub-plugin name is plugin identity — the DB stays plugin-agnostic, same principle as `SUBPLUGIN_PARAMS`) and never pushed over `/ws` either — folded into the GUI's existing `fetchObs()` poll (`GET /observations/steps`) instead, since a completed step simply showing as done at the next ~3s poll is an accepted tradeoff over true mid-step liveness. Keyed per (obs_id, **stage**), not just per obs_id, specifically so SEQUENCER's line still renders "all done" once REDUCTION starts (REDUCTION would otherwise overwrite SEQUENCER's entry). Each line stays visible while its own stage is `"running"`, or for `STEP_PROGRESS_HOLD_SECONDS` (10s, `main.ts`) after the whole observation finishes (`obs.stages["archive"].done_at`) — a display-only grace period, not tracked server-side, giving the observer time to see the full pipeline at a glance before it collapses back to the primary stage row alone. SHARING is excluded (a program declares exactly one sub-plugin, not a list — no "current step" to show progress through).
- Login: `auth.ts::LoginView` is shown before the dashboard by `AppShell` (`main.ts`) — the actual `setMainView()` target (x4js doesn't support calling `setMainView()` a second time to swap the root view — its `mounted` guard is declared but never actually set to `true` anywhere in `core_application.ts`), which instead swaps its own content between `LoginView` and a freshly-built `MainView` via `setContent()`. `fetchStatus()`/`fetchObs()` stop rescheduling themselves and fire a local `"auth.logout"` global event on a 401 (session expired) rather than polling forever unauthenticated in the background; `AppShell` listens for that same event (also fired by the "Déconnexion" item in `AppHeader`'s menu) to show the login screen again. `MainView` is deliberately rebuilt from scratch on every `showMain()` rather than cached — a cached instance's polling loop, once stopped by a 401, would never resume on the next login.
- Two non-obvious x4js behaviors worth knowing before writing another form: `Button._on_click()` always calls `preventDefault()`/`stopPropagation()`, whether or not a `click` prop was given — a `<button>` inside a `Form` therefore never triggers the browser's native submit-on-click, so wire the button's own `click` prop directly rather than relying on the form's `submit` event for anything a click should do. And `Form` extends `Box`, not `VBox` — `%box` (`shared.scss`) only sets `position:relative`, no `display:flex` — so a `Form`'s own stylesheet needs explicit `display:flex;flex-direction:column` (or `row`) for `gap`/child stacking to work at all; it isn't inherited the way it would be from `VBox`/`HBox`.

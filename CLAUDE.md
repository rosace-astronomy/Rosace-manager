## Language policy

All code artifacts must be in English: variable names, function names, comments, docstrings, log messages, and any text written to files. This applies even though the user communicates with Claude in French. Conversations happen in French; code is written in English.

The repository's parent directory (`~/ROSACE/`) holds the user's other
projects: Claude never creates or writes anything there, outside this
repository. Analyses, scripts and reports that do not belong in the
repository go to the scratchpad, `~/Téléchargements/` (documents for the
user) or another place the user names.

## Planning policy

Claude follows the Claude Code permission mode the user has selected — it is how
the user says how much autonomy Claude has for the task at hand:

- **Manual (default) mode**: every file edit and command goes through its own
  permission prompt; the user validates each one.
- **Plan mode**: read-only until the plan is approved. Approving the plan approves
  all of it; how it is then applied follows the choice made at approval (all at
  once, or each edit confirmed).
- **Auto mode**: green light to apply the whole agreed change in one pass, without
  asking again.

In every mode, anything outside the agreed scope still needs the user's go, and
so do outward-facing or hard-to-reverse actions (commits and pushes — see the
git-commit workflow, database writes, deleting files).

**Never change code or configuration while an observation session is
running**, whatever the permission mode, unless the user explicitly agrees
to that specific change during the session. Check first (`GET /status`'s
`session_active`, or the end of `rosace.log`) before any edit under
`rosace/` or `~/.rosace/`; while a session runs, only read, analyse and
write outside the repository and the data directory (scratchpad, reports,
memory). `TODO.md` is not code or configuration and may still be appended.

## Versioning

Rosace's version is **X.Y.Z.n**, written in one place only,
`rosace/pyproject.toml` (`version = ...`); everything else reads the installed
package's version (`importlib.metadata`: the FITS `SWCREATE` keyword, the API
docs). X changes when a new instrument works with Rosace (1.0.0.0 once the
72ED setup really works), Y for a new function (e.g. a new plugin), Z for a
bug fix, n for an internal version.

- **Published versions always end in `.0`** (X.Y.Z.0), and only they get a
  git tag, annotated, `vX.Y.Z.0`, and go to the Codeberg container registry
  (moving `latest` along). Internal versions (X.Y.Z.1, .2…) come after the
  published version they start from, so the numbers always sort in time order;
  n is raised when the user wants a build identifiable (e.g. before a sky night).
- Last published version: `git tag -l 'v*.0' --sort=-v:refname | head -1`.
- After changing the version, rerun `pip install -e "rosace/[dev]"`: an
  editable install only reads the number again when reinstalled.
- `CHANGELOG.md` (repo root) lists what changed for a user in each published
  version. Each commit that changes something a user can see adds a line
  under `[Unreleased]` (drafted with the commit message); at publication,
  `[Unreleased]` becomes `[X.Y.Z.0] — <date>` and a new empty `[Unreleased]`
  is opened. Internal versions get no section of their own. The *why* stays
  in HISTORY.md.

## Project overview

**Rosace** is an async REST API (FastAPI + Python 3.12) that orchestrates spectroscopic observation sessions end-to-end. It is designed to run autonomously at night, cycling through a state machine from target selection to archiving.

**Out of scope: protecting the instrument and deciding when to observe.** Sun height, weather (rain, wind, humidity, clouds as a safety matter), roof or dome, and the decision to start or stop a night belong to a system outside Rosace, which may differ for every installation. That system protects the instrumentation and drives Rosace through its start/stop controls (`POST /control/start`/`stop`, or the scheduled start/stop). Rosace observes when it is told to and stops cleanly when asked; it does not check the Sun or the weather itself, and such checks are not to be added to it.

- Python package: `rosace/rosace/`
- Build config: `rosace/pyproject.toml`
- Virtual environment: `rosace-manager/`

### Scheduled session start / stop

The GUI's controls bar schedules a start and/or a stop at a **time of day** (no
date), typed in **local time** (what the browser's time picker offers; the server
converts it to UTC once, in `next_occurrence()`, and everything after that is UTC
like the rest of Rosace): a time field next to each button — filled, the button
schedules ("START 21:20"); empty, it acts now as before. The time is resolved to
its **next occurrence within 24 hours** (`control_schedule.py::next_occurrence()`;
a stop after the scheduled start, if any). The schedule lives in the server
(`state.scheduled_start`/`scheduled_stop`, aware UTC, in memory only — lost on a
server restart), checked every second by `main.py::_control_schedule_loop()`
(started in `lifespan()`): a due start starts the session like `POST /control/start`
(ignored with a WARNING if a session is still active), a due stop is the usual clean
stop (the current observation finishes). A manual start cancels a scheduled start,
a manual stop a scheduled stop; each leaves the other one. API: `PUT
/control/schedule/{start|stop}` `{"time": "HH:MM"}` (local time; 422 on a bad
time), `DELETE /control/schedule/{start|stop}`, and `GET /status`'s
`scheduled_start`/`scheduled_stop` (ISO UTC or `null`). In the GUI, one chip per
scheduled instant (local time) with a countdown and a ✕ to cancel. The PC must
still not suspend.

#### Alternative: systemd timer

To start a session at a given time without the GUI, use a systemd
transient timer (`at` is not installed on the observatory PC): one command to
log in, one to schedule `POST /control/start`. Validated on the real setup
2026-09-19.

```bash
# 1. Log in once (the session cookie stays valid for 14 days; kept in the home
#    directory, not /tmp). Do it BEFORE the scheduled time: without a valid
#    cookie the start is refused with a 401.
curl -f -c ~/.rosace_cookie -X POST http://localhost:8000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"<user>","password":"<password>"}'

# 2. Schedule the start (local time of the PC)
systemd-run --user --unit=rosace-start-2120 --on-calendar="2026-09-19 21:20:00" \
  curl -f -b /home/observatoire/.rosace_cookie -X POST http://localhost:8000/control/start

# Check it is scheduled (NEXT must show the wanted time), read the result, cancel
systemctl --user list-timers rosace-start-2120.timer
journalctl --user -u rosace-start-2120.service
systemctl --user stop rosace-start-2120.timer
```

Pitfalls, all met in practice:

- **Absolute cookie path, never `%h`.** `systemd-run` does not expand `%h` in
  the command line: `curl` receives the literal `%h/.rosace_cookie`, and
  `curl -b` silently ignores a missing file, so the request goes out without a
  cookie and comes back 401. A read-only way to test the exact same path under
  systemd: `systemd-run --user --wait --pipe --collect curl -s -o /dev/null -w "HTTP %{http_code}\n" -b /home/observatoire/.rosace_cookie http://localhost:8000/status` (expect `HTTP 200`).
- **Use a new `--unit` name each time** (e.g. `rosace-start-MMDD-HHMM`).
  Reusing one fails with `Unit ... was already loaded or has a fragment file`
  even when no unit file exists anywhere; a failed run also leaves a failed
  service behind (`systemctl --user reset-failed <unit>.service` clears it).
- **`curl -f` does not catch a refused start.** `/control/start` answers HTTP
  200 with `"Session déjà en cours"` when `session_active` is true, so the
  journal must be read for `Session démarrée`, not just the exit code. Check
  `GET /status` (`session_active: false`) beforehand; after a manual stop, wait
  for CLOSE_SESSION to finish.
- **The PC must not suspend** before the scheduled time — a transient timer
  does not wake the machine (`--timer-property=WakeSystem=true` would, if the
  hardware clock supports it; untested here).
- The password ends up in the shell history; log in through the web GUI
  instead if that matters.

## Architecture

### State machine (`main.py`)

The global singleton `state` (a `SystemState` instance) drives the orchestration loop:

```
IDLE → INIT_SESSION → [SCHEDULER → SEQUENCER → REDUCTION → SHARING → ARCHIVE] × N → CLOSE_SESSION → IDLE
```

The session runs as an asyncio task. `POST /control/start` starts it; `POST /control/stop` sets `state.is_running = False`; both can also be scheduled at a time of day (see "Scheduled session start / stop" above). No plugin needs to know about this flag: `session_runner()`'s own loop checks `state.is_running` before every stage call, so a stop request is picked up between stages and reaches `CLOSE_SESSION` cleanly — no exception involved. **A stop lets the current observation finish completely**: SEQUENCER runs every remaining step and every series to the end (so a stop during a long series can take up to its full duration), then REDUCTION/SHARING/ARCHIVE run as usual before `CLOSE_SESSION`. Only a stop during the SCHEDULER's retry wait, or during INIT_SESSION's camera cooldown, takes effect at once. Before 2026-09-28, sub-plugins cut their series short on a stop and each remaining calibration step then started and stopped after one frame, leaving useless 1-frame series behind (see HISTORY.md).

On any plugin error in the observation loop, the error is recorded in the DB, and the loop restarts from **SCHEDULER** (not from INIT_SESSION) — except `SessionFatalError` (`errors.py`, a tiny module with no imports so anything can import it), raised by a plugin that finds an unrecoverable fault: `session_runner()` stops the session instead (`CLOSE_SESSION` still runs, the log line carries the failing stage's own name). `SchedulerFatalError` (see SCHEDULER plugins below) is its subclass for a SCHEDULER configuration/data problem that retrying cannot fix, and stops the session the same way. `main.py` knows only `SessionFatalError`, never which plugin raised it.

**Post-observation stages run in their own thread.** Once SEQUENCER has succeeded, `session_runner()` hands a copy of the observation to `_launch_post_obs()` and moves on to the next SCHEDULER at once. `_launch_post_obs()` submits `run_post_obs()` (REDUCTION → SHARING → ARCHIVE) to `_post_obs_executor`, a `ThreadPoolExecutor` with **one** worker (`post-obs`), where it runs under its own event loop (`asyncio.run`, same pattern as the selector's planners): a blocking computation in a REDUCTION sub-plugin never delays the sequencer, whose loop stays free. One worker on purpose: observations are post-processed one at a time, in order, so steps that share files across a session (`export_demetra`'s session ZIP) never run concurrently — if post-processing gets slower than observing, observations simply queue up. `state.pending_post_obs` is only ever changed by `_launch_post_obs()`, on the main loop. `CLOSE_SESSION` still waits for every post-obs to finish (`gather()`), and one already started cannot be interrupted. What the post-obs thread shares with the main loop is made safe for it: logging (`WebSocketLogHandler.emit()`, already thread-safe), `step_progress.py` (a lock) and `ws_image_broadcaster` (hands a send from another loop over to the main loop, see the GUI section); aiosqlite opens its own connection per call and works under any loop. Sub-plugins need no change and never know which thread they run in.

The orchestrator (`main.py`) and the stage plugins themselves (`INIT_SESSION`/`CLOSE_SESSION` included) know no sub-plugin and no program: anything specific to a program or to a sub-plugin's data lives in a sub-plugin declared by that program's YAML (e.g. the exposure suggestion is written by `calculate_flux`, never by `CLOSE_SESSION`). `session_log_extractor.py`, called from `CLOSE_SESSION`, is generic and program-agnostic — not a precedent for program-specific work there.

**Guiding-chain recovery** (`plugins/sequencer_plugins/guiding_chain_recovery.py`, `sequencer_backend=indi`): a dead guiding camera used to look like any other failure, so the night of 2026-09-24/25 lost 30 observations in a row (see HISTORY.md) — 28 of them failing at the very first PHD2 call of the pointing (then in `pointing_72ed`, now in `slew_72ed`). `run_with_guiding_recovery(obs, operation, what)` wraps one guiding-chain operation; on a `DeviceError` it asks PHD2 to stop (best effort), then probes the camera with a 1 s exposure (nothing written to disk). Camera answers → the original error is re-raised untouched (ordinary failure, restart from SCHEDULER as before; a healthy camera is never disconnected). No answer → disconnect + reconnect + probe, up to 2 attempts 15 s apart, then the operation is replayed once. Still no answer → `SessionFatalError`. Guarded: `capture_guide_image()`'s exposure (which covers `slew_72ed`, `slit_xy`, `pointing_72ed`, `stop_phd2_guiding`, `home_sync_am3` and `focus`), `slew_72ed`'s leading `stop_capture()` and `pointing_72ed`'s first `start_guiding()` — deliberately not the second `start_guiding()`, which follows `set_lock_position()`: a recovery in between would lose PHD2's lock offset and a replay would guide on the wrong position without any error. PHD2's own equipment link is never disconnected here (on INDI that might drop the mount's connection too — not verified); it self-heals at the next `start_guiding()`. The whole mechanism lives in the sub-plugin layer on purpose: the orchestrator has no counter and no hardware knowledge. Reading the Stellarmate's kernel log: a `usb 1-2.4: reset high-speed USB device` line per exposure is the ZWO driver's own normal behaviour (`indi_asi_ccd` issues `USBDEVFS_RESET` on every exposure — confirmed with `strace`, see HISTORY.md 2026-09-25), not a fault by itself; a real link problem shows up as `disconnect`, error `-71`, `Cannot enable` or over-current messages.

**Plugins never block waiting on external conditions.** The active SCHEDULER plugin is the one plugin that could, in principle, need to wait (for a target to become observable) — but it must still answer within a few seconds: if nothing is observable right now, it sets `obs.scheduler_data["target"] = None` and returns immediately, rather than sleeping internally. `session_runner()` treats `target is None` as "nothing to do yet" (not an error — no `db_set_error`, no restart-from-SCHEDULER log): it waits `SCHEDULER_RETRY_SECONDS` (`config.py`, in small interruptible steps via `_interruptible_sleep()` so a stop request during the wait still takes effect promptly) and asks SCHEDULER again.

No SCHEDULER plugin imports `main.py` or touches `state` — a plain top-level `from ..main import state` fails at import time with a circular-import error, since `main.py` imports the plugin registry before defining `state` (see HISTORY.md for the incident that established this rule).

For a sub-plugin whose own work spans several internal steps (e.g. `star_spectra_acquisition.py` looping over several sub-exposures, see below), the same no-`state`-import rule still applies — but it still needs *some* way to notice a stop request between two of its own steps, not just between stages. `Observation.stop_check` (`models.py`) is that narrow, read-only escape hatch: a plain callable, `None` outside a real session run — same "live, not persisted" pattern as `hardware` below. A sub-plugin that wants to be interruptible checks `obs.stop_check()` between its own steps (`star_spectra_acquisition`, the four calibration acquisitions, `home_sync_am3`), exactly like it reads `obs.hardware[...]`, without ever touching `main.py` itself. **`session_runner()` currently leaves it `None`** on every `Observation`, deliberately: a stop must let the current observation finish (see above), so these checks never fire today. They stay in place for a possible future "stop now" option, which would only have to hand `stop_check=lambda: not state.is_running` back to the `Observation`. `SessionContext.stop_check` (`plugins/camera_cooldown.py`) mirrors the same mechanism onto the one other object that ever needs it: `INIT_SESSION` acts on a `SessionContext`, not yet an `Observation`, so its own multi-step cooldown wait needs the same narrow escape hatch — set by `session_runner()` right before `INIT_SESSION` runs, `lambda: not state.is_running` (this one is actually set: no series is at stake during a cooldown).

### Plugin system (three mechanisms)

**Stage plugins** (`plugins/__init__.py` registry) — one per `OrchestratorStage` enum value. Two interfaces (`models.py`): `SessionStagePlugin` for `INIT_SESSION`/`CLOSE_SESSION` (`run(self, ctx: SessionContext) -> SessionContext`), and `ObservationStagePlugin` for `SCHEDULER` → `ARCHIVE` (`run(self, obs: Observation) -> Observation`).

**SCHEDULER plugins** (`plugins/schedulers/` registry) — the SCHEDULER stage itself is pluggable: several interchangeable target-selection algorithms can coexist, each in its own subdirectory with its own class and its own tests, one chosen at startup via `active_scheduler` (`conf/config.yaml`, resolved to `ACTIVE_SCHEDULER` in `config.py`). This is a distinct axis from `SEQUENCER_BACKEND` below — that one is a closed, binary technical choice (simulated vs. real hardware protocol for the *same* sequencing logic); this one is an open-ended set of alternative *scheduling algorithms*, meant to grow as different observers contribute their own. `plugins/schedulers/__init__.py::_build_registry()` is the explicit name→class registry (no filesystem auto-discovery, consistent with `pipeline_loader.py`'s own registry below); `load_scheduler()` instantiates the active one, called once by `plugins/__init__.py` at import time. `SchedulerFatalError` also lives here (`plugins/schedulers/__init__.py`) rather than inside any one scheduler, since any SCHEDULER plugin may raise it.

  Every SCHEDULER plugin must honor the same `scheduler_data` contract (documented in full, in English, in `plugins/schedulers/blank/scheduler.py`'s docstring — the copyable template): populate `target` (a `Target`), `queried_name`, `program`, `priority`, and `exposure` (an `ExposureConfig`) when a target is selected, or set `target = None` when nothing is observable right now (see the "never block" rule above). Two optional keys, `proposed_by` (str) and `estimated_duration_s` (seconds), are set when the scheduler knows them (the selector does) and recorded in `rosace.db` (`NULL` when absent); any other key is the scheduler's own information. Each real scheduler's docstring states which keys it fills. This contract is **not** checked at runtime in plugin code — by design, to keep plugins simple — but every scheduler's own test suite must verify it via `conftest.py::assert_scheduler_contract()` (the optional keys only when present), with explicit failure messages naming the offending key.

  Three schedulers exist today: `schedulers/scheduler_rosace_2026/` — the real one, described below —, `schedulers/selector/` — the multi-program scheduler (see "The multi-program selector" below), which replaces it once validated on the sky — and `schedulers/blank/` — a minimal example (hardcoded Vega/Arcturus/Castor, no `targets.db` access at all) meant purely as a template to duplicate when writing a new scheduler. To add one: duplicate `schedulers/blank/`, implement `run()`, write its tests (checking the contract via `assert_scheduler_contract()`), register the class in `_build_registry()` (the only list of schedulers: `load_scheduler()` and `--check-config` validate `active_scheduler` against it), and set `active_scheduler` accordingly.

**Sub-plugins** — loaded dynamically by `pipeline_loader.py` at runtime from a YAML program file, one reload per observation (`obs.scheduler_data["program"]`, set by the active SCHEDULER plugin — there is no global "active program" setting). A program's own `sequencer:` list is never the *whole* SEQUENCER story: the active hardware profile may declare its own `sequencer_prefix:` (a list, e.g. `[guiding_dark_acquisition, home_sync_am3]` for an AM3 mount) — steps every program run against that equipment needs, regardless of which science it's doing. `pipeline_loader.py::hardware_sequencer_prefix()` is the single source of truth for this list (`[]` if the key is absent, or if `SEQUENCER_BACKEND` isn't `"indi"`), read identically by `load_pipelines()` (to build the actual pipeline) and by `SequencerPlugin.run()` (to set `obs.program_steps["sequencer"]`) — both prepend the same list, so the two can never disagree and desynchronize the step names from the sub-plugin instances they're `zip()`-paired against. Loaded through the exact same dynamic-resolution mechanism as any program-declared step (same directory convention, same `DISPLAY_NAME`/docstring discovery, same tests) — this isn't a new plugin family or a new extension point, just a second source feeding the same SEQUENCER list. This is what keeps equipment-specific sub-plugins out of scientific program YAMLs entirely — a program never needs to know or declare anything about the mount (or any other equipment) it happens to run on (see HISTORY.md 2026-09-08). Sub-plugins share the same interface as stage plugins: `execute(self, obs: Observation) -> Observation` (`sub_plugin_base.py`). A sub-plugin *may* write its own nested sub-dict inside its parent stage's casier, keyed by its own declared name (e.g. `reduction_data["calculate_flux"] = {"images": {...}}`) — but only when it has something genuinely descriptive to add to the observation record (data about what the observation *contains*: images, positions, computed values). A sub-plugin with nothing descriptive to report (e.g. a cleanup step whose only fact is "it ran") writes **no casier at all**.

  **Casiers are not a flow-tracking mechanism.** `Observation`/the observation YAML describe the observation — target, session, images, dates — not the pipeline's own execution history; which step ran, in what order, and whether it succeeded is the log's job, not the YAML's. Concretely: a sub-plugin never checks a previous step's casier just to confirm "did it succeed" — the orchestrator's own `try/except` around every `execute()` call already guarantees that a failed step stops the whole stage before the next sub-plugin is ever reached, so re-checking that is redundant, dead code that can never actually catch anything. A sub-plugin *does* still read a previous casier when it genuinely needs that step's **data** to do its own job (e.g. `extract` reads the corrected frames an earlier step produced — the actual files to process, not a signal that the earlier step "succeeded") — and if that data isn't there, it still raises an explicit error naming what's missing, the same as any other required input. The difference is purely about *why* the check exists: validating that a real input is present, never gatekeeping on another sub-plugin's completion for its own sake. This is also why a casier should never repeat data that's already elsewhere in `obs` (e.g. the target's name — already in `scheduler_data`) purely to be "complete": a casier only ever holds what that specific sub-plugin uniquely produced. (See HISTORY.md for the incident that established this principle.)

  A sub-plugin has access to the whole `obs` object — every casier collected so far, not just its own stage's. This is an implementation choice made by whoever writes that sub-plugin, not a dependency the framework tracks or enforces. No fallback chains: the program YAML is trusted to sequence steps consistently with what each sub-plugin actually reads, not defended against at runtime. Sub-plugins have no config of their own — all configuration lives in `conf/` (see below), consistent with the rest of the app.

**Logging convention**: the orchestrator (`sequencer.py`/`reduction.py`/`sharing.py`) already announces each step before calling it (`"[SEQUENCER] → {step}"` etc.) and logs a failure itself if `execute()` raises — a sub-plugin doing one atomic action (a single hardware/IO call, nothing else worth tracing) should therefore log **once**, after that action succeeds, not once before and once after. A sub-plugin with several genuinely distinct internal phases (not just one action) is the exception — a log line per phase there is legitimate, since each one is a real checkpoint useful for diagnosing a failure partway through. Documented in each `blank_*` template's own docstring.

  **One directory per sub-plugin**, named after the sub-plugin itself (e.g. `sequencer_plugins/slew/`, `reduction_plugins/tilt/`) — chosen deliberately over a purely flat layout so the catalogue of sub-plugins stays discoverable/documentable as it grows (a real concern once many programs/equipment variants each need their own sub-plugins, most unused by any single observation). Resolved **dynamically via `importlib`** by `pipeline_loader.py` — a sub-plugin declared `"<name>"` in a program YAML resolves to module `<name>/<name>.py`, class `<Name>Plugin` (snake_case `<name>` converted to PascalCase per underscore-separated word, e.g. `pointing_72ed` → `Pointing72edPlugin`), by naming convention alone. No central registry file to maintain, and only the sub-plugins actually declared by the program being loaded are imported — not the whole catalogue. Both the program name and every step name (sequencer/reduction/sharing) are validated against `^[A-Za-z0-9_]+$` (`pipeline_loader.py::_validate_name()`) before being interpolated into a filesystem path or a Python module path — defense in depth against path traversal, since `ProgramCreate.name` (below) is already validated at the API boundary but this module has no way to know a given caller did that.

  Sub-plugin directory names must additionally be all-lowercase (PEP8: modules/packages are all-lowercase) and unique across the three families (sequencer_plugins/, reduction_plugins/, sharing_plugins/) — both checked once at server startup by `pipeline_loader.py::validate_subplugin_catalogue()` (called from `plugins/__init__.py`), which raises a `RuntimeError` naming the offending director(y/ies) rather than letting either mistake surface later as a confusing `ModuleNotFoundError` mid-observation or an ambiguous program YAML/observation dossier. Lowercase matters because `build_pipeline()`/`load_sharing_plugin()` lowercase whatever name a program YAML declares before resolving it to a module path — an uppercase directory could never be found that way. Cross-family uniqueness matters for human readability, not correctness: `sequencer_data`, `reduction_data` and `sharing_data` are separate casiers, so e.g. a sequencer sub-plugin and a reduction sub-plugin sharing a name would never actually collide in code — but they would make every program YAML and every observation dossier ambiguous to a reader (is `dark` the capture step or the processing step?). This is also why the three copyable templates are named `blank_seq`/`blank_red`/`blank_share`, not a bare `blank` reused three times.

- Sequencer sub-plugins: `plugins/sequencer_plugins/<name>/` (`slew`, `focus`, `star_spectra_acquisition`, `dark_acquisition`, `bias_acquisition`, `calib_acquisition`, `flat_acquisition`, `guiding_dark_acquisition`, `home_sync_am3`, `slew_72ed`, `slit_xy`, `pointing_72ed`, `spectro_light_source_to_sky`, `stop_phd2_guiding`, `wide_field_acquisition`) — read/write `obs.sequencer_data`, read `obs.scheduler_data` for target/exposure. The only sub-plugin family with a backend axis (`SEQUENCER_BACKEND`, `config.py`), resolved **inside each sub-plugin's own directory** rather than as a separate directory tree:
  - `<name>/<name>.py` — the canonical, no-suffix filename, used whenever there's no backend ambiguity: always for REDUCTION, and for SEQUENCER when `SEQUENCER_BACKEND="indi"`. `focus.py` measures the guiding camera's own focus sharpness (mean FWHM over a handful of clean stars, see below) — `indi`-only, no `_internal.py` counterpart, same reasoning as `guiding_dark_acquisition`/`home_sync_am3` (no real guiding camera to measure in simulation).
  - `<name>/<name>_internal.py` — a **deliberate, narrow exception**, not a first-class backend: used only when `SEQUENCER_BACKEND="internal"` (simulation, level-1 demonstrator). The demo no longer uses it (it runs the real `indi` sub-plugins on replayed hardware, see "Trying Rosace without hardware"); `internal` remains for the automated tests only, and is to be removed later (TODO.md). **Only the sub-plugins needed for `programs/demo.yaml` have an `_internal.py` file** — its absence for a given sub-plugin is normal, not a gap. Nesting `internal`/`indi` as a subdirectory inside each sub-plugin (`slew/internal/slew.py`) was explicitly rejected (see HISTORY.md). `star_spectra_acquisition_internal.py` still names its produced files via `acquisition_helpers.py::build_fits_root_name()` — same convention as the `indi` backend (see below) — even though it only `touch()`s an empty placeholder file, not a real FITS image; a plain simulation-only filename was tried first and dropped once `--demo-mode` made these files visible to an actual observer trying the app (see HISTORY.md).
  - `pipeline_loader.py::_resolve_module_and_class()` does this resolution; `SequencerPlugin.run()` itself stays agnostic of the backend.
- Reduction sub-plugins: `plugins/reduction_plugins/<name>/` — read/write `obs.reduction_data`. The native chain (`master_bias` → … → `summary`, all implemented) is described in "Native reduction chain" below; `calculate_flux` (relative flux of each raw frame, see "Spectrum trace axes and relative flux") is real. No backend axis at all: these steps process already-acquired files, no hardware dependency — the INDI/ASCOM axis never concerns them, and their module name is never suffixed. `export_demetra` runs in **parallel** with the native chain rather than continuing it — it reads directly from `obs.sequencer_data` (the raw science and calibration files, under the shared keys `star_spectra_images`, `bias_images`, `dark_images`, `flat_images` and `calib_images`), never from `obs.reduction_data`, so it never depends on the native chain having run. It writes a Demetra-compatible `.obs.srl` project file (XML) into `obs.obs_dir` (the session directory) and adds it, with every raw FITS file it references, flat, to a ZIP — `subplugin_params.export_demetra.global` (default `true`) and/or `.individual` (default `false`, one ZIP per observation, `<observation file>_demetra.zip`; both `false`: nothing exported). Its installation names (observer, site, equipment, telescope, spectrograph, camera...) come from the configuration's Core `observatory` block (`config.OBSERVATORY`), shared with `write_spectrum`. The global option writes **one ZIP per session** (`<session dir>_<session_id>_demetra.zip`, opened in append mode: created by the session's first observation, completed by each next one; a name already in the ZIP is skipped, so the calibration frames shared by the whole session are stored once — Demetra reads a ZIP holding several observations; a server killed mid-append can damage the ZIP, rebuildable from the files left in the session directory) — an alternative reduction path for Shelyak's own Demetra software, offered alongside Rosace's native pipeline while that pipeline matures, not a replacement for it. Most of the generated XML (the entire `<Process>` element — extraction geometry, wavelength-calibration reference lines, etc.) is a **static, per-instrument template** (`plugins/reduction_plugins/export_demetra/demetra_process_template.xml`), copied byte-for-byte into every export: these are instrument-profile facts Demetra itself fills in progressively as it reduces, never observation-specific values Rosace could or should compute.

  **Shared, purpose-named keys, when a stage can have more than one interchangeable way to produce the same kind of output**: a *downstream* reader shouldn't need to know exactly which sub-plugin produced the data it needs. `star_spectra_acquisition.py` (both backends) appends every produced filename straight to `sequencer_data["star_spectra_images"]` — a fixed, purpose-named key. `calculate_flux.py` (and `blank_red.py`, the REDUCTION template) read only `sequencer_data["star_spectra_images"]`: REDUCTION must never need to know which specific SEQUENCER sub-plugin produced the raw science files, only that they land under this one fixed key. Any future alternative acquisition sub-plugin is expected to append to the same shared key rather than inventing its own. The calibration series follow the same rule: `bias_acquisition`, `dark_acquisition`, `flat_acquisition` and `calib_acquisition` put their series' filenames under `sequencer_data["bias_images"]`/`["dark_images"]`/`["flat_images"]`/`["calib_images"]` (one series per observation, plain assignment), and their own casier only keeps `origin` — a reader (`export_demetra`, the native masters) never reads an acquisition's casier.
- Sharing sub-plugins: `plugins/sharing_plugins/<name>/` — read what they need from the observation (preferably its files, never assuming a given REDUCTION sub-plugin ran, since every program declares its own list; nothing to share is not an error), may write their own nested key in `obs.sharing_data`. Unlike SEQUENCER/REDUCTION, a program declares exactly **one** (`sharing: <name>`, a singular YAML key, not a list) — `SharingPlugin.run()` (`plugins/sharing.py`) resolves and calls that single sub-plugin via `pipeline_loader.py::load_sharing_plugin()`, instead of iterating a list. A program that needs to notify several destinations handles that *inside* its one sharing sub-plugin — the mechanism itself deliberately doesn't support a list, to keep it simple. `sharing_plugins/blank_share/` is the only one that exists today — a placeholder (logs the observation dossier, no real email/FTP/API yet) used by every program for now, and doubles as the copyable template (its docstring documents the contract in full, in English), same idea as `schedulers/blank/`. The ARCHIVE stage plugin (`plugins/archive.py`) is a placeholder too, logging the dossier only: archiving is not designed yet, and will work from the observation's own files, never from a given sub-plugin's casier.
- Programme definitions: `rosace/programs/*.yaml` — declare which sub-plugins run in order (`sequencer`, `reduction`) plus the single `sharing` sub-plugin. `demo.yaml` is a minimal, backend-agnostic program (same step names as any other) used as the default for a fresh install and for quick end-to-end verification; `Be_stars.yaml`, `bright_stars.yaml`, `nova_monitoring.yaml` are real-hardware/scenario programs.

To add a new sub-plugin: create `plugins/<sequencer_plugins|reduction_plugins|sharing_plugins>/<name>/<name>.py` (and `<name>_internal.py` too, only if a demo counterpart is actually needed — SEQUENCER only) with its own `test_<name>.py`, then declare its name in the relevant program YAML (a list entry for `sequencer`/`reduction`, the single `sharing` value for sharing) — no registry file to edit.

**Before writing a new one, check what already exists**: `python -m rosace.main --list-subplugins [sequencer|reduction|sharing]` (`pipeline_loader.py::list_subplugins()`) walks the same three directories `validate_subplugin_catalogue()` discovers from and prints each sub-plugin's name plus the first line of its own module docstring — meant for reuse/duplication decisions, not just naming hygiene. Reads via `ast.parse()`, never imports the module, so it never triggers a sub-plugin's own import-time side effects (device connections, backend-specific dependencies) and works regardless of `SEQUENCER_BACKEND`. Every module docstring's first line must already be a short, human-readable summary — `TestSubpluginDocstrings` (`plugins/test_pipeline_loader.py`) fails the test suite if any real sub-plugin is missing one.

**`DISPLAY_NAME`**: every sub-plugin also declares a short, human-readable `DISPLAY_NAME = "..."` module constant, right after its docstring and before its imports (e.g. `DISPLAY_NAME = "Dark"` in `dark_acquisition.py`) — a GUI label (see "Live SEQUENCER/REDUCTION step progress" below), deliberately separate from the docstring: the docstring documents the sub-plugin for a developer, `DISPLAY_NAME` names it for an observer watching the GUI, and the two audiences don't want the same length or tone. Read the same way as the docstring — `pipeline_loader.py::_module_display_name()`/`get_display_names()`, `ast.parse()`, never imported — for the same reasons. A sub-plugin missing one falls back to its own raw snake_case name rather than failing (not a runtime correctness risk, same posture as a missing docstring); `TestSubpluginDisplayNames` (`plugins/test_pipeline_loader.py`) still fails the test suite if a real sequencer/reduction sub-plugin lacks one. For the two sub-plugins with both a canonical and an `_internal.py` file (`slew`, `star_spectra_acquisition`), both files must declare the *same* `DISPLAY_NAME` — they represent one logical step, and the GUI must show the same label regardless of `SEQUENCER_BACKEND`; also enforced by `TestSubpluginDisplayNames`.

### Session context and the observation dossier (`SessionContext`, `Observation`)

Two separate Pydantic objects (`models.py`), deliberately not merged:

- **`SessionContext`** — passed only to `INIT_SESSION`/`CLOSE_SESSION`. Minimal and stable for the whole night: `session_id`, `started_at`, `site_name`, `session_dir`. Recorded once in the `sessions` table.
- **`Observation`** — passed from `SCHEDULER` through `ARCHIVE`, unwrapped (no wrapper — the dossier *is* what flows). `main.py`'s `session_runner()` creates a fresh, empty instance for each observation (`id`, `created_at`, `session_id`, `obs_dir` — the only fields the orchestrator itself knows or sets) right before calling the active SCHEDULER plugin, which fills it in.

  The orchestrator owns the `Observation` — it creates it, persists it and hands it to each stage in turn — but never writes business data, and never reads a casier's content except the **SCHEDULER contract**: each stage plugin (and its sub-plugins) owns one casier, free-form (`dict[str, Any]`), that only it writes to: `scheduler_data`, `sequencer_data`, `reduction_data`, `sharing_data`, `archive_data`. `models.py` only declares that these casiers exist, never what's inside them. The contract keys of `scheduler_data` (see SCHEDULER plugins above) are the minimum every SCHEDULER plugin must provide, and the core reads them: `main.py` checks `target` (`None` → wait and retry), `database.py::db_insert_observation()` records them in the observation's row. The same contract keys are also read by a deliberate, cosmetic exception on the model itself: `Observation.suggested_filename` (a `@property` on the model itself) reads `self.scheduler_data["queried_name"]` (falling back to `self.scheduler_data["target"].name`, the canonical Simbad name, if `queried_name` isn't set yet) purely to build a human-readable filename — a conscious, minimal, cosmetic exception, kept on the model (not in `main.py` or a stage plugin) precisely so `main.py` and the plugins never need to know it exists. The name goes through `file_names.py::safe_name()`, **the one rule for every file or directory named after a star or the site** (observation file and everything derived from it, raw FITS frames via `build_fits_root_name()`, the intermediate directory, the Demetra project, the session directory): each run of spaces becomes `_`, every character outside `[A-Za-z0-9_-]` is removed (Simbad's `*` among them), repeated `_` collapse, leading/trailing `_` drop — `*   8 Lac A` → `8_Lac_A`, `HD  45995` → `HD_45995`. A small core module like `time_helpers.py`, imported by the plugins that name files; no plugin family depends on another for it. Files written before 2026-10-14 keep their old names (`*___8_Lac_A`, `8LacA`): they are referenced by name in the database, the observation files and the Demetra projects, and Rosace never finds a past file by rebuilding its name. Prefers `queried_name` over the canonical name for the same reason every other operator-facing log line does (see the Logging section) — the observer-typed name, not Simbad's own designation. Computed lazily on every access, not cached — reflects whatever `scheduler_data` currently holds (falls back to `"target"` before SCHEDULER has run).

  `Observation` also carries two top-level fields, not casiers (neither is owned by one stage) — `program_file` (the program YAML's filename, e.g. `"demo.yaml"`) and `program_steps` (the expected step lists, `{"sequencer": [...], "reduction": [...], "sharing": "blank_share"}`, the literal names declared in that YAML — `sequencer`/`reduction` are lists, `sharing` is the single value, matching its own singular YAML key) — both set together by `SequencerPlugin.run()` as its very first action, before executing any sub-plugin, so they're already on disk (`main.py` writes `obs` to its YAML file even on the exception path) even if the observation later crashes mid-pipeline. This is what lets a crash be diagnosed later: the nested casier data alone only proves what *succeeded*, not what was *supposed* to happen. Deliberately called `program_steps`, not `pipeline`: "pipeline" is internal plumbing vocabulary (`pipeline_loader.py`, `load_pipelines()`'s ordered lists of sub-plugin instances) — the observation file only ever talks about the *program*, the scientific concept the observer actually asked for.

  `Observation` is also serialized as-is to the observation's YAML file (`obs.yaml_file`) after **every** stage (`observation_file.py::write_observation_file()`, called from both the foreground loop and `run_post_obs()`) — the file only grows, becoming the complete, self-contained record of the observation by the time ARCHIVE finishes. Useful for crash diagnosis: whatever was last written on disk shows exactly how far the observation got.

**`Observation.measurements`** (a top-level `dict`, not a casier — no single stage owns it): measurements describing the observation, under agreed names that describe the measurement, never the sub-plugin that made it (`ambient_temp_c`/`camera_temp_c` — read by `star_spectra_acquisition` right before its first science exposure, best effort —, `pier_side` by `slew_72ed`, `slit_y_px` by `slit_xy` when calculated, `focus_fwhm_px` by `focus`). Persisted in the YAML dossier like every field. `main.py::_persist_observation()`, called after every stage (success and error paths) where the dossier is written, also copies the names declared in `database.py::MEASUREMENT_COLUMNS` into the observation's row (`db_record_measurements()`); undeclared names stay in the dossier only. Plugin-agnostic, same pattern as `db_insert_observation()` reading `scheduler_data` — the `observations` table is written by `main.py` only (through `database.py`); sub-plugins never write it.

Naming convention: the local variable holding an `Observation` is `obs`, a `SessionContext` is `session`. Plain `ctx` is reserved for the few genuinely generic spots (e.g. `run_stage()`) that accept either type.

### Two SQLite databases

- **`rosace.db`** (`database.py`) — sessions and observations, plus two measurement-history tables: `pointing_errors` (first-pointing error, see `slew_72ed`) and `spectrum_flux` (one row per measured science sub-exposure, see `calculate_flux`), and `bess_validation` (the Be spectra waiting for the observer's decision before BeSS, see "BeSS validation" below). Functions: `db_init`, `db_insert_session`, `db_close_session`, `db_insert_observation`, `db_stamp_stage`, `db_set_error`, `db_set_yaml_file`, `db_get_recent_observations`, `db_count_observations_for_target`, `db_get_successes_for_target`, `db_get_last_failure`, `db_count_trailing_failures`, `db_get_last_success_per_target`, `db_get_program_time_s`, `db_record_measurements`, `db_insert_pointing_error`, `db_insert_spectrum_flux`, `db_queue_bess_validation`, `db_get_bess_validations`, `db_get_bess_validation`, `db_set_bess_decision`. Observation columns added for the multi-program selector (all nullable, so older code keeps working on the extended table; added by hand with `ALTER TABLE` on an existing database, never by migration code): `ended_at`/`outcome` (`success`/`failed`, set by `db_stamp_stage(SEQUENCER)` / `db_set_stage_status(SEQUENCER, 'error')` — the end of the telescope time used), `proposed_by`/`estimated_duration_s` (from `scheduler_data`, selector only), and the measurement columns of `MEASUREMENT_COLUMNS` (see `Observation.measurements` above). `db_get_recent_observations` only returns observations from the current *astronomical day* (local noon to noon, via `time_helpers.py::astronomical_day_start_utc()`) — assumes the server runs in the site's own local timezone, since there is no explicit site timezone setting anywhere in `conf/`. Each observation row also records `program_name`, `queried_name`, and `priority` (from `obs.scheduler_data["program"]`/`["queried_name"]`/`["priority"]`) alongside `target_name` — `db_get_recent_observations()` (and so `GET /observations/recent`) includes `program_name` in every returned row, shown as its own column in the GUI's observations list, next to priority. `db_count_observations_for_target(program_name, target_name)` counts how many observations already exist during the current *astronomical day* (not scoped to a single `session_id` — stopping and restarting the session doesn't reset the count) for a given (program, target) pair, which is how the default scheduler (`scheduler_rosace_2026`) knows a target has already been "consumed" (see below).

`time_helpers.py` (`rosace/rosace/`) is a small shared module for exactly this "local noon to noon" concept — `astronomical_day_start_utc(now=None)` (a UTC instant, for DB comparisons) and `astronomical_day_local_date(now=None)` (a `YYYY-MM-DD` string in the site's own local date, for naming one directory/file per night) both derive from the same private `_local_noon_boundary()`, so the two can never disagree about where the boundary falls. `InitSessionPlugin` (`plugins/init_session.py`) uses `astronomical_day_local_date()` to name the session directory (`<date>_<site_name>/`, see "On-disk layout" below).
- **`targets.db`** (`targets.py`) — stars catalogue and scientific programs (N-N via `program_stars`, which also carries an optional per-pair `exposure_time`). CRUD functions follow the pattern `star_*` / `program_*`. `ProgramCreate.name` is restricted to `^[A-Za-z0-9_]+$` (a `field_validator`, logging the rejection) — this name later becomes a filesystem path and a Python module path in `pipeline_loader.py` (see above), so anything else is rejected before it ever reaches the database. Stars also have a `star_aliases` table (alternate names, e.g. catalogue cross-references) — `star_get_by_name()` tries the canonical `stars.name` first, falls back to `star_aliases` if nothing matches. Populated exclusively through `main.py`'s REST API (`/stars`, `/programs`, `/simbad/import` — all addressed by name, never by internal id, since the id is not something a user thinks in terms of); of the SCHEDULER plugins, only `scheduler_rosace_2026` reads it (see below), and does so read-only — `blank` never touches it. Two bulk-import endpoints exist for populating the catalogue quickly: `POST /stars/import-list` (uploaded text file, one star name per line, each line goes through the same Simbad-backed logic as `/simbad/import`) and `POST /programs/import-list` (uploaded YAML file, `{program: [star, ...]}`, links existing stars to existing programs — no Simbad call, both must already exist). Both accept real file uploads (`UploadFile`, `python-multipart`), not a server-side path, so the GUI or caller can be on a different machine than the server. Both return a per-line report (`status`: `created`/`existing`/`error` or `linked`/`program_not_found`/`star_not_found`) rather than failing the whole batch on the first bad line.

Default path is `~/.rosace/databases/` (`config.py`). Both databases are created automatically on startup.

### Authentication (`auth.py`)

Session-cookie auth. `users`/`auth_sessions` tables live in `rosace.db` (same file `database.py` uses, own module) — named `auth_sessions`, not `sessions`, specifically to not collide with `database.py`'s own unrelated `sessions` table (one row per observation night). Passwords hashed with `bcrypt`; a session is an opaque `secrets.token_urlsafe(32)` token in an `HttpOnly`/`SameSite=Lax` cookie (`rosace_session`), checked against `auth_sessions` on every request — not a signed JWT, deliberately: no secret-key rotation to manage, and revoking a session is just deleting a row.

Every existing REST route sits behind `main.py`'s `protected` `APIRouter` (`dependencies=[Depends(get_current_user)]`) — default-closed: a new route must be added to `protected` (or `admin_router`) consciously, the opposite of a middleware allowlist someone could forget to update for a route added later. `admin_router` (`prefix="/auth/users"`) additionally requires `is_admin` (`Depends(require_admin)`), for account management (`POST`/`GET`/`DELETE /auth/users...`). `/ws` is on neither router — a `Depends()`-raised `HTTPException` doesn't close a WebSocket handshake cleanly — it's checked by hand in `ws_logs()`, before `accept()`, reading the same cookie directly. `POST /auth/login`/`POST /auth/logout` are the only public API routes, declared directly on `app`. The API documentation pages `/docs` (Swagger UI) and `/redoc` are public routes too, but show the operations only to a logged-in user — otherwise a short page saying to log in on `/` first (FastAPI's own `docs_url`/`redoc_url`/`openapi_url` are turned off, Rosace serves them itself); `/openapi.json`, which they read, is on `protected`.

First admin: `python -m rosace.main --create-admin <username>` (password prompted via `getpass`, never passed as an argument, to keep it out of shell history/`ps`). Refuses once any account already exists (`ensure_first_admin()`) — creating further accounts after that goes through `POST /auth/users` (admin-only), not shell access to the machine. If the only admin account is ever lost, direct `sqlite3`/DB-browser access to `rosace.db`'s `users` table is the deliberate recovery path (no separate "forgot password" flow) — just keep `password_hash` a real bcrypt hash if editing it by hand, a plaintext value there fails login silently.

`SESSION_TTL_HOURS`/`SESSION_COOKIE_SECURE` — see config table below. Session length defaults long (14 days) since the app runs unattended overnight; `secure` defaults `false` since the app typically serves plain HTTP on the local network — `true` would silently stop the browser sending the cookie back over HTTP, including on `localhost`.

### The default scheduler: `scheduler_rosace_2026` (`plugins/schedulers/scheduler_rosace_2026/scheduler.py`)

Reads `OBSERVATION_LIST_PATH` (`subplugin_params.observation_list_path`, shared with the selector's `manual_list`) fresh on every call — a plain-text, read-only CSV plan (`Priority, Program, Star, commentaire`) that this plugin never modifies. Each line is resolved against `targets.db` (program exists, star exists — by canonical name or alias, see above — and is linked to that program via `program_stars`); invalid lines are logged and skipped, never fatal. Valid lines are sorted by priority ascending (1 first; file order breaks ties) and walked **individually, one line at a time** — deliberately not collapsed into one group per (program, canonical star) with a single priority, since the same target can appear on multiple lines at *different* priorities (e.g. priority 2 and priority 4), and another target at an intermediate priority (3) must then be offered between the two occurrences, not after both. For each line, its rank among occurrences of the same (program, canonical star) seen so far in this pass — two lines naming the same star under different aliases count as the same target — is compared against `db_count_observations_for_target()` (this astronomical day — not scoped to a single session, see above): once that rank has already been fulfilled, the line is skipped. This is how a target gets "consumed" without ever rewriting the plan file, and without a session restart mid-night re-offering already-consumed targets. A line whose target's current altitude (`astro_math.py::altitude_deg()`, site position from `SITE_LATITUDE_DEG`/`SITE_LONGITUDE_DEG`) is below `MIN_TARGET_ALTITUDE_DEG` is also skipped the same way — logged, not consumed, next line tried. No day/night (sun-below-horizon) check: out of Rosace's scope (see the Project overview).

**Local horizon mask (optional, `HORIZON_FILE`)**: when `horizon_file` is declared in `config.yaml` (a Core, site-level key of the `observatory` block, next to `latitude_deg`, exposed as `HORIZON_FILE`; absent = no mask, behavior identical to a config without it — the packaged and demo configs declare none), a line whose target is above `MIN_TARGET_ALTITUDE_DEG` but below the terrain obstruction at its current azimuth (`astro_math.py::azimuth_deg()`, North through East) is skipped the same way — logged (`below local horizon (alt < horizon at az ...)`), not consumed, next line tried. The two checks combine: the flat floor is tested first, then the mask (strict `<`, a target exactly at the horizon altitude is accepted); the mask never replaces the floor. The file is a KStars "Artificial Horizon" text export (`~/.rosace/horizon/`), read fresh on every SCHEDULER call like the plan file, parsed by `horizon.py` (a core module next to `astro_math.py`, which stays pure sky maths — shared by this scheduler, the selector's `checks.py` and `cli.py`'s `--check-config`; it raises its own `HorizonFileError`, which each scheduler turns into `SchedulerFatalError`, so the core never imports a plugin): `#` comments and blank lines ignored, the first non-numeric line is the profile name, then one `azimuth altitude` pair per line (degrees; azimuth in [0, 360] with 360 == 0, altitude in [0, 90]). Points must be listed in increasing azimuth, wrapping through 360/0 at most once and stopping before the first point again (a profile may start mid-circle, like the real St-Pancrasse export which starts at 220 — but a point out of place is almost surely a typo, which sorting alone would have silently turned into a plausible, wrong mask); identical duplicate points collapse, two different altitudes at one azimuth, fewer than 2 distinct points, or any unparseable line is an error. Altitude between points is linearly interpolated, circular across 360/0. Validate a file without starting a session with `python -m rosace.main --check-config` (see below).

**Meridian filter (optional, `min_meridian_distance_deg`)**: when `subplugin_params.scheduler_rosace_2026.min_meridian_distance_deg` is > 0 (default 0 = off, so the demo mode, the simulator and the packaged config are unaffected; the 72ED config (`~/.config/rosace/config.yaml`) sets 3), a line whose target's **hour angle** is within that many degrees of the meridian on either side (`|HA| < threshold`, strict — exactly at the threshold is accepted) is skipped the same way as the other filters: logged (`too close to the meridian (HA +1.2° within ±3.0°)`), not consumed, next line tried. Checked last, after the flat floor and the local horizon. Why it exists: `slew_72ed._slew_with_backlash_approach()` first slews to `ra + backlash_offset_deg`, i.e. an approach point at hour angle `HA - backlash_offset_deg` (the RA offset is in coordinate degrees), then to the exact position; a target with `0 < HA < backlash_offset_deg` therefore has its approach point before the meridian and its exact point after it, and the AM3 flips pier side (up to three flips on V923 Aql, 2026-09-14, HA +0.2 to +1.5°). Add the 0.25°/min drift over the few minutes the four slews take and the dangerous window is roughly `(-1°, +backlash_offset_deg)` plus the mount's hysteresis, so the threshold should be at least `backlash_offset_deg + 1°` (2 + 1 = 3 on the 72ED). It is a separate parameter, deliberately not derived from `backlash_offset_deg`: that one is a per-device value of the hardware YAML, which a scheduler never reads (interchangeable, hardware-agnostic schedulers). Measured in degrees of **hour angle**, not of arc on the sky (`astro_math.py::hour_angle_deg()`, `LST - RA`, positive after the meridian): hour angle advances 15°/hour at every declination, which is what the RA axis sees, so the excluded window is the same 24 minutes per sidereal day for every target — an arc distance (`~|HA| × cos(dec)`) would make a near-polar target look permanently "on the meridian" and never selectable. Not covered: a target crossing the meridian during an already-running observation (the flip is decided at the slews in the first minutes; tracking through the meridian does not flip). Related, separate and not fixed: the same approach slew sends `dec + backlash_offset_deg`, which exceeds 90° for a target above declination 88° (see `TODO.md`).

`astro_math.py` (`rosace/rosace/`) is a small, dependency-free spherical-astronomy helper (Meeus' low-precision GMST formula + the standard altitude/azimuth formulas, plain `math`/`datetime`; `azimuth_deg()` is North through East, the exact inverse of `equatorial_from_horizontal_deg()`), used instead of AstroPy's `AltAz` transform (see HISTORY.md for why the AstroPy/IERS path was dropped) — accurate to a few arcminutes, orders of magnitude better than `MIN_TARGET_ALTITUDE_DEG` needs, with zero external data dependency and zero maintenance burden. If every line is either invalid, already fully consumed, or currently too low, `scheduler_data["target"] = None` (see the `target=None` contract above). On success, populates `scheduler_data["target"]` (canonical `Target`), `["queried_name"]` (the name as written in the file — may be an alias), `["program"]`, `["priority"]`, and `["exposure"]` (`ExposureConfig`, `exposure_time` taken from `program_stars` if set there, otherwise `None` — computing it from magnitude is a future chantier, not yet implemented, so `ExposureConfig.exposure_time` is `Optional`).

A missing/malformed plan file or horizon file (when `horizon_file` is declared — a declared file is mandatory, no silent fallback to "no mask"), or invalid data in `targets.db` (e.g. `program_stars.exposure_time` corrupted to `''` instead of `NULL` by an external tool) raises `SchedulerFatalError` — a dedicated exception, distinct from an ordinary exception, a subclass of `SessionFatalError` (`errors.py`). `session_runner()` treats it like an `INIT_SESSION` failure (`state.is_running = False`, session stops) instead of the usual "log and restart from SCHEDULER" retry loop, since retrying can't fix a configuration/data problem — this is the difference between `SchedulerFatalError` (stop) and any other exception from a stage (retry).

### The multi-program selector (`selector`, `plugins/program_schedulers/`)

Full design and phases: [docs/scheduler_multi_program_spec.md](docs/scheduler_multi_program_spec.md). Phases A, B1, B2 and C (the Be stars planner) are implemented; `active_scheduler: selector` switches to it, `scheduler_rosace_2026` stays the one-line fallback.

- **One planner per scientific program**, declared by the program YAML's `scheduler:` key (`name`, free-form `params`); a program is active as soon as its YAML has that key. `programs/manual_list.yaml` (the hand-written observation list) is the minimal program, required: without it the selector raises `SchedulerFatalError`. Planners live in `plugins/program_schedulers/<name>/<name>.py`, class `<PascalName>Scheduler`, resolved by `program_schedulers/__init__.py::load_planner()` — a family of its own, deliberately not one of `pipeline_loader.py`'s three sub-plugin families. Adding a program never touches `_build_registry()` or `config.py`. `blank_program/blank_program.py`'s docstring is the developer guide.
- **The exchange** (`program_schedulers/__init__.py`): `async propose(ctx: SchedulingContext) -> Candidate | None`. At most one candidate (`queried_name` resolved by the selector in `targets.db`, `program` whose YAML runs the observation, `priority` 0–4, `exposure` as today — the split into sub-exposures stays in `star_spectra_acquisition` —, `window` = `TimeWindow`, `reason`). `start_after` is the start of the science exposures — the observation is launched `overhead_minutes` earlier (`checks.launch_time()`) — and `end_before` the end of the whole observation; a candidate whose launch time is still ahead, within `lookahead_minutes`, is **booked**. Planners keep no state between calls: the history is read from `rosace.db` (`database.py::db_get_successes_for_target()`).
- **Priority levels**, "what do we lose if we wait?": 0 interrupts (not implemented: only goes first), 1 next element of a series already started (chosen by the planner — the selector knows nothing about series), 2 lost if not tonight, 3 ordinary, 4 filler.
- **Shared checks** (`program_schedulers/checks.py`): the planners use them to choose, the selector re-runs them to verify, so both apply the same rules. `estimate_duration_s()` = total exposure (same `compute_exposure_time_and_count()` and settings as `star_spectra_acquisition`) + `overhead_minutes`; `check_feasible()` returns `None` or the reason: installation floor and planner minimum altitude, local horizon (the core `horizon.py`, a bad file raising `SchedulerFatalError`), sampled every 5 minutes over the whole duration (or a series' duration passed by its planner), plus the mount's meridian rules: no start within `min_meridian_distance_deg` of the meridian, and a target east of the meridian at the start must not be tracked further than `meridian_tolerance_deg` past it by the end (`hour_angle_deg()` at start and end, a wrap through ±180° being the antimeridian, not the meridian; absent = not checked — 15° in the 72ED config (`~/.config/rosace/config.yaml`), provisional, to be checked on the AM3). `check_feasible(..., start=)` checks a booked candidate from its launch time. `check_window()` → `open`/`booked`/`refused`. `check_not_recently_failed()` (async) refuses a target that failed (SEQUENCER error) for the same program less than `failure_backoff_hours` ago (`db_get_last_failure()`) — not applied at level 1 (`backoff_applies()`): a series retries at once and its planner bounds the retries (`db_count_trailing_failures()`). Installation settings in `subplugin_params.selector`.
- **Each planner runs in its own thread with its own event loop** (`ThreadPoolExecutor` + `asyncio.run`, bounded by `planner_timeout_seconds`): a slow or blocked planner never freezes the main loop. A thread can't be killed, so a planner that timed out is skipped until its thread ends. Exception → program skipped this round; `SchedulerFatalError` → disabled until the session ends (re-raised for `manual_list`).
- **Selection**: an immediate candidate not more urgent than a booked one and ending after its launch time is dropped; lowest level first; at equal level, (a) at level 1 the program of the previous observation (read from `rosace.db`) keeps the hand, (b) `manual_list` before the others, (c) a candidate with a window before one without (closing first between two), (d) the program furthest behind its time share, (e) program name. A booked candidate is never observed early: when only booked ones remain, `target = None` and `main.py` asks again after `scheduler_retry_seconds`. `scheduler_data` keeps the usual contract and adds `proposed_by`, `estimated_duration_s`, `reason`. `main.py` is unchanged.
- **Time shares**: optional `share_percent` in a program's `scheduler` block; time used = Σ(`ended_at − created_at`) per program over 60 rolling days (`db_get_program_time_s()`), failures included; only breaks ties (d). Checked at the first call of each session: total > 100 % → `SchedulerFatalError`, < 100 % → WARNING, none → shares off. `manual_list`'s own share is ignored (its observations count for the program they execute).
- **Planners are read-only** (no write to the databases or the installation's files, no hardware), with one exception: a planner may keep its own copy of an external data file up to date under `~/.rosace/<program>/`, with a bounded network access and without ever depending on it to answer. Cadence history across nights: `database.py::db_get_last_success_per_target(program)` (last successful observation of every target, any night).
- **`be_scheduler`** (`program_schedulers/be_scheduler/`, class `BeSchedulerScheduler`, declared by `Be_stars.yaml` with `share_percent: 80`): observes the Be stars of `Be_stars` (the 1 335 BeSS Be stars down to mag 10, imported 2026-10-03, `magnitude_v` = BeSS value) brighter than `limit_magnitude` (7) as regularly as possible. Last observation = the most recent of BeSS (`Last_Obs` of Arasbeam's robot file `ObsC2A_15.txt`, every observer included — BeSS validation can take weeks) and of Rosace (`db_get_last_success_per_target`); robot lines matched to stars by their `HD n` alias or BeSS name (`targets.py::star_aliases_map()`, one query). Period = `period_days` (30), or BeSS's `Obs_Period` when shorter, but never shorter than `min_period_days` (10 in `Be_stars.yaml`, 0 = no floor by default — without it the ~20 nightly BeSS stars filled the whole night of 2026-10-12, see HISTORY.md). Level: overdue (never observed, or age ≥ period) with a BeSS period shorter than `period_days` → 2, overdue → 3, not due → 4 (filler, leaves the telescope to the other programs). Within a level: lateness (age in whole days / period) by steps of half a period, never observed first; then altitude at mid-observation; then brightness (shorter exposure); then name. A star observed successfully tonight is never proposed again. The first star of that order passing `check_not_recently_failed`, the `max_duration_minutes` guard (90; WARNING once per star and night) and `check_feasible` (with the program's optional `min_altitude_deg`) is proposed. The robot file copy (`robot_path`, `~/.rosace/be/ObsC2A_15.txt`) is downloaded again when older than `robot_max_age_hours` (12, i.e. at the first call of each night), 5 s timeout, replaced only by a valid file; a failure → WARNING, previous copy kept, retry at most every 30 min; no copy at all → ERROR once per night and Rosace's history only.
- **`random_pick`** (`program_schedulers/random_pick/`, class `RandomPickScheduler`): the simplest real planner, shared by the programs without a planner of their own — `PN` (12 planetary nebulae, 300 s per sub-exposure) and `Cataclysmic` (6 cataclysmic variables, 1 800 s), 10 % share each (with `Be_stars` 80 %: 100 %). Shuffles the program's targets and proposes the first not observed successfully tonight nor in the last `min_interval_days` (params, 0 by default; 5 in `PN.yaml`/`Cataclysmic.yaml` — then a program whose targets are all too recent proposes nothing, and its time share is not reached), not failed recently and feasible, at `priority` (params, 3 by default, so that the shares break the ties with the other programs' ordinary candidates).
- **`manual_list`** reads the file named by `subplugin_params.observation_list_path` in the configuration — the same key, and so the same file, as `scheduler_rosace_2026`: an installation setting, not a program parameter, so not in `manual_list.yaml` (CSV `Priority, Program, Star, Start_after, End_before, Series, comment`, `none` or empty = not given, the last three columns optional) on every call, so it may be edited during a session. Priority 0/2/3/4 (1 reserved). `Start_after`/`End_before` in UT, `HH:MM` (that time in the current astronomical night) or `YYYY-MM-DD HH:MM`. Same resolution and rank counting as `scheduler_rosace_2026`, except that only **successful** observations count: a failed observation never consumes its line, which is offered again once the failure backoff has elapsed. A line with a time window only counts the successes started inside its window (`db_get_successes_for_target(..., start=, end=)`), the lines without a window share the others — otherwise another line's observation of the same star would consume a windowed line. `Series: true`: first element at the line's priority, then level 1 while the night's last observation is that (program, star) and the window is open, without backoff, until `max_series_failures` (params, 3) consecutive failures; the line is done once the series is over with ≥ 1 success. Still one candidate: while a booked line waits, `manual_list` only proposes a line ending before its launch (or a more urgent one), else the booked line itself. Known limit: another program's more urgent candidate can still delay a booked manual line (cross-program filling comes later). A file problem never stops the session: ERROR in the log (repeated at DEBUG while unchanged), line or file ignored until corrected.

### Observation YAML persistence (`observation_file.py`)

Plays the same role for the observation's YAML file that `database.py` plays for SQLite: a dedicated persistence module, kept separate from both the orchestrator (`main.py`) and the pure data model (`models.py`). `create_observation_file(obs, target_dir)` fixes `obs.yaml_file` (using `obs.suggested_filename`) without writing anything; `write_observation_file(obs)` serializes the current full state (`obs.model_dump(mode="json")`) to that path — a no-op until `create_observation_file` has run. `main.py` only ever calls these two functions, the same way it calls `db_insert_session` — it never touches YAML or filesystem details directly.

### INDI hardware drivers (`hardware_indi/`) and connectivity check (`plugins/hardware_connectivity.py`)

`hardware_indi/` (`wrapper/` + `devices/`) holds the real, blocking (non-asyncio) Python classes that talk to an INDI server — one class per device type (`devices/camera.py::IndiCamera`, `devices/mount.py::IndiMount`, `devices/focuser.py::IndiFocuser`, etc.), all built on `wrapper/indi_device.py::IndiDevice` and `wrapper/indi_client.py::IndiClient`. Adapted from the PANOPTES/POCS observatory control software (see HISTORY.md) — the POCS-specific config loader and MongoDB-backed database layer have been stripped out (`wrapper/base.py` is now just a logger), since Rosace has its own config/databases. Devices sharing the same INDI server (`indi_host`/`indi_port`) share a single `IndiClient` instance under the hood (`SingletonIndiClientHolder`), whose setup is not thread-safe. **Every full connection starts from a brand-new client**: `_connect_all()` (session start and hardware test alike) first calls `indi_client.py::reset_shared_clients()`, which `disconnectServer()`s and forgets every cached client — the client's own state is not trusted, since after an INDI server restart (KStars relaunched, 2026-10-13) it received `serverDisconnected()` yet `isServerConnected()` kept answering true and it never reconnected. `disconnectServer()` only closes Rosace's own link to the server: the drivers stay connected to the hardware and the other clients (KStars/Ekos, PHD2) are untouched — unlike `disconnectDevice()`. An INDI server restart in the middle of a session is not handled (TODO.md).

Each device's class is declared in the active hardware YAML (`HARDWARE_CONFIG_PATH`, e.g. `conf/hardware_indi_simu.yaml`) via `module`/`module_dir`/`class_name` fields and loaded **dynamically** (`importlib`) rather than imported directly — this is what lets the set of devices vary freely per hardware profile (a camera here, an ASI camera there, an extra `pointing_camera` in one profile but not another) without any Python code change. Each device entry also declares a `role` field (`mount`/`camera`/`focuser`/`filter_wheel`/`spectroscope`) — an explicit string, not inferred from the class — used to pick which `hardware_indi/adapters/` class wraps it (see below); a device whose role has no registered adapter yet is still connected but simply isn't included in the session's hardware mapping.

`plugins/hardware_connectivity.py::connect_session_hardware()` is called from `INIT_SESSION` (`init_session.py`), **only when `SEQUENCER_BACKEND == "indi"`**: it reads the hardware YAML into a plain dict, dynamically loads and connects every declared `INDI_drivers` device — **for the whole session, connections are left open** — plus checks PHD2 reachability (a plain TCP connect, deliberately separate from the real `phd2/phd2_client.py::Phd2Client` used later by `pointing_72ed` below — this `INIT_SESSION` check only needs to confirm the server is listening, not perform an actual RPC handshake), each bounded by `HARDWARE_CONNECT_TIMEOUT_SECONDS` (single attempt, no retry). Because of the shared-`IndiClient` thread-safety concern above, devices are connected **one at a time** (not concurrently); PHD2, an independent plain `asyncio` TCP connection, runs concurrently with the device connects. Each blocking device connect runs in a worker thread (`asyncio.to_thread`) so it never blocks the FastAPI event loop. Any failure (timeout or exception, on any device or PHD2) raises a single aggregated `RuntimeError`, which `INIT_SESSION` lets propagate — `session_runner()` already treats an `INIT_SESSION` exception as a critical, session-cancelling failure, so no extra error handling is needed there. Known simplification: if one device fails partway through, devices already connected before it are left connected rather than explicitly rolled back — acceptable since the session is about to stop anyway, revisit if it becomes a real problem.

**Hardware test (GUI "Test" button, `POST /control/hardware-test`)**: `test_hardware(hold_seconds=3.0)` runs the same connection sequence (`_connect_all()`, shared with `connect_session_hardware()`, log lines tagged `[HW_TEST]` instead of `[INIT_SESSION]`) outside any session, stays connected 3 s, then disconnects — no unpark, no cooling, no image, no observation. It leaves the hardware as it found it: an INDI connection belongs to the driver and is shared by every client (Ekos/KStars, PHD2), so `_connect_device_sync()` reads whether each device was already connected before connecting it (`connect(connect_device=False)`, then `device.isConnected()`), and only the devices the test connected itself are disconnected; PHD2 only loses the test's own TCP connection (`Phd2Client.disconnect()`), its equipment stays connected. `_connect_phd2()` closes its TCP connection on a failure (session and test alike). Returns `{ok, connected, errors}`. `main.py`: 409 in simulation (`sequencer_backend` not `indi`), during a session, or while another test runs (`state.hardware_test_running`); while a test runs, `POST /control/start` is refused (`"Test matériel en cours — démarrage refusé"`) and a scheduled start that falls due waits for its end (`_check_control_schedule()` skips it until then). `GET /status` adds `hardware_test_running` and `hardware_test_available`. A green test means INIT_SESSION's connection step just succeeded with the same profile — not the camera cooldown, the unpark, or anything later in the night.

`connect_session_hardware()` also splits each device's YAML entry, implicitly, into two halves — chosen deliberately over adding a new hardware YAML field for every business parameter, since the whole point is that SEQUENCER sub-plugins should be able to read a value a hardware profile declares (a camera's `cooling_capability`, a focuser's `focus_range`, a spectrograph's future calibration settings...) without this module, or any orchestrator code, ever having to know that field exists. A closed, universal list (`_PLUMBING_KEYS` — `role`/`module`/`module_dir`/`class_name`/`indi_client`/`indi_name`) covers exactly what's needed to load and connect *any* device, checked for every device regardless of role (missing one raises a clear error naming it, collected the same way as a connection failure); everything else in that device's entry — whatever it is — becomes that device's **params**, extracted verbatim by `_extract_device_params()` with no field named there. Devices declared purely as placeholders (e.g. `spectroscope`'s `SpectroscopePlaceholder`, see below) still declare `indi_client`/`indi_name` even though they never use them, deliberately, so this validation never needs a per-role exception. Returned as a small `ConnectedHardware(adapters, hardware_config)`, not a bare dict — `adapters` is what becomes `Observation.hardware` (unchanged), `hardware_config` is the new parallel structure, same device-name keys, holding each device's params (see below).

### Generic device interfaces (`hardware/`) and INDI adapters (`hardware_indi/adapters/`)

`hardware/` holds backend-agnostic device contracts — one `typing.Protocol` per device role (`hardware/mount.py::Mount`, `camera.py::Camera`, `focuser.py::Focuser`, `filter_wheel.py::FilterWheel`, `spectroscope.py::Spectroscope`), plus `hardware/errors.py`'s generic exception hierarchy (`DeviceError` → `DeviceConnectionError`/`DeviceTimeoutError`/`DeviceCommandError`). SEQUENCER sub-plugins are meant to depend only on these, never on a specific backend's classes — this is what keeps the door open to a future `hardware_ascom/` (Ascom/Alpaca) without touching sub-plugin code. Each interface declares only what Rosace actually needs today, not full API coverage — e.g. `Focuser` has no `autofocus()`, since the underlying INDI focuser doesn't expose one either (autofocus is a measure-move-remeasure algorithm that belongs in the focus SEQUENCER sub-plugin, not the device layer); `Camera` covers any camera role (science, guiding — see `hardware_indi_simu.yaml`'s `science_camera`/`guiding_camera` entries) via one shared contract, not a per-role interface. Method names deliberately follow ASCOM's own published device interfaces (naming only, not philosophy — INDI's more open design is still the model followed elsewhere). `Spectroscope` is a light-source selector only (`set_light_source`/`get_light_source`, `LightSource` enum: `SKY`/`DARK`/`FLAT`/`CALIB`) — deliberately narrow, since real spectrograph control varies enormously by model; richer per-model capabilities are expected to live on that model's own device class, not on this shared contract.

`hardware_indi/adapters/` (`mount.py::MountAdapter`, `camera.py::CameraAdapter`, `focuser.py::FocuserAdapter`, `filter_wheel.py::FilterWheelAdapter`, `spectroscope.py::SpectroscopeAdapter`) are the concrete INDI implementations: each owns a device instance's whole lifecycle — `connect()`, business calls, `disconnect()` — running every blocking INDI call via `asyncio.to_thread`, so the generic interfaces stay uniformly async regardless of backend. `CameraAdapter.expose()` runs the whole blocking acquisition sequence (`prepare_shoot` → `setExpTimeSec` → `shoot_async` → `synchronize_with_image_reception` → `get_received_image`) as one unit in a single worker thread, since these must happen in strict order on the same device. Adapters translate whatever `IndiDevice`/`pyindi-client` raises into `hardware/errors.py`'s generic hierarchy. `SpectroscopeAdapter` is the odd one out here: every other adapter wraps exactly one INDI device shape (INDI standardizes mount/camera/focuser/filter-wheel control), but spectrograph control isn't standardized at all — so `SpectroscopeAdapter` itself stays generic (deliberately not type-hinted to one specific device class) and the model-specific translation lives entirely in `hardware_indi/devices/` instead, one class per spectrograph model, all sharing the same small method surface. `devices/spectroscope_placeholder.py::SpectroscopePlaceholder` — a pure in-memory stand-in (no real INDI protocol at all, `connect()`/`disconnect()` are no-ops), needed because no INDI simulator exists for a spectroscope, unlike the mount/camera/focuser simulators — is still what `hardware_indi_simu.yaml` declares with `role: spectroscope`. The 72ED profiles (`hardware_indi_72ED-LAN.yaml`/`-WIFI.yaml`) instead declare `devices/spectro_Alpy600.py::IndiSpectroAlpy600` — the real Alpy600 light-source control, driven not through any dedicated spectroscope protocol (none exists) but through the Stellarmate SM Pro powerbox's own switch vector `POWER_CHANNELS`, elements `POWER_CHANNEL_3`/`POWER_CHANNEL_4`: both channels off is `SKY`, both on is `DARK`, channel 3 alone on is `CALIB`, channel 4 alone on is `FLAT` — all four confirmed against the real instrument. `hardware_indi/devices/usis_spectroscope.py::IndiUsisSpectro` also exists (real USIS protocol, used by devices like UVEX) but is unrelated to the 72ED's Alpy module and currently unused by any hardware profile — left in place, not wired up yet.

`IndiMount.slew_to_coord_and_track()`/`slew_to_coord_and_stop()` (`hardware_indi/devices/mount.py`) let the mount say when a slew is over, but never with a plain "wait for OK" on `EQUATORIAL_EOD_COORD`: right after another command on that same property (a SYNC, or the previous slew) it still reads OK, and such a wait can return before the driver has switched it to `BUSY` — i.e. before the mount has even left (field test 2026-09-11, HISTORY.md 2026-09-12). Both methods send the coordinate with `set_coord(coord, wait=False)` then call `_wait_for_slew()` (skipped if the mount is parked, since `set_coord()` itself no-ops then): wait for `BUSY` (the mount has started, up to `SLEW_START_TIMEOUT_SECONDS`, 5 s), then for the end of `BUSY` (the mount has arrived, up to `SLEW_FINISH_TIMEOUT_SECONDS`, 60 s — the longest slew seen in the logs takes 30 s; an `ALERT` is an error), then read the position once as a consistency check (within `SLEW_POSITION_TOLERANCE_ARCMIN`, 10′ — well above real completed-slew readback noise, ~1-2″, and well below the smallest deliberate close slew, the 2° backlash-approach offset below — or an error). No `BUSY` within 5 s: the position decides — on target (already there, or a slew too short to be seen) is accepted, anywhere else is an error. Rosace never judges arrival from the position itself: an earlier version did, polling the position until within 10′, and declared the mount arrived while it was still finishing a long slew — the next command then made the driver abort it (night of 2026-09-27, HISTORY.md). `sync_to_coord()` keeps the plain OK wait (`set_coord()`'s default). A device-layer guard, transparent to every caller (`MountAdapter.slew_to()`, `slew_72ed`, `home_sync_am3`'s own homing attempts below) — none of them need to know it exists.

**Wired into SEQUENCER**, minimally — `slew.py` (backend indi) calls `obs.hardware["mount"].slew_to(...)` for real; `focus.py` (see below, in "Guiding-camera focus quality measurement") captures its own guide image and measures its sharpness. `star_spectra_acquisition.py` (backend indi) — the science acquisition sub-plugin — switches `obs.hardware["spectroscope"]` to `LightSource.SKY` first (leaves it in SKY afterward, no further action needed), then calls `obs.hardware["science_camera"].expose(...)` for each sub-exposure. Neither it nor `slew.py`/`focus.py` check for a previous step's casier before running — the orchestrator's own `try/except` already guarantees a failed pointing step never lets a later one run (see the Plugin system section above); this is also what lets `slew_72ed`/`slit_xy`/`pointing_72ed` (below) replace `slew` in a program without this sub-plugin needing to know or care which one pointed the telescope. Exposure time/count is computed by `acquisition_helpers.py::compute_exposure_time_and_count()`, which accepts *either* an explicit `scheduler_data["exposure"].exposure_time` (already known from `program_stars.exposure_time` in `targets.db` — meant to be set there only when the magnitude-based duration wouldn't do, e.g. it would saturate that particular star) *or*, when that's unset, a target magnitude (`exposure_time_mag0 * 10**(magnitude / 2.5)`). Either way, that duration (raw) is a per-sub-exposure target, not a total integration budget to divide: if `raw <= max_exposure_time`, every sub-exposure is `raw` seconds long, repeated at least `min_exposure_count` times (a bright star with a short duration still gets a proper stack, e.g. cosmic-ray rejection, instead of a single frame); if `raw > max_exposure_time`, sub-exposures are capped at `max_exposure_time` and repeated `max(min_exposure_count, ceil(raw / max_exposure_time))` times (e.g. a raw 780s at a 300s max becomes 3×300s, not one 780s exposure) — `min_exposure_count` only ever raises the count, never lowers a higher `ceil()` result. The multi-sub-exposure loop itself stays in the sub-plugin, not the helper. Each sub-exposure is captured via `acquisition_helpers.py::capture_science_image()` (a plain `expose()`-then-`writeto()` primitive, the shared foundation the DARK/BIAS capture sub-plugins also use), writing one file per sub-exposure named via `acquisition_helpers.py::build_fits_root_name("STAR", target_name=scheduler_data["queried_name"], ...)` (a shared root name across the whole series, `-1`/`-2`/... appended per file — see `build_fits_root_name()`'s own docstring for the full naming convention, also used by `capture_guide_image()` for guide images — kept as its own separate function rather than reusing `capture_science_image()`, since it still needs to stamp FITS header cards on the image between `expose()` and `writeto()`), checking `obs.stop_check()` between two sub-exposures (not during one already started on the camera — no real hardware abort here) — a check that never fires today, since a stop lets the observation finish (see the State machine section). No casier of its own — every produced filename is appended straight to the shared `sequencer_data["star_spectra_images"]` key that REDUCTION actually reads (see the "Shared, purpose-named keys" note above). `ExposureConfig` (`scheduler_data["exposure"]`) only carries that optional `exposure_time`: the number of frames is never set by the scheduler, always by `compute_exposure_time_and_count()`. No FITS header keywords are stamped on science images yet beyond what the camera driver itself writes. `Observation.hardware`/`SessionContext.hardware` (`models.py`) carry the connected adapters, keyed by device name — `Field(exclude=True)`, never persisted to the YAML dossier or the DB, since these hold live connections, not observation data. `InitSessionPlugin` populates `SessionContext.hardware`; `session_runner()` (`main.py`) copies it onto every freshly-created `Observation` (sub-plugins never see `SessionContext`); `CloseSessionPlugin` disconnects each adapter (one failure doesn't block the others). `Observation.hardware_config`/`SessionContext.hardware_config` carry each device's own params (see `connect_session_hardware()` above), same device-name keys, same lifecycle — but plain, picklable data, not live connections. Also `Field(exclude=True)` — same policy as `hardware`, but by choice rather than technical necessity: a sub-plugin that wants a specific value recorded in the observation YAML copies it explicitly into its own `sequencer_data` casier, the same way any other sub-plugin output works.

**Critical detail**: `session_runner()` clears `obs.hardware` to `{}` *before* calling `obs.model_copy(deep=True, ...)` and restores it after, wrapped in its own `try/except`. `model_copy(deep=True, update={...})` does **not** skip deep-copying fields named in `update` — it deep-copies everything first and only overwrites afterward, so deep-copying live INDI adapters raises (`TypeError: cannot pickle '_thread.lock' object` — see HISTORY.md). Post-obs stages (REDUCTION/SHARING/ARCHIVE) never touch hardware anyway, hence clearing it is safe.

A 72ED program points the telescope in three SEQUENCER steps, declared *in place of* `slew` for `SEQUENCER_BACKEND="indi"` (`Be_stars.yaml` also runs `focus`, see above, right after them): `slew_72ed` (`plugins/sequencer_plugins/slew_72ed/`), `slit_xy` and `pointing_72ed` (`plugins/sequencer_plugins/pointing_72ed/`). The two pointing steps each refine the previous one's precision, since only the astrometric measurement is precise enough to put the star exactly in the spectrograph slit; `slit_xy` sits between them so the slit is measured with the telescope in its final position, right before PHD2 puts the star on it (split out of a single `pointing_72ed` 2026-09-26, see HISTORY.md):

- **`slew_72ed` (mount-precision correction)**: slews to the target (a two-step slew every time, see below), captures a guide image, plate-solves it while recording the mount's pointing error to the `pointing_errors` DB table (`plate_solve_helper.py::solve_wcs(record_error=True, observation_id=obs.id, pier_side=...)` — `pier_side` is read from the mount just before, best effort: `"east"` = mount east of the pier, tube pointing west (hour angle > 0), the ASCOM/INDI `TELESCOPE_PIER_SIDE` convention; `None` if unreadable, never failing the pointing; the column is `NULL` on every row recorded before 2026-09-26, added to the existing database by hand rather than by a migration in code), reads the actual sky position at the spectrograph slit (`solve_result(fits_path, slit_x, slit_y)`), computes the offset between that and the aimed-at target (`SkyCoord.spherical_offsets_to()`), and derives a corrected target position (`spherical_offsets_by()`, same offset applied in reverse) — then slews there. Records `sequencer_data["slew_72ed"] = {"guide_image", "corrected_ra_deg", "corrected_dec_deg"}` — the corrected position is what `pointing_72ed` stamps into its own guide image and narrows its plate solve around. Always uses the *default* `slit_x`/`slit_y` (`slit_xy` hasn't run yet; this correction is only accurate to about an arcminute, `pointing_72ed` corrects the rest). After this step the mount no longer moves on its own — only PHD2 nudges it afterwards.
- **`slit_xy` (slit position)**: see "Slit position measurement" below. Runs with the telescope in its final position and PHD2 not yet guiding (a lamp-lit image must never be taken while PHD2 guides).
- **`pointing_72ed` (PHD2-guiding-precision refinement)**: captures a guide image at the corrected position (read from `sequencer_data["slew_72ed"]`, an explicit error if missing), starts PHD2 guiding (`obs.hardware["phd2"].start_guiding()` — auto-selects its own guide star, generally *not* the science target itself, and only returns once settled), reads which pixel PHD2 locked onto (`get_lock_position()`), plate-solves that image (this time without recording a pointing error — the mount is already corrected, this isn't a mount-accuracy measurement anymore — and with a much tighter search radius than `slew_72ed`'s, `phase2_search_radius_deg` below, since a precise position hint is already available and a tight cone directly cuts this synchronous solve's real wall-clock cost — found 2026-08-30 to be the actual source of a multi-second gap observed live between PHD2 settling and its lock position actually being corrected, see HISTORY.md), computes where the corrected target actually falls in this image's pixel space (`plate_solve_helper.py::world_to_pixel()`, the inverse of `solve_result()`) versus the slit position in force (`acquisition_helpers.py::slit_position()`: `slit_xy`'s calculated position, or the configured default — the log line of the residual says which), and nudges PHD2's lock position by that same residual pixel offset (`set_lock_position(lock_x - dx, lock_y - dy, exact=True)`) — PHD2 then drives the mount until its own guide star reaches that new lock position, dragging the whole field (target included) onto the slit with sub-pixel guiding precision, impossible to reach via the mount's own slew precision alone. A second `start_guiding()` call waits for this new settle.

Every slew of `slew_72ed` goes through `_slew_with_backlash_approach()` (module-private, not on the generic `Mount` Protocol): a preliminary slew offset by `backlash_offset_deg` (hardware YAML, under `mount:` — a mechanical trait of that specific mount unit) in both RA and DEC, then the exact slew — always approaching from the same mechanical side makes backlash reproducible instead of varying with slew direction. The guiding camera's own exposure time for these direct (non-PHD2) captures, along with `sampling_arcsec`/`slit_x`/`slit_y`, comes from `SUBPLUGIN_PARAMS["guiding"]` (`conf/config.yaml`'s `subplugin_params.guiding`) rather than the active hardware YAML: these four describe the optical alignment/plate-scale of the whole telescope+spectro+guiding-camera assembly, not a property of the guiding camera device in isolation — they stay the same across hardware profiles that differ only in how they reach the same physical instrument (e.g. `hardware_indi_72ED-LAN.yaml` vs `-WIFI.yaml`), unlike `backlash_offset_deg` above, which really is per-device (see HISTORY.md 2026-09-06). `pointing_72ed.py`, `slit_xy.py` (`slit_x`/`slit_y`, the default it measures around), `stop_phd2_guiding.py` (below) and `guiding_dark_acquisition.py` (`exposure_seconds` only) read the same `SUBPLUGIN_PARAMS["guiding"]` block. A `phd2.stop_capture()` at the very start of `slew_72ed` defensively stops any guiding left running from the previous observation (nothing else stops it explicitly) — otherwise its own corrections would fight the slews. That call and `pointing_72ed`'s first `start_guiding()` go through `run_with_guiding_recovery()` (see "Guiding-chain recovery" above); the second `start_guiding()` deliberately does not.

**Slit position measurement (`slit_xy`, `plugins/sequencer_plugins/slit_xy/`, backend `indi` only, no `_internal.py`)** — the slit's position in the guiding field can move with the telescope's flexure, and `subplugin_params.guiding.slit_y` was measured once, by eye (the 2026-09-24 measurement put it 3.2 px higher). Captures one guide image with the spectroscope on `subplugin_params.slit_xy.light_source` (`CALIB`/`FLAT`/`SKY`, never `DARK`; default `CALIB`), exposed `exposure_seconds`, after a `light_settle_seconds` pause between the spectroscope command and the exposure (`capture_guide_image()`'s `light_source`/`light_settle_seconds` parameters, `SKY`/`0` by default for every other caller), no guiding-dark subtraction (different exposure time; hot pixels are bright, harmless when looking for a dark feature), spectroscope always switched back to `SKY` afterwards, followed by the same `light_settle_seconds` pause (a lamp can keep shining for a moment after its power is cut). In every case the slit is a dark line on a brighter background: the search zone (`slit_x_area` × `slit_y_area`, total sizes centred on the default `slit_x`/`slit_y`, clipped to the frame; `none`/absent = whole width/height) has each column's median subtracted (a lamp's illumination gradient along the slit would otherwise be many times the noise), then `axes_helpers.py::find_axes(invert=True)` gives the line's centroid and angle. Only trusted when elongated (`sigma_major / sigma_minor` ≥ `MIN_ELONGATION`, 10), near-horizontal (`|angle|` ≤ `MAX_ANGLE_DEG`, 10°) and inside the zone at `slit_x`. **X stays the configured `slit_x`** (where along the slit the star should sit — the slit is tilted, so only its Y at a given column means anything); Y is the measured line's height at that column, plus `offset_y` (default 0): the slit seen against a lamp does not sit exactly where the sky's light goes through it, so the offset is measured on SKY/lamp image pairs taken seconds apart and set in the configuration (measurements in HISTORY.md). The slit can drift with the telescope not moving — the reason to measure it on every observation. In the configuration, not the hardware YAML, for the same reason as `slit_x`/`slit_y`: an optical fact of the spectro + guiding-camera assembly, identical across the LAN/WIFI profiles. The GUI's retained point includes the offset; the drawn line stays the measured slit. Same pixel convention as `slit_x`/`slit_y` (0-indexed, Y up — `find_axes()` works on plain array indices), no conversion beyond the zone's own corner offset; values rounded to 2 decimals. **Never blocking**: any failure (unusable light source, capture error, nothing found, a feature that doesn't look like the slit) logs a WARNING naming the image and the reason and leaves the default in force — except `SessionFatalError` (guiding-chain recovery), re-raised. Casier: `sequencer_data["slit_xy"] = {"status": "calculated", "slit_x", "slit_y", "angle_deg", "segment", "image"}` or `{"status": "default", "image"}` (`image` `None` if the capture itself failed). `segment` is the measured slit as `[xa, ya, xb, yb]` on the fitted line (without `offset_y`): its ends are the columns where the dark line, sampled ±`END_HALF_ROWS` rows around the line and smoothed over `END_SMOOTH_COLUMNS`, is at least `END_DEPTH_FRACTION` (half) of its deepest — a faint dark trace beyond the slit itself is left out (QHY, 2026-09-27: x = 700–1218, +0.23°); recorded since 2026-10-10, drawn by the observation summary. `acquisition_helpers.py::slit_position(obs)` is the one place that decides which slit is in force (calculated, else default — also when a program doesn't run `slit_xy`), read by `pointing_72ed` and `stop_phd2_guiding`. The image is shown on the GUI's "Guidage" panel with an overlay (see the GUI section).

`stop_phd2_guiding.py` (`plugins/sequencer_plugins/stop_phd2_guiding/`, backend `indi` only) must come after the science acquisition in a program's SEQUENCER steps, not necessarily last (`Be_stars.yaml` runs it right after `star_spectra_acquisition`, before the calibration series, which need no guiding) — nothing else stops PHD2 once guiding has started, so without this it keeps running past the whole observation and into the next one, fighting that next observation's own mount slews. Beyond the stop itself, it also captures and plate-solves one post-science guide image, purely to log where the target actually ended up relative to the slit at the end of the observation (`sequencer_data["stop_phd2_guiding"] = {"guide_image": ..., "residual_arcsec": ...}`) — deliberately never with `record_error=True`: the `pointing_errors` table only ever records the mount's own *initial* pointing error, measured right after its first slew of the night, meant for long-term polar-alignment drift detection; a plate-solve-corrected post-science position would only pollute that signal, not extend it. Because of that capture, it's no longer a bare, no-risk "stop guiding" drop-in for any program — it needs `subplugin_params.guiding` configured and `guiding_dark_acquisition` to have already run earlier in the same session (`capture_guide_image()`'s own default dark-subtraction raises otherwise); already true of every program that starts PHD2 guiding at all, since that's the same requirement its own guide-image captures already have. Right after the stop, it also writes the observation's **PHD2 guide log**: `<final name>_PHD2_GuideLog.txt` in the session directory (`file_names.final_name()`, moved there from `reduction_helpers.py` so a SEQUENCER step can use it too), under the shared key `sequencer_data["guide_log_file"]` — never blocking (no section received since the observation's `created_at` — Rosace's receipt time, `RecordedSection.received_at`, not PHD2's own start time, which the demo replays from the recording — or a write error, is a WARNING). PHD2's own GuideLog stays on the guiding computer, out of Rosace's reach, so the file is **rebuilt from PHD2's Event Monitoring events**: `phd2/guide_log.py` (the format, both ways: `GuideLogRecorder` writes, `parse_guide_log()` reads) — `Phd2Client._dispatch_event()` passes every event to its recorder: `StartGuiding` opens a section (not when one is still open: PHD2 keeps one section through `pointing_72ed`'s second `guide`), `GuideStep` → a CSV row, `StarLost` → a `DROP` row, `SettleBegin`/`Settling`/`SettleDone` → `INFO: SETTLING STATE CHANGE` lines, `LockPositionSet` → `INFO: SET LOCK POSITION`, `GuidingStopped` → `Guiding Ends at`; times local, like PHD2's. The header lines are read by RPC once guiding starts, in a background task, best effort (`get_profile`, `get_pixel_scale`, `get_current_equipment`, `get_exposure`, `get_calibration_data`, `get_algo_param_names`/`get_algo_param`, `get_lock_position`): what PHD2 cannot tell by RPC (focal length, mount position...) is left out, never invented. The first line says `[recorded by Rosace]`. `Phd2Client.guide_log_section()` returns the current or last section (`RecordedSection(started_at, text)`). A temporary diagnostic variant, `stop_phd2_guiding_diag.py`, existed alongside it from 2026-08-30 (5-shot statistics, for the Phase 2 residual investigation) until the investigation was closed and the directory deleted 2026-09-15 (see HISTORY.md).

`home_sync_am3.py` (`plugins/sequencer_plugins/home_sync_am3/`, backend `indi` only) re-homes the AM3 mount once per session, before the first real pointing — not before every observation, since re-homing is comparatively slow and the mount is expected to hold its position for the rest of a session that stays connected throughout. Declared via `hardware_indi_72ED-WIFI.yaml`/`-LAN.yaml`'s own `sequencer_prefix: [guiding_dark_acquisition, home_sync_am3]` (see the Plugin system section above and `guiding_dark_acquisition` above — its median dark must exist before this step's own guide captures), not inside `Be_stars.yaml` itself — re-homing is an equipment concern (specific to this one mount), not a scientific-program one, so a program YAML never mentions it. `hardware_indi_simu.yaml` deliberately excludes `home_sync_am3` from its own `sequencer_prefix`: the INDI Telescope Simulator isn't an AM3, and syncing it risks activating its own `ALIGNMENT_SUBSYSTEM_ACTIVE` model (see HISTORY.md, 2026-08-26) — this step simply never runs when testing against the simulator, instead of needing a special case anywhere in the code. It still declares `sequencer_prefix: [guiding_dark_acquisition]` on its own (added 2026-09-20) — `pointing_72ed`'s guide captures need that casier to exist regardless of hardware profile, and the simulator's `SpectroscopePlaceholder` (`obstructs_light: false`) already makes `guiding_dark_acquisition` take its harmless "synthetic" origin (an all-zero placeholder, no real capture) here, so including it carries none of `home_sync_am3`'s risk.

It parks then unparks the mount (`mount.park()`, `mount.unpark()`) for a mechanical zero-position reference, then (unless `SYNC_HOME_VIA_PLATE_SOLVE`, a one-line kill switch, is flipped to `False` and the server restarted) attempts a **measured** sync rather than a computed one — closing the gap between the mount's mechanical zero and the real sky without ever trusting a value that hasn't itself been verified against the sky (see HISTORY.md, 2026-08-26/2026-09-11: a sync to a theoretically-computed position, RA=local-sidereal-time/DEC=+90, was found on the real AM3 to leave a consistent ~25′ residual — no better than `unpark()` alone, since both derive from the same time+site math — versus 1-3′ for a measured one). Up to `MAX_HOMING_ATTEMPTS` (7) homing attempts, each: picks a fresh random point at a fixed altitude (`HOMING_ALTITUDE_DEG`, 65°) and a random azimuth in `[HOMING_AZIMUTH_MIN_DEG, HOMING_AZIMUTH_MAX_DEG]` (5°-175° — the whole eastern half of the sky, never within 5° of either meridian crossing, keeping every attempt on the same side of the pier and avoiding a mid-homing flip); converts it to RA/Dec via `astro_math.py::equatorial_from_horizontal_deg()` (the same no-IERS pure-trigonometry family as the scheduler's own altitude check — not AstroPy's `AltAz`, for the same reason); slews there, captures a guide image, and plate-solves it. The first attempt that solves is synced to (`mount.sync_to_coordinates()`, the measured position) and the loop stops; a failed attempt (slew or plate-solve) is logged at WARNING and retried at a new random point — `obs.stop_check()` is checked between attempts — and running out of attempts falls back to park/unpark only, exactly as if the kill switch were off: this step must never turn into a session-blocking failure over a homing sync it couldn't get. Every slew here already goes through `IndiMount`'s own slew wait (`_wait_for_slew()`, see below) — found necessary by the same field test that motivated this retry loop in the first place (see HISTORY.md, 2026-09-11/2026-09-12): a slew issued immediately after a sync can silently return before the mount has actually moved.

Casier (unlike the computed-sync version this replaced, which had none — a measured sync genuinely produces data worth recording): `sequencer_data["home_sync_am3"] = {"method": "measured_sync"|"park_unpark_only", "attempts": <int>, "guide_image": <filename>|None, "synced_ra": <float>|None, "synced_dec": <float>|None}` — only ever set on the one observation where homing actually ran (every later observation in the same session returns early, before reaching it). Tracked via a module-level "last session_id already homed" value: cheap, in-process only (lost on a server restart, same as `main.py`'s own `state` singleton — but *not* lost across a plain stop/restart of the session within the same server process, since sub-plugin modules are imported once via `importlib.import_module()` and then reused from `sys.modules`, never re-executed). Reset implicitly whenever `session_id` changes, rather than through any explicit call from `INIT_SESSION`, so `INIT_SESSION` never needs to know this sub-plugin — or the AM3 — exists.

`INIT_SESSION` also unparks the mount generically, right after connecting hardware (`plugins/init_session.py`, `sequencer_backend=indi` only) — symmetric to `CLOSE_SESSION`'s own generic `park()` (below), and deliberately not gated behind `sequencer_prefix`/`home_sync_am3`: a mount left parked by a previous session's close (or never unparked at all) can't be slewed at all until this runs (`IndiMount.set_coord()` silently no-ops, not raises, on a parked mount) — a baseline precondition every hardware profile needs regardless of which mount it declares, not an AM3-specific concern. Found 2026-09-08: before this existed, moving `home_sync_am3` out of `Be_stars.yaml` (above) meant the simulator profile — which declares no `sequencer_prefix` — never unparked its mount either, since `home_sync_am3`'s own `unpark()` call had implicitly been serving both roles at once. On the real AM3, this generic unpark is immediately followed by `home_sync_am3`'s own `park()`/`unpark()`/sync sequence — redundant but harmless, since `unpark()` alone is a fast state change, not physical motion; the real, slow re-homing motion still happens exactly once, inside `home_sync_am3`.

Not yet done: no `hardware_ascom/` (no Windows environment to validate against yet); no real Alpy/Stellarmate device class beyond the Alpy600 (`SpectroscopePlaceholder` stands in on the simulator profile). DARK/BIAS/CALIB/FLAT acquisition are all done (see below) — but no native REDUCTION step consumes their output yet (see "Native reduction chain").

### Science camera temperature and the dark-frame library (`dark_acquisition`, `bias_acquisition`, `calib_acquisition`, `flat_acquisition`, `plugins/camera_cooldown.py`)

Every DARK frame must come from the *same* science camera used for the observation, at the *same* sensor temperature as the science images — but a full DARK series is slow to shoot, so a reusable, temperature-bucketed library (`DARK_LIBRARY_DIR`) avoids reshooting one every observation when a compatible series already exists.

**Camera temperature control** (`hardware/camera.py::Camera`): `set_temperature`/`get_temperature`/`get_frame_size`/`set_cooling_on`/`set_cooling_off` (`get_frame_size` returning `(NAXIS1, NAXIS2)` of the camera's **currently configured** `CCD_FRAME`/ROI — read live via `IndiCamera.get_roi()`, not INDI's `CCD_INFO`/`CCD_MAX_X`/`CCD_MAX_Y`, which only reports the sensor's maximum capability and is otherwise unused by Rosace. Deliberately not "the full sensor resolution": a sub-framed (windowed) acquisition is a legitimate, deliberate configuration, and the four acquisition sub-plugins below only ever need "whatever size a new exposure will actually come out as right now," not "the sensor's max." Found the hard way, 2026-09 — see HISTORY.md: a stuck `CCD_FRAME` sub-window left over from an external tool made every real exposure smaller than `CCD_INFO`'s reported max, permanently breaking the dark/bias/calib/flat reuse check below until the mismatch was diagnosed and `get_sensor_size()` was replaced with this live-ROI query), with matching `CameraAdapter` methods (same `asyncio.to_thread` + `DeviceCommandError` pattern as `expose()`). The cooler on/off switch (INDI's `CCD_COOLER`) is a separate property from the temperature setpoint (`CCD_TEMPERATURE`) on many cameras — the setpoint alone has no physical effect until the cooler is actually switched on (see HISTORY.md). **Ambient temperature** comes from the focuser's own probe — `hardware/focuser.py::Focuser.get_temperature()`, backed by `IndiFocuser.get_temperature()` reading INDI's `FOCUS_TEMPERATURE`/`TEMPERATURE` property. This is an explicit, user-confirmed hypothesis, **not yet validated against the real 72ED focuser** — if that focuser turns out not to expose a temperature probe, an alternative ambient-temperature source will be needed.

**Two distinct responsibilities in `plugins/camera_cooldown.py`**, both `sequencer_backend=indi` only:

- `activate_cooling_for_every_camera()` / `deactivate_cooling_for_every_camera()` — generic, apply to **every** connected camera-role device whose hardware YAML entry declares `cooling: true`, not just the science camera (a guiding or pointing camera can independently have its own cooler). No explicit role check needed: only camera-role devices ever declare a `cooling` field at all, so iterating `hardware_config.items()` and checking `.get("cooling")` naturally filters to the right devices. Called once each, symmetrically: `activate_...` from `InitSessionPlugin` right after `connect_session_hardware()` (failures propagate — same posture as connectivity itself); `deactivate_...` from `CloseSessionPlugin`, **before** the device-disconnect loop (the cooler-off command needs a still-live connection) — each device's failure is caught and logged, not raised, same "one failure doesn't block the others" posture as the disconnect loop right after it.
- `cool_science_camera_to_target()` — specific to the science camera only, and assumes its cooler is already on (`activate_cooling_for_every_camera()` ran first): only when the active hardware profile's `science_camera` entry additionally declares `cooling: true` (checked a second time, specifically for this camera, since only it needs a precise target — a guiding camera's cooler is just switched on, never given a computed setpoint): reads ambient temperature from the focuser, computes the session's fixed target sensor temperature (`camera_cooldown.py::compute_camera_target_temperature()` — 80% of the camera's `cooling_capability` device param as a margin below ambient, rounded **up** to the next multiple of 5 (`TARGET_TEMPERATURE_STEP_C`) so darks bucket cleanly — the dark library's bucket step (`dark_library_helpers.py::DARK_LIBRARY_TEMP_STEP_C`) is the same 5 °C, a convention kept equal on both sides, with no import between them — e.g. ambient 15°C, capability -30°C → delta 24°C → raw -9°C → target -5°C), also clamped to never come within `MIN_COOLING_MARGIN_DEG_C` (5°C, a fixed module constant) of ambient — a weak enough `cooling_capability` could otherwise let the naive rounded-up target land at or above ambient itself, which a cooling-only camera can never reach (see HISTORY.md); when the naive target doesn't leave that margin, the next colder multiple of 5 is used instead. Commands `set_temperature()`, then polls `get_temperature()` (every 5s, logging the current reading each time so a long cooldown is visible in progress rather than silent until it either reaches target or times out) until within the camera's own `temperature_tolerance_deg_c` device param, or `CAMERA_COOLDOWN_TIMEOUT_SECONDS` elapses (fatal — `INIT_SESSION` lets the exception propagate exactly like an unreachable INDI device, session does not start; no automatic best-effort fallback), or `ctx.stop_check()` (see above) becomes true (a manual stop simply interrupts the wait, not treated as a failure). It returns `(ambient_temp_c, target_temp_c)`; `INIT_SESSION` stores only the target, as `SessionContext.session_data["camera_target_temperature_deg_c"]` — the start-of-night ambient was only an input to that computation and is just logged (the per-observation ambient is `measurements["ambient_temp_c"]`). `session_data` is a generic dict of session-wide values: `session_runner()` copies it onto every freshly-created `Observation` without reading it (same mechanical copy as `hardware`/`hardware_config`, but **not** `exclude=True`: plain descriptive facts worth persisting in the observation YAML — same top-level placement as `program_file`/`program_steps`, session-wide data that isn't any one stage's casier), so a new session-wide value never needs a `models.py`/`main.py` change.

**`dark_acquisition`** (`plugins/sequencer_plugins/dark_acquisition/`, backend `indi` only, no `_internal.py`) resolves a usable DARK series for the observation, trying three origins in order, cheapest first, and records which one it used:

`dark_library_helpers.py::ensure_dark_library_structure(library_dir)` pre-creates `DARK_LIBRARY_DIR` and one empty subdirectory per temperature bucket, from `DARK_LIBRARY_MIN_TEMP_C` to `DARK_LIBRARY_MAX_TEMP_C` (step `DARK_LIBRARY_TEMP_STEP_C` — module-level constants, `-20`/`0`/`5` by default) — a fixed range in code, deliberately not a `conf/config.yaml` key: a few extra empty directories cost nothing, so a wide-enough fixed range removes the need for a config knob entirely. Their only purpose is to show the observer where to transfer darks by hand: a missing bucket directory is simply "nothing found" for the lookup below. Called by `dark_acquisition` at the start of every execution (before 2026-10-04, by `main.py`'s `lifespan()` at server startup — moved so the orchestrator knows nothing of the library, see HISTORY.md), using `temperature_bucket_dirname()` — the same function `dark_acquisition` itself calls to look a bucket up, so the two can never name a bucket differently. `mkdir(..., exist_ok=True)` makes every call idempotent and side-effect-free on a directory that already has darks in it (from a manual library transfer) — on a fresh installation the directories appear at the first run of `dark_acquisition`.

1. **`current_session`** — a usable series already sits in this session's own directory (e.g. shot for an earlier observation tonight).
2. **`library`** — a usable series exists in `DARK_LIBRARY_DIR / <temperature bucket>` (`dark_library_helpers.py::temperature_bucket_dirname()` — e.g. `TempMinus5degrees`, `Temp0degrees`, `TempPlus5degrees`; never a leading `-` in a path segment), copied into the session directory before use (every session image must live there, per the on-disk layout above) — **never the other way around**: no dark is ever written into the library by this codebase (only its empty bucket directories are created, see above), only a manual transfer by the observer puts darks there.
3. **`camera`** — neither of the above: switches the spectroscope to `LightSource.DARK` and shoots a fresh `DARK_COUNT`-frame series with the science camera, exposure `MAX_EXPOSURE_TIME_SECONDS`, same `capture_science_image()`/`build_fits_root_name()`/`obs.stop_check()`-between-sub-exposures pattern as `star_spectra_acquisition.py`.

"Usable" (`dark_library_helpers.py::find_usable_frame_series()`, one implementation shared by every lookup below — DARK's three origins and BIAS's two — so the matching rule can never silently diverge between them) means: the **most recent series** (files sharing one root name, minus the trailing `-N` index; sorted by the capture timestamp in that root) with at least `count_required` files of the given `image_type` (`"DARK"`/`"BIAS"`) — every series judged on its own, so an older one cut short by a stop request or shot at another frame size is skipped instead of hiding every newer usable series (the old "oldest N files" rule made the night of 2026-09-27 reshoot its darks/bias/flats on every observation, see HISTORY.md) — whose filenames encode a temperature (the same `_{temp}deg_` token `build_fits_root_name()` already writes) within `TEMPERATURE_TOLERANCE_DEG_C` (2°C, a fixed module constant) of the target — not an exact match: a session restart can recompute a slightly different target temperature, and without this tolerance an otherwise perfectly usable same-night series would be rejected and reshot for no real reason. The temperature is parsed back out of the filename (regex, not a substring check) precisely to compare it numerically against the tolerance — there is no temperature card in the FITS header to fall back on. The first file's FITS header (read alone, never the pixel data) must also report `NAXIS1`/`NAXIS2` matching the camera's own `get_frame_size()` (its currently configured `CCD_FRAME`, not the sensor's max — see above) and an `EXPTIME` at least the required exposure time minus `EXPOSURE_TIME_TOLERANCE_SECONDS` (1s, same reasoning — a real camera driver doesn't guarantee the exact requested duration to the millisecond). A longer exposure is still accepted outright. Deliberately reads `EXPTIME` from the FITS header rather than parsing it back out of the filename — `build_fits_root_name()`'s own docstring already marks that field human-readable only, not meant to be machine-parsed. The origin found is recorded both in the log and in the sub-plugin's own casier — `sequencer_data["dark_acquisition"] = {"origin": ...}` — and the series' filenames under the shared `sequencer_data["dark_images"]` key (see "Shared, purpose-named keys" above). The log itself never lists every filename — one line states the series shape (`Origin={origin}, series of {count}x{exposure}s at {temp}deg`), a second gives `dark_library_helpers.py::summarize_series_root_name()`'s one-name stand-in for the whole series (the first file's name with its trailing per-file index replaced by `-xxx`, e.g. `DARK_-15deg_5x300s_..._-xxx.fits`) — same two-line shape for `bias_acquisition` below.

Never re-sets or re-checks the camera's temperature itself — trusts the once-per-session cooldown above and reads `obs.session_data["camera_target_temperature_deg_c"]` directly, which is also why the reference frame size comes from the camera's own live `get_frame_size()` rather than an already-acquired science image: this step's position in a program's `sequencer` list relative to `star_spectra_acquisition` doesn't matter. Wired into `Be_stars.yaml` (the real-hardware program), positioned *before* `spectro_light_source_to_sky` — since the `camera` origin leaves the spectroscope on `DARK`, it must run before the step that resets it to `SKY`, not after. Deliberately **not** added to `demo.yaml`, which is backend-agnostic (`internal`/`indi`) by design; `dark_acquisition` has no `_internal.py` counterpart.

**`bias_acquisition`** (`plugins/sequencer_plugins/bias_acquisition/`, same naming reasoning as `dark_acquisition` — the `_acquisition` suffix keeps capture steps apart from reduction steps) follows the identical shape with only two origins, no library — a BIAS series is fast enough that in practice it only ever needs remaking once, for the session's first observation: `current_session` (reused from the session directory) or `camera` (freshly shot, `BIAS_COUNT` frames at `BIAS_EXPOSURE_TIME_SECONDS`). The `camera` origin also switches the spectroscope to `LightSource.DARK` — there is no dedicated `BIAS` value on `hardware/spectroscope.py`'s `LightSource` enum, since a bias needs the exact same "no light reaches the sensor" state as a dark, just a zero-length exposure. Casier: `sequencer_data["bias_acquisition"] = {"origin": ...}`; filenames under the shared `sequencer_data["bias_images"]`. Wired into `Be_stars.yaml` right after `dark_acquisition`, same before-the-`SKY`-reset positioning and same `demo.yaml` exclusion.

**`calib_acquisition`** (`plugins/sequencer_plugins/calib_acquisition/`, same naming reasoning as `dark_acquisition`/`bias_acquisition`) also follows the same two-origin shape (`current_session`/`camera`, no library at all — simpler than DARK, which does have one) but with a fundamentally different staleness criterion: **age**, not temperature. A CALIB image is a science-camera exposure of a calibration lamp — its flux dominates any dark-current concern, so this sub-plugin never reads or requires the session's `camera_target_temperature_deg_c`, unlike DARK/BIAS. `current_session` is only accepted if a usable series already sits in the session directory *and* its capture timestamp (parsed from the filename, same convention as DARK/BIAS's temperature token) is younger than `max_age_hours` (`subplugin_params.calib_acquisition`, `conf/config.yaml`) — e.g. `max_age_hours: 1` forces a reshoot roughly every hour, `max_age_hours: 24` reuses one series for the whole night. When the session directory holds more than one batch (an earlier one gone stale, reshot since), only the single most recent batch is ever considered — an older stale batch must never be picked over a fresher one sitting right next to it (`_find_usable_calib_series()`'s own docstring). `camera` (otherwise) switches the spectroscope to `LightSource.CALIB` and shoots a fresh `CALIB_COUNT`-frame series at `CALIB_EXPOSURE_TIME_SECONDS`. Casier: `sequencer_data["calib_acquisition"] = {"origin": ...}`; filenames under the shared `sequencer_data["calib_images"]`. Wired into `Be_stars.yaml` right after `bias_acquisition`, same before-the-`SKY`-reset positioning and same `demo.yaml` exclusion.

**`flat_acquisition`** (`plugins/sequencer_plugins/flat_acquisition/`, same naming reasoning as the other three) is the simplest of the four: same `current_session`/`camera` two-origin shape, no library, but **no staleness check at all** — neither temperature (DARK/BIAS) nor age (CALIB). Flat-field correction is about optical vignetting/sensor uniformity, not sensor temperature or lamp drift, so once a usable `FLAT_COUNT`-frame series exists anywhere in the session directory it's reused for the rest of that session, indefinitely — shot at most once per session. `_find_usable_flat_series()` picks its series with the same `dark_library_helpers.py::pick_most_recent_usable_series()` as DARK/BIAS (most recent complete series) and still checks sensor size and `EXPTIME` (same `EXPOSURE_TIME_TOLERANCE_SECONDS` tolerance the DARK/BIAS/CALIB checks use), just no temperature or age filter. Like `calib_acquisition`, never reads or requires the session's `camera_target_temperature_deg_c`. `camera` (otherwise) switches the spectroscope to `LightSource.FLAT` and shoots a fresh series at `FLAT_EXPOSURE_TIME_SECONDS`. Casier: `sequencer_data["flat_acquisition"] = {"origin": ...}`; filenames under the shared `sequencer_data["flat_images"]`. Wired into `Be_stars.yaml` right after `calib_acquisition`, same before-the-`SKY`-reset positioning and same `demo.yaml` exclusion.

### Guiding-camera dark subtraction (`guiding_dark_acquisition`, `capture_guide_image()`)

Found 2026-09-05: the guiding camera carries several fixed hot/defective
pixels, present at near-identical values in every exposure regardless of
where the telescope is pointed (confirmed by comparing the same pixel
coordinates across completely unrelated fields the same night). These land
among the brightest "sources" `solve-field`'s extractor ranks and tries to
match first, and were found to be the actual cause of most of one night's
plate-solve timeouts in `pointing_72ed`/the now-deleted `stop_phd2_guiding_diag` — see
HISTORY.md for the investigation. Same family reasoning as the science
camera's DARK/BIAS/CALIB/FLAT acquisition above, applied to the guiding
camera instead.

**`guiding_dark_acquisition`** (`plugins/sequencer_plugins/guiding_dark_acquisition/`,
backend `indi` only, no `_internal.py`) resolves a usable guiding-camera
dark **median** for the session, same `current_session`/`camera`
two-origin shape as `flat_acquisition` — no staleness check at all: the
guiding camera is uncooled (the 72ED profile `hardware_indi_72ED-WIFI.yaml`'s
`guiding_camera.cooling: FALSE`), so there's no temperature to bucket, and
the fixed defects this exists to remove don't drift meaningfully within
one session. `current_session` reuses an existing
`GUIDINGDARK_*_median.fits` file already sitting in the session directory;
`camera` otherwise switches the spectroscope to `LightSource.DARK`, shoots
a fresh `GUIDING_DARK_COUNT`-frame series (`subplugin_params.guiding_dark_acquisition.count`,
default 7) with the guiding camera at
`subplugin_params.guiding.exposure_seconds` (the same duration every real
guide image uses — deliberately not a separate config value, so the dark's
exposure time can never drift out of sync with the images it corrects),
and median-combines them (plain per-pixel `numpy.median`,
computed in `float64` then cast back to the sensor's own dtype) into one
file. A third origin, **`synthetic`** (added 2026-09-08): when the active
hardware profile's spectroscope entry declares `obstructs_light: false`
(`hardware_indi_simu.yaml`'s `SpectroscopePlaceholder` — its own
`set_light_source()` never physically blocks light, so a "DARK" shot there
would just be another star exposure, not a real dark), writes a single
all-zero frame matching the guiding camera's current frame size instead of
shooting anything — subtracting an all-zero array is a true no-op, so
every downstream guide image comes out exactly as if no correction had
ever been requested, without `capture_guide_image()` or any of its callers
needing to know this equipment can't produce a real dark at all. Read the
same way as any other device param (`obs.hardware_config["spectroscope"]`)
— absent (defaults `true`) on every real spectroscope profile, so this
never changes behavior on real hardware. Casier:
`sequencer_data["guiding_dark_acquisition"] = {"origin":
"current_session"|"camera"|"synthetic", "dark_files": [...raw frames,
empty on reuse or synthetic...], "median_dark_file": "<combined or
synthetic filename>"}`. Declared via the active hardware profile's own
`sequencer_prefix: [guiding_dark_acquisition, home_sync_am3]` (72ED
profiles), ahead of `home_sync_am3` rather than inside `Be_stars.yaml`
itself (moved there 2026-09-12, see HISTORY.md) — `home_sync_am3`'s own
measured-sync homing (see below) captures and plate-solves guide images
too, so a usable dark median must already exist before it runs, same
requirement as any other guide-image capture. Deliberately **not** added
to `demo.yaml` (backend-agnostic, no real guiding camera to shoot darks
with).

Deliberately its own sub-plugin rather than folded into
`capture_guide_image()` itself (considered and rejected, see HISTORY.md):
keeps the acquisition visible as its own step in the GUI's live progress
and the orchestrator's own per-step logging, keeps it independently
testable, and keeps `acquisition_helpers.py` a plain-functions module with
no casier of its own, consistent with every other sub-plugin in this
codebase.

**`capture_guide_image()`** (`acquisition_helpers.py`) is where the actual
correction happens, consumed by every guide-image caller
(`slew_72ed.py`, `pointing_72ed.py`, `stop_phd2_guiding.py`) with no changes needed on
their side. It always writes the untouched raw exposure first — named
`build_fits_root_name("GUIDING", ...)` with `RAW_` inserted right after
`GUIDING_` (e.g. `GUIDING_RAW_Vega_10s_....fits` alongside
`GUIDING_Vega_10s_....fits`) — never touched again afterward. A new
`subtract_dark: bool = True` parameter then controls what else happens:
`True` (the default, matching every real caller's actual need) reads
`sequencer_data["guiding_dark_acquisition"]["median_dark_file"]`, subtracts
it from the raw data (clipped to `>= 0`, cast back to the sensor's dtype),
and writes that as the plain `GUIDING_...` file — the one every downstream
plate-solve call already worked from before this raw/corrected split
existed, so `solve_wcs()` and its callers needed zero changes. Raises
`RuntimeError` if `guiding_dark_acquisition` hasn't run yet — no silent
fallback that skips the correction. `subtract_dark=False` skips the dark
lookup and the second file entirely (a byte-identical "corrected" copy
next to the raw one would be pure waste) and returns the raw path instead.
`image_to_gui` (unchanged behavior) writes whichever file the call
actually returns to the GUI's live "Guidage" panel.

### Guiding-camera focus quality measurement (`focus`)

`focus.py` (`plugins/sequencer_plugins/focus/`, `indi` backend only, no
`_internal.py`) runs on **every** observation (unlike
`guiding_dark_acquisition`/`home_sync_am3`, which run once per session),
right after `pointing_72ed` in a program's own `sequencer:` list — so it
measures the actual guide star PHD2 is locked onto for that specific
observation, not an arbitrary pre-slew field. It captures its own guide
image (`capture_guide_image()`, same shared `subplugin_params.guiding.
exposure_seconds` every other guiding capture uses, `image_to_gui=False`,
then published on the GUI's "Guidage" panel by `focus` itself, before the
measurement, with its search window as overlay — see "Live image
preview" below), restricts the measurement to a
square window centered on the frame, sized as a fraction of the guiding
camera's **smaller** frame dimension (`subplugin_params.focus.
window_fraction` — a per-instrument fact, like `backlash_offset_deg`: how
far off-axis the optics stay clean before coma/field curvature degrades
the PSF varies with the actual guiding optics; the smaller dimension is
used rather than always the height, so the window still fits a
portrait-oriented sensor, should one ever be used), detects stars with
`photutils.detection.DAOStarFinder`, and rejects a candidate for any of
three reasons before it's trusted to contribute: non-round shape (hot
pixels, elongated "potato-shaped" sources, satellite trails —
`sharpness`/`roundness` filters — a check on shape, not position, so it
can't substitute for the window above: a star blurred by off-axis field
curvature is still round, just soft, which is exactly what this
sub-plugin needs to measure, not reject), saturation (peak ADU at or
above the sensor's ceiling, which biases a Gaussian fit's width upward),
or SNR below a fixed minimum (a raw peak-pixel statistic on the
uncombined image, deliberately kept distinct from — and looser than —
`DAOStarFinder`'s own convolved-domain detection threshold, so the two
don't duplicate the same rejection at two different, uncoordinated
strictness levels). At most 25 survivors (brightest first) are each
fitted with a 2D Gaussian (`astropy.modeling`) for their own FWHM; the
mean FWHM, the star count, and the weakest SNR among the kept sample are
logged at INFO (a WARNING if no star survived every filter). DEBUG adds a
funnel view of the same run — candidate count straight out of detection
(before shape filtering), count after shape filtering, then how many of
those were rejected for saturation, low SNR, or a failed fit — so a bad
night can be diagnosed from the log alone instead of re-deriving where it
lost its stars by hand.

Found 2026-09-20 while diagnosing a night's worth of plate-solve failures
traced to a defocused guiding camera (no way to measure this existed at
all); retuned 2026-09-22 after a full night (2026-09-20/21) came back
with zero usable measurements out of eleven observations — the
shape/SNR filters, tuned against clean simulator data, turned out to
reject exactly the broadened, less-peaked PSFs a real defocus produces,
i.e. the one thing this sub-plugin exists to measure (see HISTORY.md).
`window_fraction` is the one parameter now read from `subplugin_params`
— the rest (`SATURATION_ADU`, `MIN_SNR`, `MAX_STARS`, `SHARPNESS_RANGE`,
`ROUNDNESS_MAX_ABS`, `DETECTION_SIGMA`, `FWHM_KERNEL_PX`, `CUTOUT_HALF`)
stay hardcoded module constants for now — still diagnostic-stage tuning
knobs rather than confirmed values, `SATURATION_ADU`/`FWHM_KERNEL_PX`
being the two most likely future candidates for promotion to a
per-instrument parameter (both describe the physical sensor/optics, same
reasoning as `window_fraction`), not done since neither has been shown to
actually need to vary. Still no casier, no threshold-based rejection or
alert, no autofocus loop — this sub-plugin measures, it doesn't adjust
anything.

Replaces a much older `focus` placeholder (science-camera autofocus,
`sleep(1)`, never implemented, not used by any real program) — for this
instrument (Alpy 600 + 72ED), there is no meaningful science-camera-side
focus concept at all, so the project keeps a single `focus` sub-plugin
rather than two differently-named ones.

### Native reduction chain (`Be_stars.yaml`, in progress)

The native REDUCTION chain turns the raw frames into a calibrated, cleaned 1D spectrum: a 1D FITS carrying every keyword the BeSS specification requires, then PNG/PDF/SVG plots. One simple operation per sub-plugin, so each one is easy to explain, test and reuse. Declared in full by `Be_stars.yaml` only: `All_stars`, `Cataclysmic` and `PN` keep `calculate_flux` + `export_demetra`, and `bright_stars`, `nova_monitoring`, `demo` and the Docker demo programs declare `reduction: []` (the native steps need real, fully corrected frames; demo frames are empty placeholders). Every step is implemented (placeholders — `await asyncio.sleep(1)`, casier `{"status": "placeholder"}` — were used while the chain was built, so it ran and showed in the GUI from the start); each is described below.

In order: `master_bias`, `master_dark`, `master_flat` (masters, min/max-rejected mean), `preproc_target` / `preproc_calib` (science frames / calibration-lamp frames corrected with the masters), `tilt` (measured on the target, removed from target **and** lamp by a vertical shift per column — not a rotation), `smile` (measured on the lamp, removed from lamp **and** target by a horizontal shift per row), `extract` (window sum around the trace, sky subtracted column by column), `stack` (plain sum of the target spectra, and of the lamp spectra — not shifted, their position comes from the slit; a spectrum below 30 % of the brightest one's flux is rejected), `dispersion_law` (pixel → wavelength law of the stacked lamp spectrum, reused for the whole lamp series), `snr` (signal-to-noise ratio of the stacked target spectrum, per wavelength zone, never blocking), `guiding_stats` (guiding RMS and largest error from the PHD2 guide log, never blocking), `lambda_calibration` (law applied to the stacked target and lamp spectra, resampled to a constant wavelength step by overlap redistribution; `DISPLAY_NAME` "Calib"), `response` (division by the instrumental response), `scaling` (division by the mean level of a wavelength zone, which becomes 1 — not a normalization to the continuum, hence the name), `crop` (wavelength bounds, no resampling), `write_spectrum` (final FITS with the BeSS keywords), `plot_spectrum` (PNG/PDF/SVG of the final spectrum), `fripon_image` (the FRIPON all-sky image of the observation, target marked, never blocking; `DISPLAY_NAME` "FRIPON", see "FRIPON sky image" below), `wide_field_image` (the pointing camera's wide-field image, plate-solved, target marked, never blocking; `DISPLAY_NAME` "Grand champ", see "Wide-field image" below), `summary` (few-page PDF of the whole observation), `bess_validation` (queues the final spectrum for the observer's validation, see "BeSS validation" below; `DISPLAY_NAME` "Valid."), then `export_demetra`. `tilt` and `smile` are one step each on purpose: each measures its correction on one image and applies it to every image that needs it, so target and lamp always get the same correction.

Rules agreed for the real implementations (2026-10-06):
- **Inputs are found by shared, purpose-named keys** (like `star_spectra_images`), looked up in any casier: what matters is that the files are found under the agreed name. The program is responsible for producing consistent names. A missing input is an explicit error that stops the reduction.
- **The file name decides reuse, never the date**: a master whose name matches its source series, or a dispersion law named after its lamp series (e.g. `calib_<series>` → `calib_<series>_dispersion_law`), is reused instead of recomputed. Masters are therefore computed once per session.
- **The lamp series is the one declared in the observation**, not searched by time.
- **Where reduction parameters live**: those that depend on the instrument — the lamp's reference lines, the instrumental response, the scaling zone, the crop bounds (what the instrument can cover) — in the configuration (`subplugin_params`, decided 2026-10-10, replacing the 2026-10-06 "program YAML" rule for these); a parameter genuinely specific to one scientific program in that program's YAML. Observatory-wide BeSS fields (observatory, site...) in the observatory's config, program-specific ones in the program YAML.
- **A failing step stops the reduction**, with an explicit log message — except a non-critical step (`calculate_flux`).
- **The dark keeps its bias** (checked against Demetra).
- **Never any telluric or heliocentric correction** (BeSS requires them not to be applied).
- **Intermediate files** go to one directory per observation; deleting it loses nothing (everything can be rebuilt from the raw frames). Keeping them is meant to become an option, purged at ARCHIVE or CLOSE (TODO.md).

**Shared functions**: `plugins/reduction_plugins/reduction_helpers.py` (plain functions like `axes_helpers.py`), the one helper module of the native chain — shared-input lookup, float image writing, masters, intermediate directory, preprocessing, column and row shifts (`shift_columns()`, `shift_rows()`) per-frame transforms (`transform_frames()`, which applies a function to each frame and writes `<name>_<suffix>.fits` to the intermediate directory with extra `COMMENT` lines), the dispersion law file reader (`read_law()`: unit, coefficients, header comment lines), the constant-step resampling (`resample_linear()`), the wavelength of every point of a linear 1D spectrum (`wavelength_axis()`, `CRPIX1` = 1 when absent) and a per-spectrum transform (`transform_spectrum(obs, input_key, suffix, transform)`: reads the spectrum under a shared key, applies `transform(data, header)`, writes `<name>_<suffix>.fits` to the intermediate directory). Every computation works on whole numpy arrays, never pixel by pixel in a Python loop.

**Master calibration frames** (`master_bias`, `master_dark`, `master_flat`). A master combines a raw series **pixel by pixel**: the N values of one pixel (one per frame) are sorted, the highest and the lowest are rejected, the N−2 remaining are averaged (`minmax_mean()`, float64). Fewer than 3 frames is an error that stops the reduction. Chosen over a sigma-clipped mean: with a 5-frame series, a lone cosmic ray never stands more than ~2σ from the mean of its own pixel (it inflates σ itself), so a classic 3σ clipping rejects nothing (see HISTORY.md 2026-10-07). The master is written to the **session directory** as `<series root>_master.fits` (the first frame's name minus its `-<N>` index, `master_filename()`), float32 (`write_float_image()`), with the first frame's header (`BZERO`/`BSCALE`/`BLANK` removed — they describe the camera's integer encoding) plus plain-language `COMMENT` lines: `<label>: <N>x<exposure>s frames`, the method, one `Source: <file>` per frame. **When that file already exists it is reused, never recomputed** — so a master is computed once per session, and several sessions of the same night share it. `resolve_master(obs, input_key, label, finish=None)` does all of this; `finish(data, comments)` lets a master change the combined data and add comment lines before writing (`master_flat`). `find_shared_input(obs, key)` looks a shared key up in every casier (rule above). `dark_library_helpers.pick_most_recent_usable_series()` skips `*_master` files, so a master is never mistaken for a one-frame raw series.

- `master_bias`: `bias_images` → `reduction_data["master_bias_image"]` (the master's file name, a shared key; no casier of its own).
- `master_dark`: `dark_images` → `reduction_data["master_dark_image"]`, same shape. **Keeps its bias** (extra `COMMENT Bias not subtracted`): it is subtracted from images carrying the same bias. A series copied from the dark library keeps its file names, so its master follows the same rule. Read by the preprocessing for its hot-pixel map (not subtracted).
- `master_flat`: `flat_images` + `master_bias_image` (so `master_bias` must run first) → `reduction_data["master_flat_image"]`. The flat is used in a division, where nothing would cancel its offset: the master bias is **subtracted** (dark current over the short flat exposure neglected), then the result is **divided by its own mean** (it averages 1; the lamp's spectral shape stays in, to be absorbed by the instrumental response). Extra `COMMENT` lines name the master bias, the neglected dark current and the mean used. A master bias of another size, or a mean ≤ 0, is an error. Outside the band lit through the slit it is about 0.17, not 0; the sensor's first column is close to 0 (both seen on 2026-09-25).

**Intermediate files**: `intermediate_dir(obs)` = `<session dir>/<queried name>_<observation id>/` (e.g. `Vega_0e37017f`, `8_Lac_A_27506581`, the name made file-safe by `file_names.safe_name()`), created on first use. One directory per observation for every intermediate file of every later step; deleting it loses nothing.

**Preprocessing** (`preprocess_frames(obs, input_key)`; `preproc_target`, `preproc_calib`): each raw frame, **one by one** (stacking comes later), becomes `(frame − master bias) / master flat`. **The dark is not subtracted** for now (negligible dark current, no exposure-time scaling yet — see HISTORY.md 2026-10-08), **but the sensor's hot pixels are replaced**: `hot_pixel_map(dark, bias)` marks the pixels where master dark − master bias exceeds its median by `HOT_PIXEL_SIGMA` (5) times its noise (1.4826 × median absolute deviation) — 191 inside the useful area on 2026-10-12 (threshold 64 ADU in 180 s) —, and `replace_hot_pixels()` replaces each of them, after the division by the flat, by a linear interpolation along its row (the dispersion axis) between the nearest healthy pixels on its left and right (`np.interp` per affected row; healthy = in the useful area and not hot; at an edge, the nearest healthy value). Along the row, not across it: the trace profile is narrow (σ ≈ 2.5 px) and a vertical neighbour would bias the trace core. No exposure-time scaling needed, saturated or non-linear hot pixels handled the same way; a stack-based rejection could not remove them (same place in every frame). Only the useful area is kept: outside the band lit through the slit (`flat_band()`: rows whose median reaches `LIT_BAND_LEVEL_FRACTION`, 0.5, of the brightest flat row's) and where the master flat is below `MIN_FLAT_FOR_MEASUREMENT` (dead sensor edges), the result is 0 — so no `inf`/`NaN` or huge value reaches the next steps (the smile used to move the dead first column's 10¹⁰ values up to column 18, out of reach of a flat-based mask). Because half the frame is then exactly 0, the trace is always measured on the lit band only: `find_trace(image, flat)` crops to `flat_band()`, zeroes dead pixels, runs `find_axes()` and returns full-frame coordinates (used by `tilt`, `smile` and `extract`); on the whole frame `find_axes()` would see a zero background and take the whole lit band for the trace. It measures on `image × flat`, i.e. **before the flat division** (in memory only — the frames written and shifted stay flat-divided): the flat is faint at the blue end (~0.2 against 3.6 in the red), so the division amplifies the noise there 5–20 times, and on a faint object those noise patches outweighed the trace (M 57: −7.4° instead of −0.07°, Hα lost — see HISTORY.md 2026-10-16). Written to the intermediate directory as `<raw name>_preproc.fits`, float32, the raw frame's header plus `COMMENT` lines naming the masters and `Dark not subtracted; hot pixels replaced: N (dark - bias > X ADU)`; recomputed (overwritten) on every run. A frame or master of another size is an error.

- `preproc_target`: `star_spectra_images` + `master_bias_image` + `master_dark_image` + `master_flat_image` → `reduction_data["preproc_target_images"]`, the corrected files' paths **relative to the session directory** (shared key, no casier).
- `preproc_calib`: the same on the lamp series — `calib_images` + the three masters → `reduction_data["preproc_calib_images"]`, in the same intermediate directory. The lamp series is shared by the session, but each observation writes its own preprocessed copy.

**Tilt** (`tilt`): the trace is not exactly horizontal (−0.07° to −0.15° on the sky, ~1 px at the frame edges; −0.066° to −0.091° on the night of 2026-10-14 since the measurement is made before the flat division, see `find_trace()` above). It is not quite straight either: on HD 7636 it rises ~2 px at the blue end (x < 200), so the angle depends slightly on how much weight the blue end gets (TODO.md). **Measured once**, on the **sum of the preprocessed target frames**, by the **principal axes of inertia alone** (`axes_helpers.find_axes()`; the band method of `spectrum_flux_helpers` is deliberately not used here — user's choice, to be judged in use, see HISTORY.md 2026-10-08). The measurement goes through `find_trace()` (lit band only, dead pixels — flat below `MIN_FLAT_FOR_MEASUREMENT`, 0.05 of the normalized flat, ~300 ADU of flat signal — at 0). No trace is an error that stops the reduction. **No rotation**: every column of every preprocessed target **and** lamp frame is shifted vertically, the whole column, by `−(x − NAXIS1/2) × tan(angle)` — the trace keeps its height at the frame centre. `shift_columns()` shifts by **overlap redistribution**: moved by k + f pixels, each original pixel gives 1 − f of its value to one new pixel and f to the next, so each column's total is kept exactly (only what leaves through the top or bottom edge is lost, background) and nothing oscillates. Whole-array numpy, ~0.15 s per 1304×976 frame. Inputs `preproc_target_images`, `preproc_calib_images`, `master_flat_image`; outputs `<name>_tilt.fits` under `reduction_data["tilt_target_images"]`/`["tilt_calib_images"]` (no `COMMENT` added to their header — the angle is in the casier and the log), and the casier `reduction_data["tilt"] = {angle_deg, center_x, trace_y_at_center, trace_sigma_px}` (`trace_sigma_px` = the axes' `sigma_minor`).

**Smile** (`smile`): the lamp's emission lines are curved and slightly tilted (on 2026-09-25, −4.1 px at the top of the lit band to +1.0 px at the bottom, relative to the trace row). **Measured on the sum of the tilt-corrected lamp frames**: every row is cross-correlated (CCF, all rows at once through the Fourier transform, zero-padded, lags ±`MAX_LAG_PX` = 50) with the reference — the mean of the trace row ± 2 —, the maximum refined to a fraction of a pixel by a parabola through it and its two neighbours. Each row's median is subtracted first and dead columns (flat < `MIN_FLAT_FOR_MEASUREMENT`) set to 0. **Rows used**: those whose level (99th percentile of the row) reaches 50 % of the trace row's (`BAND_LEVEL_FRACTION`) give the lit band; 5 % of its height is left out at each edge (`BAND_MARGIN_FRACTION`, slit-edge effects, instrument-independent); a darker row inside it (dust on the slit) simply drops out, no continuity required. A **parabola** `shift(y) = a·y² + b·y + c` (0-indexed y) is fitted on them, rows further than 3σ rejected until stable (`CLIP_SIGMA`); fewer than `MIN_ROWS` (10) usable rows is an error. The trace row is found again by `find_trace()` on the sum of the tilt-corrected target frames (not read from the tilt's casier — shared-key rule); no trace is an error. Every row of every lamp **and** target frame is shifted by `−(shift(y) − shift(trace row))` with `shift_rows()` (overlap redistribution, each row's total kept): lines become straight and vertical, the trace row does not move. Outside the lit band the parabola is extrapolated (up to ~18 px at the frame's top and bottom rows on 2026-09-25 — background only). Inputs `tilt_target_images`, `tilt_calib_images`, `master_flat_image`; outputs `<name>_smile.fits` under `reduction_data["smile_calib_images"]`/`["smile_target_images"]` (no `COMMENT`), casier `reduction_data["smile"] = {"coefficients": [a, b, c]}`; one log line (rows used and rejected, shift at both ends, fit rms).

**Extract** (`extract`): from the 2D corrected frames to 1D spectra — the step that decides the final spectrum's quality. **Measured once, on the sum of the smile-corrected target frames**: the trace row (`find_trace()`, rounded); its **width** — a Gaussian fitted on the vertical profile of each of `N_COLUMN_GROUPS` (25) groups of columns (independent of the sensor size), keeping the groups whose peak reaches `GROUP_MIN_PEAK_FRACTION` (10 %) of the brightest; the trace widens towards the blue (σ 6.75–7.6 px near x = 250 against 2.5 px in the middle on 16 Peg, 2026-09-25), so the **largest σ** is kept; the **window**, a whole number of rows, the trace row ± ⌈`WINDOW_SIGMA` (3) × σ⌉ (514–560 on 16 Peg, 99.2 % of the flux within ±40 px); the **sky zones**, inside the lit band (`flat_band()` minus `LIT_BAND_MARGIN_FRACTION` of its height at each edge — the flat is not tilt-corrected, harmless at these margins) and beyond ⌈`SKY_INNER_SIGMA` (6) × σ⌉ from the trace, one below and one above (a side with no room is dropped, none is an error; 344–491 and 583–749 on 16 Peg). **Target frames**: in each column, the sky is the mean of that column's pixels in both zones after iterative rejection beyond `SKY_CLIP_SIGMA` (3σ, `astropy.stats.sigma_clipped_stats(axis=0)`, all columns at once) — gradients, light-pollution lines and hot pixels handled column by column — subtracted from every window pixel; the spectrum is the window's sum. **Lamp frames**: the same window, no sky subtraction (the lamp lights the whole slit). Dead columns (flat below `MIN_FLAT_FOR_MEASUREMENT` over the window) are 0, so a spectrum keeps the image's width. Each spectrum is a **1D FITS** (NAXIS = 1, float32, the 2D frame's header without `NAXIS2`), `<name>_1d.fits` in the intermediate directory, under `reduction_data["extract_target_spectra"]`/`["extract_calib_spectra"]`; casier `reduction_data["extract"] = {trace_y, trace_sigma_px, window: [y1, y2], sky_zones: [[Y1, Y2], [Y3, Y4]]}`; one log line with the same values. `extract_zones.png` (intermediate directory) shows the window (cyan) and the sky zones (magenta) over the target sum — built with matplotlib's

**Stack** (`stack`): sums the 1D spectra of `extract_target_spectra` into one, and those of `extract_calib_spectra` into another (the lamp sum can serve `dispersion_law`). **A sum, not a mean** (user). Each spectrum's flux is the sum of its values; one below `MIN_FLUX_FRACTION` (30 %) of the brightest spectrum's flux (a cloud, a frame without starlight, an unlit lamp) is rejected with a WARNING naming it — the brightest, not the median: once half the series is cloudy the median is itself a cloudy frame and rejects nothing (HD 175511, 2026-10-13, see HISTORY.md); the brightest always remains; a brightest flux ≤ 0 is an error. No shift, **no cosmic-ray rejection** (to be done at preprocessing, on each 2D frame — TODO.md). Header: the first retained spectrum's, plus `DATE-OBS` (start of the first retained exposure), `DATE-END` (end of the last), **`EXPTIME` = `DATE-END − DATE-OBS`** — the whole observation, readouts and pauses included, the one exposure time BeSS defines (547.5 s for 16 Peg's 5 × 107.7 s) — and **`EXPTIME2`**, not a BeSS keyword, the exposures summed from each frame's actual `EXPTIME` rounded to 0.1 s (`5x107.7s`, one group per distinct duration: `2x20s+3x30s`), plus `COMMENT` lines (`Sum of N 1D spectra`, one `Source:` per retained file, one `Rejected` per rejected file — file names only, without the directory, so each fits one card). Written to the intermediate directory as the first spectrum's name without its series index plus `_stack.fits`, under the shared keys `reduction_data["stack_target_spectrum"]`/`["stack_calib_spectrum"]` (one file each); casier `reduction_data["stack"] = {"rejected": [{file, flux_fraction}, ...]}` only when a spectrum was rejected; one log line per series. `Figure` directly, never `pyplot`, whose global state is not meant for the post-obs worker thread.

**Dispersion law** (`dispersion_law`): the pixel → wavelength law, λ(x) = A0 + A1·x + A2·x² + A3·x³ (x 0-indexed, λ in air, increasing from left to right), from the stacked lamp spectrum (`stack_calib_spectrum`) and a list of the lamp's reference lines — a text file in `<base_data_dir>/reference_lines/` (`subplugin_params.dispersion_law.reference_lines`, an instrument fact like `slit_xy`'s settings, not a program one; one wavelength per line, `#` comments, optional label after the value; `Alpy600_ArNe.txt` = the 12 lines of Demetra's `ALPY_ABSOLUTE_THRESHOLD` set). Same principle as Demetra, checked against it on 16 Peg (2026-09-25): same 8 lines kept, same 4 rejected (4200, 4426, 6099, 6677 — seen about 2 Å from their reference at the Alpy's resolution), RMS 0.20 Å against Demetra's 0.168. Steps: (1) **detection** — the lamp's continuous background is the straight lines between the local minima of the spectrum smoothed over 3 px (no size parameter); noise by MAD (median absolute deviation × 1.4826); peaks above `DETECTION_SIGMA` (7) × noise, the `MAX_LINES` (80) strongest; each position from a Gaussian + constant fit on the raw spectrum (median error 0.1 px on 16 Peg, 0.02–0.08 px on the lines kept), a failed fit, an implausible width or a centre moving > 2 px from its peak (blend) dropping the line. (2) **matching, the plate-solve way** — four detected lines and four reference lines in the same order give a provisional law, the cubic through the four pairs; the reference quadruplets **always include the two extreme lines of the list** (they spread the law over the whole domain — without them the blue end was lost and Hδ came out 8–15 Å off); only quadruplets whose two spacing ratios (x2 − x1)/(x4 − x1), (x3 − x1)/(x4 − x1) — independent of dispersion and offset — agree within `RATIO_TOLERANCE` (0.03) are tried (~23 000 hypotheses, 0.3 s); an optional `approx_dispersion` (±20 %) only prunes; a law that does not increase across the sensor is dropped. (3) **score** — for each reference line, the distance d to the nearest detected line; the smallest Σd wins (Demetra's criterion). (4) **final law** — every reference line paired with the nearest detected line within `tolerance` (1 Å), least-squares fit of the chosen `degree` (3), points beyond `CLIP_SIGMA` (3σ) rejected, pairing redone until stable. The law must keep both imposed lines; when one is missing from the lamp spectrum, its neighbour is imposed instead (WARNING); no law with `min_lines` (7) lines is an error that stops the reduction. (5) **resolving power** — R = λ / FWHM (FWHM = 2.355 σ, the usual convention), from the σ of the lines kept for the law: a straight line σ(x) fitted on them (σ grows ~12 % from blue to red on the Alpy 600), lines further than `R_CLIP_SIGMA` (3) robust sigmas — never closer than `R_MIN_TOLERANCE_FRACTION` (5 %) of the median width — rejected until stable (blends), read at the pixel of `resolving_power_wavelength` (6563 Å / 656.3 nm by default) and converted with the law's derivative there; fewer than `R_MIN_LINES` (3) lines is only a WARNING, the law is written without R. No correction of the pixel's own width; measured before resampling, so the delivered spectrum is ~2.7 % less resolved (see HISTORY.md 2026-10-17); 2026-10-16: R(Hα) = 630. Written to the **session directory**, named after the lamp series: `<lamp series>_dispersion_law.yaml` (a 3-line comment header — formula, unit, lines, RMS, valid domain — then `unit`, `A0`…`A3`), reused as is when it already exists, and `<lamp series>_reference_lines.txt`, the copy of the list it was computed with. Shared key `reduction_data["dispersion_law_file"]`; casier `reduction_data["dispersion_law"] = {degree, unit, coefficients, rms, rms_px, lines_used, coverage: [λ first, λ last line used]}` (`{degree, unit, coefficients, reused: true}` on reuse), plus `resolving_power`, `resolving_power_wavelength` (also on reuse, read from the law file), `fwhm_px` and `lines_rejected_for_r` when measured — outside the coverage the law is extrapolated, said in the log line too. `unit` (`A`/`nm`) applies to the list, the tolerance, the approximate dispersion and the law.

**Signal-to-noise ratio** (`snr`): DER_SNR (Stoehr et al. 2008 — signal = median of the flux, noise = 1.482602/√6 × median|2f(i) − f(i−2) − f(i+2)|, zero points left out; `der_snr()`), chosen by the user as the universal, documented method. Measured on the stacked target spectrum **in pixels** (`stack_target_spectrum`, before the resampling, which reads +8 % over 3750–7500 Å and +20 % over 6000–7000 Å), in each zone of `subplugin_params.snr.zones` (`[[λmin, λmax], ...]` in the law's unit, converted to pixels with `dispersion_law_file`; `[[3750, 7500], [6000, 7000]]` on the 72ED) — as many zones as wanted, all of **equal importance**, nothing program-specific (declared by `Be_stars.yaml` today, usable by any program). Known limit: at high SNR it takes the spectrum's real fine structure (FWHM ~3 px) for noise and plateaus (HD 60848, 14 × 180 s: 78 where the noise measured otherwise gives ~130) — low and moderate values are reliable. **Never blocking**: no zones, a missing input, or a zone with fewer than `MIN_POINTS` (10) points is a WARNING. Shared key `reduction_data["spectrum_snr"]` = `[{wavelength_min, wavelength_max, snr}, ...]`; casier `{"method": "DER_SNR"}`; one log line. See HISTORY.md 2026-10-17.

**Guiding statistics** (`guiding_stats`, `DISPLAY_NAME` "Guidage"): reads the observation's guide log (`guide_log_file`, written by `stop_phd2_guiding`, `parse_guide_log()`) and computes **from PHD2's last completed settling** (`guide_log.py::settled_frame()`, the last `Settling complete` line) to the end of the section — the frames before include the deliberate jump when `pointing_72ed` moves the lock position (up to ~19″), not a guiding error; `focus`'s longer frame comes after and is included: per axis the RMS (standard deviation of the raw error, as PHD2 shows it) and the largest absolute error, the total RMS √(RA² + Dec²), in arcseconds and pixels, plus frame count, lost frames (`DROP`, counted, left out of the values) and duration of the measured part. Arcseconds use `subplugin_params.guiding.sampling_arcsec` — the plate scale measured by plate solving (2.69″/px for the QHY), never the guide log's own, which PHD2 derives from the focal length typed in its profile (2.88). Program-agnostic (declared by `Be_stars.yaml` after `snr`). **Never blocking**: a missing or unreadable guide log, a section where PHD2 never completed its settling, or no guided frame after it, is a WARNING. Shared key `reduction_data["guiding_stats"]`, no casier; one log line. 2026-10-16: total RMS 0.67–1.62″, largest Dec error up to 8.5″ (isolated spikes). See HISTORY.md 2026-10-17.

**Lambda calibration** (`lambda_calibration`): applies the law (`dispersion_law_file`, read by `read_law()`) to the stacked target **and** lamp spectra (`stack_target_spectrum`, `stack_calib_spectrum` — the calibrated lamp is the check that the reference lines fall on their wavelength, and feeds the verification graph). The whole sensor is kept, extrapolated edges included (`crop` removes them later): `CRVAL1 = law(0)` and, by default, `CDELT1` = the **mean dispersion**, `(law(N−1) − law(0)) / (N−1)` — one point per pixel, 3.4723 Å on 16 Peg (2026-09-25). Not A1, which is the dispersion at pixel 0 only (the local dispersion runs from about 3.5 to 3.2 Å/px across the sensor); not an oversampled step like Demetra's 0.87 Å, which adds no information. `subplugin_params.lambda_calibration.step` imposes another step (the number of points then covers the same range). **Resampling by overlap redistribution** (`resample_linear()`): pixel x covers [law(x − ½), law(x + ½)], its flux spread evenly over it; the cumulative flux at the pixel edges is interpolated at the new interval edges and differenced — the total flux is kept exactly (16 Peg: ratio 1.000000 for both spectra), no loop over pixels, no oscillation around sharp lines; a law that does not increase is an error. On 16 Peg the retained lamp lines fall within ±0.31 Å of their reference in the calibrated lamp, i.e. the law's own residuals. Output: `<stacked spectrum>_lambda.fits` in the intermediate directory, the stacked header plus `CRVAL1`, `CDELT1`, `CRPIX1 = 1`, `CTYPE1 = 'Wavelength'`, `CUNIT1` (`Angstrom`, or `nm` with the law's unit) and `COMMENT` lines — the law file's name, its header comments (formula, lines, RMS, valid range), the resampling method — cut between words to fit the cards. Shared keys `reduction_data["lambda_target_spectrum"]`/`["lambda_calib_spectrum"]`; casier `reduction_data["lambda_calibration"] = {crval1, cdelt1, points, unit}`.

**Response, scaling, crop** (`response`, `scaling`, `crop`) — the target spectrum only (the lamp is not needed past `lambda_calibration`), each step through `transform_spectrum()`, the header otherwise unchanged (**no FITS keyword added**: the bounds are known from the spectrum itself, the scaling has no scientific effect), no casier, one log line each. Parameters in the configuration (`subplugin_params.response`/`scaling`/`crop`), in the spectrum's wavelength unit.
- `response`: divides `lambda_target_spectrum` by the instrumental response — an ordinary 1D FITS with a linear wavelength axis (`CRVAL1`/`CDELT1`, `CRPIX1` = 1 when absent, as Demetra writes it), made by hand for now, named by `response.file` (in `<base_data_dir>/response/`, or an absolute path; missing setting or file is an error). Interpolated linearly onto the spectrum's grid (0 outside its range); where it is at least `MIN_RESPONSE_FRACTION` (1 %) of its maximum the spectrum is divided by it, elsewhere set to 0 (outside its range, or near zero where the division would blow up) — `crop` removes these edges. Output `<name>_response.fits`, shared key `response_target_spectrum`. Test response on 2026-10-10: `Vega_Object_C_RI.fit` (Demetra, 2015, C8 + Alpy 600, 2752–7454 Å), not the 72ED's own.
- `scaling` (formerly the `normalize` placeholder, renamed 2026-10-10): divides `response_target_spectrum` by its mean level in `scaling.wavelength_min`–`wavelength_max` (6600–6700 Å on the 72ED, just after Hα), which then averages 1 — a single constant so the values read naturally, not a normalization to the continuum (BeSS's `BSS_NORM` stays `'none'`). A zone not entirely inside the spectrum, or a mean ≤ 0, is an error. Output `<name>_scaled.fits`, shared key `scaling_target_spectrum`.
- `crop`: keeps the points of `scaling_target_spectrum` between `crop.wavelength_min` and `wavelength_max` (3750–7500 Å on the 72ED: outside, too faint or noisy), **no resampling** — `CRVAL1` becomes the first kept point's wavelength, `CDELT1` unchanged. A bound beyond the spectrum is a WARNING and what exists is kept; no point kept is an error. Output `<name>_crop.fits`, shared key `crop_target_spectrum` (what `write_spectrum` will read). On 16 Peg (2026-09-25): 3752.7–7499.4 Å, 1 080 points, the last 14 at 0 (beyond the test response's 7454 Å).

**Write spectrum, plot spectrum, summary** — the delivered files, in the **session directory** (not the intermediate one), all named `final_name(obs)` = the observation file's name plus the observation ID (e.g. `20260925T213751_16_Peg_ba79e32c`), the ID being what finds a spectrum for sure. The names of the three BeSS forms and the equipment's parts live in the Core configuration block `observatory` (`config.OBSERVATORY`; observer, site, equipment, telescope, spectrograph, camera, resolving_power, plus Demetra-only site_uai_code/telescope_diameter_mm/telescope_focal_mm/sensor_type), shared with `export_demetra`; the site's coordinates are in the same block (`latitude_deg`/`longitude_deg`/`elevation_m`, exposed as `SITE_LATITUDE_DEG`...).
- `write_spectrum`: `crop_target_spectrum` → `<final name>.fits`, shared key `final_spectrum`, no casier. The header is **rebuilt from scratch** (ASCII, English): no card of the camera or the 2D frame survives. Target under both forms (`OBJNAME` = queried name, and `RA`/`DEC`/`EQUINOX` = catalogue position, J2000), optional `BSS_VMAG` (`target.magnitude_v`) and `BSS_STYP` (`targets.db`, when known); `DATE-OBS`, `DATE-END`, `EXPTIME` (whole observation), `EXPTIME2`, `JD-OBS`, `JD-MID`; `OBSERVER`, site under both forms (`BSS_SITE` + `BSS_LAT`/`BSS_LONG` 0–360/`BSS_ELEV`), equipment under both forms (`BSS_INST` + `TELESCOP`/`INSTRUME`/`DETNAM`), `BSS_ITRP` (typical, from the configuration) and, when the dispersion law holds one (`read_law()`), the measured `BSS_ESRP` with its wavelength `BSS_SRPW`; `SNR1`/`SNR1LO`/`SNR1HI`, `SNR2`... (not BeSS keywords, one per zone of `spectrum_snr`, when measured); `GUIDRMS`, `GUIDRMSR`/`GUIDRMSD`, `GUIDMAXR`/`GUIDMAXD` (not BeSS keywords: guiding RMS total/RA/Dec and largest RA/Dec error, arcsec, from `guiding_stats`, when measured); the axis (`CRVAL1`, `CDELT1`, `CRPIX1`, `CTYPE1`, `CUNIT1`); `BSS_VHEL = 0`, `BSS_TELL`/`BSS_COSM`/`BSS_NORM = 'none'`; `CCD-TEMP`, `SWCREATE` (`Rosace <version>`); the processing `COMMENT` lines of the earlier steps (generic camera lines dropped). Both forms are given so the file stands on its own without BeSS's forms (BeSS only issues a warning, as for Demetra's files). A missing observer/site/equipment name, a BeSS text over 40 characters or a non-ASCII character stops the reduction. `test_write_spectrum.py` checks the header against the specification's annex B rules (types, ranges, mandatory combinations); 16 Peg's passes them all. The specification's rule on the "initial sampling factor" of a resampled spectrum has no keyword name anywhere, so nothing is written (as Demetra). Once written, the spectrum is shown on the GUI's "Spectre 1D" panel (`publish_spectrum_preview()`, see the GUI section) — a display, not processing: a failure is only a WARNING.
- `plot_spectrum`: `<final name>.png`/`.pdf`/`.svg`, each only when `subplugin_params.plot_spectrum.png`/`pdf`/`svg` is true (none: nothing), casier `{"files": [...]}`. A sober A4 landscape graph (`reduction_helpers.draw_spectrum()`): the spectrum, the part outside the law's coverage shaded (`law_coverage()`, read from the law file's header comments), the Balmer lines when `balmer_lines`; title object/date/program, subtitle site/equipment/IDs/observation file/mid-observation UT/exposures. Labels in English (text written to files).
- `summary`: `<final name>_summary.pdf`, shared key `summary_file`, A4 portrait, 5 pages — the graphic counterpart of the observation file: (1) a header (`_draw_header()`): on the left three quarters the title block — star name in large type, then magnitude (`BSS_VMAG`, when known), date and program, session and observation IDs, final file name, each line smaller —, on the right quarter a framed box of the same height with the quality indicators one per line (`_quality_items()`: R = `BSS_ESRP` at `BSS_SRPW`, one SNR per zone (`SNRn` with its zone) and the guiding RMS (`GUIDRMS`), read from the final FITS, « not measured » in grey when absent); pages 2–5 keep a one-line title; then conditions (object, program, times, exposures, site, equipment, observer, dispersion law, spectrum, observation file, `config.CONFIG_PATH`, IDs), the final spectrum (Balmer and He I lines) and, right below on the same wavelength axis, the calibration lamp with every reference line kept (residual) or not — the extrapolated parts shaded on both, so the coverage visibly comes from the lines kept; (2) the post-science guide image (`stop_phd2_guiding`, else `pointing_72ed`'s corrected one), whole — with a box around the slit measured by `slit_xy`, following its slope and ends, so the slit itself stays visible (from its casier's `segment`, or measured again on its recorded slit image with `slit_xy.measure_slit()` for an observation recorded before) — and zoomed on the slit (the zoom stretched on the sky: median + `ZOOM_STRETCH_SIGMA` noise sigmas, so the slit and the background show), with the slit position in force (`acquisition_helpers.slit_position()`), the star from the image's astrometric solution (`plate_solve_helper.world_to_pixel()`), the star-to-slit offset and the image's median level (clouds, light pollution), and frame by frame against UT the star's flux (sum of its 1D spectrum) and the sky level (median of `extract`'s sky zones in its corrected frame), frames rejected by `stack` marked, each axis centred on its own values and spanning at least ±10 % of their mean (`MIN_SERIES_SPAN_FRACTION`), and below, PHD2 guiding (`_draw_phd2_guiding()`, two panels a seventh of the page high each), from the guide log against UT, the part before the last completed settling shaded grey (left out of the statistics, the error and pulse axes scaled on what follows): one panel per axis, the star's error in arcsec (curve) and the correction pulses in ms on a twin axis (bars, drawn in the direction the pulse moves the star — East and North up, so a bar opposes the error it corrects; i.e. −GuideDistance, signs checked on both pier sides, see HISTORY.md 2026-10-17), the science exposures as green bands (`#b9cdb9`, a tint of the web GUI's accent), lock position moves dashed, lost frames as black triangles along the top; the error axes stop at 1.1 × the 99th percentile of the errors (at least ±3″, pulses ±300 ms) so the lock move does not crush the rest, the time axis covers the guiding only; `guiding_stats`'s values above; (3) the whole sum of the corrected 2D target frames (true proportions) with `extract`'s spectrum window (cyan) and sky zones (magenta, dashed), stretched on the sky zones' pixels (floored at 0, so the parts preprocessing set to 0 show black) so the background and the lit band show (the trace saturates), then each frame's spectrum calibrated with the law and set to 1 on the scaling zone, and each one divided by the mean of the frames (1 = same shape as the others: a frame whose colour or level differs — guiding drift in the slit, a passing cloud, a cosmic ray — stands out); (4) sky: the FRIPON image as `fripon_image` annotated it (shared key `sky_camera`) in the left half, the wide-field image as `wide_field_image` annotated it (shared key `wide_field`) in the right half, each with its own « not available » box; (5) the observation's WARNING/ERROR log lines. Everything comes from the Observation, the files it references and the configuration, except those log lines (`session_log_extractor.read_log_lines()`): during the acquisition, between `[DB] Observation inserted: <id>` and `[DB] sequencer_done stamped for <id>`, minus lines tagged by a reduction step (the previous observation's reduction may run meanwhile); during the reduction, after the last `[REDUCTION] Starting reduction` line, only lines tagged by this program's reduction steps; at most `LOG_MAX_LINES`. Never blocking: a part that cannot be drawn says so on its page with a WARNING. Not done: a background level over the series from guide images — Rosace takes only 3–4 guide images per observation (PHD2's frames are not saved), so the science frames' sky level stands in for it.

### BeSS validation (`bess_validation`, `bess_validation_api.py`, page `/be/`)

Every Be spectrum is checked by the observer before it goes to BeSS. States, in `rosace.db`'s `bess_validation` table (one row per observation, keyed by `observation_id`, with `session_id`, `star` = queried name, `final_spectrum` = file name in the session directory, `created_at`, `status`, `decided_at`/`decided_by`/`comment`, `sent_at`, `bess_validated_at`): `pending` (waiting for the observer) → `accepted` (by the observer, « Accepter » on the spectrum's page) → `sent` (sent to BeSS by hand, then marked by the observer with « Envoyé » on the list, `sent_at`) → `bess_validated` (accepted by BeSS, which can take weeks — to be found by Rosace, no button); or `rejected` by the observer. Codes in English, French labels on the page. The observer's decision can change (`accepted` ↔ `rejected`, or taken back to `pending` with « Remettre à valider », which clears `decided_at`/`decided_by` and keeps the comment; `database.py::BESS_DECIDABLE_STATUSES`) until the spectrum is sent; a spectrum stays in the list until it is validated in BeSS, so the observer keeps an eye on BeSS's validation. Automatic sending and following BeSS's validation come next.

- **`bess_validation`** (REDUCTION, `plugins/reduction_plugins/bess_validation/`, `DISPLAY_NAME` "Valid.", declared by `Be_stars.yaml` after `summary`): adds the row (`database.py::db_queue_bess_validation()`, `INSERT OR IGNORE` — a reduction run again never undoes a decision) and prepares the spectrum's page, `build_validation_data(obs)`: next to the final spectrum, `<final>_validation.json` and two PNG plots, `_validation_guiding.png` (PHD2 RA/Dec) and `_validation_frames.png` (star flux and sky level per frame) — names from `file_names.validation_file_name()`, shared with the API. The JSON holds `header` (star, magnitude, spectral type, dates, exposures, program, IDs), `quality` (R, SNR per zone — from the final FITS header, like the summary —, `guiding_stats`, star-to-slit offset, frames rejected by `stack`), `spectrum` (final FITS + `reduction_helpers.spectrum_overlay()` with Balmer and He I lines), `guide` (post-science guide image + overlay: measured slit `line`, slit position in force `point`, star from the astrometric solution `star`), `sky` (`{fripon: {file, station, capture_time, offset_s, model, matched_stars} | null, wide_field: {file, capture_time, exposure_s, solved, scale_arcsec, field_deg, target_offset_arcmin} | null}`, from `sky_camera` and `wide_field`, each on its own — missing ones under `unavailable.sky` / `unavailable.wide_field`), `frame2d` (the last corrected 2D target frame — last of `smile_target_images`, the frame `extract` measured on — with `extract`'s spectrum `window` and sky `zones` as overlay, rows as outer pixel edges, the whole width), `plots`, `warnings` (`summary.log_events()`), `summary_pdf`, `files` (the only files the API serves for this spectrum) and `unavailable` ({part: reason}). Everything comes from the summary's own functions (`summary.py`: `SummaryContext`, `guide_image()`, `slit_segment()`, `frame_series()`, `exposure_spans()`, `draw_frame_series()`, `draw_guiding_axes()` — public for this), so the page and the PDF always agree; the PDF stays the long-term record, the page is for deciding right after the night. Missing final spectrum or queried name stops the reduction; every other part is never blocking (null + reason + WARNING). No casier.
- **`--build-validation-data [--apply]`** (`cli.py` → `bess_validation.rebuild_validation_data()`): rewrites the page data of every spectrum in the list from its YAML dossier (`load_observation()`) — for spectra reduced before the step prepared them, or after a change of the page's format. Never writes the database; refused while a session runs (a `running` session started less than 24 h ago); without `--apply`, only checks each dossier can be read. Warnings come from `rosace.log`: for an old observation they may have rotated out (the page says so; the summary PDF keeps them).
- **API** (`bess_validation_api.py`, its own `APIRouter`, prefix `/bess`, behind `get_current_user`; `main.py` only includes it): `GET /bess/validations` — every spectrum not validated in BeSS yet (sent ones included), with `sent_at`, `observed_at` and `session_started_at`, most recent session first, then by observation time; `GET /bess/validations/{obs_id}` — the row plus its page data (`data: null` when not prepared); `GET /bess/validations/{obs_id}/files/{name}` — a file of the session directory, only when named in the page data's `files` (404 otherwise: no other path is ever served); `POST /bess/validations/{obs_id}/decision` `{decision: accepted|rejected|pending, comment?}` — `database.py::db_set_bess_decision()`, user from the session cookie, 404 unknown, 409 once sent, 422 bad decision; `POST /bess/validations/{obs_id}/sent` — `database.py::db_mark_bess_sent()`, an accepted spectrum only (409 otherwise, 404 unknown); `GET /bess/validations/{obs_id}/previous` — the earlier spectra of the star (below; 404 unknown, or final FITS missing).
- **Earlier spectra** (`bess_archive.py`, a core module like `simbad.py`; `previous_spectra(row)`, searched each time the page opens): the spectrum being validated (`current`) and the `MAX_SPECTRA` (5) most recent other spectra of its star, whatever their source — `rosace` (the validation list's rows of the same `targets.db` star, any name of it, `database.py::db_get_bess_validations_by_stars()`, rejected ones left out), `bess`, or `bess_rosace` (a BeSS spectrum starting within 60 s of a Rosace one and from our `observatory.site`, counted once). BeSS through its SSAP service (`ssapBE.pl`): TARGETNAME must be BeSS's exact name, so the star is looked up by the BeSS name the robot file gives for its `HD n` alias (`found_by: "robot"`; `subplugin_params.bess_archive.robot_path`, the file `be_scheduler` keeps up to date — its line regex lives here, imported by `be_scheduler`), else by each of our names (`"name"`), else by its coordinates, 36″ (`"position"`, flagged on the page: a neighbour could be taken for the star); every query restricted to the rows overlapping H-alpha (BAND), and over 1000 rows (`OVERFLOW`, no row returned) to the last 2 years, 1 year, 90 days; one row per echelle order, only one kept per spectrum; the VOTable read as plain XML (astropy refuses its `dateTime` type). Spectra downloaded once into `<base_data_dir>/bess_cache/<BeSS id>.fits` (1D image or WAVE/FLUX table), only for those shown. Each entry: date, observer, instrument, site, R (`BSS_ESRP`, else `BSS_ITRP`), wavelength/flux — every spectrum, the validated one included, divided by its median over the two continuum zones of the equivalent width (6510–6530 and 6595–6615 Å), the same rule for all so they share one scale; `scaled: false` when a spectrum does not cover both (shown as it is, flagged in its legend line and in the panel's notice), `degraded` — a finer spectrum (R ≥ 1.5 × the validated one's, or R unknown and a step under 1 Å) convolved to the validated spectrum's R over its whole range, on a regular grid in ln λ (where a constant R is a constant width; 8 points per resolution element) —, and `halpha_ew`, the Hα equivalent width (Å, negative in emission, as in BeSS) measured on what « Résolution Rosace » shows (the degraded copy when there is one): ∫(1 − F/Fc) over 6535–6590 Å, Fc a straight line fitted on 6510–6530 and 6595–6615 Å (`EW_*` constants; `null` when not covered). A BeSS failure never hides the Rosace spectra (`bess_error`).
- **Page** (`gui/src/be_validation.ts`/`.html`/`.scss`, a second x4build entry point in `gui/package.json`; the HTML is copied to `bin/be/index.html` and loads `/be_validation.js`/`.css` by absolute path, so the static mount serves it at **`/be/`** with no Python route): deliberately separate from the main page, which never links to it (not every installation observes Be stars). Same login (`auth.ts::LoginView`, same cookie), same look (`@use "./common"`, see the GUI section; dark mode from the same browser `settings` entry). Two views by the address: `/be/` lists the spectra, one panel per session (local date, session ID, count), one line per spectrum in fixed-width columns aligned across rows and sessions (« Ouvrir » button, star, observation ID, status chip, an « Envoyé » button on an accepted line, asking for a confirmation — `MessageBox.showAsync` —, that marks it sent, then the decision's comment on the rest of the width, cut with « … », whole in the tooltip); `/be/#<obs_id>` shows one spectrum — a decision bar always visible at the top (comment, optional; « Accepter » → `accepted`, « Refuser » → `rejected`, « Remettre à valider » → `pending` (only once decided), all back to the list; frozen once sent; « Annuler » back without change; a previous decision is recalled and its comment pre-filled), then the observation facts with the quality indicators (not measured in grey) and the summary PDF link, the interactive 1D spectrum (`SpectrumViewer`), « Spectres précédents » (`widgets/spectra_compare_viewer.ts::SpectraCompareViewer`, same toolbar and gestures as `SpectrumViewer`, Ctrl + wheel to zoom; « Hα » zooms on 6500–6650 Å, « Résolution Rosace » shows the degraded copies; the validated spectrum bold red, other Rosace spectra red shades, BeSS blue, BeSS-Rosace violet — `--cmp-*` variables of `be_validation.scss`; a legend line per spectrum with a checkbox — date UT, observer, source, R, instrument, Hα equivalent width —, the checkbox also hiding the spectrum's point on the equivalent-width plot below, `widgets/ew_time_plot.ts::EwTimePlot`, one point per spectrum against its date, its value beside it, the validated spectrum larger; an orange notice when found by position, or when BeSS failed), « Spectre 2D (dernière pose corrigée) » (`FitsViewer`, the `frame2d` image with its cyan window and dashed magenta sky zones; « Non disponible » for page data prepared before it, until `--build-validation-data --apply`), « Ciel » (two columns: the annotated FRIPON image, `Image`, with its caption — station, UT, offset from mid-observation, how the positions were found —, and the annotated wide-field image with its caption — UT, exposure, field, scale, target offset from the centre, or not solved; each one « Non disponible » with its reason when missing, or for page data prepared before it), the guide image (`FitsViewer`, overlay `star` drawn as an orange circle — the one new overlay element) beside the frame-by-frame plot, the PHD2 plot, and the warnings and errors.

The 74 Be spectra produced before 2026-10-18 were added to the list by hand (script run by the user, backup first); their page data by `--build-validation-data --apply`. They were reduced before R, SNR and the guide log existed: those show as not measured.

### FRIPON sky image (`fripon_image`, `plugins/reduction_plugins/fripon_image/`)

The image of a FRIPON all-sky camera (Fireball Recovery and InterPlanetary Observation Network; one 1296 × 966 JPEG every 10 min; station FRRA12 is at St-Pancrasse itself) at the time of the observation, with the target and a dozen bright stars marked, so one sees whether the sky was clear and where the target was. Declared by `Be_stars.yaml` after `plot_spectrum`; post-observation thread, so it runs minutes after the exposures. **Disabled** (one INFO line) without `subplugin_params.fripon.station` — the demo and every other config never reach the network.

- **FRIPON access** (found 2026-10-18): the « Capture » list, `https://fireball.fripon.org/ajax/liste_capture.ajax.php` (DataTables parameters), covers the **last 24 hours** of every station only; its search filters fail server-side (SQL error), so the whole list (~18 000 rows, 4 MB, 1 s) is read and the station's rows kept (`parse_capture_list()`); an image, `protect.php?img=capture/<STATION>/<YYYYMM>/<STATION>_<YYYYMMDDTHHMMSS>_UT-0.jpg`, needs a guest session cookie (`list_capture.php` opened first); the exact second varies, so the name is always read from the list. Older images cannot be reached.
- **Which capture**: the one nearest the middle of the science exposures (first `DATE-OBS`, last `DATE-OBS` + `EXPTIME` of `sequencer_data["star_spectra_images"]` — independent of the native chain), and only within `max_offset_minutes` (15; a running station is never more than 5 min off) — otherwise a WARNING naming the nearest one and its offset, « station stopped? » when the station's latest capture is itself that old. **Nothing done twice** for the same capture (observations sharing the same 10 min, a reduction run again): it keeps FRIPON's name in the session directory (`FRRA12_<YYYYMMDDTHHMMSS>_UT.jpg`); one there less than 5 min (half the capture interval) from mid-observation is necessarily the nearest, so the list is not even read (`local_capture()`); one found in the list is not downloaded again; its lens fit is kept next to it (`<capture>.json`: the fitted model, the identified stars, the stored lens it started from — fitted again only when that changes) and read back. Only the annotated image, which marks this observation's target, is drawn again.
- **Positions** (`fisheye.py`, plain functions): lens model `LensModel` — zenith distance z, `r = k·z + k3·z³`, `x = cx + mirror·r·sin(az − rotation)`, `y = cy − r·cos(az − rotation)`, JPEG pixels (origin top-left, y down; these images never leave the module and its drawing). `fit()` detects the image's stars, places the bright stars above `MIN_ALTITUDE_DEG` (12°) with `astro_math.py`, and fits the model: refined from the stored one (`subplugin_params.fripon.lens`), or, without one, searched over every orientation (1°, both mirrors, a few scales; the 10 best refined, since the coarse score alone can prefer a wrong orientation); `None` under `MIN_MATCHED_STARS` (15, clouds). Slowly varying levels (sky disk, background) are median-filtered on the image reduced 4 times (`_slow_median()`; full size took seconds). **Fitted live on every image** (a few seconds, nothing to configure): from the stored lens when there is one, by the full search otherwise; kept only with ≥ 15 stars and an rms ≤ `MAX_RMS_PX` (2 px; ~1 px on clear images) → `model: "fitted"`; failing that (clouds), the stored lens as is (`"stored"`, which still places the target through clouds), or no marks without one (`null`). On a FRIPON image of FRPC03 (Royan, 2026-10-18): 83–91 stars at ~0.95 px rms (~0.17°).
- **Bright stars**: `rosace/rosace/data/bright_stars.csv` (300 stars, V < 3.5, whole sky; Simbad name, usual name — the shortest one-word Simbad `NAME`, e.g. Polaris —, J2000 position, V), built once by `scripts/build_bright_stars.py` (Simbad TAP; only `* `/`V* ` main names, which leaves out galaxies and clusters with a V magnitude) and committed — reference data, deliberately not `targets.db`.
- **Lens fit**: `scripts/fit_fripon_lens.py --station FRRA12 [--at "<UT>"]` (or `--image FILE --time <UT> --latitude --longitude`) runs the full search on a clear-night capture (the morning after: 24 h only), writes an annotated PNG to check and prints the `lens:` block for the configuration. Optional: a stored lens only helps on cloudy images.
- **Output**: `<final name>_fripon_annotated.png` in the session directory (`draw_annotated()`, matplotlib `Figure`): green circles on the identified stars, about 12 usual names (Polaris first when visible, then the brightest, ≥ 70 px apart), N/E/S/W on the horizon, the target as a red open cross with its name, a caption (station, UT, offset, how the positions were found). Shared key `reduction_data["sky_camera"] = {station, capture_time, offset_s, file, annotated_file, model, matched_stars, rms_px, target_pixel}`. **Never blocking**: FRIPON unreachable, no capture close enough, not a JPEG → WARNING, nothing written. Read by `summary` (page 4) and `bess_validation` (part `sky`).

### Wide-field image (`wide_field_acquisition`, `wide_field_image`)

The pointing camera's image of the target's field (ZWO ASI224MC, a colour camera, `pointing_camera` in the 72ED hardware profiles; focal length not known — measured by the plate solves), so one sees whether clouds crossed the target's field and where the target sits; beside the FRIPON image on the summary's page 4 and the Be page's « Ciel » panel.

- **`wide_field_acquisition`** (SEQUENCER, `indi` only, no `_internal.py`, `DISPLAY_NAME` "Grand champ"): declared by `Be_stars.yaml` right after `star_spectra_acquisition`, before `stop_phd2_guiding` — still on the target, guided. One exposure of `obs.hardware["pointing_camera"]`, `subplugin_params.wide_field.exposure_seconds` (5 s); gain/offset from the hardware YAML. File `build_fits_root_name("WIDEFIELD", target_name=queried name)` (`WIDEFIELD` follows the prefix like `GUIDING`), RA/DEC/EQUINOX (catalogue J2000) and OBJECT stamped "by Rosace"; shared key `sequencer_data["wide_field_images"]`. Never blocking: no `pointing_camera` in the profile (replay demo, simulators) → one INFO line; a failed exposure → WARNING. Not under the guiding-chain recovery (another camera).
- **`wide_field_image`** (REDUCTION, `DISPLAY_NAME` "Grand champ", after `fripon_image`): colour by **superpixel** (`bayer_superpixel()`: each 2×2 block of the Bayer mosaic — `BAYERPAT`, `XBAYROFF`/`YBAYROFF` — one RGB pixel, greens averaged, no interpolation; an RGB cube as is; no `BAYERPAT` → grey binned 2×2). The grey sum is written to the intermediate directory and plate-solved (`plate_solve_helper.solve_wcs`, around the target, `SEARCH_RADIUS_DEG` 10°, 60 s; `wide_field.sampling_arcsec` bounds the scale when set, otherwise every scale is tried — the 4200 indexes cover wide fields). Solved: target as a red open cross (only when inside the field), bright stars of `data/bright_stars.csv` in the field (green circles, usual names; the target's own name not repeated), N/E arrows from the WCS; the log line gives field, scale and the target's offset from the centre (where the camera points relative to the telescope). Not solved: the image without marks, the reason in its caption (WARNING). Displayed with FITS row 0 at the bottom, each colour stretched on its own percentiles (1/99.5, which also balances the colours). Writes `<final name>_wide_field.png`; shared key `reduction_data["wide_field"] = {file, annotated_file, capture_time, exposure_s, solved, scale_arcsec, field_deg, target_offset_arcmin, target_pixel}`. Nothing without `wide_field_images` (INFO); never blocking. Not yet seen on a real image (Bayer orientation, exposure, alignment: next clear night).

### Spectrum trace axes and relative flux (`axes_helpers`, `spectrum_flux_helpers`, `calculate_flux`)

Two plain-function modules at the top of `plugins/reduction_plugins/` (same status as `sequencer_plugins/acquisition_helpers.py`: not sub-plugins, never declared in a program YAML, not resolved by `pipeline_loader.py`), used by the `calculate_flux` REDUCTION sub-plugin (below).

**`axes_helpers.py`** is deliberately generic. `find_axes(data, invert=False, n_sigma=5.0, min_component_pixels=20)` returns a `FeatureAxes` (centroid `cx`/`cy`, `angle_deg`, `sigma_major`/`sigma_minor`, plus the retained-pixel `mask` and the background-subtracted `signal`), or `None` when nothing survives (never an axis fabricated from noise): sigma-clipped background/noise of the whole frame, keep pixels more than `n_sigma` above the background, drop every connected group smaller than `min_component_pixels` (hot pixels, cosmic rays) while keeping every larger one — an emission-line spectrum is several separate segments, not one blob — then the principal axes of inertia of what is left. **Weighted by intensity**: the mask only decides which pixels count, each one carries its background-subtracted value as weight. `invert=True` flips the sign first (background minus image), so the same code finds a *dark* feature — the spectrograph slit seen by the guiding camera — with no other change; the slit measurement itself (which image, centre along the slit, local background) is not built yet. `angle_deg` is folded into (-90°, 90°] (the eigenvector sign is arbitrary). `rotate_to_horizontal(image, angle_deg)` rotates a *background-subtracted* image about its centre (bilinear, 0 fill) and rescales the result to the exact input sum, so total power is identical before and after. Coordinates follow the app-wide pixel convention (0-indexed, Y up) below.

**`spectrum_flux_helpers.py`**: `measure_spectrum_flux(data)` measures **one raw 2D sub-exposure at a time** (never a combined stack — the point is also to see the dispersion between the frames of a series) and returns a `SpectrumFlux`, or raises `FluxMeasurementError` (no trace, width fit failed). A relative quantity, compared night to night and frame to frame, never a calibrated absolute flux. **Raw frame only** — no bias/dark/flat, no external reference; `find_axes()`'s zeroed-background frame only serves to locate the trace. Steps:

1. **Trace location, two methods.** `find_axes()` can fail *silently* on a faint star (HD 250240, mag 9.8: 122 pixels above its threshold, σ 0.95 against 3.15 for the real profile) — only an independent measurement exposes it, so the frame is also cut into `N_BANDS = 25` vertical bands (`width // 25` each, camera-independent), each band's summed profile fitted by a Gaussian around `find_axes`'s row (or, when it returns `None`, the row with the highest **median** — a sum can be fooled by a star or defect confined to a few columns), noise bands rejected (amplitude S/N ≥ 5 from the fit covariance, centre error < 1 px, σ in [0.5, 20] px, centre inside the search zone), and a weighted line fitted through the survivors (≥ 3 bands, iterative 3σ clipping). `find_axes`'s line is kept when both agree within max(3 × band-line error, **1 px**) at the frame centre and both edges (on bright stars they differ by 0.2–0.6 px, harmless); otherwise the band line, with a logged warning. `trace_method` records which (`"axes"`/`"bands"`).
2. **Width σ always from a Gaussian fit of the cross profile** along the retained line — pixels binned by distance to the line (0.25 px bins, nothing resampled), per-column background removed — never `find_axes`'s `sigma_minor`, which is the spread of the thresholded pixels only (a different quantity: Vega 3.31 vs 2.68 even when `find_axes` works); mixing the two would change what the window means from one frame to the next.
3. **Tilted window, no rotation, no interpolation**: yc(x) = cy + (x − cx)·tan(angle); window |y − yc| ≤ **4σ** (±3σ held only 96.7–98.8% of the flux, star-dependent, because of the profile's wings); background zone 6σ to 9σ on both sides. Edge pixels are weighted **pro rata** of their height inside the window, w = clip(4σ + 0.5 − |y − yc|, 0, 1), so every column is measured over exactly 8σ wherever the trace sits in the pixel — whole pixels would make the width (and so the flux, especially the column max) depend on the trace's sub-pixel position, which changes night to night.
4. **Hot pixels / small cosmic rays**: a 5-pixel running median along the dispersion axis; a pixel is replaced only when it exceeds it by more than 6 × the **local** noise (1.4826/√2 × running median over 51 columns of |pixel − right neighbour|, floored at the background noise) — local so it includes the trace core's photon noise; a whole-row noise replaced real signal (only positive excursions are replaced, which biases the flux low). Multi-pixel cosmic rays are not handled.
5. **Background per column** (median of the background zone, smoothed by a 21-column running median) is **subtracted from every window pixel of that column**, then the weighted sum is taken: `total_adu` (all columns) and `column_max_adu`/`column_max_x` (the brightest column along the dispersion axis — on a bright star ~480 times smaller than the total). Offset, dark and sky are removed together, gradients included.
6. **Peak pixel**: raw, background **not** subtracted, the brightest window pixel after hot-pixel replacement (a hot pixel must not fake a saturation), with its x/y; `saturated` when ≥ `SATURATION_ADU` (60000). `background_adu` is the mean column background (raw: offset + dark + sky).

**Meant for stars** (a continuum across the frame, the same cross profile in every column). An extended emission-line object (M57) is measured without complaint, but only relative to itself: its lines each have their own shape along the slit (σ 11.7 px on 2026-09-25), and its narrow lines trip the hot-pixel step (160 replaced).

**`METHOD_VERSION`** (module constant, stored with every measurement): every tuning value is a module constant, not configuration, so results never vary between installations. **Bump it only when a change alters a measured value** — `test_spectrum_flux_helpers.py::EXPECTED` pins each version's results on a fixed synthetic frame; never edit an existing entry, add a new one with the bumped version. A change that alters no number (rename, log, speed) keeps the version.

**`calculate_flux`** (`plugins/reduction_plugins/calculate_flux/`, `DISPLAY_NAME = "Flux"`) measures every file of `sequencer_data["star_spectra_images"]` and records each result in the log (one line per frame) and as one row of `rosace.db`'s `spectrum_flux` table — **not** in the observation dossier: the per-frame values (several YAML lines per frame) serve long-term statistics, not the dossier, whose casier only holds the exposure suggestion below (`reduction_data["calculate_flux"] = {"exposure_suggestion": {...}}`; see HISTORY.md 2026-10-09) (`database.py::db_insert_spectrum_flux()`, which receives the values as a dict and holds the column list itself, `SPECTRUM_FLUX_MEASUREMENT_COLUMNS`, so the database layer never imports a plugin). **Never blocking**: an unreadable file, a frame without trace or a database error is a logged warning and that frame is skipped; `execute()` never raises. Deliberately sequential (about 0.5 s per frame). Declared first in `Be_stars.yaml`'s `reduction:` list; since post-observation stages run in their own thread (see the State machine section), this time no longer delays the sequencer.

**Exposure suggestion** (also `calculate_flux`, not a separate sub-plugin): from the brightest raw pixel of the series, `exposure_suggestion()` computes the sub-exposure duration that would put it at `target_peak_fraction` (`subplugin_params.calculate_flux`, 0.7) of `SATURATION_ADU` — exposure × (target − background) / (peak − background), rounded to 0.1 s; a saturated frame makes it an upper bound (`<=`). An aid for setting `program_stars.exposure_time` by hand. Recorded in the casier (`reduction_data["calculate_flux"]["exposure_suggestion"]`) and as one tab-separated line per observation (observation ID, UTC, star, magnitude, frames, exposure, peak pixel max, column max, background, saturated frames, suggestion) in `exposure_suggestions.txt` in the session directory (header written with the file). Never blocking either; it changes no measured value, so `METHOD_VERSION` is unchanged.

`scipy` (connected-component labelling, image rotation, Gaussian fits, median filters) and `matplotlib` (diagnostic and spectrum plots, e.g. `extract_zones.png`) are declared dependencies in `pyproject.toml`; `skimage`/`opencv` are deliberately not used.

### Coordinate frame convention: J2000/ICRS everywhere

Every coordinate that crosses a module boundary in Rosace — `Target.ra`/`dec` (`targets.py`, sourced from Simbad's `basic.ra`/`dec`, themselves ICRS), `hardware/mount.py::Mount.slew_to(ra, dec)`'s arguments, `scheduler_data["target"]` — is **J2000/ICRS, always**, in degrees. This is a deliberate, app-wide decision: mixing J2000 and JNow would misdirect the mount by an amount that matters at Rosace's targeting precision (well under a pixel of tolerance), so consistency across the whole chain is load-bearing, not cosmetic.

JNow (equatorial coordinates "of date", precessed/nutated for today) exists **only** inside `hardware_indi/devices/mount.py::IndiMount` — the one place that must speak it, since INDI's own standard mount property (`EQUATORIAL_EOD_COORD` — "EOD" = epoch of date) is JNow by protocol definition, not a configurable choice. `IndiMount.set_coord()` converts an incoming ICRS/J2000 `SkyCoord` to `FK5(equinox=Time.now())` right before sending it to INDI; `get_current_coordinates()` does the reverse conversion on the way back out. Every layer above `IndiMount` — `MountAdapter`, the `Mount` Protocol, every SEQUENCER sub-plugin — only ever sees J2000, and must never re-derive or assume JNow itself.

`solve-field` (astrometry.net, see the plate-solve chantier) solves against index files built from a J2000/ICRS catalogue and writes a J2000 WCS (`RADESYS`/`EQUINOX` in the resulting FITS header) — consistent with the rest of the chain, no conversion needed when comparing a plate-solved position to a catalogue target position.

`acquisition_helpers.py::capture_guide_image()` (see also "Guiding-camera dark subtraction" above, for the raw/dark-corrected file split this function writes) switches `obs.hardware["spectroscope"]` to `LightSource.SKY` before every exposure by default (`light_source` parameter — only `slit_xy` ever passes another one, for its lamp-lit slit image; no real guide image needs any other light source), and nothing upstream (a previous sub-plugin, an interrupted session) can be trusted to have already left the spectroscope there. Added 2026-09-04 after a real incident: a disconnect mid-`dark_acquisition` left the spectroscope on `DARK`, and a guide image captured afterward (by a different sub-plugin, in a later session) came out solid black. This is also why the function takes the whole `obs: Observation` rather than a bare `camera` — it needs both `obs.hardware["guiding_camera"]` and `obs.hardware["spectroscope"]`, and `obs.obs_dir` besides, so passing `obs` itself is simpler than threading three separate arguments through every caller. It stamps `RA`/`DEC`/`EQUINOX`/`OBJECT` into every guide image it writes, whenever the caller passes `ra_deg`/`dec_deg`/`target_name` (`slew_72ed`/`pointing_72ed` always do). This exists because the camera driver may already have written its *own* `RA`/`DEC`/`OBJCTRA`/`OBJCTDEC`/`EQUINOX` via mount-snooping (e.g. INDI's CCD Simulator does, labelled J2000) — but that value isn't trusted app-wide: a different camera driver, especially on real hardware, could just as easily copy the mount's raw `EQUATORIAL_EOD_COORD` (JNow) verbatim without converting it. So Rosace always overwrites these keys with its own value — the RA/DEC it actually commanded or computed (`slew_72ed`'s aimed-at or corrected target position, see above), never the driver's. Every stamped card's comment ends "stamped by Rosace" so a human reading the header later can tell which value the app itself vouches for — comments deliberately never contain a literal `/` character (KStars' FITS header viewer truncates a comment at the first `/`, even one that's just part of the comment text and not a real FITS delimiter — the FITS standard itself only treats the *first* `/` after the value as the comment separator, but KStars doesn't respect that).

### Pixel coordinate convention: 0-indexed, origin bottom-left

Every pixel coordinate that crosses a module boundary in Rosace — `slit_x`/`slit_y` (`subplugin_params.guiding`), `solve_result()`/`world_to_pixel()` arguments and results (`plate_solve_helper.py`), the residual-vs-slit computations in `pointing_72ed`/`stop_phd2_guiding`, and the GUI's pixel readout — is **0-indexed, with the origin at the centre of the bottom-left pixel, X to the right and Y upwards** (FITS row order: row 0 is the bottom row). This is what astropy's `WCS.pixel_to_world()`/`world_to_pixel()` already speak, and what every array index in the code already is (`data[y * width + x]`); the GUI's `FitsViewer` draws FITS row 0 at the bottom for the same reason.

Viewers outside Rosace (KStars, DS9) count from **1**: subtract 1 from each axis before copying a value read there into the config, or add 1 to compare a Rosace value against them. Not respecting this is exactly what put `slit_x`/`slit_y` off by one pixel until 2026-09-04 (measured in KStars, compared against zero-indexed plate-solve output — see HISTORY.md). PHD2's own convention for its lock position is not documented and not assumed: `pointing_72ed` only ever uses it as a difference (`lock_x - dx`), where a constant origin offset cancels.

### Simbad client (`simbad.py`)

Queries Simbad's TAP service via ADQL over HTTPS. Returns `StarCreate`. Raises `SimbadNotFoundError` (404) or `SimbadQueryError` (no server gave a readable answer). In tests, mock `rosace.simbad.httpx.AsyncClient` as an async context manager.

Several servers answer the same queries (the CDS in Strasbourg, its mirror at Harvard): `SIMBAD_TAP_URLS` (Core key `simbad_tap_urls`, required — the addresses live in the configuration only, never in the code) lists them, **the first one preferred**. `simbad_search(name, servers=None)` tries them in order; a network error, timeout, HTTP error or unreadable answer → WARNING and the next one; "not found" is an answer, never a reason to ask another server. `SimbadServers` is one search: a new one (each `/simbad/search` or `/simbad/import`, and each uploaded list) starts from the first server again, while the stars of one `/stars/import-list` share one instance and start with the server that answered last — a server that is down costs one timeout (10 s) per list, not per star (CDS down on 2026-10-31, see HISTORY.md).

### Configuration (`rosace/rosace/conf/`)

The configuration files shipped with the code live in `conf/`, split into separate files by concern rather than crammed into a single monolith; an installation's own `config.yaml` and hardware profiles live outside the code, in `~/.config/rosace/` (see "Which config.yaml is active" below):

| File | Purpose |
|---|---|
| `config.yaml` | Core application settings (data paths, site name, active hardware profile, active scheduler) — the packaged copy is the INDI simulators, with every key explained: the template `rosace --init-config` copies to `~/.config/rosace/config.yaml`, where an installation's own config lives |
| `config_demo.yaml` | The replay demo's config (`--demo-mode`) — the 72ED's settings with neutral names |
| `logging.cfg` | Logging setup (`fileConfig` ini format — see below) |
| `hardware_<variant>.yaml` | Hardware/instrument definitions, one file per variant: packaged, `hardware_indi_simu.yaml` (INDI simulators) and `hardware_replay.yaml` (demo); an installation's own next to its config (`hardware_indi_72ED-LAN.yaml`/`-WIFI.yaml` in `~/.config/rosace/` for the real telescope). Which variant is active is selected via `active_hardware` in `config.yaml`, resolved to `HARDWARE_CONFIG_PATH` by `config.py::_resolve_hardware_path()`: `<active_hardware>.yaml` next to the active `config.yaml` first, else the packaged one, else a startup error naming both places. Declares, under `INDI_drivers`, one entry per device (`role`, `module`/`module_dir`/`class_name` for dynamic loading, plus device-specific fields incl. `indi_client: {indi_host, indi_port}`), and a `PHD2_config` section (`host`/`port`/...) — parsed by `plugins/hardware_connectivity.py` when `sequencer_backend=indi`. |

Note: `programs/*.yaml` (scientific program definitions) intentionally live outside `conf/` — they're a catalogue of interchangeable observation plans, not app configuration.

### Which config.yaml is active (multi-instrument support)

The packaged `conf/config.yaml` is the INDI simulators
(`sequencer_backend: indi` — it expects an INDI server with the simulator
drivers, and PHD2) — but a real installation's own settings (site, observer,
network, active hardware, observation list...) must not live inside the code
(a pip upgrade would replace them, publishing would expose them), and someone
running more than one instrument needs more than one config. `config.py::_resolve_config_path()` picks the
active file in priority order, evaluated once at import time:

1. **`ROSACE_CONFIG` env var**, if set — an explicit path (any location, `~` expanded), highest priority. `python -m rosace.main <path>` sets this from a positional CLI argument before any other import runs (every command-line option is handled by `cli.py`, which the `rosace` command, or `main.py` run as a script, calls first thing — required to run before `from .config import ...` triggers `config.py`'s own loading; kept out of `main.py` so the orchestrator knows nothing of these installation tools); a `uvicorn rosace.main:app` launch needs the env var set directly instead (`ROSACE_CONFIG=<path> uvicorn ...`). Meant for one-off overrides — a second instrument, a test config, `--demo-mode` (below) — not the everyday case.
2. **`~/.config/rosace/config.yaml`**, if it exists (`$XDG_CONFIG_HOME/rosace/` when that variable is set — the Linux convention, `config.py::_user_config_dir()`). This is the installation's own config, found on every launch with no argument — the day-to-day case once the instrument is configured. `rosace --init-config` creates it as a copy of the packaged simulators config (refuses if one is there). Its hardware profile sits next to it (see the `conf/` table above). On the observatory PC: the 72ED config and its two hardware profiles (moved out of the repository 2026-10-25). Where the *data* go is a separate matter, the config's own `base_data_dir` (`~/.rosace`).
3. **The packaged `conf/config.yaml`** — the INDI simulators: what a fresh install starts with, nothing configured yet. On a PC with its own config, the simulators are started by giving this file's path (`rosace <package>/conf/config.yaml`).

The tests never see this machine's own config: `conftest.py` sets `ROSACE_CONFIG` to the packaged `config.yaml` and `XDG_CONFIG_HOME` to an empty temporary directory before anything imports `rosace.config`.

**Running as a systemd service**: a service does not read `~/.bashrc`, so a `ROSACE_CONFIG` exported there must be given again in the unit (a config in `~/.config/rosace/` needs nothing). A user unit, `~/.config/systemd/user/rosace.service`: `[Service]` with `ExecStart=<venv>/bin/rosace` (and `Environment=ROSACE_CONFIG=<path>` if needed), `Restart=on-failure`; `[Install]` `WantedBy=default.target`; then `systemctl --user enable --now rosace`, and `loginctl enable-linger <user>` to keep it running with nobody logged in. Not set up on the observatory PC.

`rosace --check-config [path]` validates a config without starting the server: with no argument, it validates whatever step 1–3 above would resolve to; with a path, it validates that file specifically (via the same `ROSACE_CONFIG` mechanism). It prints the config file and the hardware profile file it found. Prints `[OK]`/`[FAIL]` and exits 0/1 — never reaches `uvicorn.run()` either way, so it's safe to run against a candidate config without risking a real session starting. When the config declares `horizon_file`, it also parses and validates that file (`horizon.py::load_horizon()`) and prints its point count (`[OK] horizon file valid: <path> (N points)`, or `[FAIL] horizon file invalid: ...` and exit 1) — so a freshly copied KStars export can be checked before a session ever reaches the SCHEDULER. Finally it imports the plugin registry, which instantiates the active scheduler and validates the sub-plugin catalogue: an unknown `active_scheduler` (or a bad catalogue) prints `[FAIL] plugins invalid: ...` and exits 1, otherwise `[OK] plugins valid (active scheduler: <name>)`.

`rosace --help` (or `-h`; `python -m rosace.main` is the same command) prints this same CLI's usage — the positional `config_path` argument, `--demo-mode`, `--host`, `--port`, the tool options `--check-config`, `--init-config`, `--create-admin`, `--list-subplugins`, `--purge-simulated`, `--purge-failed`, `--purge-demo`, `--build-validation-data` (with `--apply` for the last four), and `--version` — and exits, without starting the server either. The options are declared once, in `cli.py::build_parser()` (argparse): `--option=value` works, the tool options are mutually exclusive, and a usage error — an unknown option or a typo (`--prot`), a bad `--port`, an unknown `--list-subplugins` family, `--apply` without its tool option, a config path with a tool option or with `--demo-mode` — is reported on stderr with argparse's usage line and exit code 2, nothing run (a tool option's own failure stays a `[FAIL]` line on stdout, exit 1). Tab completion (argcomplete, a dependency; `# PYTHON_ARGCOMPLETE_OK` at the top of `cli.py`, where argcomplete looks for it) reads the same parser, so a new option is completed with nothing else to do; `.yaml` files are offered for `config_path` and `--check-config`, the families for `--list-subplugins`. Enabled once per user with `eval "$(<venv>/bin/register-python-argcomplete rosace)"` in `~/.bashrc` — the full path, since the environment is not active when `~/.bashrc` runs (a bare `register-python-argcomplete` fails there silently and nothing completes) — and `rosace` itself found without activation through a link in `~/.local/bin` (zsh: after `autoload -U bashcompinit && bashcompinit`); without argcomplete installed, everything works but Tab. For a published package, pipx (`pipx install rosace`) will do both the environment and the link. `cli.py::main()` is the entry point of both commands: it builds the parser, hands it to argcomplete, lets `run_cli()` run a tool option or set `ROSACE_CONFIG` (defaults `--host 0.0.0.0`, reachable from the local network, and `--port 8000`), then starts uvicorn; the server's first log line gives the version and the active config (`[MAIN] Rosace <version> started (config <path>)`). Run as a script, `main.py` calls `main()` before importing anything else and stops there, so the application is loaded once, by uvicorn.

`python -m rosace.main --create-admin <username>` bootstraps the first admin account (see Authentication above) and exits — also never starts the server.

`python -m rosace.main --purge-simulated [--apply]` (`simulated_data.py`) removes the data of the sessions run with simulated equipment — so that simulator tests never count as real nights for cadence planners or time shares, nor fill the disk. Each session row records `hardware_profile` (`ACTIVE_HARDWARE`) and `simulated` (`SIMULATED_EQUIPMENT`: the `internal` backend, or a hardware profile declaring the top-level key `simulated: true` — `hardware_indi_simu.yaml` does), written by `db_insert_session()`; `NULL` on rows recorded before these columns existed (added by hand to the existing database on 2026-10-03, never by migration code). Selected: `simulated = 1`, except a session still marked `running` and started less than `RUNNING_MAX_AGE_HOURS` (24) ago — it may really be in progress; an older `running` row was left by a server stopped without `CLOSE_SESSION` (13 such rows existed on 2026-10-03), no night lasts that long. Its files, in its session directory: those whose name contains the session id (session log, Demetra ZIP) and those modified while it ran (`started_at` → `closed_at` + 2 min, or the next session's start when it never closed — only one session runs at a time, so whatever was written there meanwhile is its own); a directory left empty is removed. Its rows, in one transaction: `spectrum_flux` and `pointing_errors` of its observations, its observations, the session. Without `--apply` it only reports (per session and in total: rows, files, size); never starts the server.

`rosace --purge-failed <date> [--apply]` (`failed_data.py`) removes what the observations of one night whose **acquisition failed** (`sequencer_status = 'error'`) left behind — under clouds Rosace tries again every minute all night (night 10-29: 576 failures, 5.4 GB of guide images). The night is the date of its session directories (`<date>_<site>`); every session of it is processed. Every other observation is kept, rows and files: a success, one whose reduction failed (its frames may be reduced later), one cut by a crash. Rows, in one transaction: the failed observations' `spectrum_flux`, `pointing_errors` and `bess_validation` rows, then the observations; the session row too when it keeps no observation. Files, top of the session directory only (subdirectories hold the kept observations' reduction): a failed observation's YAML and the files named after it (its YAML stem, or its id as a whole word), every file its YAML names, and the `GUIDING_*`/`WIDEFIELD_*` files modified during its attempt (`created_at` → `ended_at`) — the guide images of a pointing that failed before recording them; only the SEQUENCER writes those, one observation at a time. Never deleted: a file a kept observation's YAML names (and the `GUIDING_RAW_` twin of its guide images), a file named after a kept observation, the session log and Demetra ZIP, `exposure_suggestions.txt`. A session that keeps no observation goes entirely, its files chosen as by `--purge-simulated`; a directory left empty is removed. Refused while a session runs; without `--apply` it only reports.

### Trying Rosace without hardware (`--demo-mode`)

Onboarding runs in four stages, each a superset of the trust required by the
last: **Docker demo** (zero install — `docker/`, see `docker/README.md`) →
**`--demo-mode`** (installed locally, no telescope, no INDI server, no PHD2)
→ **INDI simulators** (`sequencer_backend: indi` + `active_hardware:
hardware_indi_simu`, needs a real INDI server and PHD2 running) → **real
hardware** (`active_hardware` pointed at the real profile, e.g.
`hardware_indi_72ED-LAN`). Only the last two share one evolving config/
catalogue — the demo is deliberately isolated under `~/.rosace-demo`, so it
can never interfere with a real installation. The Docker image runs the same
replay demo (below), packaged: see "The Docker image".

**The demo runs the real process on replayed hardware.** `conf/config_demo.yaml`
uses `sequencer_backend: indi` and the real `programs/Be_stars.yaml`: every
SEQUENCER sub-plugin of the 72ED (slew_72ed, slit_xy, pointing_72ed, focus,
star_spectra_acquisition, stop_phd2_guiding, the four calibration
acquisitions, guiding_dark_acquisition) and the whole native reduction run
unchanged, plate solving included (real `solve-field`, which must be
installed). Only the devices are replaced, by the hardware profile
`conf/hardware_replay.yaml`, whose device classes (`hardware_replay/`) hand
back the frames recorded on a real night instead of exposing. Chosen over
`_internal.py` copies of each step, which would have shown demo code, not
Rosace's (see HISTORY.md 2026-10-16).

- **`hardware_replay/`** (same place as `hardware_indi/`): `devices.py` —
  `ReplayMount`, `ReplayCamera` (`replay_frames: science|guiding`,
  `max_wait_seconds`), `ReplayFocuser`, `ReplaySpectroscope` — offers the
  method names the `hardware_indi/adapters/` call on the INDI device classes,
  so `plugins/hardware_connectivity.py` loads and wraps them like any device
  (module/module_dir/class_name, plumbing fields declared but unused).
  `bench.py` holds the dataset and what the devices share: the mount points
  at the dataset observation nearest to its commanded position (none farther
  than 2°: the homing image); the science camera serves, by the
  spectroscope's light source, the observation's next science frame (SKY), a
  bias (DARK, 0 s), a dark (DARK), the lamp (CALIB) or the flat (FLAT); the
  guiding camera its guide images in the night's order (slew, pointing,

  guiding dark on DARK. Counters restart only when the mount points at
  *another* observation — slew_72ed's approach point (2° off, far from every
  observation) does not count. Exposures wait at most `max_wait_seconds`
  (5 s science, 2 s guiding) but keep their recorded header, real `EXPTIME`

runs (the fake PHD2's port answers). Without `--apply` it only lists what
would go. Each demo session is also recorded as simulated

### Key configuration (`config.py` loads the active `config.yaml`)

`config.py` is a thin loader: it resolves which `config.yaml` is active (see above), reads it at import time, and exposes the same constants the rest of the codebase already imports (`from .config import BASE_DATA_DIR, ...`).

`conf/config.yaml` is split into two sections, and the two follow different rules — a deliberate architectural decision (see HISTORY.md): sub-plugins are meant to vary freely per installation/observer (a parameter one program's plugin needs may be meaningless to another), so requiring every installation to declare every plugin's parameters (as a flat, unconditionally-indexed `config.yaml` would) doesn't scale as the sub-plugin catalogue grows.

- **Core** — read directly by `main.py`/`auth.py`/`database.py`, or a selector key needed to pick which plugin family is active (`active_hardware`, `active_scheduler`, `sequencer_backend`) — a plugin can't declare its own selector. Every installation must set these. `config.py` reads each with `_cfg["key"]` (fails fast, at server startup, if missing) and exposes it as its own named constant, one per key — the table below. `is_demo`/`IS_DEMO_MODE` is the one deliberate exception: read with `.get("is_demo", False)`, since it's meaningful only to `conf/config_demo.yaml` — every other config simply omits it.
- **Plugin** — everything specific to one or a few sub-plugins (DARK/BIAS frame counts, the schedulers' observation list path...). Lives under one free-form `subplugin_params:` block in `config.yaml`, with no schema enforced. `config.py` exposes exactly one constant for the whole block, `SUBPLUGIN_PARAMS: dict = _cfg.get("subplugin_params", {})` — it is never edited again just because a new plugin parameter was introduced. Each consuming sub-plugin reads its own slice with its own default (e.g. `SUBPLUGIN_PARAMS.get("dark_acquisition", {}).get("count", 5)`), so an installation that doesn't use a given sub-plugin needs no entry for it at all. A parameter read by several interchangeable sub-plugins (e.g. `max_exposure_time_seconds`, read by both `star_spectra_acquisition` and `dark_acquisition`) sits at the *root* of `subplugin_params` rather than nested under one plugin's name — the same "shared, purpose-named key" principle already used for casiers (see the Plugin system section above), applied to config. A group of several such shared values describing one coherent concept (e.g. `guiding`'s `exposure_seconds`/`sampling_arcsec`/`slit_x`/`slit_y`, read by `pointing_72ed`/`stop_phd2_guiding`/`guiding_dark_acquisition`) is still nested — under a domain name, not any one sub-plugin's name — purely for readability, without changing which "tier" (root/shared vs. plugin-specific) it belongs to. `DARK_LIBRARY_DIR` is the one exception kept in Core despite being consumed only by `dark_acquisition`: it's a directory, same shape/lifecycle as `BASE_DATA_DIR`/`LOG_DIR` above it, not a tunable behavior.

| `exposure_seconds` / `sampling_arcsec` | `wide_field` | `5` / none (every scale tried) | Exposure of the pointing camera's wide-field image (`wide_field_acquisition`); scale of its 2×2-binned image, from the first plate solves' log line (`wide_field_image`) — see "Wide-field image" below |
| `station` / `max_offset_minutes` / `lens` / `latitude_deg` / `longitude_deg` | `fripon` | none (step disabled) / `15` / none (fitted on each image; no marks on a cloudy one) / the observatory's | FRIPON camera whose image is shown, farthest capture from mid-observation accepted, its lens model (from `scripts/fit_fripon_lens.py`), its position — see "FRIPON sky image" above |

**When adding a new config key**: if it's read by `main.py`/`auth.py`/`database.py`, or is a plugin-family selector, it's Core — add it to `test_rosace_core.py`'s `_write_tmp_config` test helper too, or tests that don't pass it will fail outright (`config.py` indexes it directly, no fallback). Otherwise it's Plugin — add it under `subplugin_params:` (nested under the plugin's name, or at the root only if genuinely shared by several interchangeable sub-plugins), read it with `.get(key, default)` inside the consuming sub-plugin's own module, and `test_rosace_core.py` needs no change at all.

### Logging (`log_config.py`, `conf/logging.cfg`)

Centralized logging, configured once via `configure_logging()`, called at the very top of `main.py` (right after importing `.config`, before any other internal import) — so that log messages emitted at plugin-instantiation time (which happens at import time) are also captured.

- Config format: classic `fileConfig` ini file (`conf/logging.cfg`), not `dictConfig`.
- Logger hierarchy: everything under the `spectro` logger (`spectro.main`, `spectro.plugin.*`, `spectro.subplugin.*`) propagates to a single `spectro` handler set — no per-module setup needed.
- Two handlers configured via `logging.cfg`: console (`StreamHandler`, INFO+) and rotating file (`RotatingFileHandler`, DEBUG+, 1 MB × 9 backups) at `~/.rosace/log/rosace.log`.
- `root` logger stays at WARNING to silence FastAPI/uvicorn/httpx noise.
- `configure_logging()` sets `logging.Formatter.converter = time.gmtime` right after loading `logging.cfg`, so `%(asctime)s` prints UTC, not the server's local time — `fileConfig`'s ini format has no `converter` key of its own, so this can't be expressed inside `logging.cfg` itself. Consistent with the rest of the app: DB timestamps, FITS filenames, and the astronomical-day boundary (see `time_helpers.py` below) are all UTC too, which matters when cross-referencing a log line against a FITS header or a DB row. Since `converter` is a class attribute (not per-instance), this switch is permanent for the whole process once `configure_logging()` has run once — never reset back to local time.
- A third handler, `WebSocketLogHandler` (`log_broadcast.py`), is attached to the `spectro` logger **programmatically** (not via `logging.cfg` — it needs a live asyncio loop and the set of connected GUI clients), in `main.py`'s `lifespan` startup. It buffers INFO+ records and flushes them in periodic batches (every `FLUSH_INTERVAL`, capped at `MAX_BUFFERED` with a dropped-count warning) over the `/ws` route to the GUI's Journal panel — see GUI section below.

`hardware_indi/` (`wrapper/` and `devices/`) uses `spectro.indi.*` logger names (e.g. `spectro.indi.mount`, and per-device-class names like `spectro.indi.IndiCamera` from `wrapper/base.py::Base.__init__`, the one actually in effect for every `IndiDevice` subclass — a subclass's own `self.logger = logger or logging.getLogger(...)` line, if it has one, is set before `IndiDevice.__init__()` runs and gets immediately overwritten by `Base`'s own assignment) — same `spectro` hierarchy as every other logger in the app, so these records reach the rotating file and the GUI Journal, not just the console (fixed 2026-08-30; see HISTORY.md — previously used a bare `logging.getLogger(__name__)`/class-name, which propagated to `root`, WARNING-level console only).

**Session log extraction** (`session_log_extractor.py`): the global rotating log above is the only place session activity is logged — but the on-disk layout principle (below) is that a session's own directory should hold everything about that session, already true for each observation's YAML dossier. `extract_session_log(ctx: SessionContext) -> Path`, called from `CloseSessionPlugin.run()` near the end (wrapped in try/except — one failure here must never block the session from closing, same posture as the park/disconnect steps beside it), copies just this session's own lines (`read_log_lines(since)`, also used by the `summary` sub-plugin) into `<session_dir>/<started_at>_<session_id>_session.log` (same `YYYYMMDDTHHMMSS` timestamp convention as an observation dossier's own filename, `session_id` suffix so several sessions started within the same astronomical night — a restart, or several short runs in a row — never collide on one file). Filters by **timestamp window** (`ctx.started_at` → the moment of extraction), not by tagging every log call site with a `session_id` — simpler, and correct since only one session ever runs at a time (`state.is_running` is a singleton). Reads across `rosace.log` plus however many rotated backups (`rosace.log.1`..`.9`) the session's own window spans, oldest backup first; a line with no parseable leading timestamp is treated as a continuation of whichever record precedes it. The written file opens with a header (night-of-date via `time_helpers.py`, site, session ID, started/extracted UTC timestamps, source log path) and closes with an `# End of file` footer (same rule-line style as the header, so a reader can tell at a glance the file wasn't cut short) — and if the session's own early history has already been rotated out of the source log by the time extraction runs, the header carries an explicit `# WARNING:` line instead of silently starting mid-session.

### GUI (`rosace/rosace/gui/`)

The control interface is a single-page application built **exclusively with [X4 (x4js)](https://github.com/rlibre/x4)**. No other UI framework or DOM manipulation library is permitted.

**Before writing or changing GUI code, read x4js's own instructions for AI assistants**, shipped with the package (since 2.3): `gui/node_modules/x4js/aiguide.md` (how to write idiomatic x4 code — follow it), `aicontext.md` (exact classes and signatures — check every x4 API used against it, or against `node_modules/x4js/src/`; never guess one) and `aicli.md` (the `x4js` command line). They describe the installed version, so they are read again after an x4js update. Where they and this file disagree, this file wins for Rosace's own conventions (language, layout, styles).

Known x4js behaviour: a tooltip closes only on its element's `mouseleave`, which an element removed from the page never sends — a view replaced while the mouse is over a tooltip element keeps the tooltip on screen. `be_validation.ts::Shell.route()` sends that `mouseleave` itself before changing view.

- Entry point: `src/main.ts` — one `RosaceApp` class, all layout via X4 components
- Styles: `src/_common.scss` holds everything shared by the pages (colours and dark theme, base, panels, the shared part of the header, x4js patches, tooltips, image/spectrum viewers, login screen); each page has its own file importing it with `@use "./common"` — `main.scss` (main page), `be_validation.scss` (BeSS validation page). A style used by more than one page goes in `_common.scss`.
- All containers must be `VBox` / `HBox`; all text via `Label`; all interactive elements via `Button` or `Component`
- Build: `npm run build` inside `gui/`, via `x4build` (esbuild-based CLI dedicated to x4js), outputs to `gui/bin/`
- `gui/bin/` is **committed to git** (since 2026-10-31), so that installing Rosace from source needs no Node.js: after changing the GUI sources, rebuild and commit `gui/bin/` in the same commit — otherwise the committed GUI lags behind its sources. The Docker image still builds its own (`.dockerignore` leaves `gui/bin/` out).
- Serve: FastAPI mounts `gui/bin/` as static files directly (`main.py`, end of file) — same process, same port as the API, no separate GUI server
- x4js is a regular npm dependency (`package.json`, `devDependencies.x4js`), installed under `node_modules/x4js`. TypeScript decorators are compiled correctly by `x4build` even from `node_modules`, so no local vendoring is needed.
- After editing `package.json` (e.g. bumping x4js), always run a full `npm install` and confirm `node_modules/` matches `package-lock.json` before rebuilding — a partial/interrupted install here has caused the built app to silently fail to render (blank page, no build error).
- `bin/main.js` has no version hash in its filename — after `npm run build`, a hard browser refresh (cache bypass) may be needed to actually load the new bundle; a stale cached bundle fails silently (no console error, feature just isn't there).
- Live log streaming: `RosaceApp` opens the `/ws` WebSocket via X4's built-in `Application.setupSocketMessaging()` (no custom WebSocket code — see `connectWebSocket()` in `main.ts`), subprotocol `"messaging"`. Backend batches are delivered as global events `{msg: "log.create", params: {lines: [{level, text}, ...]}}`; `MainView` picks them up via `this.onGlobalEvent(...)` and appends them to the existing Journal panel (`logMany()`). Sticky auto-scroll: `logMany()` checks whether the panel's own `<textarea>` was already scrolled to (or within a few px of) the bottom *before* appending, and only calls `scrollToBottom()` (an existing `SimpleTextArea` primitive) if it was — scrolled up to read earlier lines, the view stays put instead of being yanked back down on every new batch. `setupSocketMessaging()` has no built-in reconnect, so `main.ts` owns retry-with-visible-`Notification` on disconnect — never silent.
- Live image preview: three fixed panels in the right column — "Spectre 1D" on top (panel `spectre1d`, a `SpectrumViewer`, see below), a divider (x4js `VSizer`, height remembered by the browser), then "Guidage" (panel `guidage`, left) and "Spectre 2D" (panel `spectre`, right) side by side (`MainView`'s `spectre_viewer`/`guidage_viewer`, both a generic `FitsViewer` widget — x4js `Canvas`, zoom/pan). Backend side (`image_broadcast.py`'s `ws_image_broadcaster`, `main.py`'s `GET /images/{panel}`): each panel is one fixed-name preview file (`GUI_PREVIEW_DIR/{panel}.fits`, e.g. `guidage.fits`/`spectre.fits`), overwritten on every new capture — the WebSocket message only ever needs to say *which panel* changed (`{msg: "image.new", params: {panel, kind}}`), never a filename, since the GUI already knows the fixed URL for each panel and just re-fetches it. `acquisition_helpers.py`'s `capture_guide_image()`/`capture_science_image()` both take an `image_to_gui: bool` (default `False`, so an existing caller keeps behaving exactly as before) — when `True`, writes the extra preview copy and calls `ws_image_broadcaster.broadcast(panel, kind=...)`. `kind` is the type of image — `acquisition_helpers.frame_kind(filename)` for the 2D spectrum (`dark`/`bias`/`flat`/`calib` from the calibration file-name prefixes, `science` otherwise), `guide` or `slit` (lamp-lit, `slit_xy`) for the guiding panel — because the FITS header cannot tell: every frame says `IMAGETYP = 'Light Frame'` (Rosace never sets INDI's `CCD_FRAME_TYPE`, TODO.md). Display rules (`FitsViewer.loadFits(buffer, kind)`): the 1 %/99 % stretch is recomputed on the whole image for the first image and whenever `kind` changes, kept otherwise (a manual « Seuils » too); zoom, position and zone are kept while the new image has the same size, otherwise the image is fit and the zone released. The connected WebSockets belong to the main event loop, recorded at startup (`ws_image_broadcaster.bind_loop()`, in `lifespan()`, next to the log handler's): a `broadcast()` from the main loop sends directly, one from another thread's loop — the post-obs thread, see the State machine section — is handed over with `asyncio.run_coroutine_threadsafe()` and sent from the main loop, so a REDUCTION step may publish an image too. "Spectre 2D" is shared by every science-frame producer (`star_spectra_acquisition.py`, `dark_acquisition`, `bias_acquisition`) — it shows whichever kind of frame was captured most recently (target/dark/bias), not a per-type history; "Guidage" is fed by `slew_72ed`'s, `slit_xy`'s, `pointing_72ed`'s, `stop_phd2_guiding`'s, `home_sync_am3`'s, and `focus`'s guide-image captures alike, same "most recent wins" rule. At startup (page load), every panel shows the last image it received — the preview files survive a server restart — with its overlay when one was kept (`MainView.loadLastImages()` for the 2D panels, `loadSpectrum()` for the spectrum); a panel that never received anything stays empty. `MainView.loadPanelImage()` maps a panel name to its viewer by a plain string match — a new panel needs a new branch there, plus a viewer instance and layout slot, not just a new backend panel name. **"Spectre 1D"** is fed by the reduction only: `write_spectrum`, once the final BeSS FITS is written, calls `reduction_helpers.py::publish_spectrum_preview()` — same mechanism as the images (`spectre1d.fits` + `image.new`), never blocking (a failure is a WARNING). Its overlay is `{title, lines: [{name, wavelength}], coverage: [λ1, λ2] | null}`: title = queried name — obs ID (shown in the panel's title bar), the Balmer lines within the spectrum (angstrom spectra only), the dispersion law's coverage (`law_coverage()`; outside it, shaded as extrapolated). It is also written next to the file (`spectre1d.json`), served by `GET /images/{panel}/overlay` (`null` when absent), so a reloaded page shows the last spectrum with its title and lines (`MainView.loadSpectrum()` at startup). `gui/src/widgets/spectrum_viewer.ts::SpectrumViewer` is `FitsViewer`'s twin for a curve — same toolbar classes and gestures: Tout (whole spectrum — the 2D viewers' button has the same name), Zone (drag a wavelength range to zoom on), wheel = zoom in wavelength around the cursor, drag = pan in wavelength, the flux axis always fits the visible part, readout `λ / F`, followed by `(extrapolé)` outside the coverage (no text drawn on the plot); colours from the page's CSS variables (dark mode). `fits_parser.ts` reads a 1D FITS (`NAXIS=1`) as an image one row high. Each `FitsViewer`'s toolbar also ends with a pixel readout (`X: 613  Y: 614  I: 1234`, a bold monospace `Label` flush right): X/Y follow the "Pixel coordinate convention" above (0-indexed, Y upwards — directly usable as `slit_x`/`slit_y`), `I` is the physical pixel value (BZERO/BSCALE applied). It updates on cursor move (including during a drag or a zone selection) and after a wheel zoom, and is cleared when the cursor leaves the canvas or a new image is loaded. **Panel titles**: each panel's title bar reads « <PANEL> <object> — <observation ID> » for the image shown (`panelTitle()`, `main.ts`): the panel name in capitals and the accent colour like every panel title, the object and ID in their own case and the text colour (`.title-detail`, built as HTML with the object name escaped). For the 2D panels these come from two cards the server stamps on the **preview copy only** (`acquisition_helpers._label_preview()`, from `capture_guide_image()`/`capture_science_image(..., obs=obs)`/`publish_guide_preview(..., obs=obs)`): `OBJECT` (queried name) and `OBS_ID` — never on a file of the observation; read back by `FitsViewer.getHeader()`, so they survive a page reload with the preview file. For the 1D spectrum, from its overlay's title. Darks, flats and lamps taken during an observation carry that observation's name.

**Mouse gestures, the same on the three panels** (`FitsViewer`, `SpectrumViewer`; listed by the toolbar's « Aide » button, in a menu centred on the image): left drag draws the zone (yellow rectangle, or a wavelength range on the 1D spectrum), kept until a double-click or a click on the « Zone » button (yellow while a zone exists — no mode to switch on) releases it, the stretch staying as it is; right drag pans (Ctrl: vertically only, 2D); a right click without moving opens the actions menu — « Agrandir zone », « Agrandir zone horizontale » (greyed without a zone), « Seuils » (1 %/99 % on the zone, or the whole image), « Tout », « Zoom H », « 1:1 »; on the 1D spectrum « Agrandir zone » and « Tout » only (its flux axis fits itself). The browser's own context menu never shows. Cursor: plain arrow (easier to aim at one pixel), crosshair while drawing a zone, closed hand while panning, `ns-resize` for a vertical pan.

  **Image overlays** — a sub-plugin that wants something drawn over its image captures with `image_to_gui=False`, then publishes the image itself via `acquisition_helpers.py::publish_guide_preview(path, source=..., overlay=...)`; the overlay travels with the WebSocket message (`ws_image_broadcaster.broadcast()`'s optional `overlay`, omitted when `None`). It is a dict of generic drawing elements in Rosace's pixel convention, all optional (`fits_viewer.ts::ImageOverlay`): `window` (`[x0, y0, x1, y1]` outer pixel edges, solid cyan rectangle), `zone` (same format, dashed magenta rectangle), `zones` (several of those), `line` (`[xa, ya, xb, yb]`, solid red) and `point` (`[x, y]`, green cross) — colours distinct from the yellow "Zone" selection drawn by the user. The GUI never knows which sub-plugin sent an overlay: `main.ts`'s `image.new` handler passes it to `loadPanelImage()`, which applies it with `FitsViewer.setOverlay()` once the new image is loaded; an image without one clears the previous overlay, so it never lingers over the next capture on the same panel. `source` is still sent but informative only — the GUI does not read it. `FitsViewer.paintOverlay()` converts with `toCanvas()` (pixel centre on integers, `height - y - 0.5` for the top-down display). Two senders today, both on "Guidage": `focus` (`window` = the search window actually used for the measurement, published before measuring — it depends only on the frame size and `window_fraction`) and `slit_xy` (`zone` = search zone, `line` = measured slit line across it, `point` = retained slit position; `line`/`point` `null` when the measurement failed — the zone alone is drawn). A third would need no GUI change.
- Live SEQUENCER/REDUCTION step progress: each observation row's primary stage-chip line can grow up to two extra, temporary lines underneath — one showing SEQUENCER's own sub-plugin steps, one showing REDUCTION's — each a row of `Tag` chips (pending/running/done, reusing `.stage`'s color semantics via a lighter `.substep` variant in `main.scss`) built from `entry.steps`/`entry.step` and labelled via `subplugin_display_names` (`GET /subplugins/display-names`, fetched once at startup — see `DISPLAY_NAME` above — not polled, since it's static for the server's lifetime). Backed by `step_progress.py`: an in-memory-only `dict[obs_id][stage] -> {step, steps}` (behind a `threading.Lock`: SEQUENCER writes from the main loop, REDUCTION from the post-obs thread, while the API reads), deliberately never persisted to `rosace.db` (a sub-plugin name is plugin identity — the DB stays plugin-agnostic, same principle as `SUBPLUGIN_PARAMS`) and never pushed over `/ws` either — folded into the GUI's existing `fetchObs()` poll (`GET /observations/steps`) instead, since a completed step simply showing as done at the next ~3s poll is an accepted tradeoff over true mid-step liveness. Keyed per (obs_id, **stage**), not just per obs_id, specifically so SEQUENCER's line still renders "all done" once REDUCTION starts (REDUCTION would otherwise overwrite SEQUENCER's entry). Each line stays visible while its own stage is `"running"`, or for `STEP_PROGRESS_HOLD_SECONDS` (10s, `main.ts`) after the whole observation finishes (`obs.stages["archive"].done_at`) — a display-only grace period, not tracked server-side, giving the observer time to see the full pipeline at a glance before it collapses back to the primary stage row alone. SHARING is excluded (a program declares exactly one sub-plugin, not a list — no "current step" to show progress through).
- Header "Test" button (`AppHeader`, `#hwtest`, between the observation count and the settings menu): discreet (muted text and border); click → "Test…" disabled while `POST /control/hardware-test` runs (timeout 120 s), then green (`.ok`) or red (`.fail`) for 5 s, not clickable, the tooltip giving "Matériel OK", the failures or the refusal; greyed during a session, in simulation ("Pas de matériel à tester (simulation)") and while a test started from another page runs (`status.hardware_test_running`). START is disabled while a test runs. The details reach the Journal as the server's `[HW_TEST]` log lines.
- « Arrêt demandé » (`MainView.stop_notice`, orange, centred between START and STOP in the controls bar): shown while `status.session_active && !status.is_running` — a stop was asked and the current observation goes on to its end (a stop lets it finish, see the State machine section), then CLOSE_SESSION runs. The two words only, kept short on purpose.
- DEMO MODE badge (`AppHeader`, `#demo-badge`, white on orange, right of the title): shown only when `status.demo_mode` is true (`AppHeader.refreshTitle()`, on every `/status` poll), which also sets the browser tab's title to "… — DEMO mode" (plain text only there). Orange, not red: red already means an error in this GUI.
- Footer (`AppFooter`): three clocks ticking every second — "UTC", "Heure sidérale locale (TSL)" (middle) and "Heure locale" (the browser's). The sidereal time is computed in the browser (`formatSiderealTime()`, the same Meeus GMST polynomial as `astro_math.py`, duplicated on purpose for a display) from `site_longitude_deg`, the configuration's `observatory.longitude_deg` returned by `GET /status`; `--:--:--` until the first `/status` answer.
- Login: `auth.ts::LoginView` is shown before the dashboard by `AppShell` (`main.ts`) — the actual `setMainView()` target (x4js doesn't support calling `setMainView()` a second time to swap the root view — its `mounted` guard is declared but never actually set to `true` anywhere in `core_application.ts`), which instead swaps its own content between `LoginView` and a freshly-built `MainView` via `setContent()`. `fetchStatus()`/`fetchObs()` stop rescheduling themselves and fire a local `"auth.logout"` global event on a 401 (session expired) rather than polling forever unauthenticated in the background; `AppShell` listens for that same event (also fired by the "Déconnexion" item in `AppHeader`'s menu) to show the login screen again. `MainView` is deliberately rebuilt from scratch on every `showMain()` rather than cached — a cached instance's polling loop, once stopped by a 401, would never resume on the next login.
- Two non-obvious x4js behaviors worth knowing before writing another form: `Button._on_click()` always calls `preventDefault()`/`stopPropagation()`, whether or not a `click` prop was given — a `<button>` inside a `Form` therefore never triggers the browser's native submit-on-click, so wire the button's own `click` prop directly rather than relying on the form's `submit` event for anything a click should do. And `Form` extends `Box`, not `VBox` — `%box` (`shared.scss`) only sets `position:relative`, no `display:flex` — so a `Form`'s own stylesheet needs explicit `display:flex;flex-direction:column` (or `row`) for `gap`/child stacking to work at all; it isn't inherited the way it would be from `VBox`/`HBox`.

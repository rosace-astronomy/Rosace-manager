# HISTORY.md

This is the narrative companion to [CLAUDE.md](CLAUDE.md): bug postmortems, dated incidents, rejected alternatives, and the reasoning behind decisions that CLAUDE.md only states as a rule today. Each entry names the CLAUDE.md section it relates to, so you can jump between the two.

Read this when you want to know *why* something is the way it is, or when you're about to reintroduce something that was already tried and reverted.

Dated entries below are in chronological order, oldest first — append new entries at the end. Entries whose original date was never recorded are kept together in **Undated**, right below, rather than guessed into the timeline.

## Undated

**No SCHEDULER plugin imports `main.py`** (relates to: "State machine" in CLAUDE.md) — earlier, the default scheduler used to poll `state.is_running` in its own internal wait loop, which required a late/deferred `from .. import main` (a top-level `from ..main import state` fails at import time with a circular-import error, since `main.py` imports the plugin registry before defining `state`). Removing the internal wait (SCHEDULER now returns immediately with `target=None` instead of sleeping) removed the need for that coupling entirely.

**Why `internal`/`indi` aren't nested subdirectories** (relates to: "Plugin system" in CLAUDE.md) — explicitly rejected: nesting `internal`/`indi` as a subdirectory inside each sub-plugin (`slew/internal/slew.py`) — the user's call: it forces a full duplicate implementation for zero benefit, since `internal` doesn't need first-class-citizen status. A future `ascom` backend, if it ever needs its own duplicate `<name>_ascom.py` per sub-plugin, is the concrete trigger that would justify resolving the backend axis at the device layer instead — not decided yet, deliberately deferred.

**INDI hardware drivers' POCS heritage** (relates to: "INDI hardware drivers" in CLAUDE.md) — `hardware_indi/` is adapted from the PANOPTES/POCS observatory control software: the POCS-specific config loader and MongoDB-backed database layer that the original `Base` class used to pull in on every instantiation have been stripped out (`wrapper/base.py` is now just a logger), since Rosace has its own config/databases that have nothing to do with POCS's.

**FITS header comments — the KStars `/` truncation quirk** (relates to: "Coordinate frame convention" in CLAUDE.md) — comments stamped by `capture_guide_image()` deliberately never contain a literal `/` character. Found empirically that KStars' FITS header viewer truncates a comment at the first `/`, even one that's just part of the comment text and not a real FITS delimiter. The FITS standard itself only treats the *first* `/` after the value as the comment separator, but KStars doesn't respect that distinction.

**GUI — x4js quirks found while building the login form** (relates to: "GUI" in CLAUDE.md) — two non-obvious x4js behaviors were discovered the hard way: `Button._on_click()` always calling `preventDefault()`/`stopPropagation()` regardless of whether a `click` prop was given (breaking native submit-on-click inside a `Form`), and `Form` extending `Box` rather than `VBox` (so `display:flex` isn't inherited and must be declared explicitly in that component's own stylesheet). Also from this era: `setMainView()` cannot be called a second time to swap the root view — its `mounted` guard is declared in `core_application.ts` but never actually set to `true` anywhere, confirmed by reading the source rather than assumed — which is why `AppShell` swaps content via `setContent()` instead.

## 2026-08-05 — The `Observation.hardware` deep-copy crash

*Relates to: "Wired into SEQUENCER" (hardware handling) in CLAUDE.md.*

A whole session silently stopped processing after its first observation, `state.is_running` stuck `True` forever, GUI showing Start and Stop both enabled. Root cause: `obs.model_copy(deep=True, update={"hardware": {}})` does **not** skip deep-copying fields named in `update` — it deep-copies everything first and only overwrites afterward, so this line still ran `copy.deepcopy()` on the live INDI adapters, which raised (confirmed empirically: `TypeError: cannot pickle '_thread.lock' object`), uncaught, silently killing the `session_runner()` background task (that line sits in the `for...else` right after the per-stage `try/except`, not inside it). Fixed by clearing `obs.hardware` to `{}` *before* calling `model_copy(deep=True)` (no `update` needed) and restoring it after, wrapped in its own `try/except` so a future failure here logs and moves on to the next observation instead of taking the whole session down silently.

## 2026-08-15 — `CCD_COOLER` vs `CCD_TEMPERATURE` are separate properties

*Relates to: "Science camera temperature and the dark-frame library" in CLAUDE.md.*

The cooler on/off switch (INDI's `CCD_COOLER`) is a separate property from the temperature setpoint (`CCD_TEMPERATURE`) on many cameras — the setpoint alone has no physical effect until the cooler is actually switched on. Found the hard way testing against the INDI CCD Simulator: the setpoint accepted and echoed back regardless of cooler state there, masking the gap until real-hardware testing would have hit it.

## 2026-08-16 — AstroPy/IERS dropped for the scheduler's altitude check

*Relates to: "The default scheduler: scheduler_rosace_2026" in CLAUDE.md.*

`scheduler_rosace_2026`'s altitude check originally relied on AstroPy's `AltAz` transform. That path depends on IERS Earth-orientation tables: with `auto_download` disabled (the observing site has no guaranteed internet access), AstroPy's default `IERS_Auto` table (IERS-A, predicted values) goes stale after `conf.auto_max_age` (30 days) and raises — found in production on this date, `INTERPOLATE_ERROR`/`ValueError` on every single call, so the SCHEDULER could never select a target at all. Forcing `IERS_B` (measured-only) avoided the crash but left two permanent `AstropyWarning`s, since IERS-B is by design always weeks behind "now" — no snapshot freshness could ever close that gap. Neither variant fit an unattended site with unreliable connectivity, so the whole IERS dependency was dropped for this one calculation: the new `astro_math.py` module (Meeus' low-precision GMST formula + the standard altitude formula, plain `math`/`datetime`) is accurate to a few arcminutes (cross-checked against AstroPy's own `AltAz` during development, worst case ~0.25° off) — orders of magnitude better than `MIN_TARGET_ALTITUDE_DEG` needs, with zero external data dependency and zero maintenance burden. 594/594 tests passing at the time.

## 2026-08-25 — Camera cooldown target-temperature safety margin

*Relates to: "Science camera temperature and the dark-frame library" in CLAUDE.md.*

Found the hard way on a first real-sky test: a weak enough `cooling_capability` let the naive rounded-up target temperature land at or above ambient itself, which a cooling-only camera can never reach — this timed out the cooldown wait and failed `INIT_SESSION`. Fixed by clamping the computed target to never come within `MIN_COOLING_MARGIN_DEG_C` (5°C) of ambient; when the naive target doesn't leave that margin, the next colder multiple of 5 is used instead. Landed alongside new DARK/BIAS reuse tolerances (2°C / 1s), 619/619 tests passing.

## 2026-08-26 — `home_sync_am3`'s SYNC call was silently corrupting every subsequent GOTO

*Relates to: "Wired into SEQUENCER" (`home_sync_am3.py`) in CLAUDE.md.*

Real-hardware prep surfaced a bug: with the mount in "unparked" state (confirmed via `is_parked` reading correctly `False`), the telescope nonetheless stayed near its parking position through an entire simulated session instead of slewing to real targets.

Root cause, found by driving the live INDI Telescope Simulator directly (not just reading code): `home_sync_am3`'s original implementation called `mount.sync_to_coordinates(ra, dec)` after park()+unpark(), to tell the driver "you are now at Home's known sky coordinate." On this simulator (and potentially the real AM3 driver, if it also implements the shared INDI Alignment Subsystem library), a SYNC command doesn't just recalibrate the driver's position reference — it silently records a persistent alignment point and activates the driver's own pointing-correction model (`ALIGNMENT_SUBSYSTEM_ACTIVE`, "Nearest Math Plugin"). Every subsequent GOTO then gets "corrected" against that single point, dragging the mount back toward the sync/home region instead of the real target.

Empirical proof (via a script driving `IndiMount` directly against the running simulator):
- With alignment active (after a SYNC): a slew to RA 100°/DEC 20° landed near RA 113°/DEC 32° — pulled toward the sync position, tens of degrees off target.
- With alignment disabled, or with no SYNC ever issued: the same slew landed within ~3 arcseconds of the requested target.
- A plain park()+unpark(), with **no** SYNC at all, already gives the driver a position matching Rosace's own `astro_math`-computed Home coordinate to within 0.0000001° — the driver derives Home's sky position itself from time + configured site, exactly like Rosace's own code does. So the SYNC call was not just risky but strictly unnecessary.

The fix: `home_sync_am3` now only calls `park()`+`unpark()`, never SYNC. The user's framing of the fix, worth keeping in mind for any future mount-recovery work: building a pointing-correction model on purpose is one thing (a deliberate, multi-point calibration procedure); feeding that model from routine re-homing is another, and a recovery step like this must never do the latter.

As a consequence, `sync_to_coordinates()`/`get_home_position()` were removed as dead code from the `Mount` Protocol (`hardware/mount.py`), `MountAdapter` (`hardware_indi/adapters/mount.py`), and `IndiMount` (`sync_to_coord()`/`get_home_position_icrs()`, `hardware_indi/devices/mount.py`) — no other caller existed. If a future need for an explicit manual sync resurfaces (e.g. a GUI-triggered recalibration), re-add it deliberately then, with the alignment-subsystem risk above in mind rather than assuming SYNC is a harmless position marker.

## 2026-08-27 — `config.yaml`/`config.py` split into Core and Plugin sections

*Relates to: "Key configuration" in CLAUDE.md.*

Before this date, every key in `config.yaml` was read the same way: `config.py` indexed it directly (`_cfg["key"]`, `KeyError` if missing) and exposed it as its own named constant. This worked while every key was genuinely universal, but broke down once the user raised, ahead of adding the FLAT/CALIB SEQUENCER sub-plugins, a real architectural concern: sub-plugins are meant to be volatile and observer-specific — an open-ended, contributed catalogue (see "Pluggable SCHEDULER" and the SEQUENCER sub-plugin directories in CLAUDE.md) — so a config key needed by only one or a few sub-plugins should never be a hard requirement for every installation. Under the old scheme, `DARK_COUNT`/`BIAS_COUNT` etc. were already silently mandatory for an observer who never uses `dark_acquisition`/`bias_acquisition` at all (`SEQUENCER_BACKEND="internal"`) — nobody had noticed, because the packaged demo config always carried every key.

Considered and rejected along the way:
- A single flat namespace with no distinction at all — rejected first: doesn't scale as the sub-plugin catalogue grows, and mixes concerns config.py's own readers care about (site, active hardware/scheduler selection) with concerns only one plugin cares about.
- Per-key `.get(key, default)` still declared individually in `config.py`, just without the hard requirement — rejected: still means `config.py` grows a line for every future plugin parameter, the exact coupling the user wanted removed.
- A single key shared by *several* plugins nested under just one of them — rejected once the user pointed out this exact case exists (`max_exposure_time_seconds`, read by both `star_spectra_acquisition` and `dark_acquisition`): resolved the same way the codebase already resolves the analogous problem for casiers (`sequencer_data["star_spectra_images"]`) — a shared key sits at the *root* of `subplugin_params`, not nested under any one plugin's name, since no plugin should need to know which of its siblings originally "owns" a shared setting.

Landed design: `config.yaml` (and `config72ED.yaml`, kept in lockstep) split into a Core section (unchanged behavior — `config.py` still does `_cfg["key"]` per key, fails fast at startup) and a free-form `subplugin_params:` block. `config.py` exposes the whole block as one constant, `SUBPLUGIN_PARAMS: dict = _cfg.get("subplugin_params", {})`, and is never touched again for a new plugin parameter. Each consuming sub-plugin computes its own module-level constant from its own slice with its own default (e.g. `dark_acquisition.py`: `SUBPLUGIN_PARAMS.get("dark_acquisition", {}).get("count", 5)`) — deliberately kept as a plain module-level name, not a dict lookup inline at every use site, specifically so the existing test convention (`monkeypatch.setattr(da_mod, "DARK_COUNT", 2)`) needed no changes at all across the whole migration. `DARK_LIBRARY_DIR` was the one deliberate exception kept in Core: even though only `dark_acquisition` reads it, it's a directory with the same shape/lifecycle as `BASE_DATA_DIR`/`LOG_DIR`, not a tunable behavior — the user's own call. `SITE_LATITUDE_DEG`/`LONGITUDE`/`ELEVATION` and the hardware-connectivity/cooldown timeouts were also kept in Core on the user's explicit call, despite being read by only one plugin (`scheduler_rosace_2026`) or one conditional code path (`sequencer_backend=indi`) respectively — judged to be physical/infrastructural facts about the installation rather than one plugin's own algorithmic choice. 615/615 tests passing at the time, no test changes needed beyond `test_rosace_core.py`'s `_write_tmp_config` helper (simplified — the migrated keys are no longer mandatory).

## 2026-08-27 — `calib_acquisition`: age-based staleness, not temperature-based

*Relates to: "Science camera temperature and the dark-frame library" (`calib_acquisition`) in CLAUDE.md.*

Landed as the first consumer of the `subplugin_params` split above — its three parameters (`count`, `exposure_time_seconds`, `max_age_hours`) went straight into `subplugin_params.calib_acquisition`, never touching `config.py`. User-supplied defaults: 3 frames × 3s, `max_age_hours: 24`.

The interesting design question was reuse criteria. DARK/BIAS reuse (`find_usable_frame_series()`, `dark_library_helpers.py`) is temperature-tolerance-based and, by construction, never ambiguous within one session: the session-wide cooldown target temperature never changes mid-session, so once a matching series exists it's reused forever, and a fresh reshoot only ever happens if none exists yet — there's never more than one candidate batch sitting in the session directory. CALIB breaks that assumption on purpose: a calibration lamp's spectral response can drift over hours, so `calib_acquisition` reshoots once an existing series turns older than `max_age_hours` even though a technically-matching series is still sitting right there — meaning a session directory can end up holding *both* an old stale batch and a fresh one after a reshoot, something DARK/BIAS never has to handle. Naively reusing `find_usable_frame_series()`'s "take the first N matching files, sorted" logic would have silently preferred the *oldest* batch (wrong) instead of the freshest one. Fixed by writing a dedicated `_find_usable_calib_series()` (`calib_acquisition.py`, kept local — not added to `dark_library_helpers.py`, since nothing else shares this age-based logic) that first isolates the single most recent batch (by the shared capture timestamp already embedded in every filename via `build_fits_root_name()`) and only then checks its age, count, sensor size, and exposure time — user-confirmed: **only** that single most recent batch is ever a candidate, with no fallback to an older batch even if the freshest one turns out short a frame or otherwise unusable (that case simply reshoots, same as finding no series at all).

Also user-clarified during design: unlike DARK/BIAS, `calib_acquisition` never reads or requires `obs.camera_target_temperature_deg_c` — a calibration lamp's flux dominates any dark-current concern, so the once-per-session cooldown this sub-plugin family normally trusts (see `plugins/camera_cooldown.py`) simply doesn't apply here. No reusable library either (explicit user simplification vs. DARK) — only `current_session`/`camera` origins, same shape as `bias_acquisition`. Wired into `Be_stars.yaml` right after `bias_acquisition`, same before-the-`SKY`-reset positioning. 629/629 tests passing (14 new).

## 2026-08-27 — `flat_acquisition`: no staleness check at all

*Relates to: "Science camera temperature and the dark-frame library" (`flat_acquisition`) in CLAUDE.md.*

The last of the four SEQUENCER acquisition sub-plugins (DARK/BIAS/CALIB/FLAT), and by the user's own framing the simplest: shot once per session and reused for the rest of it, full stop — two parameters (`count`, `exposure_time_seconds`, user-supplied defaults 5 × 3s), one existence check, no library. Explicitly and deliberately simpler than `calib_acquisition`: no `max_age_hours`, no most-recent-batch logic, since flat-field correction depends on neither sensor temperature (DARK/BIAS's axis) nor lamp drift over time (CALIB's axis) — it's about optical vignetting/sensor uniformity, which doesn't change within a session. `_find_usable_flat_series()` still checks sensor size and `EXPTIME` tolerance (same `EXPOSURE_TIME_TOLERANCE_SECONDS` constant `dark_library_helpers.py` already defines), just with no temperature or age filter at all — kept local to `flat_acquisition.py` rather than folded into the shared `find_usable_frame_series()`, same reasoning as `calib_acquisition`'s own local helper: each acquisition sub-plugin's staleness policy is different enough (temperature / age / none) that forcing them through one increasingly-parameterized shared function would cost more clarity than it would save. Wired into `Be_stars.yaml` right after `calib_acquisition`. `reduction_plugins/flat` does not yet consume `sequencer_data["flat_acquisition"]` — it still only reads `reduction_data["dark"]`, unchanged by this chantier, a separate future gap now noted in CLAUDE.md's "Not yet done" line. 640/640 tests passing (11 new).

## 2026-08-28 — Live SEQUENCER/REDUCTION step progress: design pivot, `DISPLAY_NAME`, and two real bugs

*Relates to: "GUI" (Live SEQUENCER/REDUCTION step progress) and "Plugin system" (`DISPLAY_NAME`) in CLAUDE.md.*

The user's own idea, floated at the end of an earlier session's planning: raw sub-plugin names (`star_spectra_acquisition`, `dark_acquisition`...) would make unreadable GUI chip labels, so each sub-plugin should declare a short `DISPLAY_NAME` — deliberately mirroring the existing module-docstring convention (`ast.parse`, never imported, same never-trigger-import-side-effects reasoning). Landed across all `sequencer_plugins/`/`reduction_plugins/` modules plus `sharing_plugins/blank_share` (added there purely for catalogue consistency with the docstring rule, even though SHARING never shows step progress).

The step-progress feature itself started from a design already fully worked out in a *previous* session (see the now-superseded plan this entry's CLAUDE.md section replaces): one shared, temporary line per observation, showing whichever stage (SEQUENCER or REDUCTION) currently "owned" it, in-memory only (`step_progress.py`), folded into the GUI's existing poll — a DB column and a WebSocket push were both considered and rejected back then (plugin names are plugin identity, must stay out of the plugin-agnostic DB; true mid-step liveness wasn't required). That mechanical design landed unchanged. What *did* change, once the user tested the shipped feature live in a real browser:

- **REDUCTION's line was never actually visible** — not a bug, a consequence of the single-shared-line design: `step_progress.py` originally kept one entry per `obs_id`, overwritten every time a new stage's steps ran, so the instant REDUCTION's fast (simulated) steps started, SEQUENCER's already-finished data was gone, and REDUCTION itself typically completed inside one ~3s poll window. The user asked for a dedicated third line for REDUCTION, shown independently of SEQUENCER's — this forced `step_progress.py`'s data model from `{obs_id: {stage, step, steps}}` to `{obs_id: {stage: {step, steps}}}`, so each stage's last-known state survives the other stage starting or finishing.
- **10-second post-observation hold** — the user additionally asked to keep both lines visible (showing their final "all done" state) for a short grace period after the whole observation finishes, so the full pipeline can be seen at a glance before the row collapses back to just the primary stage chips. Implemented entirely client-side (`STEP_PROGRESS_HOLD_SECONDS`, `main.ts`) from timestamps `GET /observations/recent` already returns (`obs.stages["archive"].done_at`) — no backend change needed for the hold itself, only for making both stages' data survive long enough to still be there when the hold window checks it.

Two real bugs were caught only because the user insisted on testing in an actual browser after each change, not just running `pytest`:

1. **Dead `sub_cols` wiring** — `renderObs()` computed `stagesColumn` (the `VBox` wrapping the new step-progress lines) but the actual `sub_cols` array entry still hardcoded a fresh `new HBox({cls:"obs-stages", content: stages})`, ignoring the computed variable entirely. TypeScript compiled clean, no console error — the feature was simply invisible end-to-end until a live test reported "same UI as before," which is what surfaced it.
2. **`from __future__ import annotations` must be the literal first statement after a module's docstring** — inserting `DISPLAY_NAME = "..."` before it in every edited sub-plugin file raised a `SyntaxError` at import time in all ~20 files at once, caught immediately by the test suite (not by the browser this time). Fixed with one `perl -0777` pass swapping the two lines back into the correct order everywhere, at the user's explicit request for "one global command" once it was clear the fix was mechanically identical across every file.

A third, non-visual issue also surfaced from full-suite (not per-file) test runs: `step_progress._current_steps` is deliberately process-global, in-memory state — once `plugins/sequencer.py`/`reduction.py` started calling the *real* `step_progress.set_step()` from tests that don't mock it, those tests leaked entries into the shared dict for the rest of the pytest session, occasionally failing an unrelated, later `test_step_progress.py` test depending on run order. Fixed with a new `autouse=True` fixture in the shared `conftest.py` (`_clear_step_progress`), the same isolation pattern `tmp_data_dir` already uses for the temporary database paths.

No browser-automation tooling was available in the assisting agent's own sandbox (no `npm`/`node` on `PATH`, no `chromium-cli`, no Playwright) — every live-browser verification in this session, including catching both real bugs above, was done by the user directly, not by the agent. 658/658 tests passing.

## 2026-08-29 — GPLv3 adopted; PANOPTES/POCS attribution formalized

*Relates to: "Licensing" in CLAUDE.md.*

The user asked what it would actually take to make the whole app GPLv3-compliant — specifically whether a file simply stating "we comply with GPLv3" would be enough (it isn't: the license itself, verbatim, is what has to be distributed with the software, not a statement of intent). Landed as **GPLv3-or-later**, copyright held by "The ROSACE project" (a deliberate choice over an individual's name).

A full dependency license audit was done before writing anything, rather than assuming: every Python/GUI dependency turned out to already be GPLv3-compatible (MIT/BSD-3-Clause/Apache-2.0, plus `pyindi-client` itself being GPLv3-or-later — actually an argument *for* this choice, not just a compatibility check). One real gap surfaced: `x4js`, the GUI's sole framework, declares **no license at all** — not in its `package.json`, not on the npm registry, not on its GitHub repo (`rlibre/x4`), checked three independent ways. Under default copyright that grants no usage/redistribution rights, but the user knows the library's author personally and is handling it directly — explicitly not something this codebase or a future session needs to chase. **Corrected 2026-09-08**: the user later pointed at x4js's own official documentation site, which does state a license — see the same-day entry below.

The more substantial finding was that `hardware_indi/` (`wrapper/` and most of `devices/`) is not just "inspired by" PANOPTES/POCS as CLAUDE.md's existing one-line mention implied, but contains real, substantial derived code — read in full rather than assumed: `indi_client.py`'s shared-singleton client-per-host, BLOB queue/listener architecture, and generic property-handler registry, and `indi_device.py`'s INDI property-type abstraction dictionaries, both sharing a distinctive comment style (`# Basic stuff` / `# Indi stuff`, `<begin=Virtual methods>` markers) with the two files that already carried an explicit "adapted from POCS" note (`base.py`, `errors.py`). POCS's own license (verified: MIT) only requires retaining its copyright/permission notice — no copyleft propagation, so combining it into a GPLv3 project raised no compatibility conflict. The user's own reaction mattered here: rather than treating this as an unwanted compliance burden, they explicitly wanted to credit PANOPTES ("ce projet a vraiment été à l'origine de pas mal de nos réflexions") while avoiding needless overhead — resolved by pointing out those aren't actually in tension: MIT's entire obligation *is* a retained credit, so a `THIRD_PARTY_LICENSES.md` file satisfies both at once. Rewriting the substantial files to dodge attribution was considered and rejected — real risk (this code drives actual mount/camera hardware) for zero practical gain against an obligation this light.

Landed: `LICENSE` (full GPLv3 text) and `THIRD_PARTY_LICENSES.md` (POCS MIT attribution + license text) at the repo root; a `## License` section in the README (GPLv3-or-later, `GPL-3.0-or-later` SPDX id, link to the third-party file, plus a plain-language bullet summary explicitly marked non-authoritative); the POCS-heritage docstring note extended to the 5 remaining substantially-derived files that lacked one (`indi_client.py`, `indi_device.py`, `indi_web_manager_client.py`, `mount.py`, `camera.py`, `focuser.py`, `filter_wheel.py`); and a deliberately limited per-file header pass — the full FSF boilerplate on `main.py` only, the short 2-line SPDX form on 13 other core modules (`models.py`, `config.py`, `database.py`, `auth.py`, `targets.py`, `observation_file.py`, `log_config.py`, `log_broadcast.py`, `image_broadcast.py`, `step_progress.py`, `astro_math.py`, `time_helpers.py`, `simbad.py`), and nothing at all in `plugins/`, any sub-plugin directory, or test files — a header on every one of the package's ~160 `.py` files would repeat what the root `LICENSE` already covers, for no added legal effect.

Two process notes worth keeping: first, "(at your option) any later version" is the license grant's own legal phrasing (addressed to whoever exercises rights over the software) and doesn't read naturally as a project's *description* of its own licensing choice — the README instead uses the `GPL-3.0-or-later` SPDX identifier, which says the same thing without the awkward second-person clause. Second, and more procedurally: fetching the *exact* GPLv3 text through an AI-mediated tool (WebFetch) was judged too risky for a legal document of that length (674 lines) — its own tool description warns large content "may be summarized" — so the user downloaded it directly (`curl` from their own machine) instead, verified afterward for structural completeness (all 18 sections present, correct preamble/ending). The much shorter MIT text (POCS's own `LICENSE.txt`, ~20 lines) was judged low-risk and fetched via WebFetch directly, cross-checked against well-established knowledge of the standard MIT boilerplate.

## 2026-08-29 — `--demo-mode`: a dedicated, isolated config for zero-hardware local trials

*Relates to: "Trying Rosace without hardware" and "Sequencer sub-plugins" (`_internal.py` naming) in CLAUDE.md.*

Prompted by the community-readiness push (same overall thread as the GPLv3 entry above): the app already had one "try it without hardware" path — the Docker demo — but nothing for someone who has `pip install -e`'d the package locally and wants to see it run before configuring any instrument. The user's first instinct was a `--demo-mode` CLI flag toggling `sequencer_backend` between `internal`/`indi` on the fly; talking through the implications surfaced that this doesn't fit how the rest of the app resolves configuration — everything else here is config-driven, resolved once at import time (`config.py::_resolve_config_path()`), never mutated by a runtime flag.

Two designs were walked through and rejected before landing on the final one:
- **The `blank` scheduler + `sequencer_backend: internal`** — cheapest on paper (zero `targets.db` seeding, `blank` already exists purely as a template). Rejected once actually traced through: `blank`'s hardcoded `_PROGRAM = "Be_stars"` label is *also* the literal program YAML name `pipeline_loader.py` resolves (`scheduler_data["program"]` → `programs/<name>.yaml`) — and the real `Be_stars.yaml` is `indi`-only (`pointing_72ed`, `dark_acquisition`, none of which have an `_internal.py` counterpart). Nobody had noticed because nothing had ever combined `blank` with `internal` before. Fixing `blank`'s label was considered but would only have produced a toy 3-star demo with no catalogue/scheduling features visible at all.
- **A single flag-level override baked into `config.py`** (e.g. `ROSACE_DEMO_MODE=1` forcing `SEQUENCER_BACKEND` regardless of the YAML) — rejected: a second, parallel override mechanism sitting next to the config file itself, when the app has spent real effort (see the Core/Plugin split entry above) making "the YAML is the one source of truth" a load-bearing principle.

Landed design, after the user pushed back with "on peut peut-être s'en passer, non ?" once the mechanics were fully traced through and it became clear `--demo-mode` really was just going to be a path shortcut: a new packaged `conf/config_demo.yaml` — a **full sibling** of `conf/config.yaml` (every Core key present; `config.py` still indexes each with `_cfg["key"]`, no exceptions) — with `sequencer_backend: internal`, the real `scheduler_rosace_2026` (not `blank`, so the catalogue/priority machinery is actually visible), and `base_data_dir: ~/.rosace-demo`, a sibling of the real `~/.rosace` so a demo trial can never contaminate a real installation being built up in parallel. `--demo-mode` itself does nothing but resolve `Path(__file__).parent / "conf" / "config_demo.yaml"` and set `ROSACE_CONFIG` — the same mechanism the pre-existing bare `config_path` positional argument already used, just resolved from a location that doesn't depend on where `pip` happened to install the package (a real requirement once a non-editable `pip install rosace` becomes plausible, not just today's dev checkout). This is also why the file lives inside `rosace/rosace/conf/`, unlike Docker's own `docker/config.demo.yaml`, which the Dockerfile comment deliberately keeps *outside* `rosace/` — Docker's constraint (obviousness that it's not part of the real app) and the native flag's constraint (must travel with the installed package) point in opposite directions.

What actually triggers `demo_seed.py`'s one-time catalogue seeding is `config_demo.yaml`'s own `is_demo: true` key — deliberately optional everywhere else (`config.py`: `bool(_cfg.get("is_demo", False))`, the one Core key that isn't hard-required), read from the *config*, not the CLI flag, so `ROSACE_CONFIG` pointed at this file by hand (e.g. a `uvicorn` launch) behaves identically — consistent with "the flag is sugar for a path, nothing more." The seed data itself (2 stars — Vega/Arcturus, reusing `blank` scheduler's own already-vetted coordinates rather than inventing new ones — one program named `"demo"`) deliberately avoids Docker's richer-but-heavier approach (10 stars, `Be_stars`/`PN`, shadow-copied program YAMLs) — naming the program `"demo"` means it resolves directly to the existing backend-agnostic `programs/demo.yaml`, with no file-shadowing trick needed at all.

Investigating this surfaced two further, unrelated latent bugs, both fixed in the same pass: `docker/seed_demo_data.py` imported `OBSERVATION_LIST_PATH` from `rosace.config`, which had moved to `scheduler_rosace_2026`'s own module during the Core/Plugin split and was never updated there (confirmed broken: a plain `ImportError` on that line); and the packaged `conf/config.yaml`'s actual `sequencer_backend` default was `indi`, while CLAUDE.md's own config table still documented `internal` as the default — a stale doc, now corrected (the user explicitly chose to keep the packaged default at `indi`, real-world-oriented, rather than revert it to `internal`, once `config_demo.yaml` existed as the dedicated zero-hardware path). 664/664 tests passing.

## 2026-08-30 — `hardware_indi/`'s loggers weren't reaching the rotating file or GUI Journal

*Relates to: "Logging" and "INDI hardware drivers" in CLAUDE.md.*

A long-flagged known gap (present in CLAUDE.md's Logging section since before this file existed): every `hardware_indi/` module used a bare `logging.getLogger(__name__)` (or, in `wrapper/base.py::Base.__init__`, `logging.getLogger(self.__class__.__name__)`) instead of a `spectro.*`-prefixed name — so its records propagated to `root` (`conf/logging.cfg`: WARNING-level console only), never reaching the rotating file or the WebSocket-fed GUI Journal. A rejected mount command or a device-level warning was invisible except on the raw server console.

The user asked to fix it, but first asked to confirm it was actually still broken rather than assuming a stale doc line — a real `grep` across `hardware_indi/` (not a memory check) found every call site unchanged.

Tracing which `getLogger()` call actually ends up as each device instance's live `self.logger`, before touching anything, turned up a real subtlety: most `Indi*` device classes (`mount.py`, `focuser.py`, `filter_wheel.py`, `spectro_Alpy600.py`, `usis_spectroscope.py`) set `self.logger = logger or logging.getLogger(__name__)` at the very top of their own `__init__`, *then* call `IndiDevice.__init__(self, ...)` without passing that `logger` through as a kwarg — which itself calls `Base.__init__(self)`, unconditionally overwriting `self.logger` with `logging.getLogger(self.__class__.__name__)` (e.g. `"IndiMount"`, no module path at all). So each subclass's own assignment is effectively dead beyond the one or two debug lines it logs before being overwritten — `wrapper/base.py` is the one call site that actually determines the logger every device instance uses for the rest of its life. `camera.py` was the extreme case: its own `logger = logger or logging.getLogger(__name__)` is a bare local variable, never even assigned to `self.logger`, and never passed anywhere — fully inert.

Given that, `wrapper/base.py` was the highest-leverage fix (`logging.getLogger(f"spectro.indi.{self.__class__.__name__}")` — kept the useful per-class distinction, e.g. `spectro.indi.IndiCamera`/`spectro.indi.IndiMount`, while fixing propagation), but every other call site was fixed too rather than left as confusing not-quite-dead code, for consistency and to close the gap for those transient early lines as well. Landed as a flat `spectro.indi.<short_name>` scheme (module-level loggers) or `spectro.indi.{self.__class__.__name__}` (per-instance, in `base.py`) — user's own call to use the short `indi` segment rather than `hardware_indi`, to keep log lines shorter. `wrapper/indi_web_manager_client.py` got the same treatment after the user asked what that file even was: real, reachable POCS-heritage code (remote INDI driver start/stop via the INDI Web Manager HTTP API, wired into `IndiClient.__init__` when a device's hardware YAML entry declares an `indi_webmanager` key) that happens to be unused by any of Rosace's own hardware profiles today — not dead code to remove, just unexercised. No test changes needed: nothing asserted on logger names. 682/682 tests passing.

## 2026-08-30 — Multi-second gap between PHD2 settling and its lock-position correction: a real plate-solve, not a bug

*Relates to: "INDI hardware drivers" (`pointing_72ed`, Phase 2) and "Key configuration" (`SUBPLUGIN_PARAMS`) in CLAUDE.md.*

Reported directly from a live session: the user watched PHD2's own display and saw several seconds (5+) pass between guiding visibly settling (the green lock-position cross appearing) and the lock position actually being nudged onto the slit — expecting this to be near-instant, and hoping it wasn't a stray `sleep()`.

Phase 1's own call is untouched, still using `solve_wcs()`'s own wider default. Not yet measured against real hardware how much wall-clock time this actually saves — to be confirmed at the next live session. 683/683 tests passing.

## 2026-09-03/04 — DARK/BIAS/CALIB/FLAT reuse: `get_sensor_size()` was the wrong reference, replaced with a live `get_frame_size()`

*Relates to: "Science camera temperature and the dark-frame library" in CLAUDE.md.*

Continuing the DARK/CALIB/FLAT-reshoot anomaly flagged in the 2026-08-31 entry above: live on the real Atik 314L, `CCD_INFO` (`CCD_MAX_X`/`CCD_MAX_Y`, what `get_sensor_size()` read) correctly reported the full sensor, `1391×1039`, throughout — but real exposures kept coming out at `1304×976`. Root cause: the driver's `CCD_FRAME` (its ROI) was stuck on a leftover sub-frame, almost certainly saved by a prior KStars/Ekos session and reloaded from the driver's persisted INDI config on reconnect — confirmed via `indi_getprop`, which even returned the property three times in one call, two of the three already showing the stale size, a sign the driver was re-announcing its saved config. `indi_setprop` from the command line failed to force it back; only forcing the frame size from KStars/Ekos's own INDI control panel actually stuck. Not a Rosace bug in itself — `prepare_shoot()` (`hardware_indi/devices/camera.py`) never touched `CCD_FRAME` before an exposure, so every acquisition just used whatever ROI the driver currently held.

While diagnosing this live, the user raised a real forward-looking problem: sub-framed (windowed) science acquisition is planned for the future, to save memory/disk. The moment that's used deliberately, comparing a candidate dark/bias/calib/flat series against `get_sensor_size()`'s full-sensor max would permanently reject every valid sub-framed series — the exact same symptom as this incident, except self-inflicted and expected rather than a bug to chase. The actual invariant that matters was never "matches the full sensor" — it's "matches whatever the camera is currently configured to produce," full-frame or sub-framed alike.

Fixed by replacing `hardware/camera.py::Camera.get_sensor_size()` (INDI `CCD_INFO`) with `get_frame_size()`, backed by `IndiCamera.get_roi()` (`CCD_FRAME`) instead — a live query of the *currently configured* ROI, not the sensor's max capability. The four acquisition sub-plugins (`dark_acquisition`, `bias_acquisition`, `calib_acquisition`, `flat_acquisition`) and `dark_library_helpers.py::find_usable_frame_series()` (plus `flat_acquisition.py`'s own local `_find_usable_flat_series()`) were switched to call it, with their `sensor_size` parameter renamed to `frame_size` throughout to match. The raw `IndiCamera.get_sensor_size()` device method itself was left untouched — still used internally by the unused-by-Rosace `get_thumbnail()` (a POCS leftover), out of scope here. This also fully resolves the reshoot symptom itself, regardless of *why* `CCD_FRAME` got stuck: whatever the camera is configured to produce at the moment of comparison is now what a freshly-shot library series is compared against too, so the two can never structurally disagree the way `CCD_INFO` vs. real `CCD_FRAME` just did.

Explicitly deferred by the user until after the in-progress sky-test period, then implemented at a calm moment as agreed — no hardware-facing code was touched during or immediately before a live session. 683/683 tests passing.

## 2026-09-06 — Hardware YAML vs. general config: moving `guiding_camera.exposure_seconds`/`slit_x`/`slit_y`/`sampling_arcsec` out of the hardware profile

*Relates to: the 2026-09-05/06 entry above (its "deliberately not touched" note), "Guiding-camera dark subtraction", `pointing_72ed`, and the "Configuration" section's Core/Plugin split in CLAUDE.md.*

Picked up the chantier the previous entry deliberately deferred. The user restated Rosace's underlying principle first, before any file was touched: the hardware YAML should hold only what's genuinely specific to one unitary device (connection data first and foremost, but also a device's own physical/electrical traits — `cooling_capability`, `temperature_tolerance_deg_c`, `focus_range`, a mount's own `backlash_offset_deg`); anything describing the *instrument as a whole* belongs in the general config file instead. The hardware/general split exists specifically so the physical-connection layer stays swappable and isolated — including down to running with no hardware connected at all (demo mode) — while the centralized config file stays the one place describing how the assembled instrument actually behaves.

Two decisions were made explicitly before any edit, both by the user's own judgment call, not decided by Claude in isolation:

- **PHD2 stays entirely in the hardware YAML**, connection fields and behavior (`profile_name`, `exposure_time_sec`, `settle`) alike — not split. Claude's first proposal was to split PHD2's own `host`/`port` (hardware) from its guiding-strategy fields (general config), by the same device/instrument reasoning as everything else. The user pushed back: PHD2 is a self-contained, "detached" subsystem (on the 72ED it runs remotely on the Stellarmate, independent of Rosace's own process) that describes its own complete operation on its own — splitting it would fragment one coherent thing for no real gain, unlike `guiding_camera`'s slit/scale values, which genuinely don't belong to the camera in isolation.
- **`slit_x`/`slit_y`/`sampling_arcsec`/`exposure_seconds` move, evaluated one at a time, not as a bulk category.** `slit_x`/`slit_y` (spectrograph slit position in the guiding camera's field): an alignment fact of the assembled telescope+spectro+camera, not the camera's own trait — swap the guiding camera and the physical slit position doesn't move, only its pixel coordinates would. `sampling_arcsec` (plate scale): derived from telescope focal length *and* camera pixel size — an instrument-level fact even though it mixes in one device property. `exposure_seconds` (direct guide-image exposure time): an operational choice of the pointing/guiding strategy, not a device capability — same category as `bias_acquisition.exposure_time_seconds` already living in `subplugin_params`.
- This directly resolves the stale-LAN-profile problem the previous entry flagged: `hardware_indi_72ED-LAN.yaml`'s `slit_x`/`slit_y` were left as an uncalibrated placeholder while `-WIFI.yaml`'s were the real, field-calibrated values (`613`/`616`, tuned 2026-09-04) for what the user confirmed is the *same physical instrument*, only reached over a different network path. The user chose the WIFI values as the single reference now shared by both profiles — LAN's placeholder is gone, not silently perpetuated.

Placement within `config.yaml`/`config72ED.yaml` was also worked through explicitly rather than assumed: applying CLAUDE.md's own already-documented Core/Plugin rule (Core = read by `main.py`/`auth.py`/`database.py` or a selector key; everything else is Plugin) settles it cleanly — these four values are read only by SEQUENCER sub-plugins (`pointing_72ed`, `stop_phd2_guiding_diag`, `guiding_dark_acquisition`), never by the orchestrator, so they're `subplugin_params`, not Core. Landed as a new nested `guiding:` block at the *root* of `subplugin_params` (`subplugin_params.guiding: {exposure_seconds, sampling_arcsec, slit_x, slit_y}`) — root because several sub-plugins share it (the existing rule for a shared key), nested (a first for a root-level entry — every prior root key was a flat scalar) purely for readability, grouping four values that describe one coherent concept under a domain name rather than either scattering four `guiding_`-prefixed scalars at the root or arbitrarily attaching them to one of its three consumers (`pointing_72ed`) as if it alone owned them. `config.yaml` (paired with `hardware_indi_simu`) and `config72ED.yaml` (paired with the real 72ED profiles) each carry their own `guiding:` values matching their own paired instrument — consistent with the existing one-config-per-instrument principle.

`pointing_72ed.py`/`stop_phd2_guiding_diag.py` now read `SUBPLUGIN_PARAMS.get("guiding", {})` at call time inside `execute()` rather than `obs.hardware_config["guiding_camera"]`; `guiding_dark_acquisition.py` does the same for `exposure_seconds` alone. Deliberately *not* hoisted into module-level constants (unlike `PHASE2_SEARCH_RADIUS_DEG`/`GUIDING_DARK_COUNT` elsewhere in these same files, which do use that pattern): `slit_x`/`slit_y` have no sensible built-in default, so a missing key must raise clearly the moment it's actually needed — hoisting the lookup to import time would instead crash server startup for *any* installation, including ones that never use `pointing_72ed` at all.

## 2026-09-06 — Reinstating the AM3's post-unpark SYNC, provisionally, to field-test on real hardware whether the 2026-08-26 concern actually applies to it

## 2026-09-08 — `sequencer_prefix`: hardware-driven SEQUENCER steps, so equipment concerns stop leaking into scientific program YAMLs

*Relates to: `home_sync_am3` (2026-08-26, 2026-09-06 entries above), `guiding_dark_acquisition` (2026-09-05/06 entry), and the Plugin system section in CLAUDE.md.*

The user flagged a real architecture smell while testing the previous SYNC-reinstatement change: `home_sync_am3` was declared inside `Be_stars.yaml`, a *scientific* program YAML — but re-homing/syncing the AM3 is an *equipment* concern, unrelated to which stars a program observes. Any future program using this same instrument would have to remember to declare it too; swapping mounts would mean editing every program YAML by hand.

**Design, confirmed with the user before coding**: the active hardware profile can now declare `sequencer_prefix:` (a list, e.g. `[home_sync_am3]`) — steps prepended automatically to every program's own `sequencer:` list. Two clarifying questions from the user shaped the final design: whether one or several names should be supported (a list, from day one — costs nothing over a single string and avoids a future reshape), and whether the mechanism itself special-cases the simulator (it doesn't — `hardware_sequencer_prefix()` just reads `.get("sequencer_prefix", [])`; the simulator profile simply never declares the key, exactly like any other profile with nothing equipment-specific to add). The user also asked directly what `zip()` does and why a single source function was needed — worth remembering the *reason* it's a single function, not a rule to just follow: `SequencerPlugin.run()` builds `obs.program_steps["sequencer"]` (the step *names*) independently from `load_pipelines()` building the sub-plugin *instances*, then `zip()`s the two together positionally — if each place computed its own prefix, a bug in either one would silently pair the wrong name with the wrong instance, with no error, just a wrong name in the observation dossier.

Landed: `pipeline_loader.py::hardware_sequencer_prefix()` (gated on `SEQUENCER_BACKEND == "indi"` — no hardware profile is meaningfully "active" for the internal/demo backend), called identically by `load_pipelines()` and `SequencerPlugin.run()`. `hardware_indi_72ED-WIFI.yaml`/`-LAN.yaml` gained `sequencer_prefix: [home_sync_am3]`; `Be_stars.yaml` lost its own `- home_sync_am3` line (replaced with a one-line comment pointing future readers at the hardware profile instead — the user was explicit that a comment explaining *what changed* has no value to a future reader, but a comment explaining *where else to look* does). `hardware_indi_simu.yaml` declares nothing, by design.

**Immediately surfaced two more bugs, live**, both found by the user actually testing against the simulator right after this landed:

1. **The mount stayed parked forever on the simulator.** `CLOSE_SESSION` parks the mount generically at the end of *every* session (`plugins/close_session.py`, pre-existing). `home_sync_am3`'s own `park()`+`unpark()` used to run unconditionally in `Be_stars.yaml`, so it always undid that park at the start of the next session — including, incidentally, on the simulator. Once `home_sync_am3` stopped running there, nothing did. `IndiMount.set_coord()` — used by every slew — silently no-ops (a warning log, not an exception) on a parked mount, so `pointing_72ed` kept "slewing" without the mount actually moving; every guide image captured the same static field regardless of the intended target, and `solve-field` timed out searching for a target that wasn't anywhere in the frame. Fixed with a **generic** `mount.unpark()` in `INIT_SESSION`, symmetric to `CLOSE_SESSION`'s park — deliberately *not* folded into `sequencer_prefix`/`home_sync_am3`, since "let the mount move at all" is a baseline precondition for any mount, not an AM3-specific ritual. Confirmed compatible with `home_sync_am3` on the real AM3: `unpark()` alone is a fast state change, not physical motion, so the two calls (generic, then `home_sync_am3`'s own re-park/unpark/sync) don't conflict — the real, slow re-homing motion still happens exactly once.
2. **`guiding_dark_acquisition` can't produce a real dark on the simulator either** — same underlying shape of problem, caught by the user *before* writing any code this time, purely by reasoning through the consequences: `SpectroscopePlaceholder.set_light_source()` is a pure in-memory no-op (confirmed by reading its source), so a "DARK" shot on the simulator is just another star exposure mislabeled as dark. Claude's first proposal (move `guiding_dark_acquisition` into `sequencer_prefix` too, mirroring `home_sync_am3`) was flagged by the user as more complexity than needed, and rightly so: `capture_guide_image()`'s dark-subtraction defaults to `subtract_dark=True` and raises `RuntimeError` if the casier is missing — moving the sub-plugin out of the simulator's path without also touching that default would have just traded one crash for another. The user's own alternative, simpler by construction: keep `guiding_dark_acquisition` exactly where it is (it's useful on *any* hardware, unlike `home_sync_am3`) and have it write a synthetic all-zero "dark" when the equipment can't produce a real one — a true no-op once subtracted, with zero changes needed anywhere downstream. Implemented via a new `obstructs_light: false` flag on the simulator's `spectroscope:` entry (`hardware_indi_simu.yaml` only — real profiles need nothing, default `true`), read through the same generic `hardware_config` mechanism already used for `cooling`/`cooling_capability`. New `synthetic` origin alongside `current_session`/`camera`.

## 2026-09-11 — Real-AM3 field test: computed sync vs. measured sync, plus a live session exposing a USB-disconnect cascade

*Relates to: `home_sync_am3` in CLAUDE.md (the 2026-09-06 "Reinstating the AM3's post-unpark SYNC" entry above), and [[project_am3_home_sync]]/[[project_pointing_phase2_investigation]] in memory.*

Two things happened the same evening: a dedicated field test of `home_sync_am3`'s homing strategies, then a full real observing session run right after with the current (computed-sync) code — together they gave the clearest picture yet of where this mount's pointing accuracy actually stands.

**The field test** was a standalone script (not part of the app, not committed — same throwaway status as `check_science_camera_sensor_size.py` before it), comparing three homing strategies side by side on the same hardware, each followed by blind GOTOs to three widely-separated stars (bet Peg, gam Cas, Deneb) with a plate-solve measuring the real landing position:

- **A. `sync_computed`** — today's `home_sync_am3` behavior: park → unpark → sync to the theoretically-derived Home position.
- **B. `park_unpark_only`** — park → unpark, no explicit sync (`SYNC_TO_COMPUTED_HOME=False`'s path).
- **C. `sync_measured`** — park → unpark → slew to a calibration point ~20° from zenith, 10° east of the meridian (deliberately not *on* the meridian, to avoid a pier-flip risk right after unpark) → capture a guide image → plate-solve it → sync to that *measured* position instead of a computed one.

First run: the Stellarmate's clock had drifted again (the same still-unresolved "mount-reference mystery" from `project_am3_home_sync` in memory) — A and B landed 5-9° off, **identical to each other** (confirming a plain sync to a computed value adds nothing over `unpark()` alone: both derive from the same time+site math, so of course they agree), while C corrected instantly to 1-3′. Once the clock was fixed by hand, A and B dropped to a consistent **~25′** residual across all three stars — remarkably stable given the three targets sit at very different declinations (28°, 45°, 61°) and were tested minutes apart. C's own calibration-point measurement independently found the same ~27′ offset, a nice cross-check. The user's working hypothesis is a leveling defect rather than polar alignment specifically (polar alignment was otherwise unchanged and had already been confirmed good) — plausible, but not yet distinguished from a small polar-alignment defect by this data alone: all three measurements were taken within the same few minutes of sidereal time, too narrow a spread of hour angles to apply the DEC-sign-flip test already established in `project_pointing_phase2_investigation`. **A real risk found in method C, not previously anticipated**: the very first `slew_to()` issued immediately after the measured sync was silently ignored on the real AM3 — `mount.get_position()` right after that "slew" still read back the just-synced calibration coordinates, not the commanded target, and the resulting guide image's plate-solve timed out searching in the wrong part of the sky (the position hint was the commanded target, ~49° away from where the mount actually still was). This confirmed the mount never actually started moving before `slew_to()`'s wait returned, then presumably began the real 50° slew during the following 10s exposure, producing the visible trail.

**Root cause**: `IndiDevice.set_number(..., sync=True)` (`hardware_indi/wrapper/indi_device.py::__wait_prop_status()`) polls the target property's state starting immediately after `sendNewNumber()`, with no pause. `EQUATORIAL_EOD_COORD` had just been left at `IPS_OK` by the SYNC operation moments before (a SYNC completes near-instantly, no physical motion) — when the very next `slew_to()` call wrote a new coordinate to that same property, the first poll ran before the driver had a chance to flip the property to `IPS_BUSY`, so the wait saw the stale `IPS_OK` and returned immediately, believing the slew already complete. A pure client-side race, specific to two coordinate-changing commands issued back-to-back on the same INDI property (sync immediately followed by slew here; in principle any rapid slew-then-slew sequence too) — not a driver bug.

**Fix — `IndiMount._verify_slew_reached()`** (`hardware_indi/devices/mount.py`), called from both `slew_to_coord_and_stop()`/`slew_to_coord_and_track()` right after `set_coord()` (skipped while parked, since `set_coord()` itself no-ops then): re-reads `get_current_coordinates()` and compares it to the commanded coordinate, polling every 0.5s for up to `SLEW_VERIFY_TIMEOUT_SECONDS` (180s, matching `set_coord()`'s own property-wait timeout) until within `SLEW_POSITION_TOLERANCE_ARCMIN` before returning — raising `RuntimeError` (wrapped by `MountAdapter` into `DeviceCommandError` like any other mount failure, no adapter change needed) if it never converges.

The 10′ tolerance itself was a deliberate, jointly-reasoned choice, not a guess: a genuinely completed slew's own readback noise, from the same night's real session log, is ~1-2″ (e.g. `commanded 279.23473` vs `mount reports 279.23418`) — three orders of magnitude below any reasonable threshold — while the smallest deliberate *close* slew this codebase issues today is `_slew_with_backlash_approach()`'s own 2° (120′) preliminary offset (confirmed against all three real hardware profiles' `backlash_offset_deg`). The user's own instinct was to keep the tolerance as small as the noise floor allows rather than generously large (initially considering 30′), specifically to minimize the (already small) residual risk of two real, angularly close successive targets masking a stuck slew — 10′ sits comfortably below the backlash offset with over 100x margin above the noise floor, so there was no reason not to take the tighter value.

## 2026-09-16 — Minimum sub-exposure count, a config-lookup bug it exposed, and a real-time demo backend

*Relates to: "Science camera temperature and the dark-frame library"/"Key configuration" in CLAUDE.md (the `compute_exposure_time_and_count()` policy and `subplugin_params` placement rules); [[project_exposure_min_count_policy]], [[feedback_config_key_placement_verify_lookup]], [[project_demo_mode_realtime_and_catalogue]], [[project_gui_observations_list_reorder]] in memory.*

Starting point: the user wants to move Rosace's exposure times from short debug values to realistic ones, and separately wants a guaranteed minimum number of frames per star, since `compute_exposure_time_and_count()` previously gave a bright star a single sub-exposure whenever the computed/explicit duration stayed under `max_exposure_time` — no stacking margin, no cosmic-ray rejection.

**Design deliberation on the splitting rule.** My first proposal was to keep the *total* exposure time fixed and divide it evenly across at least `min_exposure_count` sub-exposures (`sub_exposure = raw / count`) — the natural generalization of the existing over-max `ceil()` splitting. The user rejected this in favor of a different, simpler model: below `max_exposure_time`, the computed/explicit duration is the *per-frame* target, not a total budget — repeat it unchanged at least `min_exposure_count` times, so the total exposure actually grows with the frame count instead of staying fixed. Above `max_exposure_time`, the existing `ceil(raw/max)` behavior stays, with `min_exposure_count` only ever raising that count, never lowering it. This reframes `program_stars.exposure_time`/the magnitude formula as "the ideal single-exposure duration," meant to be overridden per star specifically when it would saturate that star — not as a total integration budget, which is how the code (and its docstring) had read until now.

**Config placement, and a bug it caused.** `min_exposure_count` is read only by `star_spectra_acquisition` (both backends), which by CLAUDE.md's own stated default rule ("nest a single-consumer key under its own sub-plugin name") argued for nesting it under `subplugin_params.star_spectra_acquisition`. The user overrode this twice, pointing out the exact precedent CLAUDE.md already documents for `exposure_time_mag0_seconds`: it sits at `subplugin_params`'s *root*, alongside `max_exposure_time_seconds`, despite having a single consumer too — because both are arguments of the very same `compute_exposure_time_and_count()` call, and grouping arguments of one call together for readability outranks the consumer-count rule. `min_exposure_count` moved to the root to match.

The YAML files were updated to the new location, but the Python lookup in both `star_spectra_acquisition.py`/`_internal.py` was left reading the old nested path (`SUBPLUGIN_PARAMS.get("star_spectra_acquisition", {}).get("min_exposure_count", 5)`) — a plain oversight, not caught by the 744-test suite because every test that exercises the count logic monkeypatches the resulting module constant directly (`monkeypatch.setattr(ssa_mod, "MIN_EXPOSURE_COUNT", ...)`), never the real `SUBPLUGIN_PARAMS` lookup chain. It only surfaced once the user actually ran `--demo-mode` and got 5 exposures instead of the 3 configured in `config_demo.yaml` — the hardcoded fallback default, silently winning every time. Fixed by reading `SUBPLUGIN_PARAMS.get("min_exposure_count", 5)` directly, matching the two sibling keys. Lesson generalized in [[feedback_config_key_placement_verify_lookup]]: a `subplugin_params` key's *location* and its code lookup path have to be changed together, and tests that patch the constant instead of exercising the real config chain can't catch a mismatch.

**Values landed**: `min_exposure_count`/`max_exposure_time_seconds` are `3`/`10` in both `config.yaml` (INDI simulator) and `config_demo.yaml`, and `5`/`120` in `config72ED.yaml` (the real telescope) — the user's own choice, keeping the simulator/demo configs fast to iterate on while the real-hardware config gets a realistic ceiling. `exposure_time_mag0_seconds` stayed at `1.0` everywhere, not revisited. ## 2026-09-20 — A guiding camera running at gain=0, a night's post-mortem, and a new `focus`

*Relates to: "Guiding-camera dark subtraction", the new "Guiding-camera focus quality measurement" section, "Generic device interfaces (`hardware/`) and INDI adapters" (`IndiCamera`/`IndiASICamera`), and the PHD2 client in CLAUDE.md; [[project_guiding_camera_gain_offset]], [[project_session_2026-09-19_night_analysis]], [[project_guiding_camera_focus_check]], [[project_usb_disconnect_hardening]], [[project_focus_subplugin_removal]] in memory.*

The 2026-09-19 night ran almost entirely unattended and almost entirely failed — only Vega, the first target, completed. Diagnosing why, the same morning, turned into the day's real work: a genuine hardware bug, two wrong hypotheses correctly rejected by the user before the right one held, a new sub-plugin, and a session-close PHD2 fix, all from one thread pulled on a report of black guiding images.

**The night's own post-mortem, first.** Reading the session log end to end: Sheliak through nu Cyg (ten observations) failed with PHD2's `all equipment must be connected first` — the same non-recovering equipment-link loss as 2026-09-11 and 2026-09-18, this time with no visible INDI device churn in Rosace's own log, so the root trigger stayed unexplained even as the symptom repeated. Independently, from Electra (20:53) to the last target before the user stopped the session (03:02), every remaining observation failed at Phase 1's own plate-solve — a problem `pointing_72ed` reaches before PHD2 is ever involved, so it could not be the same cause. Not clouds (a clear sky that night, by the user's own report): the pattern across six hours, regardless of target brightness or position, pointed at something systematic on the guiding camera itself.

**Three wrong turns before the real one, working from that same guiding camera.** First, comparing raw guide frames against their darks: the darks (a single `GUIDINGDARK_..._median.fits` shot once at session start and reused all night, by design) came out with `std == 0` and 91–92% of later-night frames clipped to exactly zero once subtracted — read as "the dark doesn't block real light" (DAOStarFinder even reported dozens of "stars" in a dark frame). The user asked for the exact filename and looked himself: a genuine flat, uniform ~32 ADU frame. Re-examining the "detections" showed peaks of 48–240 ADU on a 32±6.6 background — pure noise passing a 6-sigma shape filter across over a million pixels, and the frame's real 32000+ ADU outlier had been correctly rejected by that same filter, unrelated to the false "stars". Second hypothesis, also proposed and also rejected on the user's own first-principles objection: that the sky had simply grown darker than the fixed once-per-session dark as the night went on. He pointed out that a real night image always *contains* the dark plus a non-zero sky background — it can never read below the dark level on a site that isn't perfectly black — so a raw frame reading at the dark's own level was impossible if both were behaving normally. Checking raw pre-subtraction frames confirmed his objection: Vega's (48 ADU, real noise, std 26.9) sat clearly above the dark; zeta Tau's and kappa Dra's (32.0 ADU, std ~7) were statistically indistinguishable from the dark itself.

**The real cause, found by the user from one observation**: "a std of exactly 0 in a real image dark doesn't exist — gain/offset problem?" Every pixel value in the raw dark frames turned out to be an exact multiple of 16 (98 distinct values, dominated by 32 then 16, 48, 64…) — the signature of a 12-bit ADC value stored left-shifted by four bits, meaning "32" is a native reading of 2 out of 4095, pinned almost exactly to the converter's floor. He checked KStars directly: the guiding camera's gain and offset were both 0. Grepping the codebase found why — `IndiCamera.set_gain()`/`set_offset()` (`hardware_indi/devices/camera.py`) exist and work, but nothing had ever called them: `self.default_gain`/`self.default_offset` (falling back to class constants when a hardware YAML doesn't declare them, which none did) were stored as plain attributes and never pushed to the real device, which had simply been running on whatever it already had.

**Confirming the fix live turned up a second bug, not just a missing call.** `IndiCamera.connect()` was given a small override that pushes `set_gain()`/`set_offset()` once, right after connecting, but only for a device whose hardware YAML explicitly declares the values (a CCD like the Atik 314L has no such properties and must never be touched) — requiring `__init__`'s attribute assignment to move ahead of `connect_on_create`, since the override reads `self.gain`/`self.offset` before they would otherwise exist. The first real-hardware test capture then timed out waiting for a `CCD_GAIN` property that doesn't exist on this driver: querying the connected device directly showed gain/offset live under a single combined `CCD_CONTROLS` vector (elements `Gain`/`Offset`), not the separate `CCD_GAIN`/`CCD_OFFSET` the PANOPTES-derived `IndiCamera` assumes. The fix already existed — `IndiASICamera` (`hardware_indi/devices/asi_camera.py`), which the user confirmed his own team had written months earlier and simply forgotten, already overrides exactly these four methods correctly. `guiding_camera` was switched from `IndiCamera`/`camera` to `IndiASICamera`/`asi_camera` in both `hardware_indi_72ED-LAN.yaml` and `-WIFI.yaml`; the same class change was applied pre-emptively to `pointing_camera` (unused by any sub-plugin today, but a CMOS camera all the same, "plutôt que de retomber sur un bug le moment venu").

**Tuning the value itself, once the mechanism worked.** The user asked for the offset that would leave no pixel at zero even under a minimum-exposure (64 microsecond) dark — the worst case for read-noise clipping. Three real captures at gain 50: offset 10 left only ~2 native ADU units above the floor (comparable to the noise itself, rejected); offset 15 left ~9–10 sigma of margin (adopted); offset 20 (the value first confirmed working in KStars) left ~17–18, more margin than needed. Both hardware YAMLs now declare `gain: 50`/`offset: 15` on both cameras — the config key itself renamed from `default_gain`/`default_offset` to plain `gain`/`offset` at the user's request, since the "default" prefix implied a fallback that was never how the value was actually used.

**A last paradox, resolved without touching code.** With the fix live, an ultra-short DARK-mode exposure still showed the spectrograph slit's own silhouette — apparently impossible if the beam really is obstructed. It resolved once reframed: the guiding camera doesn't image the sky through the slit at all, it images a pickoff mirror with the slit's shape cut into it, reflecting the surrounding field to the guide camera while the slit's own light goes straight to the spectrograph — the slit's edge is a permanent mechanical feature of that field of view, visible under any trace of stray light regardless of the SKY/DARK/CALIB state, and simply too faint to register at the old, broken gain=0. The user confirmed real stars would not appear this way at night with DARK engaged — the beam genuinely is obstructed for sky light, just not for this one fixed mechanical edge.

**A new `focus`, and a smaller PHD2 fix, closed out the day.** With no way to measure guiding-camera sharpness at all, and the night's plate-solve wave pointing squarely at defocus, the user asked for exactly that: mean FWHM over up to 25 clean stars (hot pixels, elongated "potato" shapes, and saturated stars rejected; SNR floor of 30) in a window centered on the frame, logged at INFO — diagnostic only, everything hardcoded, meant only to confirm the measurement itself is trustworthy before any real autofocus loop is considered. He then asked to fold it into a single `focus` sub-plugin rather than a separately-named one, since the Alpy 600/72ED combination has no meaningful science-camera focus concept at all to keep the old, never-implemented placeholder (`sleep(1)`, unused by any real program) around for — done through Claude Code's plan mode, approved as one block, which also caught two Docker demo program YAMLs (`docker/demo_programs/*.yaml`) that a same-session grep scoped to the main package had missed, and that this file's own August entry on the deferred removal had already flagged. Separately, `phd2_client.py` gained `get_connected()`/`set_connected()` and a self-check inside `start_guiding()`: PHD2 can lose its own equipment link independently of the TCP connection to it, and the fix is deliberately narrow — check and repair only at the one place the failure actually bites, no polling. Why PHD2 loses that link in the first place is still open. 826 tests by the end of the day; neither fix has yet been seen running on a real night.

**First simulator test of the day's changes found one more gap.** Running `Be_stars` against `hardware_indi_simu.yaml` for the first time with the new `pointing_72ed`/`focus` sequence, `Pointing72edPlugin` crashed immediately: `capture_guide_image()` requires `sequencer_data["guiding_dark_acquisition"]` to already exist, but the simulator profile declared no `sequencer_prefix` at all, so that sub-plugin never ran. The fix is narrower than it first looks: add `sequencer_prefix: [guiding_dark_acquisition]` to `hardware_indi_simu.yaml`, deliberately *not* `home_sync_am3` (still excluded, same `ALIGNMENT_SUBSYSTEM_ACTIVE` risk as 2026-08-26) — the simulator's `SpectroscopePlaceholder` already declares `obstructs_light: false`, which is precisely the flag that makes `guiding_dark_acquisition` take its harmless "synthetic" origin (an all-zero placeholder, no real camera capture) rather than shooting a real dark that wouldn't be dark at all on this equipment; the user confirmed that's exactly the property he needed, not a new one. Five tests broke from the same change, all for the same reason: they resolved a real program's pipeline without mocking `hardware_sequencer_prefix()`, implicitly relying on the default test config's simulator profile having an empty prefix — the same class of fragility already fixed once earlier in the day for `demo.yaml`'s step count. Fixed with explicit mocks (an autouse fixture in `TestLoadPipelines`, two added `monkeypatch.setattr` calls in `test_sequencer.py`) rather than updating the hardcoded expectations, so a future hardware-profile change can't silently break them the same way again. 826 tests, unchanged.

## 2026-09-22 — Tuning `focus`'s shape/SNR filters after a 0/11 night, making its window a per-instrument parameter, and a GUI overlay for it

*Relates to: "Guiding-camera focus quality measurement" and "Live image preview" (GUI section) in CLAUDE.md; [[project_guiding_camera_focus_check]], [[project_session_2026-09-20_night_analysis]] in memory.*

The night of 2026-09-20/21 came back with `focus` reporting zero usable measurements out of eleven observations — noted at the time, not yet diagnosed. Revisiting `focus.py`'s own filters directly with the user turned up two false economies, both rejected by the user's own reasoning before any value was actually changed.

**First false lead: could the `roundness` shape filter replace the central search window entirely?** The window's own justification, already in the module's docstring, is that PSF quality away from the optical axis (coma, field curvature) isn't representative of focus. The user asked whether `roundness` — which already rejects non-round shapes — made the window redundant. It doesn't: coma distorts a star's shape (which `roundness` can catch), but field curvature simply defocuses it uniformly — the star stays round, just softer, which is exactly the failure mode this sub-plugin exists to measure, not filter out. A window restricted to the optically-clean part of the field and a shape filter that rejects contamination anywhere in it are answering two different questions (position vs. shape) and neither substitutes for the other. The window stays.

**Second false lead, this one real: `DETECTION_SIGMA` (`DAOStarFinder`'s own convolved-domain threshold, 6σ) and the hand-written `MIN_SNR` (a raw peak-pixel statistic, 30σ) were both gating "is this bright enough to trust", at wildly different strictness, with neither aware of the other.** At 30σ, `MIN_SNR` alone rejected almost everything `DETECTION_SIGMA` had already let through, making the latter contribute nothing beyond a first candidate list. Worse, a raw peak-pixel SNR is directly what a defocused star's spread-out flux reduces, so a threshold this high compounded the same problem as `sharpness` below: penalizing the very thing being measured. Resolution: `MIN_SNR` lowered to `10.0`, `DETECTION_SIGMA` lowered to `5.0` — kept as two distinct checks (different domains, and `MIN_SNR`'s human-readable unit is worth keeping for the log even once it stops being the binding constraint), but no longer redundant at their new, coordinated values. `SHARPNESS_RANGE` — narrower than `photutils`' own default `(0.2, 1.0)` at `(0.4, 0.9)` — was retuned back to that default for the same reason: the tighter lower bound had been penalizing exactly the broadened, less-peaked PSF a real defocus produces. All three new values were checked before being written anywhere, by monkeypatching them onto the existing synthetic test fixtures (hot pixel, elongated "potato" source, low-SNR star) in a throwaway script — all three still correctly rejected, confirming the retune didn't just trade one failure mode for another.

**The search window itself became a real, per-instrument parameter.** Originally a fixed `WINDOW_SIZE = 400` px, then a fraction of the frame height — the user pointed out a fraction of the frame's *smaller* dimension is the more robust definition (no assumption about a landscape sensor baked in, though every guiding camera in use today is one), and that the value itself (0.8) belongs in `config72ED.yaml`, not a code default, since how far off-axis a given instrument's optics stay clean is a fact about *that* instrument, the same category as `backlash_offset_deg`. `subplugin_params.focus.window_fraction` now carries it; the module constant (`DEFAULT_WINDOW_FRACTION`) remains only as the fallback for a config that omits it, same convention as every other `subplugin_params` entry.

**Asked whether any hardcoded constants remained, and got an honest answer, not a silent scope creep**: yes — `SATURATION_ADU` and `FWHM_KERNEL_PX` are, by the same reasoning as `window_fraction`, genuine per-instrument physical facts (sensor ADC scaling, guiding-optics plate scale) rather than algorithm-tuning knobs, and are flagged in CLAUDE.md as the likely next candidates for promotion — not promoted now, since neither has been shown to actually need a different value yet, and turning every constant into a config key pre-emptively was explicitly not the goal.

**A DEBUG-level funnel was added on top of the retune**, precisely so the next bad night doesn't need this same by-hand diagnosis: candidate count straight out of detection (before shape filtering, via a second, gated `DAOStarFinder` pass — the only piece of this logging with a real compute cost, hence the only one behind `log.isEnabledFor(logging.DEBUG)`), the count surviving shape filtering, then how many of those were rejected for saturation, low SNR, or a failed Gaussian fit. INFO-level output is unchanged.

**A separate, smaller finding while proposing this**: `focus.py`'s own `capture_guide_image()` call never passed `image_to_gui=True`, so its guide image was never actually shown on the GUI's "Guidage" panel at all — confirmed by reading the code, not assumed. Fixed alongside the rest.

**The user then asked for a visual reference on "Guidage" itself**: a rectangle showing `focus`'s search window, drawn on the actual displayed image. Since the window is always centered, the rectangle's geometry needs no per-image data from the backend — the GUI can compute it itself from the loaded image's own dimensions and one static fraction, fetched once at startup (`GET /config/focus`, same pattern as `subplugin_display_names`). The one real design question was scoping: the user was explicit that the rectangle must appear **only** on a `focus`-produced image, never on `pointing_72ed`/`stop_phd2_guiding`/`home_sync_am3`'s own captures sharing the same "Guidage" panel — none of those distinguish themselves in the existing WebSocket message at all (`{panel}` only). Solved with a new optional `source` on `capture_guide_image()`/`ws_image_broadcaster.broadcast()`, omitted from the message entirely when not given (so every existing caller's message is byte-for-byte unchanged); `focus.py` is the only caller that passes one (`"focus"`). `main.ts` clears the rectangle explicitly on any non-`focus` image on the same panel, not just on a `focus` one — otherwise it would linger over the next `pointing_72ed` capture pushed to "Guidage". `FitsViewer.paint()` draws it in a solid line, distinct from the "Zone" selection's existing dashed rectangle, reusing that same drawing mechanism rather than inventing a second one. Backend changes verified against the full test suite; the GUI side could not be built or visually checked in this environment (see [[reference_dev_environment]]) and needed `npm run build` plus a hard refresh before it could be.

**First real test, against `hardware_indi_simu`, showed no rectangle at all** — the guide image itself did update on "Guidage" during `focus`, so the `image_source`/broadcast plumbing was working; only the overlay was missing. Root cause: `GET /config/focus` returns `subplugin_params.focus.window_fraction` with no fallback, by design — but `window_fraction` had only been added to `config72ED.yaml` (the real-hardware config, per the user's own "it's per-instrument" reasoning above), never to the packaged `conf/config.yaml` that a simulator run actually uses. The first fix attempted was wrong and caught immediately by the user: duplicating `focus.py`'s own default value as a second constant inside `main.py`, so the endpoint could fall back to it — exactly the orchestrator/plugin boundary this codebase draws everywhere else (`main.py` must never know a sub-plugin's own internals, see the Plugin system section), rejected on sight. The real fix left `main.py` untouched and instead declared `subplugin_params.focus.window_fraction: 0.8` in `conf/config.yaml` too, mirroring `config72ED.yaml` — there's no real optics to protect on the CCD Simulator, but declaring it is what makes the GUI feature visible when testing against the simulator, the same way any other `subplugin_params` entry needs an explicit value to be exercised. Caught a second, unrelated latent issue along the way: a new test for the "unconfigured" branch of `GET /config/focus` had been written to rely on the packaged `config.yaml` genuinely lacking the key — true when written, false the moment this same fix added it — fixed by monkeypatching `SUBPLUGIN_PARAMS` explicitly instead of depending on the ambient config's real content, matching the sibling "configured" test right next to it. 859 tests passing.

**Before trusting any of this to a real night, the retuned algorithm was run against real data**: every corrected guide image still on disk from the 2026-09-20/21 night itself (77 files, `~/.rosace/observations/2026-09-20_St-Pancrasse/GUIDING_*.fits`) — the exact images that produced that night's 0/11. Reconstructing the pre-retune constants in a throwaway script for comparison: the OLD tuning produced a measurement on 14/77 images, the NEW tuning (this entry's `SHARPNESS_RANGE`/`MIN_SNR`/`DETECTION_SIGMA`) on 59/77 — but 22 of those 59 rested on only 1-2 stars, and 3 had a suspiciously small FWHM (<1.5px, one at 0.51px) that turned out, on inspection with the new DEBUG funnel, to be single-star detections right at the SNR floor with astropy's own fitter flagging an unsuccessful fit — noise passing through, not real measurements. Summed across all 77 images, the funnel showed *why*: of 643 candidates surviving shape filtering, 344 (53%) died on the SNR check alone (saturation: 0; failed fit: 6) — by far the dominant bottleneck.

The user asked which single parameter to move to get more stars per image; answered by sweeping the real candidates instead of guessing: `DETECTION_SIGMA=4` turned out to be a false lead (61/77 hits but still only 37 robust — identical to baseline — since it only adds candidates the shape/SNR filters reject anyway), and `MIN_SNR` alone bought more stars at a cost that scaled *faster* than the gain (SNR=7: 71/77 but tiny-FWHM count nearly tripled, 3→8; SNR=5: 77/77 but 12 tiny, one measurement in six looking like noise). `window_fraction` was the better lever on its own: 0.8→0.9 gained 8 robust images for almost no added noise (3→4 tiny) — more real sky area surveyed rather than a lowered bar for what counts as a trustworthy star — though pushed all the way to 1.0 it started reintroducing the off-axis aberration the window exists to keep out, and roughly doubled the noise count (3→6). The user chose a combination, `window_fraction=0.9` + `MIN_SNR=7.0` (also lowering `DEFAULT_WINDOW_FRACTION`, the code fallback, to match): 74/77 images produce a measurement, 54 on ≥3 stars (vs 37 at the previous tuning), 11 with a suspiciously tiny FWHM — a real, sky-data-driven improvement, not a synthetic-only one, but the noise floor is now visibly non-zero and worth watching in the DEBUG log (a lone star at `SNR` just above 7 is the profile of the false positives seen here). 859 tests passing throughout — none of this touches the test suite's synthetic fixtures, only the module constants and one config value.

## 2026-09-24 — Principal-axis trace finder and relative flux helpers, and a first night-wide flux report

*Relates to: "Spectrum trace axes and relative flux (`axes_helpers`, `spectrum_flux_helpers`)" in CLAUDE.md; [[project_spectrum_flux_measurement]], [[project_session_2026-09-23_night_analysis]] in memory.*

The design of a "universal" spectrum-intensity measurement was agreed on 2026-09-23; today built its first two pieces, prototyped against real raw sub-exposures in a throwaway script (session scratchpad) before anything was written to the repository. The trace is located by the principal axes of inertia of its bright pixels — literally intensity-weighted PCA on pixel coordinates — and the same function serves the spectrograph slit later (`invert=True`: the slit is darker than its background, the opposite of a spectrum), which the user asked for explicitly. The slit itself, its centre along the slit and its local background were left for later on purpose.

**3σ vs. 5σ.** On 16 Peg both give the same axis (`cy` 532.28, angle -0.113° at either), but 5σ cuts the noise pixels rejected as isolated from 5,067 to 795 and leaves the retained trace nearly unchanged; the user kept 5σ. Only two connected groups survive (the body of the spectrum, and a faint end at the right edge, 46 px at 5σ — not far above the 20 px minimum, so a faint or single-line emission spectrum could lose such a piece: to watch, though it changes nothing for the axis).

**Intensity weighting.** Asked directly whether retained pixels count as 1: no, the mask only decides *which* pixels count, and each carries its background-subtracted intensity as weight for the centroid and the covariance.

**A false lead of mine on the profile, corrected by the user's method.** Summing all columns of the rotated, background-subtracted image and taking the standard deviation of that profile gave garbage (centre row 580 instead of 532, a negative variance). I first blamed background noise summed over 1391 columns; the user asked whether background pixels were actually set to 0 in my test — they were not, only the median level had been subtracted. Plotting both versions showed the real culprit: a few isolated hot pixels and cosmic rays far from the trace, whose distance-squared lever arm dominates a variance (visible as spikes in the profile). Zeroing every pixel outside the retained mask *before* summing removes them and gives a stable σ (3.12 px on 16 Peg) with no iterative windowing needed. Price: about 7% of the energy (the sub-threshold wings), accepted by the user since the measurement is meant to be relative — always the same computation, compared night to night and frame to frame, never a calibrated absolute flux.

**Rotation.** About the image centre, bilinear, on the background-subtracted image with 0 fill so the uncovered corners add nothing; bilinear interpolation alone drifted the total by +0.02%, so the result is rescaled to the exact input sum (user's request). The angle is folded into (-90°, 90°] since the eigenvector's sign is arbitrary.

**A definition error, found by the user.** "Maximum column intensity" was implemented as the peak of the profile obtained by summing all the columns of each row — the transverse cut of the trace — so total power / that peak is simply the trace thickness in rows (7.0 on 16 Peg, ≈ σ√(2π)). The user, expecting a ratio reflecting how many of the ~1400 columns are used, saw at once that a 1:10 ratio couldn't mean that. What was meant (his original step 7) is the highest value of the per-column sums along the dispersion axis: 54,897 at x=461 on the same image, ratio 481 (1,139 columns carry signal, 266 hold half the power). The code still computes the transverse peak under the name `peak_intensity`, and the night report's "max colonne" column and its two charts show it; left unfixed pending the user's own rethinking of how the powers should be computed ("on retravaillera sur la manière de calculer les puissances") — the raw-pixel maximum, the one needed to tune exposure times, is correct.

**Night report (31 observations of 2026-09-23/24).** Raw single sub-exposure per series, plus every sub-exposure's total power for series dispersion (PDF in `~/Téléchargements/`, generated by a scratchpad script, not part of the repository). Findings: the trace's peak pixel reaches only 14-16% of 65,535 for most stars that night (`exposure_time_mag0_seconds` is 1.0 in `config72ED.yaml`, which is what the 28 s / 2 s exposures encode), so there is a lot of headroom before saturation; per-second flux falls with magnitude at -0.33 to -0.36 dex/mag against the -0.40 the exposure law implies, bright stars getting slightly too little exposure; HD 250240 (exposure imposed at 180 s × 20, magnitude 9.81) sits well below the extrapolated trend, its second observation showing only 488 ADU at the peak pixel (barely a detected trace). A few series show large intensity drops between their own sub-exposures (Aldebaran -35% over five frames, bêta CMi -23%); the pointing residual measured by `stop_phd2_guiding` does not explain the same-star low observations (Spearman +0.48, the wrong sign, and kap Dra/Castor have small residuals) — the user is investigating this himself. ## 2026-09-25 — The guiding camera that never came back, and recovery confined to the sub-plugin layer

*Relates to: "State machine" (`SessionFatalError`) and "Guiding-chain recovery" in CLAUDE.md.*

**The night of 2026-09-24/25.** 8 observations completed (Vega through V923 Aql), then at 20:59:16 UTC the ZWO ASI120MM Mini guiding camera vanished from the driver: `Exposure failed after 2 attempts. Attempting USB reset...`, `Failed to reset USB device`, `Failed to reopen camera after USB reset (ASI_ERROR_CAMERA_REMOVED)`. It never came back. The next 30 SEQUENCER attempts all failed (28 of them `PHD2: stop_capture did not confirm Stopped state within 10.0s`, `pointing_72ed`'s very first PHD2 call; the first was `guiding did not settle within 190s` at 21:02:12), each one restarting from SCHEDULER, until the user pressed stop at ~04:18 UTC. Nothing in the code could tell a dead camera from an ordinary failure, so nothing ever stopped it.

**Recovery on the Stellarmate.** Restarting the INDI server was not enough; rebooting the Stellarmate brought the camera back. So no cable fault (it re-enumerated cleanly at boot), but a state a software restart of the server did not clear.

**Root cause, established from the Stellarmate's kernel journal and `strace`.** The kernel logged only `usb 1-2.4: reset high-speed USB device` lines — no `disconnect`, no error `-71`, no over-current — so the fault was not the bus, the cable or the power. `sudo strace -f -e trace=ioctl -p <indi_asi_ccd pid>` showed `ioctl(11, USBDEVFS_RESET, 0)` issued by a *new thread per exposure*, both for a single KStars exposure and for every frame of a PHD2 loop: **`indi_asi_ccd` resets the camera's USB device on every exposure**, whatever the client (Rosace, PHD2 and KStars alike). Every real night since 2026-09-20 shows the same (about 1000 resets/hour). The sum of the driver's own delays (0.5 s + 1 s + 2 s = 3.5 s) matches the ~3.4 s spacing seen in the kernel log — an inference from matching numbers, not a measurement. Each reset closes and reopens the camera, so every exposure is a small chance of not reopening; `Exposure failed after 2 attempts` appeared in the session logs of 2026-08-31, 09-03, 09-11, 09-19, 09-20 (three times), 09-22 and 09-24, and 09-24 is the only one where the recovery itself failed. The installed driver (package `indi-asi 2.4+z`, reports itself as 2.5, SDK `libasi 1.37`, no newer version available through `apt`) exposes **no** `USB_RESET` property. The `master` branch of `indilib/indi-3rdparty` reads differently — reset opt-in, disabled by default, only after failed exposures — so the installed build behaves differently from `master`; that reading was a summary of the source, not verified against the installed binary. Not fixable in this repository.

**A wrong turn worth keeping.** A first "baseline" of zero resets was read from 19:40 *CEST* (17:40 UTC), before the session had even started — it proved nothing, and led to a wrong claim that the resets were the anomaly. The true first-reset times (21:31:33 CEST on 09-24, matching the first guide exposure in the Rosace log) showed they start with the very first exposure of the night, every night, and are the driver's normal behaviour.

**Decision: recover first, stop only when recovery fails — and keep it out of the orchestrator.** `main.py` knows nothing about plugins, and the problem is in a plugin, so the whole mechanism sits in the sub-plugin layer (`guiding_chain_recovery.py`, see CLAUDE.md). Rejected: (1) a consecutive-failure counter in `main.py`, which would have put hardware knowledge in the orchestrator and needed it to know which failures mean "camera" — the failure itself, where it happens, is the trigger now; (2) reusing `SchedulerFatalError` (wrong name, a cross-family import, and a log line reading "[SCHEDULER] Fatal error" for a guiding fault) — a generic `SessionFatalError` was added instead, `main.py` only widening one `except` and taking the log prefix from the failing stage; (3) `phd2.set_connected(False)` as part of the recovery, because on INDI disconnecting PHD2's equipment might also drop the mount's own INDI connection (not verified) — PHD2 already self-heals its link at the next `start_guiding()`; (4) guarding `pointing_72ed`'s *second* `start_guiding()`, because it follows `set_lock_position()` and a replay after a camera recovery would silently guide on the wrong position. A healthy camera is never disconnected: the probe exposure comes first, so several plate-solve failures under cloud cannot trigger a needless reconnect.

**Open, outside this repository.** Whether a software reconnect can revive a camera in `CAMERA_REMOVED` at all is unverified — in this incident restarting the INDI server did not. If it cannot, the session simply stops cleanly with an explicit message, which is the intended behaviour. Follow-ups were added to `TODO.md`: report the per-exposure `USBDEVFS_RESET` upstream, try a lower `BandWidth` on the ASI120, and evaluate another guiding camera or a USB hub with per-port power control.

**Consequence for earlier USB diagnoses (added the same day).** The 2026-09-18 analysis had read a kernel-level reset loop on the guiding camera's port (`usb 1-2.4: reset high-speed USB device`, one every 3-4 s during 19:23:39-19:26:28 UTC) as a genuine electrical or cabling fault, and the user cleaned and reinforced the USB cabling on that basis. Since the same lines are the driver's own per-exposure reset (about 1000 an hour on every real night since 2026-09-20), that reset loop was most likely PHD2 or Rosace exposing at the time — not a fault by itself, and that particular conclusion should no longer be relied on. What remains open, as a hypothesis only: the guiding camera and the Atik share the same parent hub (`ASM1074 High-Speed`), so the per-exposure reset of the ASI120 may be what disturbed the Atik's concurrent transfer on 2026-09-18 (`Image size is unexpected`), and possibly PHD2's loss of its equipment link on 2026-09-19/20. Nothing tested; the `pointing_camera` USB3 cable fault (`Cannot enable. Maybe the USB cable is bad?`) is a separate, still valid physical fault.

## 2026-09-26 — `calculate_flux`: spectrum flux of every raw sub-exposure, and what was tried and dropped on the way

*Relates to: "Spectrum trace axes and relative flux" in CLAUDE.md.*

**The confusion that started it.** The 2026-09-24 `peak_intensity` ("column max") was the maximum of the profile obtained by summing each *row* over all the columns — the cut across the trace — so total / column max was ~7, the trace thickness, while the user expected ~480 (about a thousand lit columns). The French "sommer les colonnes" reads both ways: adding the columns together (one value per row, what the code did) or summing each column (one value per column, what was meant). The whole measurement was then redesigned with the user, rather than patched: `measure_spectrum_power` is gone, replaced by `measure_spectrum_flux`, used by a new REDUCTION sub-plugin, `calculate_flux`, which records every sub-exposure in its casier and in a new `spectrum_flux` table.

**Choices, and the prototype numbers behind them** (real frames of 2026-09-25, 16 Peg unless stated).
- Raw frame only, no bias/dark/flat — the user wants no external reference; a per-column local background removes offset, dark and sky together (the background varies from 258 to 320 ADU across the 16 Peg frame, hence per column rather than per frame).
- A window following the tilted trace instead of rotating the image: rotation interpolates pixel values (smoothing the noise and so any σ-based threshold); the tilted window gave the same total as the rotated image within 0.4%. Then the user pointed out that whole pixels at the window edges still make the measured width depend on where the trace sits in the pixel, a bias that changes night to night — edge pixels are now weighted pro rata of their height inside the window (exactly the same effective width in every column).
- ±4σ window, not ±3σ: ±3σ of a Gaussian fit held 98.8% of the flux on 16 Peg but only 96.7% on Vega (wider wings); ±4σ holds 99.3–100%.
- `find_axes` fails silently on a faint star (HD 250240, mag 9.8: σ 0.95 against 3.15 for the real profile, from 122 pixels above its threshold; on another frame, nothing at all). Asked whether a failure could be detected with certainty, the honest answer was no — only an independent measurement exposes it — hence the band fits, always computed. The user's rule: keep `find_axes` when both agree, the bands otherwise. The agreement floor was first 0.5 px, but on healthy bright frames the two lines differ by 0.2–0.6 px at the edges (the band line is the more precise, 0.02–0.08 px), so the user set 1 px. σ, however, always comes from a profile fit: `find_axes`'s σ is another quantity (Vega 3.31 vs 2.68 while it worked), and switching between the two would change what the ±4σ window means. The fallback starting row when `find_axes` finds nothing uses the row *median*: the row *sum* picked row 624 on HD 250240's 7th frame (something else in the field), the median row 537, the trace.
- Hot pixels: a 3×3 median everywhere cost −1.9% of the flux (it flattens the trace core); a 5-pixel median along the dispersion axis replacing only far outliers costs −0.03%. The first threshold used a whole-row noise, which underestimates the photon noise of the trace core: 154 "hot" pixels replaced inside the window, excesses of only 89–238 ADU — real signal, and since only positive excursions are replaced, a flux bias. With a local noise (neighbour differences along the row), 14–19 replaced against 0–1 symmetric negative outliers, all 30–84 times the noise; on HD 250240 these few hot pixels were worth 2.5% of the flux.

**Horne optimal extraction — tried, then dropped by the user.** The user wanted a second, optimally weighted measurement (Horne 1986) for faint stars, with its cosmic-ray rejection and a detector gain estimated from the frame itself (0.24–0.32 e⁻/ADU found, consistent with the Atik 314L). No variant held on both bright and faint stars: a per-column profile matched bright stars (±0.1%, 0–3 rejected pixels) but drifted with magnitude on faint ones (+2.8 to +3.8% against the plain sum); a single profile for the frame did the reverse (hundreds of pixels wrongly rejected on bright stars, gain estimate collapsing to 0.02); Horne's own polynomial profile and a variance model with a relative profile-error term did no better. At a bright star's signal-to-noise, a 1% profile error already exceeds the photon noise, so the rejection throws away real signal. It did reduce the noise by about 30% on the faint star. The user's verdict: too complicated to explain and maintain — removed; the plain sum is the only measurement.

**Not wired into a program yet.** Discussing whether the ~0.5 s per frame of computation should move to a worker thread showed that REDUCTION shares the sequencer's event loop (`run_post_obs()` is a task of the same loop) — the user had assumed separate threads. Any blocking work in a reduction sub-plugin therefore stalls the sequencer (probably already `export_demetra`'s zip, not measured). The user wants the separation at the orchestrator level, keeping sub-plugins sequential; that change is in TODO.md, and `calculate_flux` joins `Be_stars.yaml` only after it. M57 (an extended emission-line object) is measured like a star and documented as such: σ 11.7 px, and its narrow lines trip the hot-pixel step.

**The 2026-09-25/26 night, measured after the fact (same day).** The sub-plugin's own code was run offline on every observation of that night (scratchpad script, `~/Téléchargements/rosace_scripts_2026-09-26/night_0925.py`; database backed up first with SQLite's backup API, `rosace.db.bak-2026-09-26-flux`; the observation YAML files only read — checksums identical before and after, as the user required). A first attempt failed on `database is locked` (the user had DB Browser open), a second measured nothing: reloaded from YAML, `scheduler_data["target"]` is a plain dict, not a `Target` — the sub-plugin logged a warning per observation and never raised, as designed; the script rebuilds the `Target`. Result: 209 of 215 frames in `spectrum_flux` (their `recorded_at` is the time of this computation, not of the exposure), report `~/Téléchargements/Rosace_flux_nuit_2026-09-25.pdf`. Findings: **zet Tau's first observation (00:35) holds no starlight in any of its 5 frames** — PHD2's refine settle took 123.6 s and the post-science guide image put the star at y = 672.9 px against a slit near 617, i.e. out of the slit, yet the observation counted as successful; kap Dra's first observation (03:33) is 4 to 40 times fainter than its second one five minutes later, with σ down to 1.4 px on three frames (thin cloud or star partly off the slit, not settled); flux against magnitude −0.362 dex/mag against the expected −0.400, as on 2026-09-23.

**Wired into `Be_stars.yaml` after all (same day).** The user chose to add `calculate_flux` (first in `reduction:`) right away, accepting that each measured frame stalls the sequencer for about 0.5 s until post-observation stages get their own thread.

**`exposure_time_mag0_seconds` 1.0 → 4.0 in `config72ED.yaml` (same day).** With 1.0 the brightest trace pixel stayed at 14–17% of 65535 on the 2026-09-25 night. Scaling that night's measured peaks linearly (180 s cap kept, stars with a fixed `program_stars.exposure_time` excluded), 5.0 would have put the brightest stars (omi And, bet CMi, nu Cyg, Sheliak, omi Her) near 80% — too little margin for seeing and centring variations, and the Atik's real linearity limit is not checked — so the user chose 4.0 (~64%). ## 2026-09-26 — Slit position measured every observation; `pointing_72ed` split in two

*Relates to: "`slew_72ed`/`slit_xy`/`pointing_72ed`" and "Slit position measurement" in CLAUDE.md.*

`calculate_flux` made the flux of a spectrum measurable, and that flux depends on where the star sits in the slit. The configured slit position (`subplugin_params.guiding.slit_y: 614`) was read by eye in KStars; the 2026-09-24 measurement with `find_axes(invert=True)` put the slit at Y = 617.2 at the same column, i.e. the star was placed on the slit's lower edge. The slit's position in the guiding field can also move with the telescope's flexure, so the user asked for a step that measures it on every observation, in a lamp-lit guide image (bright, star-free, reproducible, the slit a dark line across it), falling back to the default whenever the measurement fails.

**Where to measure.** The user first proposed "right after pointing, before science". But the slit position is used *inside* the pointing: its second phase nudges PHD2's lock onto the slit, so once `pointing_72ed` has finished the star already sits on the default slit, and a later measurement could only be used by re-nudging PHD2 — while lighting a lamp in front of a camera PHD2 is guiding with. Measuring before the whole pointing was rejected by the user too: the telescope's movement is precisely what may move the slit, so it must be measured with the telescope in place. Hence the split, chosen by the user: `slew_72ed` (former phase 1: stop PHD2, slew, plate-solve correction, corrected slew — after which the mount no longer moves on its own), then `slit_xy`, then `pointing_72ed` (former phase 2, name kept: PHD2 guiding onto the slit in force). A lighter alternative — the existing generic `slew`, then `slit_xy`, then the unchanged `pointing_72ed` — was set aside: `pointing_72ed` would have re-done its 2° approach slew after the measurement, costing tens of seconds per observation and moving the mount again. `slew_72ed`'s own correction still uses the default slit: it is accurate to about an arcminute, and `pointing_72ed` corrects the rest. The `pointing_errors` table is now fed by `slew_72ed`; the code is unchanged.

**X is not measured.** The slit is a line about 800 px long, tilted about +1.5°: its "centre" along X is only the middle of the lit length (or of the search zone, when restricted), a meaningless value. X therefore stays the configured `slit_x` — where along the slit the star should sit — and Y is the measured line's height at that column.

**Column-median subtraction** was added before `find_axes()`, which is not in the 2026-09-24 measurement: on a lamp-lit field, a few percent of illumination gradient along the slit is many times the photon noise, and `find_axes()`'s single frame-wide background would take the darker end of the zone for the feature. Not yet checked against a real lamp-lit image — none had been taken when this was written.

Other choices: the light source takes the spectroscope's own names (`CALIB`/`FLAT`/`SKY`; `DARK` refused, the image would be black); a pause (`light_settle_seconds`, 1 s) between the spectroscope command and the exposure, since the exposure is short (0.1 s) and the lamp must really be on; the casier stays minimal (`status`, and the new `slit_x`/`slit_y` only when calculated, plus the image name) since the default is already in the configuration; the GUI shows the search zone, the measured line and the retained point on the "Guidage" panel.

**Same evening — first real images, and a lamp/sky offset (`offset_y`).** On a CALIB-lamp guide image (0.05 s; 0.1 s would saturate the field, so the configured exposure was lowered), `slit_xy` found the slit at Y = 616.95 at x = 613, agreeing with an independent band-by-band Gaussian fit of the dip within 0.1 px; the user then widened the search zone to 900 × 120 so it holds the whole slit (a few dust spots included, without effect on the result). A sky image taken ten minutes later showed the slit about 0.5 px lower, straight, where the lamp image shows a slight bow (+0.35 px sagitta over 725 columns) — pointing to the illumination path rather than flexure, which would move both alike. A series of 11 alternating CALIB/SKY pairs (1 s settle after each switch), twenty minutes later, gave SKY − CALIB = −1.07 px (std 0.05, error of the mean 0.014): very repeatable within the series, but double the first pair's value, almost entirely because the lamp image moved (+0.7 px, while the sky image moved +0.17 px; the lamp's own level had also dropped from ~26 000 to ~23 000 ADU). So the lamp sits about 1 px too high and not by a constant amount. The user chose a configured static correction, better than none: `subplugin_params.slit_xy.offset_y` (default 0), −1 in `config72ED.yaml` — in the configuration rather than the hardware YAML, same reasoning as `slit_x`/`slit_y` (2026-09-06). The FLAT lamp was ruled out by the user (too bright); `slit_xy` measured on a sky image is itself ~0.35 px low compared with the band fit, another reason to keep the lamp. Next test planned by the user: the same CALIB/SKY comparison at five telescope positions (altitude 65°, azimuths at least 40° apart), to see whether the offset depends on the tube's orientation.

**Same evening, later — five telescope positions; the "not constant" conclusion above was wrong.** The CALIB/SKY comparison was repeated at five positions (altitude 65°, azimuths 60, 100, 140, 220, 260°; the first three with the mount west of the pier, the last two east), five pairs each, 17:20–17:23 UTC. Orientation has no measurable effect: the slit's Y at x = 613 stays within 0.02 px across all five positions and both pier sides, seen against the sky as well as against the lamp, and SKY − CALIB is −1.11 px everywhere (spread 0.02 px). But the slit moved with time, with the telescope not moving: 617.73 (lamp) / 616.66 (sky) at 16:54, 616.80 / 615.70 at 17:20 — about 1 px in half an hour (cause unknown; the falling dusk temperature is only a guess). This is what made the first estimate look inconsistent: its −0.54 px came from two single images taken ten minutes apart, mixing the lamp/sky offset with that drift. Pairs taken seconds apart give −1.07 then −1.11 px, so the lamp/sky offset is stable, and the time drift is a reason to measure the slit on every observation. *Relates to: "State machine" in CLAUDE.md.*

`run_post_obs()` (REDUCTION → SHARING → ARCHIVE) was an `asyncio` task of the same event loop as the sequencer. Any blocking work in a REDUCTION sub-plugin therefore froze the sequencer for as long as it lasted: `calculate_flux` already cost about 0.5 s per frame (accepted on 2026-09-26 while waiting for this change), and `export_demetra`'s ZIP writing blocked it for 27 s on 2026-10-04 (73 files, simulator) — long enough for the GUI's 5 s requests to time out. The user's requirement, as the native reduction pipeline starts: no telescope time may be lost to data reduction.

Two ways were weighed. A separate process gives a truly separate CPU, but logs, the GUI's step progress and image broadcasts live in the server's memory and would all have needed a cross-process bridge, and the observation would have had to be copied in and out. A thread is a change in `main.py` alone: numpy/scipy, which do the heavy lifting of a reduction, release the GIL during their array operations, the PC has 4 cores, and the sequencer itself mostly waits on hardware. The thread was chosen, with a separate process kept in reserve if a measurement on the sky ever shows the sequencer still delayed.

One worker, not a pool: observations are post-processed one at a time and in order, because `export_demetra` appends every observation to one ZIP per session, and the future calibration masters will be shared across observations too. Before, several post-obs tasks could interleave on the shared loop.

Three shared points were made safe: `state.pending_post_obs` is now changed only on the main loop (`_launch_post_obs()`); `step_progress.py` got a lock (a write from the post-obs thread while the API iterates the dict would raise `dictionary changed size during iteration`); and `ws_image_broadcaster` got `bind_loop()` and hands a send from another loop over to the main loop. No post-obs step sends an image today; the user chose to build that bridge now rather than when spectra are first displayed. Logging was already thread-safe.

Test pitfall: the first version of the "blocking REDUCTION does not delay the sequencer" test passed on the old code too. On a shared loop, *when* the blocked task runs depends on which await yields first, so measuring the start of the next SCHEDULER (which ran before any yield) or a single SEQUENCER wait gave luck-dependent results. The final test measures from the end of the 1st SEQUENCER to the end of the 2nd, which awaits 0.5 s while the 1st REDUCTION blocks for 1 s: on a shared loop the block always falls in that window (3 failures out of 3), on its own thread never (3 passes out of 3).

Still to do on the sky: compare the time between two observations with and without a reduction running alongside.

## 2026-10-06 — Native reduction chain laid out as placeholders

*Relates to: "Native reduction chain" in CLAUDE.md.*

Start of the native reduction chantier, on the `reduction` branch (from the post-obs thread commit). The four old REDUCTION placeholders (`bias`, `dark`, `flat`, `extract`, which only `touch()`ed empty files) gave way to the full chain, every step a placeholder for now (1 s wait, casier `{"status": "placeholder"}`), so the chain runs end to end and shows in the GUI before each step gets its computation. `bias`, `dark` and `flat` were deleted; `extract` kept its name, its content rewritten.

The user's principle: one simple operation per sub-plugin, easy to explain and to reuse elsewhere. So the masters are three steps (`master_bias`, `master_dark`, `master_flat`), the calibration two (`dispersion_law` computes or reuses the law, `lambda_calibration` applies it — its GUI label "Calib", at the user's request). A first proposal had a `master_calib` step; the user replaced it with `preproc_calib`, alongside `preproc_target`. He then hesitated between `tilt_target`/`tilt_calib` and `smile_target`/`smile_calib` pairs (the tilt is measured on the target and must be applied as is to the lamp, the smile the other way round) and single steps; single steps were kept, since a step that measures its correction and applies it to every image guarantees both get the same one, where a pair would make the second step read the first one's measurement for nothing.

The full chain is declared by `Be_stars.yaml` only: what is built here is specific to that program. The other programs (and the Docker demo copies) only lost `bias`/`dark`/`flat` and keep a minimal `extract`.

The rules for the real implementations were settled in the same discussion and written into CLAUDE.md: inputs found by shared purpose-named keys in any casier, file names (not dates) decide reuse of masters and dispersion laws, reduction parameters in the program's YAML, a failing step stops the reduction except a non-critical one, the dark keeps its bias (checked against Demetra by the user), never any telluric or heliocentric correction (BeSS rule), intermediate files in one rebuildable directory per observation.

## 2026-10-07 — Masters: min/max-rejected mean, bias removed from the flat

*Relates to: "Native reduction chain" (master calibration frames) in CLAUDE.md.*

The 2026-10-06 rules said "sigma-clipped mean" for the masters. Before writing them, the user asked for a simpler method: for each pixel, reject the highest and the lowest of its N values (one per frame) and average the rest. Compared on our 5-frame series: a classic sigma clipping cannot work there — with 5 values, a single outlier inflates the standard deviation it is measured against and never stands more than about 2σ from the mean, so a 3σ threshold rejects nothing; making it work needs a robust variant (median and median absolute deviation), harder to explain. Min/max always removes one outlier per side, deterministically, at the cost of averaging 3 frames instead of 5 (a somewhat noisier master, accepted). Fewer than 3 frames is an error ("exotic case", user).

The flat: the dark keeps its bias because it is *subtracted* (the bias cancels between image and dark), but the flat is used in a *division*, where nothing removes its offset — in a faint part of the lamp spectrum the flat would be mostly offset and the division would correct the wrong thing. So `master_flat` subtracts the master bias (the dark current over a 3 s flat is neglected), then divides by its own mean (the lamp's spectral shape is left in, to be absorbed by the instrumental response). The flat's behaviour outside the lamp trace, where it is near 0, is left to `preproc_target`.

Masters live in the session directory, named after their series (`<series root>_master.fits`) and reused when the file exists. Before this, the calibration acquisitions' file lists were moved to shared keys (`bias_images`, `dark_images`, `flat_images`, `calib_images`), and the series lookup now skips `_master` files: a master shares its series' prefix and, with a series count of 1, would otherwise have been reused as a raw frame.

## 2026-10-08 — Preprocessing without the dark, for now

*Relates to: "Native reduction chain" (preprocessing) in CLAUDE.md.*

The darks are always shot at `max_exposure_time_seconds` (180 s on the 72ED), while science frames are often much shorter, so using the master dark would need a scaling `bias + (dark − bias) × t/180`. The 2026-09-25 masters show a median dark current of 0.33 ADU in 180 s at 0 °C: negligible. The user chose to start simple — `(frame − master bias) / master flat`, no dark — and to come back to it later if needed. Each frame is corrected on its own; stacking comes later.

The whole frame is processed with no special handling outside the slit (user). One guard only: where the master flat is ≤ 0 (144 pixels, all in the sensor's first column, on 2026-09-25), the result is 0, so no `inf`/`NaN` breaks the sums of the later steps. The same column, with a tiny positive flat, still comes out with values up to ~10¹⁰ — accepted for now. On the real 16 Peg frames: 0.05 s per frame, values checked by hand.

## 2026-10-08 — Tilt: column shifts by overlap redistribution

*Relates to: "Native reduction chain" (tilt) in CLAUDE.md.*

Before designing `tilt`, the trace angles stored by `calculate_flux` in `spectrum_flux` looked alarming: −13.6° to +3.6°, most of them from the band method. Grouped by session, every aberrant value came from the INDI simulator sessions of 2026-10-04 to 10-07 (230 frames, no real spectrum in them), left in the database because `--purge-simulated` had not been run. On the sky the angle is −0.066° (night of 2026-09-27, all by the principal axes) to −0.149° (2026-09-28, cloudy, more band fallbacks): about 1 px at the frame edges.

The user wanted no rotation: each column is shifted vertically, the whole column (a band of ~200 px around the trace would be enough and faster — TODO.md), and the shift must keep each column's total. Three methods were compared: overlap redistribution (each original pixel split between the two new pixels it overlaps, 1 − f and f — exact conservation, a slight smoothing, σ 3.00 → at most 3.04 px), a Fourier shift (conserves, but oscillates around hot pixels and cosmic rays, harder to explain) and spline interpolation (does not conserve exactly, oscillates). The first is the linear interpolation of a pure shift seen as a redistribution, which is why it conserves; chosen by the user.

On the real 16 Peg frames of 2026-09-25 (sum of 5 preprocessed frames): the principal axes gave −0.057° against −0.143° for the bands, so the band line was kept (WARNING). On the raw sum the axes give −0.102° and the bands −0.142°: the flat division reweights the trace towards its faint blue end, and the intensity-weighted axes follow the weight, slightly curved trace included, while the band fit follows the centre line. After correction the band centres lie between y = 536.70 and 537.10 from x = 182 to 1222 (±0.2 px), the column totals are kept to 3·10⁻⁶ ADU (edges excluded), and the step takes 1.4 s for 8 frames (0.14 s per frame for the shift itself). The dead first column of the sensor (flat ≈ 0.002, up to 10¹⁰ after preprocessing) is masked for the measurement by a 0.05 threshold on the normalized flat (~300 ADU of flat signal); the user first suggested 1 or 10 ADU, but the master flat is normalized, and 10 ADU (~0.0016) would not have covered the whole column.

Later the same day, before the first commit of `tilt`, the user chose to keep the **principal axes alone** and drop the band method for the tilt, to be judged in use ("the flat moving the centre of gravity changes nothing"). The divergence logic and its WARNING went with it, and the tilt no longer adds `COMMENT` lines to the corrected frames' headers (useless: the angle is in the casier and the log). Measured on the same 16 Peg frames: the axes give −0.057°; after correction they re-measure −0.003°. For the record, the band method still sees −0.085° after this correction (trace at y = 537.78 at x = 182 and 535.86 at x = 1222, about ±1 px at the edges), against −0.143° before. `calculate_flux` keeps both methods.

## 2026-10-08 — Smile: row cross-correlation and a parabola

*Relates to: "Native reduction chain" (smile) in CLAUDE.md.*

The user listed three ways to straighten the lamp lines: follow one bright line and align it row by row; fit its curvature as a circle arc and derive each row's shift; cross-correlate whole rows (CCF), thought to be the cleanest but expensive. Measured on the real lamp of 2026-09-25 (sum of 3 preprocessed, tilt-corrected frames, 1304×976), the CCF of all 976 rows through the Fourier transform takes ~0.3 s, so it is not expensive: it was combined with the second idea — the CCF gives each row's shift from every line at once, to a fraction of a pixel, and a parabola (a circle arc of large radius, here R ≈ 12 700 px, is a parabola, and fits more simply) is fitted on those shifts. Residual 0.023 px rms, so a parabola is enough. One CCF per row or every tenth row gave the same parabola; every row was kept (no extra parameter, negligible time).

The lines are not only curved but tilted: the shift goes from −4.1 px at the top of the band to +1.0 px at the bottom, the parabola's vertex sits near y = 703, not on the trace (y = 537) — as if the slit were ~0.75° off the columns. The parabola corrects both.

Selecting the rows: the user first proposed rows above 90 % of the trace row's level (30 % being already in the slit edge). Measured, the lamp's level along the slit is a flat plateau between 0.8 and 1.0 of the trace row's from y = 320 to 775, then drops within 2–3 rows (0.69, 0.40, 0.35): a 90 % threshold cut that plateau at random into some thirty pieces. The user also pointed out that dust on the slit would put a dark band in the spectrum and break any requirement of a contiguous block. Agreed rule: the band is delimited at 50 %, 5 % of its height is left out at each edge (rather than a fixed number of rows, to stay instrument-independent), rows below 50 % inside it are dropped individually, and the parabola fit rejects rows beyond 3σ until stable.

On 16 Peg + lamp of 2026-09-25: rows 339–753 used (414, 1 rejected), shift −4.15 px at row 339 and +0.98 px at row 753, fit rms 0.023 px; after correction the per-row CCF shifts are between −0.03 and +0.06 px across the band; row totals kept to 2·10⁻¹⁰ (edge columns excluded); 2.1 s for 8 frames.

## 2026-10-09 — Extract: window from the widest column group, sky per column

*Relates to: "Native reduction chain" (extract, preprocessing) in CLAUDE.md.*

The 2026-10-06 rule was "plain sum over ±4σ around the trace". Measured on 16 Peg (2026-09-25), one σ for the whole trace (3.21 px) gave a 27-row window (524–550), while the user saw the spectrum spread over 515–564: the trace widens strongly towards the blue (σ 6.75 px around x = 250, 2.5 px in the middle), where the 4σ window held only 92 % of the flux. Agreed rule (user): σ measured per group of columns (25 groups, independent of the sensor size; one column alone is too noisy for a Gaussian fit), only groups whose peak reaches 10 % of the brightest (the faint ends gave meaningless σ), the largest σ kept, window = ± ⌈3σ⌉ pixels, a whole number of rows symmetric about the trace. Result on 16 Peg: σ 7.62 px (13 groups), window 514–560, 99.2 % of the flux of a ±40 px sum.

Sky: per column (gradient, light-pollution lines), in two zones inside the lit band of the flat (minus 5 % at each edge, as for the smile) and beyond 6σ of the trace. Level = mean after iterative 3σ rejection (user: a mean is more precise than a median, the rejection handles the hot pixels left in the frames — a single 3000 ADU hot pixel among 300 sky pixels would otherwise bias the column's sky by 10 ADU, i.e. ~450 ADU in the window sum). The lamp is extracted with the same window and no sky subtraction (it lights the whole slit); one `extract` step for both, so the window is measured once. Dead columns are 0 so a spectrum keeps the image's width. A PNG of the zones is written for checking (the GUI's Spectre panel is fed by acquisitions, and the post-obs thread runs while the next observation acquires, so publishing there would overwrite the current frame); matplotlib was added as a dependency for it, and for the coming plots.

Found while checking the zones: after the smile, the dead first column's huge values (up to 1.7·10¹⁰) had moved into columns 1–18 on the rows outside the lit band, where the extrapolated parabola shifts by up to 18 px — out of reach of the flat-based mask, and enough to make `find_axes()` return an angle of 9.6° and σ 65 px on the corrected sum. Fixed at the source (user): preprocessing now sets to 0 everything outside the band lit through the slit and every pixel whose flat is below 0.05. That in turn broke the trace measurement (half the frame exactly 0 → a zero background for `find_axes()`, which then took the whole lit band for the trace: tilt −0.43°, σ 61 px); the trace is now always measured on the lit band only (`find_trace()`), which gives a tilt of −0.074° on 16 Peg (−0.057° before, when the off-band rows held noise).

The programs that declared `extract` alone as a placeholder (All_stars, Cataclysmic, PN, bright_stars, nova_monitoring, demo, the two Docker demo programs) would have stopped their reduction once `extract` became real; it was removed from them (user), the last four now declaring `reduction: []`.

## 2026-10-09 — Stack: plain sum, frames below 30 % of the median flux rejected

*Relates to: "Native reduction chain" (stack) in CLAUDE.md.*

The target's 1D spectra are summed, not averaged (user's choice: the sum keeps the photon count; the spectrum is normalized later anyway). The lamp spectra are summed too — sometimes useful for the dispersion law. No cosmic-ray rejection at this step: a per-pixel rejection between frames would first need every spectrum brought to the same level (16 Peg's frame fluxes vary from 1.00 to 1.42 with seeing and guiding), and a cosmic ray is better recognized on the 2D frame alone, at preprocessing — left for later (TODO.md). What is handled here is a frame without light (zet Tau, 2026-09-25: one "successful" frame without starlight): a spectrum below 30 % of the series' median flux is rejected, with a warning.

Exposure keywords: BeSS defines a single exposure time, `EXPTIME`, the duration of the whole observation from the start of the first exposure to the end of the last, readouts included — so the stacked spectrum's `EXPTIME` is `DATE-END − DATE-OBS` (both written; BeSS accepts `DATE-END`). The time the sensor was actually exposed goes to `EXPTIME2` (`5x107.7s`), a keyword BeSS does not define but leaves free; it is built from each frame's actual `EXPTIME` (107.75 s for 108 s requested on the Atik), not from the requested duration in the file name.

## 2026-10-09 — Dispersion law: cubic hypotheses anchored on the extreme lines

*Relates to: "Native reduction chain" (dispersion law) in CLAUDE.md.*

Method agreed with the user: Demetra's principle (a reference line list, the lamp's detected lines, the best matching, a least-squares polynomial), rebuilt and compared on 16 Peg (2026-09-25). Comparisons made (all on the stacked lamp, 38 lines detected):

- Two ways to generate hypotheses — every combination, or only the combinations whose spacing ratios agree (the plate-solve idea: ratios do not depend on the dispersion or the offset). Same laws every time; the ratios are 4 to 20 times faster (0.3 s against 1.2–4 s). Only the ratios are kept.
- An optional approximate dispersion (3.5 Å/px measured, not the 2.6 first quoted) speeds the search up 1.2–4 times and changes nothing else; kept as an option, absent by default, so that a new instrument needs no prior knowledge.
- Degree 2 against 3: the law is clearly cubic (8 good lines: RMS 2.04 Å at degree 2, 0.20 Å at degree 3). Degree 3, like Demetra.
- Three scores: number of lines within the tolerance, sum of distances (Demetra), sum of distances capped at the tolerance. With the extremes imposed, only the sum rejects exactly Demetra's four lines; the other two keep 6677 and drop 5852 (RMS 0.17 Å), the only line in the 4765–6099 gap. The sum is kept.

The first version used triplets (a parabola through three pairs) without constraint, and a tolerance of 1 Å. It kept 7 lines with a flattering RMS (0.31 Å), but the Balmer lines of 16 Peg came out up to 15 Å off (Hδ): a parabola can only follow the cubic law over part of the spectrum, the best one passed exactly through 4426 and 6099 (two of the four lines seen ~2 Å from their reference) and was 10 Å off at 4158; the final pairing, within 1 Å of the current law, could never bring the blue end back, and the cubic then extrapolated freely. A low RMS on few lines proved nothing: the check is the Balmer lines on the star (user's idea). Fixed by cubic hypotheses through four lines, always including the two extreme lines of the list (user: the extremes extend the computed domain and reduce extrapolation). Result: 8 lines, the same as Demetra (rejected: 4200, 4426, 6099, 6677), RMS 0.20 Å (Demetra 0.168), Balmer lines within 1–2 Å (measured roughly, on broad B-star lines). Demetra's coefficients (3046.14, 3.51, 1.8e-4, 1.58e-7, as read from its interface) are close to Rosace's (3054.80, 3.4976, 1.94e-4, −1.64e-7) but not directly comparable without its pixel origin and full precision. The four rejected lines are not considered errors in the list (user): Demetra uses the same list and rejects the same lines.

Background under the lamp lines: local minima joined by straight lines (user's idea), rather than a running median of a given width (a size in pixels depends on the camera). Line positions: a Gaussian fit, 0.02–0.08 px on the lines kept; the user aims at better than a tenth of a pixel.

## 2026-10-09 — Lambda calibration: mean-dispersion step, overlap redistribution

*Relates to: "Native reduction chain" (lambda calibration) in CLAUDE.md.*

The step of the calibrated spectrum (`CDELT1`) has no BeSS rule. The user first suggested A1, the linear coefficient of the law; but A1 is the dispersion at pixel 0 only, and the local dispersion A1 + 2·A2·x + 3·A3·x² runs from about 3.5 to 3.2 Å/px across the sensor (on 16 Peg A1 is 3.4976, close to the mean by chance). Demetra writes 0.87 Å, an oversampling by 4 that adds no information (the points are correlated, the file four times larger, only the curve looks smoother). Chosen: the mean dispersion over the sensor, one point per pixel (3.4723 Å on 16 Peg), with an optional `step` to impose another value. The whole sensor is kept, extrapolated edges included: `crop` removes them later (user).

Resampling by overlap redistribution (user), the same principle as the tilt and smile shifts: each pixel's flux spread over the wavelength interval it covers, shared among the new intervals it overlaps, so the total flux is kept exactly (checked on 16 Peg: ratio 1.000000) and nothing oscillates around sharp lines, unlike a spline interpolation. The lamp is calibrated too: its retained lines fall within ±0.31 Å of their reference, the law's own residuals, so the resampling adds no shift. FITS keywords `CRVAL1`, `CDELT1`, `CRPIX1 = 1`, `CTYPE1 = 'Wavelength'`, `CUNIT1 = 'Angstrom'`, expected to be accepted by BeSS (user); the calibrated 16 Peg spectrum was handed to the user to check in Demetra.

## 2026-10-10 — Response, scaling and crop; parameters in the configuration

*Relates to: "Native reduction chain" (response, scaling, crop) in CLAUDE.md.*

The last three corrections of the target spectrum before the final FITS, deliberately simple. `response` divides by the instrumental response (the observed spectrum is the true one times the response), a 1D FITS made by hand for now and named in the configuration; it is interpolated onto the spectrum's grid and the spectrum set to 0 where the response is missing or nearly zero, which `crop` then removes. The lamp is no longer carried past `lambda_calibration` (user).

The `normalize` placeholder was renamed `scaling` (user): the step divides by one constant, the mean level of a wavelength zone (6600–6700 Å, just after Hα), only so that the values read naturally; it is not a normalization to the continuum, which is what "normalize" means to a spectroscopist (BeSS's `BSS_NORM` will stay `'none'`). The user first thought of "100 pixels after Hα"; the zone is in wavelength, since a number of pixels means a different width with every step (87 Å at Demetra's 0.87 Å, 347 Å at ours). `crop` keeps 3750–7500 Å without resampling.

Where the parameters live: the 2026-10-06 rule put the crop bounds, normalization zone and response file in the program YAML. The user decided on the configuration instead: they describe what the instrument can cover, not a scientific choice, like the lamp's reference lines. No FITS keyword is added by these steps (user): the bounds are known from the spectrum itself and the scaling has no scientific effect.

Tested on 16 Peg (2026-09-25) with a response made by Demetra in 2015 on another telescope (C8 at OHP, same Alpy 600 and Atik 314L): the chain runs end to end, the scaling zone averages 1, the final spectrum covers 3752.7–7499.4 Å (1 080 points), its last 14 points 0 beyond the response's 7454 Å. A response measured on the 72ED itself is still to be made.

## 2026-10-10 — Final FITS, plots and observation summary

*Relates to: "Native reduction chain" (write spectrum, plot spectrum, summary) and `export_demetra` in CLAUDE.md.*

`write_spectrum` rebuilds the header from scratch rather than cleaning the inherited one: the camera and the 2D frame leave dozens of cards (ROWORDER, PIERSIDE, FOCUSPOS...) meaningless for a 1D spectrum, and a whitelist is the only way to be sure none survives. The BeSS specification (v1.3) lets the object, the site and the equipment be given either by name (known to BeSS) or by their details; giving both only makes BeSS issue a warning. Resolving power: only the indicative `BSS_ITRP` (600) for now; `BSS_ESRP` waits for a measurement of R (TODO.md). The final file is named after the observation file plus the observation ID (user): the ID is what finds a spectrum for sure, in the database or elsewhere.

The observer, site and equipment names were spread over nothing (only `export_demetra` had keys for them, unset on the 72ED); they now live in one block, `subplugin_params.observatory`, read by `write_spectrum` and `export_demetra` (user: no duplicate). `summary` is the graphic counterpart of the observation file (user). The user first asked for a graph of the guide images' background over the series; Rosace takes only three or four guide images per observation (before and after the science exposures; PHD2's frames are not saved), so the science frames' own sky level stands in for it, next to each frame's star flux on twin axes, and the post-science guide image gives its median level. The user first wanted the summary built from the Observation alone (a need to read the log would show a missing piece of information); the warnings and errors, though, only exist in the log, and the user then asked for them: they are read from `rosace.log` (`session_log_extractor.read_log_lines()`, factored out for this), between this observation's own DB markers for the acquisition and after the last "Starting reduction" line for the reduction, since another observation's acquisition runs during this one's reduction. Plot texts are in English, like everything Rosace writes to files.

Layout reviewed by the user on the first 16 Peg summary: A4 portrait (two sheets printed recto-verso), the whole guide image next to the zoom on the slit, and the final spectrum and the calibration lamp kept together on the first page, on one wavelength axis with the same shaded extrapolation zones, so that the coverage visibly comes from the lamp lines kept; the stacked target in ADU that duplicated the final spectrum was dropped.

The user then asked for the slit itself on the whole guide image, "modelled by the calculation, slope and ends included". `slit_xy` only recorded the retained point, so its casier now also keeps the angle and the slit's two ends (`segment`). The ends were first taken as the extent of the dark pixels `find_axes()` retained; on the real QHY images that ran to the search zone's edges, because a faint dark trace (about 15 times shallower) continues beyond the slit. For observations recorded before, the summary measures the slit again on the slit image their dossier names.

## 2026-10-13 — Hot pixels replaced at preprocessing

*Relates to: "Native reduction chain" (preprocessing) in CLAUDE.md, and the 2026-10-08 entry "Preprocessing without the dark, for now".*

Since 2026-10-08 the preprocessing did not use the dark at all: the dark current is negligible (median 0.0 ADU in 180 s at −5 °C on 2026-10-12, once the bias is removed) and subtracting it would need an exposure-time scaling. But the science camera (an Atik CCD) has fixed hot pixels: on the master dark of 2026-10-12, 431 above 100 ADU in 180 s (242 above 1 000, 44 above 5 000), found in each of the 5 raw darks (423–427 of 431). About twenty sit in the rows of the trace and went straight into every 1D spectrum as narrow spikes (6 visible in each spectrum of that night's report); the sky zones were not affected, their 3σ rejection removes them. A rejection across the frames of a series (the cosmic-ray TODO) could not remove them: a hot pixel is at the same place in every frame.

Choice (user): a hot-pixel map taken from master dark − master bias (5 × its robust noise; 64 ADU, 191 pixels in the useful area on 2026-10-12), each hot pixel replaced after the division by the flat — no exposure-time scaling, saturated or non-linear pixels handled the same way, no dark noise added. The map is computed by the preprocessing itself from the two masters it finds under their shared keys (milliseconds), so no new file or key, and it cannot get out of step with its master dark; a dark series copied from the library goes through `master_dark` like one shot that night.

Replacement along the row (the dispersion axis), linear interpolation between the nearest healthy pixels, not with the 8 neighbours weighted by distance (asked by the user, then dropped): across the row the trace profile is a Gaussian of σ ≈ 2.5 px everywhere along the spectrum, so a vertical neighbour is ~8 % below the trace core; along the row the spectrum only varies fast at a line core. Either error is about 0.5 % of one column's flux, far below a hot pixel's hundreds to thousands of ADU.

Checked on a copy of HD 174237 (2026-10-12), preprocessing to stacking, with and without the replacement: the spikes at x = 674/675, 833, 1014, 1090, 1265/1266 (red side) and 110, 128 (blue edge) are gone; every other column changes by less than 0.1 % (median 5 × 10⁻⁷).

*Relates to: "INDI hardware drivers and connectivity check" and the GUI section in CLAUDE.md.*

## 2026-10-17 — Resolving power measured on the lamp lines

*Relates to: "Dispersion law", `write_spectrum` and `summary` in CLAUDE.md.*

The final spectrum only carried `BSS_ITRP` (600, the instrument's typical value from the configuration). The BeSS specification (v1.3) also has `BSS_ESRP`, the effective resolving power of the spectrum, with `BSS_SRPW`, the wavelength it is given at (6563 in its example). The Be validation page needs both, so `dispersion_law` now measures R and `write_spectrum` writes them; `summary` shows R in large type at the top of page 1, where the SNR will go next.

Definition: R = λ / FWHM, FWHM = 2.355 σ for a Gaussian line. A convention, not a law: R is λ / Δλ with Δλ the smallest separable difference, a threshold everyone sets differently (Rayleigh historically, the FWHM of an unresolved line today); Robertson (PASA 2013, arXiv:1308.0871) shows that the same FWHM separates lines differently depending on the profile's shape. Kept for comparability with the Alpy's name, Demetra and BeSS.

Method, chosen with the user: the σ of the lines kept for the law (Gaussian fits already made for their positions), not a single line. On the Alpy 600 the width in pixels is not constant — σ grows from 1.18 to 1.33 px from blue to red — so a straight line σ(x) is fitted, read at Hα's pixel and converted with the law's derivative there; the median σ would give R 646 instead of 630. Lines far from that line are rejected (a blend reads wider), at 3 robust sigmas but never closer than 5 % of the median width: on near-identical synthetic lines the robust sigma was tiny and the clipping rejected sound lines. R is not blocking: without it the law is still written. Night of 2026-10-16: R(Hα) = 630, R(Hβ) = 469, 8 lines, none rejected.

Not corrected, on purpose: the pixel's own width (the detector integrates over 1 px, adding 1/12 px² to σ², about 3 % on R) is part of what the delivered spectrum went through. The measurement is made on the stacked lamp in pixels, before `lambda_calibration`'s resampling, which widens the lines a little more: +2.7 % on the FWHM (median of the 8 lines, 1.4 to 3.7 %), measured on 4 Aql and HD 45910 on 2026-10-16 — so the delivered spectrum's real R is about 2.7 % below the value written. Adding that term by calculation was offered and declined (simpler, and within the measurement's own uncertainty). Laws computed before this date hold no R; their spectra keep `BSS_ITRP` only.

## 2026-10-17 — Signal-to-noise ratio by DER_SNR

*Relates to: "Signal-to-noise ratio", `write_spectrum` and `summary` in CLAUDE.md.*

The Be validation page needs the spectrum's signal-to-noise ratio next to R. The user chose DER_SNR (Stoehr, Seaman, White et al. 2008, ADASS XVII, ASP Conf. Ser. 394, 505): computed from the spectrum alone, the same for any spectrum, and documented. BeSS's specification (v1.3) deliberately ignores S/N as "too method-dependent", so the values are written as non-BeSS keywords (`SNR1`, `SNR1LO`/`SNR1HI`...), which BeSS keeps without using.

Measured before deciding, on 73 final spectra of 2026-10-12/13/14/16 (reports `~/Téléchargements/Rosace_SNR_DER_2026-10-17_v1.1.pdf` and `Rosace_SNR_cumul_HD60848_2026-10-17_v1.1.pdf`): SNR / √(exposure) falls 0.27 dex per magnitude, between the photon-limited 0.2 and the background-limited 0.4 — the method follows the physics. Resampling correlates neighbouring pixels, which DER_SNR reads as less noise: the final spectrum gives +8 % over 3750–7500 Å and +20 % over 6000–7000 Å compared with the stacked spectrum in pixels, hence the measurement before `lambda_calibration`. A spectrum upsampled ×2 (midpoints interpolated) reads ×2.14 (the user remembered a collapse to 0; not reproduced). A narrow zone (6600–6700 Å, 29 points) was too noisy to use.

Limit found by summing HD 60848's 14 frames one by one: DER_SNR grows 30 → 78 instead of √N's ~113, and plateaus around 38 over 6000–7000 Å. An independent noise estimate — the difference between the odd- and even-frame sums scaled to the same flux, where everything common to the frames cancels — does follow √N (49 → 130), so the real noise falls as expected and DER_SNR takes the spectrum's own fine structure (lines and telluric bands, ~3 px wide here) for noise once the noise is low. Kept anyway (user's choice: universal and documented); the odd/even split stays in reserve. The SNR also varies several-fold along a spectrum (HD 60848: 40 at 3750–4000 Å, 247 at 4750–5000, 24 at 7250–7500): a wide zone gives a typical value dominated by its brightest part.

Two zones of equal importance, at the user's request — the whole spectrum (3750–7500 Å) and 6000–7000 Å — with no weight given to Hα: the step is program-agnostic (declared by `Be_stars.yaml` today), its zones in the configuration. HD 60848 (2026-10-16): 78 and 38.

## 2026-10-18 — BeSS validation: the earlier spectra of the star

Before accepting a Be spectrum, the observer wants to see that it shows the right star and whether it has changed: the page gets a « Spectres précédents » panel with the 5 most recent other spectra of the star, from BeSS (other observers, other instruments) or from Rosace, whatever their source.

Decisions (user): searched in BeSS each time the page opens (to be revisited if too slow — about 1 s per star on 2026-10-18); 5 at most, the most recent; Rosace in red, BeSS in blue, a Rosace spectrum found in BeSS once, in violet; each labelled with its date and observer and each can be hidden; the whole spectrum and an H-alpha zoom, where a « Résolution Rosace » button degrades the finer spectra to the resolution of the one being validated; echelle spectra by their H-alpha order only; a separate panel, « Spectre 1D » unchanged; a star found only by its position flagged as suspect.

Found by trying BeSS's Virtual Observatory service (SSAP, `ssapBE.pl`): TARGETNAME is matched exactly against BeSS's own name — `HD 65875`, `* gam Cas`, `Pleione`, `gam cas` all return nothing, while `V695 Mon`, `gam Cas`, `PLEIONE` return hundreds of spectra (BeSS's web form, which goes through Simbad, recognises them; this service does not). An empty answer is still a 13 kB VOTable describing every field — it looks like a result in a browser; only `<TABLEDATA/>` tells. On 10 recent Rosace Be stars, the name that worked was always the BeSS alias from the 2026-10-03 import, never our canonical name nor our `HD n` alias when BeSS uses another name. Order chosen (user): the BeSS name given by the Arasbeam robot file for the star's HD number (311 of 311 stars to mag 7 have one; 117 of the 1 344 to mag 10 do not), then each of our names, then the coordinates (36″) — same spectra as the right name on the 10 stars, but a neighbour could be taken for the star. More than 1000 rows: `OVERFLOW` and none at all, MAXREC ignored — hence the H-alpha BAND on every query and a time window when the whole history overflows (γ Cas, Pleione). An echelle spectrum is one row per order. A file is either a 1D image or a WAVE/FLUX/ERROR table; astropy refuses the VOTable (`dateTime` datatype), read as plain XML. Nearly every BeSS spectrum of these stars is high resolution (V695 Mon: 2 of 157 cover more than 1500 Å); degraded to R = 600, HD 47054's H-alpha peaks (2.25–2.45 at R 8 500–13 000) fall to 1.60–1.66, against 1.67 for Rosace's own spectrum.

Same day, after using it (user): « Résolution Rosace » made available over the whole spectrum, not only in the Hα zoom (more intuitive; the convolution is done in ln λ so a constant R means a constant width at every wavelength); and the Hα equivalent width of every spectrum, measured at the validated spectrum's resolution, plotted against the date. First values: HD 47054 −6.55 Å (Rosace) against −5.6 to −7.4 Å in BeSS, V695 Mon −45.2 Å against −42.2 to −46.9 Å; degrading changes them by a few tenths of an ångström at most (−5.71 → −6.07 for HD 47054's R 13 000 spectrum).

Then (user): every spectrum on the same scale. The first version divided a spectrum by its median over 6600–6700 Å (Rosace's `scaling` zone) only when it covered that zone — most BeSS LHIRES spectra (≈ 6496–6624 Å) did not and kept the observer's own normalization. Now every spectrum, Rosace's included, is divided by its median over the two continuum zones on either side of H-alpha (6510–6530 and 6595–6615 Å), which any spectrum containing H-alpha covers; one constant per spectrum, so the shapes and the equivalent widths are unchanged; a spectrum not covering both is shown as it is and flagged. On the 8 most recent stars of the list, 48 of 48 spectra were scaled. Far from H-alpha the overall shapes can still differ (Rosace corrected for the instrumental response, BeSS spectra normalized to the continuum or not): not handled, a continuum normalization over the whole range would be another operation.
